# Тестирование somewhere

Требование → кейс → план → работающая сборка → результат → готовность.
Каталог находится в cases/, конфигурация платформ/прогонов — в config.json.
Пользовательские задачи содержат testing.md и зарегистрированный testing-manifest.json.
Инструкции: [спецификация](../.agents/skills/test-spec/SKILL.md),
[приёмка фичи](../.agents/skills/feature-test/SKILL.md),
[приёмка релиза](../.agents/skills/release-test/SKILL.md).

## Пирамида

Unit проверяют правила, комбинации, границы и переходы состояний. Integration
проверяют взаимодействие модулей, API/хранилища, сессии и фоновые операции.
E2E подтверждают ключевые пути пользователя через приложение и API. Выбирайте
самый низкий уровень, который достоверно проверяет правило; не размножайте
все комбинации в E2E и не устанавливайте искусственные процентные квоты.

Каталог описывает приёмочные сценарии, а не каждую функцию/строку кода. Поэтому
число кейсов по уровням не является распределением всех автотестов проекта.
Первичный импорт содержит много UI-состояний для ручной приёмки. При автоматизации
выделяйте проверяемые ниже правила, сохраняя небольшой набор сквозных E2E;
полное покрытие пользовательского кейса нельзя объявлять по одному unit-тесту.

## Исследование по запросу

[exploratory-test](../.agents/skills/exploratory-test/SKILL.md) ищет неожиданные
проблемы через работу с UI. Запускается только по явной просьбе пользователя
об этом навыке или независимом исследовании без кейсов. Автоматический выбор
Codex отключён через `policy.allow_implicit_invocation: false`.
После фичи, в CI и перед релизом этот проход сам не запускается.

Основной агент готовит окружение и нейтральный бриф. Новый субагент без истории
разработки получает только назначение приложения, адрес/сборку, доступные роли,
ограничения, бюджет, инструментальные инструкции и пути отчёта. Он не читает
кейсы, specs, макеты, исходники, diff и известные баги, не выполняет общий
стартовый обход продуктовых документов. Это изоляция контекста инструкциями,
не технический запрет чтения файлов. Если контекст загрязнён, нужна новая сессия.

Исследователь сам выбирает пользовательские цели и следующие действия по UI.
Результат — наблюдения и evidence, включая редкие сбои и неизвестные ожидания.
Квоты багов нет, исправления приложения в проход не входят. При недоступной
платформе сохраняется blocked; доступные области исследуются в пределах бюджета.
По умолчанию — 30 минут на выбранные платформы суммарно, если не задан иной срок.

Сессия хранится в `.qa-runs/exploratory/<session-id>/`: `brief.md`, `report.md`,
`evidence/`, `checksums.json` (SHA256 исходного отчёта и evidence) и отдельный
`triage.md`. После фиксации отчёта основной агент сверяет находки с требованиями,
дедуплицирует и назначает подтверждённым дефектам регрессию по пирамиде.
Исходные наблюдения сохраняются, даже если разбор установил согласованное
поведение. В разрешённой задаче кейсы обновляются через test-spec; новые
ожидания не выводятся из текущего бага. Никаких автоматических статусов pass
или automated, импорта в acceptance run/receipt или закрытия задач по этому отчёту.

До завершения работы основной агент сохраняет обезличенный отчёт и evidence
в материалах связанного изменения; без изменения — в `testing/explorations/<session-id>/`.
Реальные личные данные остаются в разрешённом приватном хранилище с указанием
ссылки и hash, не в Git. Если долговременное место недоступно, явно сообщить
ограничение и путь локальной сессии; не выдавать `.qa-runs` за постоянный архив.
Функциональная, дизайн- и релизная приёмка выполняются по своим правилам.

## Кейсы и статусы

Файлы YAML редактируются через test-spec, а не регенерируются из текущего UI.
ID сохраняется при переименовании/архивации источника. source связывает кейс
с Requirement/Scenario и hash требования вместе со сценарием. Новая редакция
источника требует пересмотра действий/ожиданий, после чего обновляется hash.
Не переписывайте hash автоматически, не прочитав изменение.

- lifecycle: draft / active / archived — состояние документации.
- level: unit / integration / e2e — уровень достоверной автоматической проверки.
- automation отдельно для каждой платформы: manual / planned / partial / automated.
- health: unknown / stable / flaky / quarantined — пригодность автоматизации.
- результат: not_run / running / passed / failed / blocked / skipped.

automated требует ссылок path/selector/runner/level и проверенной регулярной
работы. Ссылки у partial — только частичное покрытие, а не освобождение от ручного
прохода. Ручной проход агентом не меняет automation. Ошибка обязательного
автотеста не маскируется успешным ручным сценарием или ретраем.

Первичный импорт сохраняет условия и ожидаемые результаты согласованных specs.
Он не утверждает, что продукт выполняет все эти сценарии. config.sources задаёт
область инвентаризации; добавляйте новые продуктовые specs вместе с фичей.
Новый/изменённый сценарий без согласованного кейса — пробел покрытия.
До архивирования OpenSpec используем delta specs; после него обновляем пути,
не создавая дубликаты кейсов. Отменённый сценарий архивируется с объяснением в SDD.

## Окружение и ручной проход

См. [environments.md](environments.md). Основной исполнитель — независимый
агент. Человек подключается только для недоступного аккаунта/устройства или
личного подтверждения. Реальный UI/API обязателен; просмотр исходников,
макета или сохранённых исторических screenshots не подтверждает поведение.

1. Зафиксировать сборку/API, устройство, профиль, данные, locale/timezone/время.
2. Выполнить предусловия, затем каждое действие и проверить expected.
3. Проверить сохранение/второй аккаунт/повторное открытие, когда это часть сценария.
4. Записать actual и evidence: ручной проход требует interaction log, UI E2E —
   также screenshot. Автотест требует raw результата; обязательный suite — log.
5. При ошибке сохранить дефект и воспроизведение. Продолжить независимые кейсы,
   зависимые отметить blocked. Не исправлять приложение или ожидания в роли QA.
6. Очистить только собственные тестовые данные. Исполнитель исправляет продукт,
   затем новый проход сохраняется отдельно от предыдущего.

## Команды

Из корня репозитория после npm ci:

```sh
npm run qa:check
npm run qa:test
npm run qa:plan -- --purpose feature --component web --id feature-check \
  --implementer implementation-agent --environments /tmp/environments.json \
  --cases TC-CREATE-REPLACE-WITH-ACTUAL-ID --out .qa-runs/feature-check
npm run qa:run-suite -- --plan .qa-runs/feature-check/plan.json \
  --run .qa-runs/feature-check/run.json --suite web-check
npm run qa:ready -- --plan .qa-runs/feature-check/plan.json \
  --run .qa-runs/feature-check/run.json
npm run qa:report -- --plan .qa-runs/feature-check/plan.json \
  --run .qa-runs/feature-check/run.json --out .qa-runs/feature-report
npx --no-install allure generate .qa-runs/feature-report/allure-results \
  --output .qa-runs/feature-allure
```

Замените пример ID реальным из каталога. plan создаёт новый каталог и пустой
run.json без pass. Проверяющий записывает checks по схеме
scripts/testing/schema.mjs; пути evidence относительны каталогу run.json.
SHA256 вычисляйте по сохранённым файлам. Схема строгая: неизвестные поля и
проверки вне плана отклоняются. Идентификатор проверки берётся из plan.expected.
Копирование старого inputHash/pass и сужение плана ради готовности запрещены.

qa:check проверяет каталог и заявленное завершение задач, но не запускает
продуктовые тесты. qa:ready требует все expected и suites. Полный набор релиза
выбирается автоматически, даже если старый кейс не затронут diff. Feature-план
содержит выбранные кейсы; automated E2E также получает независимый ручной проход.
Повторное использование имени уже выполненного suite запрещено: сохраняйте
старый прогон и создавайте следующий. Пауза не превращается в pass.

## Релиз

Сначала собрать кандидат, затем создать release-план с --artifact-dir и всеми
профилями config.releaseProfiles компонента. Подставьте checksum manifest
в build окружения выпускаемого клиента; для backend — в backend всех окружений.
Проверки выполняются на этих же артефактах и конфигурации.

```sh
npm run qa:plan -- --purpose release --component web --id web-candidate \
  --implementer release-builder --environments /tmp/release-environments.json \
  --artifact-dir /tmp/web-release --out .qa-runs/web-candidate
npm run qa:release-ready -- --plan .qa-runs/web-candidate/plan.json \
  --run .qa-runs/web-candidate/run.json --artifact-dir /tmp/web-release \
  --receipt /tmp/web-acceptance.json
```

Все применимые manual/planned/partial и flaky/quarantined кейсы проходят вручную.
Нет инструмента — blocked. Пропуски не исключаются из знаменателя. Полный
backend-релиз проверяет API и поддерживаемые клиенты. Поддерживаемые старые
версии добавляются отдельными обязательными профилями перед планированием.
Новый checksum/код/кейсы/окружение требует новой приёмки.

Отпечаток исходников не включает приватные `.env`/`.env.*`, `local.properties`
и `frontend/ios/Config/Local.xcconfig`: они отсутствуют в чистом checkout и могут
содержать секреты или пути этой машины. Примеры `.env.example`/`.env.*.example`
и общие build-конфигурации остаются входами проверки. Фактическая конфигурация окружения
фиксируется в плане без секретов; её изменение по-прежнему требует нового прогона.

Receipt подтверждает локально проверенный набор и привязан к artifact manifest.
Перед выкаткой повторите qa:release-ready; установщик проверяет receipt и файлы.
Receipt не является криптографической подписью доверенного QA: как и отчёт,
он требует доверия исполнителю. Нельзя вручную создавать/редактировать receipt.
Публикация файлов кандидата в GitHub Releases разрешена до ручного прогона;
она не является production-deploy или продвижением в магазинах.

## Доказательства и отчёты

JSON — источник фактов; Markdown/Allure отображают те же результаты. Экспорт
не создаёт готовность. Старые отчёты/evidence не изменяются. .qa-runs игнорируется
Git; для закрытой задачи сохраните компактный JSON и обезличенные evidence в
каталоге изменения либо доступном долговременном хранилище с hashes.
Для release храните отчёт/план/receipt и evidence вместе с историей артефакта,
не полагайтесь на семидневные логи CI. В публичный Git не попадают реальные
профили, cookies, токены и содержимое личных встреч.

Allure 3.22.1 закреплён; DOMPurify 3.4.17 переопределён только внутри
@allurereport/web-commons из-за исправленных upstream advisories версии 3.4.16.
При обновлении Allure повторите audit и генерацию отчёта; override удаляется
после перехода upstream на исправленную зависимость.

## Связь задач и результатов

Manifest классифицирует каждый ID из tasks.md. Пример структуры:

```json
{
  "schemaVersion": 1,
  "change": "example-change",
  "phase": "checkpoint",
  "plan": "openspec/changes/example-change/qa/plan.json",
  "run": "openspec/changes/example-change/qa/run.json",
  "tasks": [{"id": "2.1", "cases": ["TC-EXAMPLE"], "platforms": ["web"]}],
  "exemptTasks": [{"id": "1.1", "reason": "Подготовка документации, без изменения поведения"}]
}
```

Для завершённой задачи план должен содержать все её case/platform пары.
Разделяй задачи, если кейсы применимы к разным платформам. `exemptTasks` не
используется для обхода продуктовой приёмки. Исключения проверяются в review.
Каждый актуальный spec обязан быть в `sources` либо `excludedSources` с причиной;
последнее предназначено для инфраструктурных требований, проверяемых отдельными
тестами. При archive/sync перенеси source refs на актуальный путь, сохрани ID
и пересмотри hash после сравнения требований.

## Доказательства автоматизации

`automation-inventory.json` — исходная инвентаризация существующих файлов,
а не обещание покрытия. Кейсы с проверенной частичной связью остаются `partial`.
Все текущие регулярные runners имеют `scope=source`: они проверяют исходники,
но пересобирают собственные fixture/QA. Поэтому в релизе даже их полностью
автоматизированные кейсы дополнительно остаются в ручном проходе кандидата.
Будущий runner с `scope=artifact` обязан запускать точный кандидат из
`SOMEWHERE_QA_ARTIFACT_DIR` и окружения `SOMEWHERE_QA_PLAN`; его scope меняется
только после проверки этого контракта.

Для automated результата `evidence.kind=raw` указывает на нормализованный JSON:

```json
{
  "schemaVersion": 1,
  "planHash": "<SHA-256 плана>",
  "checkId": "TC-EXAMPLE/web/automated",
  "tests": [{
    "path": "frontend/web/tests/example.spec.ts",
    "selector": "точный заголовок теста",
    "runner": "web-e2e",
    "level": "e2e",
    "status": "passed",
    "original": {"path": "raw/playwright.json", "sha256": "<SHA-256 оригинала>"}
  }]
}
```

Значения переносятся из фактического запуска, не из ожидаемого результата.
Проверка читает оригинал: поддержаны JSON Playwright, Vitest и JSON-lines Go.
Она сопоставляет файл/selector, исходный status, время не раньше плана,
а для Playwright — projectName с environment.device и отсутствие retries.
Сохраняй оригинальный JSON с `--reporter=json` / `go test -json`.
Другие форматы (в том числе XCTest/Gradle) пока остаются manual/partial до
добавления и проверки адаптера. Наличие файла `.xcresult` само по себе не даёт pass.
Обязательные suites учитываются отдельно и также попадают в Allure; failed и
blocked не превращаются в успешный результат при экспорте.

Исходная база приёмочных кейсов импортирована из specs. Уточняй воспроизводимые
данные/действия в `test-spec` перед конкретной реализацией; это работа по сценарию,
а не подтверждение того, что все импортированные функции уже работают.

Для автономного просмотра без отдельных HTTP-запросов виджетов можно собрать
проверенный в пилоте single-file отчёт:

```sh
npx --no-install allure awesome .qa-runs/feature-report/allure-results \
  --single-file --output .qa-runs/feature-portable
```

Открывай index.html через локальный сервер или средство просмотра HTML. Исходные
JSON/evidence сохраняются отдельно; HTML — представление, а не источник готовности.
