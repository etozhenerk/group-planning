# Окружения функциональной проверки

Feature: отдельный Go memory fixture, тестовые профили и реально собранный клиент.
Не перезапускайте пользовательское демо или чужой симулятор. Unit/integration
применяют существующие команды приложений; кейсы с временем используют
управляемые часы/данные fixture. Реальные сутки ждать не требуется.

Release: настоящий release bundle/APK/IPA, зафиксированные origin/настройки
и версия API. QA APK и iOS UITestHost не равны store-артефакту. Вход через
fake-provider не закрывает реальный OAuth; memory не проверяет сохранность
PostgreSQL. Эти сценарии требуют соответствующего тестового окружения и доступа,
при отсутствии остаются blocked. Не поднимайте production/БД ради feature-проверки.

JSON окружений — массив наблюдаемых конфигураций. Для каждого элемента нужны:
id, profile, platform, application="product", url, build, os, device, locale,
timezone, data, backend. URL относится к приложению/API, не к HTML-макету.
Профили заданы в config.json; добавление нового устройства не удаляет старые
обязательные профили. web-mobile проверяется отдельно от desktop.

build — наблюдаемая идентичность сборки; release требует SHA256 manifest
выпускаемого компонента. backend — версия API, а при выпуске backend его
SHA256 manifest. Для совместимости со старыми клиентами фиксируются их реальные
версии и отдельные профили. data — идентификатор fixture/тестового набора;
секреты и приватные значения сюда не записываются.

Ручные кейсы UI выполняются через браузер/устройство. API-кейсы — через HTTP
с проверкой результата и прав. Для unit-кейса допустим отдельный воспроизводимый
запуск целевого теста; его факт и результаты сохраняются как raw, без повышения
статуса всего пользовательского пути до automated.

## Подготовка web fixture

Собери demo штатной `npm run build:demo --workspace @somewhere/web`.
Запускай `frontend/web/scripts/browser-server.ts` с отдельным свободным
`SOMEWHERE_BROWSER_ADDR=127.0.0.1:<port>`; сервер допускает только loopback.
Он использует тестовые профили Саша/Лена и in-memory данные. Рецепты создания,
CSRF и времени находятся в `frontend/web/tests/helpers.ts`, а отсечка проверяется
в `frontend/web/tests/28-meeting-refresh.spec.ts`. Подготовка данных через API
допустима; пользовательские действия и expected проверяются в живом UI.
Для границы времени используй собственную встречу и её текущую revision,
зафиксируй starts_at/starts_on/timezone и фактическое время запроса. Не меняй
системные часы или данные чужого процесса. Точная граница требует управляемых
часов unit/integration fixture; обычные сетевые задержки не доказывают «ровно».

Проверь доступность origin инструменту QA до начала кейсов. Если браузер требует
вмешательства из-за TLS или не запускается в среде агента, запиши blocked и
фактическую ошибку. Для будущего прохода подготовь доверенный браузеру тестовый
origin; автоматический runner с собственной TLS-конфигурацией не заменяет
независимый ручной проход. Не используйте публичный proxy для приватных тестов.

При release исходники проверяемых компонентов должны соответствовать commit
в manifest кандидата. CLI сравнивает Git-дерево релевантных inputs и отклоняет
изменённые или новые незакоммиченные исходники. Отдельные изменения QA-документов
не требуют пересборки неизменившегося приложения.
