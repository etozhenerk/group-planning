# Design

## Context

См. [proposal](proposal.md). Фото хранятся и выдаются через приватный media API; альбом пагинируется по created_at/id. Лимит одного фото — 10 МиБ, всей встречи — 1 ГиБ. Общий HTTP WriteTimeout — 15 секунд; длинная синхронная сборка ZIP в запросе не подходит. UX и композиция — в [ux.md](ux.md).

## Goals / Non-Goals

**Goals:** получить весь альбом с ограниченной памятью, корректной отменой, текущей авторизацией и наблюдаемыми ошибками.

**Non-Goals:** экспорт чата, файлов вложений или всех встреч аккаунта; новые публичные ссылки; постоянное хранение архивов или миграция БД.

## Decisions

- Прикладной метод meetings возвращает единый снимок опубликованных memory-фото после проверки privateSnapshot и past. Новый read endpoint отдаёт snapshot мобильным клиентам, чтобы пагинация/одновременное добавление не меняли пакет.
- Изолированный серверный адаптер archive export получает только прикладные методы чтения, без Store. POST подготовки возвращает 202 и случайный идентификатор. Фоновая сборка использует Go archive/zip без сжатия уже сжатых фото, закрытый временный файл и последовательное чтение максимум одного фото. GET состояния возвращает preparing/ready/failed; DELETE отменяет; GET файла повторно проверяет сессию, владельца и доступ.
- Максимум два одновременно удерживаемых архива на процесс, один на пользователя; ошибка занятости допускает повтор. Каждый не более существующей квоты встречи плюс ZIP headers. Готовый архив живёт до 10 минут, незавершённый — ограниченный deadline. Cleanup работает независимо от новых запросов, Close отменяет задачи и удаляет файлы. Production PrivateTmp из systemd изолирует временные файлы при перезапуске.
- Web вызывает JSON API, затем обычную authenticated download-ссылку: ZIP не читается через fetch→Blob. На странице остаётся один общий статус подготовки; «Скачивание началось» не обещает запись на диск. Смена аккаунта/доступа отменяет операцию. Закрытие экрана отменяет подготовку и удаляет готовый временный экспорт.
- iOS сначала запрашивает PhotoKit add-only, скачивает фото последовательно в приватную временную папку, повторно проверяет lease, затем сохраняет пакет одним performChanges. Данные не преобразуются в JPEG повторно. Временная папка очищается при любом исходе.
- Android repository подготавливает файлы последовательно и создаёт принадлежащие операции записи MediaStore с IS_PENDING; после завершения публикует их. При ошибке удаляет только созданные этой операцией записи, сохраняя ранее существующие фотографии. Lifecycle/ViewModel управляет отменой.
- Альтернатива client ZIP отклонена: BlobWriter до 1 ГиБ создаёт ненужный риск падения mobile web; OPFS требует отдельного покрытия квот и fallback. Прямой незавершённый ZIP stream не выбран: после HTTP200 ошибка могла бы выглядеть как успешный повреждённый архив.

## Risks / Trade-offs

- [Большой альбом] → серверный лимит диска и concurrency; native временные файлы вместо накопления всех Data/Bitmap.
- [Отзыв во время чтения] → MediaBytes проверяет доступ до/после; менеджер повторяет проверку перед выдачей и прекращает передачу при истечении/отмене. Уже сохранённые по явному запросу фотографии не удаляются из личной галереи.
- [Перезапуск сервера] → старый export ID недействителен; интерфейс предлагает подготовить заново. Архивы не являются постоянными данными.
- [Системное скачивание браузера] → после передачи браузеру страница не подтверждает факт сохранения; сетевой сбой download показывает браузер.

## Migration Plan

Новый совместимый backend выпускается перед web/mobile кнопками. Проверить snapshot/access, ZIP integrity, expiry/cancel/close и bounded disk. Затем выпустить web и установить новые native-сборки. При откате клиента старые API работают; при откате сервера новая кнопка показывает ошибку без потери альбома. Миграции БД нет.
