## Goals / Non-Goals

**Goals:**
- Сохранять каждый согласованный макет и его платформенные отличия в одном SDD-изменении.
- Поставлять одобренные пакеты независимо: запуск → знакомство → следующие экраны из инвентаризации.
- Отделять единый визуальный смысл от нативных контролов, системного входа и браузерной истории.

**Non-Goals:**
- Переписывание серверных правил голосования, транспорта, хранения и авторизации. Структурированные данные места и API карт планируются отдельно; сейчас код сервера не меняется.
- Перенос постановочного курсора, рамки телефона или демонстрационных подписей в приложение.
- Автоматический перенос макетов в код и выпуск без отдельного поручения.

## Decisions

### Изолированные макеты и поэтапная публикация

Сначала `assets`/UX и решение пользователя, затем design-system-publish и platform manifest, затем разрешённая реализация. Альтернатива — заменить глобальную систему сразу для всех экранов — инвалидирует параллельную приёмку при ещё не выбранном дизайне. Поэтому исходная публикация 5.0.0 пока не меняется; очередь публикации одобренной заставки явно записана в tasks. Перед первым кодом она обязательна, даже если перенос ограничен двумя native-клиентами.

Новый размер заставки получает смысловые роли launch, а не изменение общих brand-шрифтов шапок. Числа берём из одобренного launch-r1, не из случайной реализации. При публикации проверяются все зарегистрированные manifests и влияние общей версии; старые evidence сохраняются.

### Три мобильных клиента, отдельный desktop-контроль

iOS сохраняет SwiftUI/UIScrollView pager и системный вход; Android — Compose pager и системный Back; mobile web получает отдельную узкую композицию внутри действующего React/FSD, CSS Modules и TypeScript. Общие функции/модели не копируются из прототипа. Внутренние web-импорты используют `@/`; один небольшой компонент на каталог.

Существующий breakpoint.mobile 740 CSS px остаётся границей. Ширины 320/390/739 входят в mobile-приёмку, 740/1100/1440 — контроль отсутствия desktop-регрессии. Для стартового экрана web не создаётся фиктивный нативный splash. Изменения общих токенов, затрагивающие desktop, требуют мобильных ролей или варианта, сохраняющего desktop-значения.

### Состояние и вход сохраняются

Переиспользуем существующие session/return-context/OAuth-механизмы. Онбординг управляет только выбранной страницей и началом входа. Приглашение и RSVP остаются самостоятельным сценарием. Результат входа показывает реальный клиент; прототип демонстрирует только внешний вид состояний и не обращается в Яндекс.

### Проверки перед закрытием

[testing.md](testing.md) и testing-manifest связывают продуктовые задачи с cases. Детальная матрица всех ещё не согласованных экранов раскрывается до их реализации; укрупнённые будущие задачи 4.x нельзя закрывать как весь MVP. Перед apply каждого следующего пакета их делят по screen/state/platform, расширяют mapping и публикуют точный design-manifest.

Независимые feature-test и design-review выполняют отдельные субагенты на живой сборке; `qa:ready` и `design:ready` — до checkbox. Исследовательский exploratory-test не входит в план.

## Risks / Trade-offs

- [Устаревшие тексты «Скоро»] → сверка с функциональностью конкретного кандидата, без обещания непрошедших приёмку возможностей.
- [Точная типографика не совпадает с браузерным макетом] → отдельная визуальная приёмка iOS/Android, большой текст и safe area; HTML не выдаётся за native evidence.
- [Общие стили меняют desktop] → scoped mobile CSS/варианты, контроль граничных и широких размеров.
- [Параллельный код изменил основание] → перед переносом перечитать исходники и состояние активных изменений; не переписывать чужие правки, не использовать старый hash как pass.
- [Большой объём инвентаризации] → отдельное одобрение и приёмка каждого пакета; согласование одного экрана не разрешает менять остальные.

## Migration Plan

1. Завершить макеты текущего пакета и сохранить решения.
2. Опубликовать подтверждённый пакет, эталоны и design-manifest; уточнить кейсы и task mapping.
3. После поручения применить на каждой платформе и выполнить реальные команды её AGENTS.md.
4. Получить независимые функциональную и визуальную приёмки, затем закрывать задачи соответствующей платформы.
5. Публикация клиентских релизов — отдельная команда пользователя после release-test/receipt точных артефактов. Откат — возврат конкретного клиентского изменения/сборки без изменения контрактов API или переписывания Git-истории.

## Open Questions

- Номер клиентских версий и момент выпуска определяются после согласования пакетов и не влияют на подготовку макетов.
- Следующие экраны после знакомства выбираются из зафиксированной инвентаризации; их визуальные решения пока отсутствуют и не блокируют текущий пакет.

### Закреплённые панели следующих экранов

Согласованная геометрия create-r4 обязательна для новых мобильных закреплённых областей: полный нижний/боковые края, верхние скругления и тень, динамический резерв прокрутки. Правило сохранено в AGENTS.md и ux.md; при подготовке реализации оно публикуется через design-system-publish с соответствующими токенами и platform manifest.


### Аватарки пользователей

Уточнение пользователя 04.11.2026: места идентичности показывают фотографию пользователя, а не буквы. API userSchema уже допускает avatar_url; при переносе нужен сквозной mapping в клиентскую модель участника/сессии и UI, включая чат, прочитавших, реакции и состав. Демо-фото в макете локальные, не выдаются за изображения названных пользователей. При отсутствии/ошибке — нейтральный силуэт. Текущее приложение этим предложением не исправлено; учесть в публикации контрактов и перед apply по всем платформам.


### Яндекс Карты · план интеграции от 04.11.2026

Пользователь добавил выбор места на карте в текущий пакет предложения места. Источник требований — specs/meeting-place-picker/spec.md. Карта place-r4 одобрена; r2 отклонён визуально, r3 — из-за жестов боттомшита; создание create-r5 с тем же picker одобрено 04.11.2026. Общие права going/организатора и правила принятия опроса сохраняются. Picker добавлен в изолированный макет создания по прямому поручению пользователя; настройки пока не пересматривались. Общий API должен поддержать также initial meeting creation с optional place_location и старым текстовым place.

Целевые платформы: web-mobile — JS API Яндекс Карт v3, iOS/Android — Yandex MapKit SDK; поиск организаций/адресов и обратное геокодирование выбираются из соответствующих API/SDK, а не из HTML публичного сайта. Минимальные версии/тариф/права на хранение данных уточнить перед кодом по официальным условиям и фактическому продукту, не считать любой поиск бесплатным или встроенным в отображение карты. Ключи/ограничения домена и bundle/package, атрибуция/логотип и ошибки лимитов входят в интеграционный план; секреты не помещаются в Git или клиентский серверный ключ. Настоящие запросы не выполнялись, учётная запись/ключи не создавались.

Карта выбирает кандидата; подтверждение атомарно меняет только draft места. Поиск отменяет/игнорирует устаревшие ответы, текст/область не сбрасываются из-за старого ответа. Выбор на карте, список результатов и ручной ввод доступны без геолокации; при реализации запрос позиции — только по отдельному действию. Название бизнеса не выводится из одного обратного геокодирования. При точке без адреса показываются координаты без вымышленного заведения. Ошибка карты сохраняет форму и ручной ввод.

Предлагаемый объект `place_location`: `provider=yandex`, kind business/point, название/адрес, именованные latitude/longitude; provider id/URI только если реально возвращён и допустим к хранению. Внешние ответы нормализуются на границе; порядок GeoJSON longitude/latitude не переносится в UI молча. Объект должен проходить создание/чтение опроса → применение → детали встречи. Существующее строковое `place` остаётся отображаемым fallback, объект optional для прежних клиентов; текстовая замена очищает устаревшие координаты. Точные DTO/patch-semantics/null-clearing и ограничения фиксируются в OpenAPI перед apply, не объявлены уже работающим контрактом. Операции поиска не меняют встречу и не создают опрос. Права, revision, idempotency и memory.Store остаются действующими; БД/Docker не нужны для начала.

Официальные источники, проверены 04.11.2026: [JS API подключение](https://yandex.ru/maps-api/docs/js-api/common/connection/javascript.html), [MapKit](https://yandex.ru/maps-api/docs/mapkit/index.html), [поиск организаций: запрос](https://yandex.ru/maps-api/docs/geosearch-api/request.html), [ответ](https://yandex.ru/maps-api/docs/geosearch-api/response.html), [геокодер](https://yandex.ru/maps-api/docs/geocoder-api/index.html), [условия](https://www.yandex.ru/legal/maps_api/ru/). План не является согласием на тариф/оферту и не подключает сервис.

Полноэкранный picker r4 — отдельный navigation context, не увеличенный draggable bottom sheet. Для iOS/Android закрытие панели жестом выключено/не используется; web обеспечивает отдельную полноэкранную область и возврат истории/кнопки с сохранением формы. Prototype использует native dialog как focus boundary, его sheet region скрыт и не получает жесты карты; production должен подтвердить это на реальных MapKit/JS API, IME и системной навигации. UI-расширение создания r5 одобрено 04.11.2026; публикация и реализация остаются отдельными этапами.

Подготовка preparation-r1 одобрена 04.11.2026, см. ux.md. Прототип сохраняет действующий PreparationTask/PreparationAction и права; формы/карточки/фото/панели проектируются отдельно от реализации. При переносе реальный user→avatar mapping, актуальный состав, разрешения и надёжные действия остаются обязательными; fixture не заменяет task API. Публикация и независимая приёмка по трём клиентам планируются через4.1 после одобрения.
