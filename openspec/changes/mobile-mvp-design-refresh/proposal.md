# Proposal

## Why

Принятые мобильные макеты somewhere нужно перенести в три клиента без потери решений, работающих операций и платформенных особенностей. Изменение превращает последовательное согласование экранов в проверяемый план следующей версии MVP.

## What Changes

- Переносим принятые запуск, знакомство/вход, список/календарь/«Возможно», создание/приглашение, чат/сведения/настройки, дату/место/подготовку, вайб, профиль/помощь/обращение/сведения/документы. Точные входы, решения и SHA256 — в [реестре](approved-designs.md), переходы/состояния/движение — в [ux.md](ux.md).
- Объём: iOS, Android и mobile web. Desktop не редизайним; проверяем его сохранность, включая границу 740 CSS px и действующее исключение landscape/coarse-pointer.
- Общие элементы: тонкий Back без подписи, фото/нейтральный силуэт, mobileSheet, заметная обязательность/связанные ошибки. Sticky-оформление только для реально закреплённой при прокрутке области: три края вплотную, верхние скругления и тень вверх. Короткие формы сохраняют действие в потоке.
- Заставка native: 44/53/16, знак слева, один оборот за 1200 ms. Web не получает искусственное вступление. Знакомство r4 из восьми шагов принято; финальные состояния входа/редактура закрепляются до публикации, без повторного согласования композиции.
- Создание и предложение места используют ручной текстовый ввод. По решению пользователя 04.11.2026 карты/SDK/place_location вынесены в отдельную проработку meeting-place-picker; текущий редизайн от них не зависит.
- Сначала готовим входы и единую публикацию дизайн-системы, затем отдельную реализацию и независимую приёмку каждой платформы. [tasks.md](tasks.md) содержит зависимости и условия закрытия; [testing.md](testing.md) и manifest — кейсы/платформы.
- Удаление аккаунта остаётся скрытым по решению пользователя. Доработка общего flow-r1 остановлена; он исключён из эталонов и приёмки. Пользователь разрешил реализацию по tasks.md, начиная с подготовки 2.0–2.13; выпуск/деплой требует отдельного поручения.

## Capabilities

### New Capabilities

- product-onboarding: запуск и мобильное знакомство следующей версии; продолжает одноимённую capability активного gathering-activity-feed. При синхронизации объединить требования, не вводить второй сценарий входа.
- mobile-interface: общие мобильные контракты навигации, панелей, ошибок и идентичности, а также принятые взаимодействия списка/чата/галереи/сервисных страниц. Уточняет представление действующих операций, не заменяет их доменные требования.

### Modified Capabilities

Архивированные продуктовые capability не меняются. Рабочие требования встреч, чата, опросов, подготовки, медиа, профиля и поддержки находятся в активных изменениях; сохраняем их. Позднее решение о нейтральном силуэте заменяет исторический fallback инициалами для нового мобильного пакета, что явно отражено в mobile-interface и стабильном кейсе TC-PROFILE-YANDEX-FIELDS.

## Impact

- Клиенты: frontend/web (React/TypeScript/FSD/CSS Modules), frontend/ios (SwiftUI), frontend/android (Compose). HTML макетов служит входом дизайна; приложение использует собственную навигацию и реальные API.
- Backend/OpenAPI не меняются ради редизайна. Публичный avatar_url уже есть — нужен клиентский mapping. Работающие операции/совместимость сохраняются; SDK и поля места отложены.
- Дизайн: нормализованные референсы, tokens/contracts, одна согласованная версия и отдельные manifests пакетов/платформ до кода. Существующие версии и evidence сохраняются.
- Тестирование: новые UI-кейсы, прежние стабильные ID/автотесты и task/case/platform mapping. Одобрение макета, сборка и структурная валидация не являются приёмкой клиента.
- Номер новой версии MVP/RC и CI build назначаются отдельно до финального кандидата; пример 0.1.0-rc.2/42 не является назначением версии. Релиз требует отдельного разрешения и release-test точных артефактов.
