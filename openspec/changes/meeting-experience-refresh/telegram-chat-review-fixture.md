# Изолированный fixture для приёмки Telegram-chat

`TestTelegramChatReviewFixture` — отдельный Go test-процесс. Он не входит
в `cmd/server`, не меняет старые `design`/native/browser fixtures и не добавляет
продуктовый маршрут или обход аутентификации. Используются memory.Store,
настоящие identity/meeting services и HTTP handlers. OAuth-provider синтетический.
Этот рецепт готовит окружение; он не является UI-приёмкой.

## Подготовка

Сначала завершить текущие тяжёлые проверки. Следующие команды запускаются
последовательно, из корня проекта; каталог запуска должен быть новым.
Не останавливать чужой API, браузер или устройство. `.cache/web-demo` должен
содержать нужную уже проверенную сборку web; сохранить её hash рядом с evidence.

```sh
mkdir -p .cache
cd backend
go test ./internal/httpapi -run '^TestChatReview' -count=1
go test -c -o ../.cache/telegram-chat-review.test ./internal/httpapi
```

Запуск из корня, в отдельном терминале:

```sh
SOMEWHERE_CHAT_REVIEW=1 \
SOMEWHERE_CHAT_REVIEW_DIR="$PWD/.cache/telegram-chat-review-20261027-r3" \
SOMEWHERE_BROWSER_DIST="$PWD/.cache/web-demo" \
.cache/telegram-chat-review.test -test.run '^TestTelegramChatReviewFixture$' \
  -test.v -test.timeout 0
```

Сервер слушает новый случайный порт `127.0.0.1`, печатает только origin.
Можно задать свободный `SOMEWHERE_CHAT_REVIEW_ADDR=127.0.0.1:<port>`.
`SOMEWHERE_BROWSER_DIST` необязателен для API/native. Не применять production
origin и не открывать публичный туннель. Штатная остановка своего процесса — SIGTERM.

Каталог имеет mode 0700, файлы — 0600. В нём появляются:

- `config.json` и `config-{sasha,lena,tim}.json`: origin, DER-сертификат,
  реальные native sessions. `cases.design` указывает на выбранного человека;
  `chat-review-sasha`, `chat-review-lena`, `chat-review-tim` доступны одновременно.
  Сессии действуют восемь часов. Эти файлы и их содержимое не публиковать.
- `certificate.pem`: тот же тестовый сертификат для TLS-проверки HTTP-клиентом.
- `metadata.json`: origin, clock, IDs встреч/людей/сообщений/задач без токенов.
- `control.json`: выключенный контроллер ошибок. `control-events.jsonl` появляется
  при контролируемом запросе; содержит method/path, статус API и SHA256 body/key,
  без тел запросов, session tokens, CSRF и приватных invitation URL.
- `chat-review-one.png`, `chat-review-two.png`: два разных собственных PNG
  640 × 480 с геометрическим рисунком; без личных фотографий и метаданных.
- `chat-review-document.txt`: синтетический текстовый документ;
  `chat-review-invalid.png`: невалидные байты с расширением PNG.

Часы прикладного сервиса фиксированы на **2026-10-27T10:00:00Z** (13:00 Москва).
Identity использует реальные часы для сессий. Системные часы не меняются;
таймеров перехода встречи/закрытия опросов в этом harness нет. Это окружение
для композиции/реакций/задач, не доказательство фоновых переходов по времени.

## Реальные клиенты и два профиля

Web: открыть новый тестовый origin в двух независимых browser contexts/profiles,
пройти обычную кнопку входа и выбрать Сашу/Лену/Тимофея на тестовой странице.
Это настоящий callback и cookie/CSRF flow, без записи credentials в localStorage.
Обычные вкладки одного browser profile делят cookie и не являются двумя сессиями.
Решить доступность TLS штатным тестовым механизмом до кейсов; недоступный ручной
браузер зафиксировать blocked, не заменять API-тестом.

Native: использовать уже установленный QA host и существующий scenario `design`.
Скопировать выбранный `config-<actor>.json` в прежний bootstrap path:

- iOS: `<data-container>/tmp/ui-fixture.json`, mode 0600,
  launch environment `SOMEWHERE_UI_SCENARIO=design`.
- Android: `<QA-app-data>/no_backup/ui-fixture.json`, mode 0600,
  Intent extra `scenario=design`; настроить `adb -s <явный serial> reverse`
  только для нового порта. Пути и package сверять с установленным QA host.

Это не требует расширения whitelist. На одном устройстве профили переключаются
с перезапуском только собственного QA host; для одновременной сверки использовать
другой клиент или второй browser context. Не переписывать config текущего чужого
прохода. Перед открытием native сохранить точные bundle/APK identity, config
origin и выбранный actor без токена в evidence.

Медиа: подготовить **только выбранное изолированное** устройство. iOS — штатный
`xcrun simctl addmedia <явный UDID> <две PNG>`; документ/invalid положить в Documents
QA host и открыть через системный Files picker. Android — положить две PNG в
отдельную папку Pictures/SomewhereChatReview, документ/invalid — в отдельную
папку Download/SomewhereChatReview; после media scan выбрать через штатный picker.
Не передавать токены/config в Photos/Downloads. Если системный picker не показывает
файл или недоступен агенту, это ограничение фиксируется отдельно. В браузере
выбирать эти локальные файлы через настоящий input. После прохода удалить только
созданные QA assets; восстановить IME/orientation/font scale.

## Одноразовые pending/error/lost response

Контроллер читает private `control.json` перед запросом. Заменять файл атомарно
через `.tmp` и rename. Он действует только на exact method/path одной из двух
seeded встреч и exact actor ID, после аутентификации. Уникальный `id` включает
ровно одну инъекцию; повтор с тем же `id` идёт в API. Для следующей инъекции
нужен новый `id`; `{}` полностью выключает контроллер. Нет новых HTTP control routes.

Пример — ошибка сохранения реакции Саши до commit:

```json
{
  "id": "reaction-error-001",
  "method": "PUT",
  "path": "/api/v1/meetings/cea00000-0000-4000-8000-000000000002/messages/ced00000-0000-4000-8000-000000000065/reactions",
  "actorId": "ceb00000-0000-4000-8000-000000000001",
  "mode": "error",
  "delayMs": 0
}
```

`mode=pending` с `delayMs=10000` держит запрос до настоящего API. Для `error`
задержка также допустима. Отмена HTTP context прекращает ожидание без commit.
Максимум 30000 ms. `error` отдаёт 503 до операции; `lost` вызывает реальную
операцию и **только после успешного 2xx** заменяет ответ на 503. Это наблюдаемая
ошибка ответа после commit, как в прежних native fault wrappers; не физический
TCP disconnect. Произвольный 4xx не скрывается. Автосинхронизация клиента может
успеть прочитать committed state — её намеренно не блокируем.

Поддерживаются GET/POST/PUT/PATCH. Точные пути существующего API:

| Действие | Method + suffix после `/api/v1/meetings/<id>` |
| --- | --- |
| Загрузка состава/реакций/истории | `GET /participants`, `GET /reactions`, `GET /feed` |
| Сообщение | `POST /messages` |
| Реакция | `PUT /messages/<entry-id>/reactions` |
| Дата/место/задача | `POST /date-polls`, `/place-polls`, `/preparation-tasks` |
| Действие задачи | `POST /preparation-tasks/<task-id>/accept`, `/decline`, `/complete`, `/cancel` |
| Настройки | `PATCH` на сам meeting path |
| Подготовка/публикация вложения | `POST /media/uploads`, `POST /media/<media-id>/publish` |

Сначала включить контроль, затем выполнить действие в UI. Для подтверждения
pending записать экран до завершения задержки. При lost проверить состояние
второй сессией, затем явный повтор тем же клиентом. В `control-events.jsonl`
сопоставить `keySha256`/`bodySha256`; одинаковые hashes подтверждают неизменный
повтор, API/feed/task revision — отсутствие дубля. Новые данные не подменять
готовым result. Отдельный `id` и начальное состояние нужны каждому raw-кейсу.

## Отзыв доступа настоящим RSVP

Второй сеанс **того же человека** позволяет отозвать его доступ, пока первая
копия держит открытый chat/reactor list/task. Использовать Лeну или Тимофея:
организатор не отзывается сменой собственного RSVP. В отдельной сессии поменять
«Приду» на «Возможно» через UI либо `PUT .../<meeting-id>/rsvp` с body
`{"answer":"maybe","expected_revision":"1"}` и новым UUID Idempotency-Key.
После уже выполненных действий revision читать заново. Нативный Bearer получать
только из private config в памяти скрипта, не передавать через аргументы/логи.
Web mutation требует его собственный CSRF и Origin. Затем в первой сессии
проверить настоящие 403/очистку данных/реакций. Другая встреча остаётся доступна.
Для восстановления Going после отзыва используйте собственное сохранённое
приглашение через штатный invitation RSVP flow либо новый процесс.

## Проверки и границы

`TestChatReviewDataAndSessions` проверяет сохранение имён/IDs при повторных native
сессиях и настоящем web callback, полный roster, короткую/длинную историю,
реакции и доступность attachment. `TestChatReviewRolesAndAccess` проверяет API
действий ролей и реальный отзыв доступа. `TestChatReviewOneShotFaults` проверяет
pending, ошибку до commit, lost после commit, неизменный идемпотентный повтор и
отсутствие секретов в аудите. `TestChatReviewControlScope` ограничивает контроллер
собственными ресурсами. Они не подтверждают UI/IME/gesture/picker-поведение.

После проверок сохранить commands/results в отдельном отчёте, затем штатные
backend/QA-tooling/agent checks. Не переносить pass прежних UI-отчётов. Внешний
OAuth, production, БД, сохранность после рестарта и store-release здесь не проверяются.
