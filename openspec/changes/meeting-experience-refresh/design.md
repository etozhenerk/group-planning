# Design

Уточнение [2.3.0](design-publication-2026-10-27-composer-menu-motion-2.3.0.md)
распространяет движение на меню по плюсу. Используются существующие токены;
композиция, команды и права прежние. Требуется новая проверка трёх клиентов.

Дополнение [2.2.0](design-publication-2026-10-27-emoji-motion-2.2.0.md) уточняет
движение emoji-панели на трёх клиентах. Это тот же одобренный интерфейс с
retained exit, безопасным rapid reopen и мгновенным Reduce Motion; нормы — в UX
и chat-actions. Предыдущие проверки не переносятся на новую сборку.

Публикация [2.1.0](design-publication-2026-10-27-inline-cards-2.1.0.md) дополняет
токены уже принятого raw для inline-карточек опросов и задач на web/iOS/Android.
Карточка без аватара и пузыря сообщения; голоса перед сроком; действие задачи
компактное «Взять на себя». Это исправление реализации по прежнему эталону,
а не новая композиция. Независимая приёмка требуется на новых сборках.


## Context

Уточнение переноса `upload-file.html`: документ поддерживает необязательный
`caption` в публикации (до 2000 символов), фото и альбом остаются без подписей.
Подпись фиксируется при начале отправки и участвует в идемпотентности; новая
публикация с другим ключом не редактирует уже созданное сообщение. В API
она передаётся существующим `payload.text`, имя сохраняется в attachment.

Мотивация и состав изменения — в [proposal.md](proposal.md). Согласованные
переходы, состояния, макеты и различия платформ — в [ux.md](ux.md).

27.10.2026 пользователь отклонил `extended-draft`, затем одобрил финальную
[ревизию чата](assets/revisions/2026-10-27-telegram-chat/index.html): «Подходит,
переносим» на mobile web/iOS/Android. Дизайн-система 1.3.0 и
[публикация источников](design-publication-2026-10-27-telegram-chat.md) фиксируют
emoji-док, anchored quick/full reactions, людей и компактные панели встречи.
Это перенос композиции, не изменение API/прав. С 2.0.0 desktop-действия открываются модалками поверх чата;
все затронутые UI-задачи остаются открыты до независимой live-приёмки.

Текущие точки расширения web: `Navigation`, `HomeTabs`, `MeetingCard`,
`useCreateMeeting`, `ConversationActions` и поле сообщения. Сейчас создание
использует отдельный маршрут подтверждения; меню действий оформлено диалогом.
В iOS/Android те же сценарии реализованы нативными представлениями и владельцами
состояния, поэтому одного изменения web недостаточно.

До уточнения 26.10.2026 web запрашивал только `login:info`. Теперь авторизация
использует все выбранные в Яндекс OAuth права: info, email, avatar, birthday,
default_phone. Данные макета остаются демонстрационными, реальные поля получает
сервер из проверенного токена. Старым сессиям нужен новый вход для обновления.
Базовые правила доступа, RSVP, перехода в `past`, опросов и задач находятся в
активном изменении `gathering-activity-feed`; постоянные спецификации ещё пусты.
Новые дельты не подменяют эти правила, кроме явно добавленной часовой отсечки.

## Goals / Non-Goals

**Goals:** единые предметные данные через API; независимая реализация экранов
на web/iOS/Android; серверные проверки прав и времени; безопасные повторы
операций; полноценные состояния недостающих данных, загрузок и ошибок.

**Non-Goals:** перенос HTML-прототипа в приложения, BDUI, редактор профиля,
стикеры/GIF, публичные альбомы, автоматическое закрытие чата, новый критерий
окончания встречи, настройка цветов пользователем. Эта итерация проектирования
не разворачивает БД, очередь и файловое облако.

## Decisions

### 1. Общая навигация и данные карточки

Уточнение пользователя от 26.10.2026: bottom bar монтируется только на основных
экранах списка/календаря встреч, списка приглашений и профиля. В web правило
задаётся явным набором основных маршрутов, в native — состоянием главных
разделов, без дублирования панели во вложенных страницах. Создание, изменение,
чат, отдельное приглашение, Share, загрузка, альбом и служебные страницы
оставляют Back и обычную историю. Скрытая панель не резервирует место;
системные safe area сохраняются. Десктопная боковая навигация не изменяется.
Футер остаётся только на десктопном онбординге, исключая mobile web и native.

Добавить профиль в маршруты каждого клиента. Список и календарь используют
один компонент карточки на каждой платформе; период, вид, выбранные день/месяц
и позиция прокрутки принадлежат экрану встреч. Возврат из чата восстанавливает
это состояние. После создания заменить маршрут формы чатом и оставить под ним
исходный экран; старый маршрут подтверждения перенаправляет после проверки прав.
Альтернатива — сохранить подтверждающий экран — противоречит принятому UX.

Краткое представление встречи расширяется необязательными `participant_preview`,
`participant_count`, `cover`, `memory_photo_count`, `memory_preview`.
Превью содержит только текущих участников: ID, имя, необязательный аватар.
Получать его вместе со списком, не отдельным запросом для каждой карточки.
Отсутствующие поля старого ответа дают честные текстовые состояния. Цвет
вычисляется из календарной даты встречи, а не порядка карточки в массиве.
Роль организатора определяется ID, не строковой меткой. Обложка приглашения
остаётся отдельной от закрытых фотографий альбома.

### 2. Серверная часовая отсечка

Проверять в операции RSVP до записи: если нет точного начала — часовая отсечка
не действует; иначе `now >= starts_at - 1h` запрещает переход в участие любому,
кто сейчас не является участником. Уже подтверждённый участник не теряет доступ,
идемпотентный повтор подтверждения остаётся безопасным. История прежнего участия
не даёт исключения. Проверка и изменение выполняются в одной атомарной операции
хранилища с актуальным временем встречи; перенос времени пересчитывает границу.

В ответ приглашения добавить необязательные `join_closes_at`, `can_join` и
машинный код причины. Клиент обновляет вид по таймеру и при возврате на передний
план, но сервер остаётся окончательной проверкой. При отказе использовать
совместимый существующий формат ошибки с новым кодом и понятным сообщением,
чтобы прежние клиенты не обходили ограничение. Альтернатива — только отключить
кнопку по часам устройства — допускает устаревшие страницы и неверные часы.

### 3. Профиль отделён от публичного пользователя

Операция `GET /me/profile` возвращает ID, отображаемое имя, аватар, контакты,
логин, имя/фамилию, дату рождения и пол только владельцу. Публичный пользователь
сохраняет ID, display_name, avatar_url. Новые nullable строки совместимы со старыми
клиентами и JSON-документами identity_users; отдельная SQL-миграция не требуется.
Сервер проверяет данные у Яндекса; токены провайдера не сохраняются. Web больше
не ограничивает scope до login:info: без scope/optional_scope провайдер выдаёт
зарегистрированный набор, как SDK. Пропущенное поле сохраняет известное значение;
явные null/пустая строка для личных данных очищают его. Невалидные дополнительные
значения игнорируются без отказа во входе. Частичная birthday хранится исходной
строкой (нулевые компоненты допустимы), sex ограничен male/female/null.
См. [поля](https://yandex.ru/dev/id/doc/ru/user-information) и
[правила scope](https://yandex.ru/dev/id/doc/ru/codes/code-url).

Альтернатива — передавать полный профиль всем клиентам и скрывать поля CSS —
отклонена: контакты уже оказались бы раскрыты. Редактирование профиля не добавлять
в контракт этой итерации.

### 4. Composer и реакции

Меню плюса использует существующие команды создания предложений; меняется
представление и переход к форме, не правила опросов. Черновик, позиция курсора,
выделение и выбранные файлы принадлежат состоянию composer, а не временной панели.
Набор Unicode-эмодзи и русские поисковые имена поставлять локально с клиентом,
недавние хранить локально. Не зависеть от сетевого поиска для каждого нажатия.

Для реакций добавить идемпотентные PUT/DELETE к сообщению по нормализованному
эмодзи и текущему пользователю; уникальность `(message_id, user_id, emoji)`.
Несколько разных эмодзи одного человека допустимы. Проверка доступа та же,
что чтение/отправка в чат. В ответе агрегаты, собственные реакции и версия;
список авторов загружается отдельно без контактов. События обновления включают
ID сообщения/версию. Оптимистический UI откатывается при отказе. Старые клиенты
должны игнорировать неизвестные необязательные поля/виды событий и продолжать
показывать текст сообщений. Альтернатива — вставлять реакцию как новое сообщение —
засоряет разговор и не даёт корректного снятия реакции.

### 5. Вложения и фотоальбом

Разделить бинарный файл и привязку: файл имеет владельца, meeting_id, тип, размер,
статус подготовки/загрузки/готовности, стабильный ID и ключ повторной операции.
После успешной проверки содержимого атомарно создаётся привязка к сообщению
или альбому. Незавершённый файл не становится доступным другим участникам.
Запрос начала загрузки возвращает актуальные ограничения, сервер повторяет
проверку размера, фактического формата и текущих прав. У каждого файла свой
статус и повтор; не пересоздавать успешные при частичной ошибке.

Чтение метаданных, миниатюр и оригиналов проверяет текущий доступ к встрече.
Не выдавать постоянные публичные URL. Отделить публичную обложку приглашения.
При потере доступа клиент отменяет запросы и очищает локальные превью, поздние
ответы не восстанавливают экран. Локально интерфейс файлового хранилища использует
временный/mock-адаптер вместе с memory.Store и мок-очередью обработки. Производственное
хранение, очистка незавершённых файлов, проверка вложений и квоты входят в
заключительный этап перед выпуском медиа, без локального Docker/БД как условия старта.

Альбом — упорядоченные записи `(meeting_id, media_id, uploaded_by, created_at)`
без поля подписи. Добавляет любой текущий участник. Фото из чата не переносится
автоматически: это отдельная явная операция. Сортировка стабильная по времени
добавления и ID, страницы загружаются постепенно. Клиент держит текущий индекс
и соседние превью, полноразмерный файл получает по запросу. Визуальная стопка
не требует скачивания всего альбома. Альтернатива — делать альбом из всех медиа
чата — смешивает документы подготовки с воспоминаниями без решения участника.

### 6. Реализация клиентов и анимаций

Web: страницы профиля/вайба, features загрузки, выбора реакции и composer;
сущности user/media/reaction и общие контролы в соответствии со строгим FSD.
Импорты через `@/`, небольшие TS-модули, стрелочные функции; в файле компонента
только он и его props. Не переносить монолитный демонстрационный `interactions.ts`
в продукт. Для стопки использовать pointer events с отменой нативного drag,
определением горизонтального жеста, безопасным pointercancel и очисткой анимаций.

iOS: существующие владельцы экранов, NavigationStack, Photo/File picker и Share;
выбор реакции/фото отдельным небольшим представлением. Android: состояния
экранов/ViewModel и Compose, Photo Picker/Documents, системный Back. Системные
результаты выбора не должны теряться при пересоздании экрана. У обоих клиентов
учесть крупный шрифт, экранный диктор, безопасные области и уменьшение движения.

Переезд выделения навигации 260 ms, уход фото 240–290 ms. При уменьшении движения
менять состояние без вращения/вылета; не задерживать навигацию ради анимации.
Клавиши не перехватываются в текстовом поле. Сетка — доступный альтернативный
путь к снимку без свайпа; основной экран не содержит кнопок листания.

### 7. Обратная связь

Клиенты используют общий контракт приёма обращения: тема, описание, экран,
необязательная почта, один явно выбранный скриншот и необязательная диагностика.
Сервер проверяет ограничения независимо от клиента, нормализует значения и
возвращает номер только после записи. Идемпотентный ключ сохраняется до
подтверждения; потеря ответа не создаёт второй отчёт. Тема «проблема» доступна
и при неполадках входа: публичный приём получает ограничение частоты и размера,
без обязательной новой авторизации. Не сериализовать URL с query-параметрами,
текст чата, cookie, токены и весь профиль в диагностический пакет.

Скриншот хранится отдельно от медиа встречи, доступен только обработке обращения.
Проверить фактический формат/размер, очистить метаданные; не создавать публичную
постоянную ссылку. Не добавлять фото в чат или альбом. Контакт и изображение
передаются только если человек сам их указал. Точные сроки хранения, основания,
оператор, доступ сотрудников/разработчика и обработчики — заполняемые юридические
сведения; до их определения нельзя объявлять политику готовой.

После принятия фоновая доставка направляет сообщение ботом в отдельный закрытый
Telegram-чат. Токен и chat_id только на сервере. Номер обращения включается
в доставку; повторы с backoff и пределом попыток, видимый операционный отказ.
Идемпотентность приёма не обещает exactly-once в Telegram: потеря ответа внешнего
API после отправки может дать повтор с тем же номером. Не логировать текст,
почту, скриншот или секрет; достаточно ID, этапа и кода ошибки.

Сначала memory.Store и мок очереди/доставщика; их сброс при рестарте явно описать
как локальное ограничение. Перед production — постоянная запись и очередь
доставки в рамках заключительного облачного этапа. Не внедрять настоящего бота,
БД или сетевую отправку в HTML-макеты. Реальные Telegram credentials потребуются
на этапе подключения, не для согласования дизайна.

### 8. Сведения о сервисе и хранении

Web получает Footer только на десктопном онбординге и отдельные страницы помощи,
о приложении и документов. На остальных страницах/mobile web и во всех нативных
экранах футера нет по последнему решению пользователя; ссылки доступны из профиля.
Документы доступны до авторизации.
Версию брать из метаданных сборки: web-тег/сборка, iOS bundle version,
Android versionName/versionCode. Пример в макете не копировать как константу.
Подпись сохраняет полный SemVer, например «Версия 0.1.0-rc.2»; отдельный
номер CI «Сборка 42» доступен в разделе о приложении. Данные происходят
из открытой сборки по уточнённому release-version-policy.
Подпись Developed by MintyDev едина, реквизиты оператора отдельны.

Аудит исходников и условный правовой вывод: [privacy-cookie-review.md](privacy-cookie-review.md).
Cookie входа сохраняется до 30 дней; нельзя называть её краткой сессионной
или автоматически считать исключённой из любого согласия. В исходниках web
не найдена сторонняя аналитика, но это не аудит deployed-сайта. Окончательное
решение о согласии и его отдельном UI принимается после заполнения применимых
стран, оснований и сведений оператора. Пустые поля разрешены только в дизайн-черновике.

## Risks / Trade-offs

- Дополнительные поля Яндекс ID могут отсутствовать → необязательные поля,
  инициалы и «Не указан», отдельная проверка разрешений до выпуска.
- Старые мобильные версии не знают вложений/реакций → контракт расширяется
  совместимо, деградация текста и неизвестных событий проверяется отдельно.
- Фото увеличивают трафик/память → миниатюры, пагинация, ограниченное число соседей,
  отмена загрузок, проверка квот перед включением в production.
- Часы клиента расходятся с сервером → окончательная проверка RSVP на сервере.
- Выступающие элементы карточки обрезаются контейнером → отдельные внешние отступы
  и визуальная проверка списка/календаря с длинным названием и крупным шрифтом.
- Жест фото конфликтует с прокруткой → горизонтальный порог, вертикальный pan,
  cancel/короткий жест и reduced motion проверяются на реальных устройствах.

## Migration Plan

Сначала расширить контракт и memory/mock-реализацию, затем независимо реализовать
и проверить web, iOS и Android. Проверить старые ответы и старые клиенты до
включения новых данных. Подготовить production-хранилище медиа и операционные
ограничения на заключительном этапе, не считать mock постоянным хранением.
Выкатить серверные возможности совместимо, затем web и отдельные мобильные
сборки. При откате клиента данные вложений и реакций не удалять. Отсечка остаётся
серверной и не зависит от наличия нового UI. Финальную схему SQL/миграции
подготовить вместе с production-адаптером, не в этапе дизайна.

## Перенос форм действий

Первый приоритет после паузы 26.10.2026: заменить мобильные полноэкранные
действия чата на bottom sheets. Это прямое исправление пользователем макета:
применяется ко всем голосованиям, задачам и другим действиям из чата на mobile web,
iOS и Android. Desktop в 2.0.0 использует модалки поверх того же чата. Содержимое action-*.html и прежние
правила опросов/задач сохраняются, их мобильная оболочка меняется. Реальный источник

## Перенос одобренной композиции 1.3.0

workbench scale/iframe или его fixture-controls в приложения.

Один владелец мобильных панелей переключает info/Share/settings/task/forms,
сохраняя родительский контекст и opener. При redraw фильтров людей/состава фокус
восстанавливается на актуальном доступном элементе без scrollIntoView внешнего
чата. Системные Share, file/photo picker и IME работают реально; никакой успешной
операции до подтверждения API. Draft и idempotency lifecycle прежние.

Web сохраняет FSD и небольшие TS-компоненты; native адаптирует общие токены

320×760, 390×844, 390×430, мобильный landscape 844×390, desktop 768/1440,
системную клавиатуру, крупный текст, accessibility и reduced motion.
