# Подготовка независимой функциональной приёмки

27.10.2026, проверяющий `/root/feature_acceptance`.

Это read-only подготовка по `feature-test`, а не прогон и не отчёт о готовности.
Приложения, браузеры, серверы, сборки и устройства не запускались. Ни одному
кейсу не назначен результат. Исторические screenshots и тесты не использованы
как доказательство текущего поведения. `exploratory-test` не запускался:
текущее поручение — проход согласованного каталога.

## Полный объём

В `testing-manifest.json` найдено 100 уникальных ID. Их точные требования,
шаги, ожидаемые результаты, платформы и связи с задачами сохранены в
[case-inventory.json](case-inventory.json). Это снимок входных документов,
не `qa:plan` и не `run.json`; перед планом каталог необходимо прочитать заново.

По платформам: backend — 16, web — 82, iOS — 78, Android — 78.
Для feature-прохода согласован `web-responsive`: один реальный браузер на Mac
с явной записью viewport/input mode внутри кейса. Вместе с API/iOS/Android
это 254 case/environment пары. Каждая строка остаётся в объёме независимо
от наличия инструмента или внешнего доступа. Для ручного UI-прохода нужны
журнал действий и целевой screenshot, для API — реальные запросы/ответы
и проверка прав/состояния. Секреты и данные личных встреч не сохраняются.

Причина отдельного feature-профиля: `selectScope` фильтрует только по platform,
а `TC-INFO-28355B41` требует desktop onboarding, `TC-INFO-9D87E6B1` — touch
landscape шире 740. Четыре отдельных web environment дали бы 500 пар, включая
искусственные несовместимые предусловия. В `web-responsive` проверяются все
требуемые конкретным кейсом ширины и режимы: четыре там, где они перечислены,
широкая desktop-компоновка для desktop-кейса, touch landscape для соответствующего
кейса. Их фактическое выполнение записывается раздельно; имитация touch не
объявляется физическим телефоном. Release-профили web-desktop/web-mobile и
их отдельная приёмка не изменены. Нельзя дать pass неисполненному условию.

## Условия начала

1. Координатор фиксирует актуальные исходники, каталог и наблюдаемые сборки,
   создаёт общий feature-plan/run штатным CLI. Все ID берутся из manifest.
2. В environment указываются реальная идентичность клиента и API, тестовый
   набор, ОС/устройство, locale/timezone; URL ведёт на продукт, не на макет.
3. Проверяющий проверяет доступ к origin тем же инструментом живого прохода.
   Наличие HTML-сборки или автотест с собственной TLS-конфигурацией не
   подтверждает доступ независимому инструменту.
4. Координатор выдаёт отдельное GO и свободное окно. Сборки, Go и полные
   браузерные/мобильные прогоны не выполняются параллельно.
5. Проверка каждого кейса начинается с его предусловий, далее исполняются
   все действия и сравниваются expected/actual. Объединение маршрутов для
   экономии переходов не сокращает проверки отдельных кейсов.

Маршруты последовательно проходят web 320/390/768/1440, затем iOS и Android

Сквозная группа 7.1 выполняется на общей встрече с разными профилями:

`scripts/test-cross-platform.py` существует, но его наличие не подтверждает

## Средства: только проверено наличие

- `.cache/web-demo/index.html` и `frontend/web/dist/index.html` существуют.
  Их актуальность фиксирует координатор после последних изменений; в этом
  preflight build SHA не объявляется проверенным.
- Локальный `playwright` — 1.64.1; доступны код штатного browser-server,
  CUA и Node REPL инструменты. Их соединение с продуктом не проверялось.
- Xcode `xcodebuild`/`simctl` существуют, есть прежние `.xctestrun` файлы.
  Они не считаются автоматически подходящими новой сборке.
- Есть adb, JDK 17, INI существующего `Somewhere_API_36` и штатный Android
  UI runner. adb server/AVD не запускались и online-состояние не заявляется.
- iOS разрешён только `31262733-50DC-46A5-938E-4C462D70F109`, iPhone 18 Pro,
  runtime 27.0. Android — только `emulator-5554`; чужой `emulator-5556`
  не используется. Обычные приложения/их данные не удаляются.

Для web сервер допускает только IPv4 loopback и обслуживает реальные API.
Стандартный `browserProvider` имеет восемь синтетических профилей, но
возвращает только Subject/DisplayName. `SOMEWHERE_BROWSER_DESIGN=1` добавляет
известные встречи/медиа, а не универсальные fault/clock controls.
Origin для CSRF необходимо брать у своего fixture: helper `writeHeaders`
из тестов содержит фиксированный 8444 и не переносится на другой порт без
явной адаптации QA harness.

## Предпосылки, которые нельзя подменить

- Во время подготовки найдены два семантических пересечения. Координатор
  синхронизировал raw specs/UX и кейсы до снимка inventory:
  `TC-FEED-1BFACA40` теперь разрешает X в мобильных действиях чата
  (source hash `fb352927…`), а `TC-LIST-74A5E939` отличает обычный Back
  самостоятельного экрана от закрытия sheet (source hash `f309631e…`).
  Проверяющий прочитал изменения; живое поведение ещё не проверялось.
- Для `TC-PROFILE-YANDEX-FIELDS` в live fixtures пока не найдено управляемого
  переключения provider full/partial/clear на одном subject. Обычные providers
  отдают Subject/DisplayName, design seed — фиксированный профиль с
  `birthday=0000-12-23`, `sex=male`, без телефона. Нужен реальный тестовый
  OAuth/SDK обмен с этими вариантами, а не подстановка JSON в UI. Серверный
  identity-тест отдельно не доказывает обновление всех клиентов.
- Точная граница часов, гонки и удаление просроченных объектов требуют
  управляемых clocks/barriers. Они есть в отдельных Go тестах; обычный web
  fixture использует `time.Now`. Проверяющий сначала сопоставляет фактический
  охват целевых интеграционных тестов с каждым шагом; непроверенные шаги
  нельзя принять по одному зелёному smoke.
- Native VoiceOver на реальном устройстве, TalkBack/озвучивание, системный
  picker, web IME и системный Share требуют фактического инструмента для
  каждого действия. AX node, DOM или низкий viewport не заменяют эти
  операции. В preflight их доступность не заявлена.
- `TC-INV-DEC030F5`, `TC-CHAT-C60E942D` и совместимость задачи 7.1 требуют
  названных старых сборок. Старый JSON payload проверяет API-совместимость,
  но не является запущенным прежним клиентом.
- `TC-API-MEDIA-DURABILITY` и `TC-API-SUPPORT-DURABILITY` требуют изолированных
  постоянных среды/backup/отката либо очереди и согласованных сроков.
  Memory fixture, production и локальная БД не используются вместо них.
- `TC-INFO-PUBLIC-POLICY-RELEASE` требует согласованных реквизитов и решения
  по фактическому хранению. Для `TC-INFO-E5D26634` нельзя включать вымышленную
  аналитику ради теста; требуется кандидат с таким отслеживанием либо явная
  фиксация невыполненного условного предусловия в плане.
- Реальная отправка в Telegram не входит в разрешённую QA-среду. Мок
  пригоден для локального acceptance, но не для утверждения реальной доставки.

## Доказательства будущего прогона

Каждый case/environment получает свой ID из `plan.expected`. Журнал содержит
время, наблюдаемую сборку/API, данные, каждое действие, фактический результат
и readback/второй профиль, когда они требуются. Сохраняются действительные
HTTP/runner raw, screenshot целевого UI и SHA-256 файлов. Токены/cookie,
частные URL и неизвестные фотографии не публикуются.

Ошибка приложения после выполненного предусловия — failed с воспроизведением.
Отсутствие инструмента, внешних данных или доступа — blocked с конкретной
причиной после проверки. Зависимые случаи блокируются, независимые продолжаются.
Предварительный список требований среды не заменяет эти результаты.

Очистка касается только собственных данных/процессов/временных файлов;
сначала сохраняются доказательства. После исправлений требуется новый актуальный
план/прогон, старые результаты сохраняются без переноса pass. Перед checkbox
координатор выполняет `qa:ready` и отдельно `design:ready`.
