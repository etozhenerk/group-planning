# Независимая проверка oracle при resize

Проверяющий: `/root/web_finish_now`. Область — только падение проверки ID после resize в повторе 1 теста 39 Linux run 40855558482, source 15b6dbd3. Приложение и тест не изменялись. Проверяющий не участвовал в исправлении viewport/anchor, которое делает основной агент; раннее падение preload не оценивалось.

## Источники

- Trace: `/tmp/somewhere-ci39-diagnostic3/39-chat-window-bounded-his-83ad8-oss-prepend-and-late-resize-mobile-webkit-repeat1/trace.zip`.
- SHA256 trace: `e8fe3d144958c0b383c057cd1e5a48c70963ad447ac02e2de4f03687db94a1d5`.
- DOM snapshots: `gtxz@1830 before` (70475.503), `gtxz@1838 before` (70716.975).
- Диагностика scroll-event: 4622 ms и 4845 ms в `anchor.json`.
- Сохранённые атрибуты viewport, scroll container и соседних строк: `resize-geometry.json`.

DOM восстановлен из frame-snapshot с учётом ссылок на поддеревья прежних snapshots по формату установленного Playwright. Это анализ сохранённого Linux evidence; новый живой прогон не выполнялся. CSS задаёт inset 16 px у mobile feed, virtual rows не имеют отдельного межстрочного gap.

## Фактическая геометрия

Исходный anchor — `ef6dc081-e9d1-4cf1-b444-197db12bbe2f`, index 249, сообщение «История 247». Следующий — `30575cd4-d0cf-4fd8-823c-b64dec1e727c`, index 250.

| Величина | До resize | После resize |
| --- | ---: | ---: |
| Viewport | 402×874 | 500×700 |
| ScrollTop | 29715 | 29631 |
| Anchor translateY | 29586 | 29502 |
| Внутренний верхний отступ | 16 | 16 |
| Anchor top относительно viewport | −113 | −113 |
| Следующая строка translateY | 29713 | 29608 |
| Шаг до следующей строки | 127 | 106 |
| Следующая строка top относительно viewport | 14 | −7 |

Расчёт anchor offset: `translateY + 16 − scrollTop`. Получено ровно 0 px изменения. Anchor присутствует в обоих snapshots с тем же ID/index и `data-protected=false`.

После увеличения ширины строка стала ниже: её нижняя граница теперь находится на −7 px относительно viewport. Поэтому поиск первой строки с `bottom > viewport.top` закономерно выбирает следующий ID. Этот факт не означает потерю исходного anchor. Текущее падение возникает при сравнении повторно выбранного first-visible ID с прежним, хотя сохранённый ID остался на прежней физической позиции.

## Корректный oracle для сохранения физического anchor

1. До resize выбрать видимую строку и зафиксировать её ID и offset.
2. После resize измерить строку именно с сохранённым ID; проверить её наличие и отсутствие protected-состояния.
3. Сохранить строгую проверку изменения offset не более 2 px.
4. Для следующего отдельного действия заново захватить текущую видимую строку.

Это не ослабляет проверку drift: измеряется тот объект, позицию которого контракт требует сохранить. Сравнение first-visible ID после изменения высоты самого anchor проверяет другое условие. Для обязательной видимости уменьшающейся строки потребовалось бы менять сохранённый offset; одновременно удержать −113 px и показать строку высотой 106 px невозможно. Такое продуктовое изменение здесь не предлагается.

Вывод ограничен этим resize failure: runtime drift сохранённого anchor равен 0 px. Корректность preload, reset, remote append и остальных ветвей этим анализом не подтверждена.
