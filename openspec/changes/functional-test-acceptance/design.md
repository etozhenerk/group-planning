# Design

## Context

См. [proposal](proposal.md). Есть Go/unit/HTTP, Vitest/Playwright,
Swift Testing/XCUITest, JVM/Compose instrumentation и общий cross-platform runner.
Android CI компилирует UI tests, но device-run выполняется отдельно. Release
инструменты уже сохраняют manifest/SHA256; QA fixtures и store artifacts различны.
Основной checkout содержит чужую незавершённую UI-работу: её не затрагиваем.

## Goals / Non-Goals

**Goals:** проверяемый каталог, воспроизводимый выбор кейсов, независимый ручной
проход агентом, строгая свежесть результатов и отдельный gate выкатки.

**Non-Goals:** собственная TMS с сервером/аккаунтами, замена тестовых фреймворков,
продуктовые UI/API-правки, production-деплой или новый облачный стенд. UX/UI
продукта неприменим; Allure используется как готовый инструмент разработчика.

## Decisions

1. YAML-кейсы в testing/cases с явным уровнем пирамиды, платформами, source refs,
   действиями/ожиданиями и картой автоматизации. Инвентарь сценариев обнаруживает
   новые/изменённые источники и пробелы; старые продуктовые delta specs доступны
   до синхронизации в main specs. Переименование/архивация обновляет ссылки,
   а стабильный case ID сохраняется. Конфликт требований требует решения,
   а не обучения кейса по текущему коду.
2. JSON Schema/Ajv проверяет каталог, матрицу окружений, план и результат.
   Разделяем lifecycle, automation coverage, automation health и run status.
   Единицы/интеграция не дают E2E coverage; повторные ручные проходы не становятся
   автоматизацией. Исполнение кода не определяется из произвольного YAML shell.
3. План фиксирует выбор ID × environment, fingerprints кейсов/требований/кода,
   build identity и actor. Результат отдельно хранит каждый check и SHA256
   локального evidence. Полный release scope вычисляется каталогом, а не ручным
   списком автора отчёта. Неизвестные/дублирующиеся результаты отклоняются.
4. Feature manifests связывают tasks.md с планом/результатом; завершённые задачи
   проверяются CI. Legacy-изменения перечислены явно без ложной приёмки; при
   следующей пользовательской задаче добавляется testing.md и manifest.
   Новая общая документация сама по себе не пересобирает клиент: fingerprint
   включает исполняемые входы, тестовый контракт и применимые требования.
5. Release gate расположен после сборки/прогона, до production-deploy/store
   promotion. Кандидаты доступны для тестирования; итоговый receipt связан
   с SHA256 manifest и файлов, его нельзя использовать для другой сборки.
   Все обязательные окружения должны быть представлены. Автоматизированные
   прогоны тоже нужны; ручной pass не маскирует упавший обязательный автотест.
6. Отчёт JSON и Markdown — источник фактов. Экспорт Allure использует те же
   результаты и копии evidence; Allure не выдаёт разрешение на релиз сам.
   Точную публичную версию закрепляем после пробы. Native raw evidence остаётся
   xcresult/runner output; адаптеры могут развиваться независимо от каталога.
7. Навыки test-spec, feature-test, release-test задают алгоритм. Независимый
   проверяющий меняет только отчёт/evidence, не продукт/кейсы. Родитель исправляет
   и повторяет проверку. Отсутствие окружения — blocked. Человек нужен только
   для недоступного аккаунта/устройства/личного подтверждения.
8. Пирамида реализуется подбором уровня каждого правила, без квот. Каталог
   связывает нижние проверки и небольшой E2E-набор через требования; ручной
   проход остаётся отдельным способом выполнения. Сложные временные/ролевые
   комбинации проверяются ниже; пользовательский путь имеет свой E2E.

## Risks / Trade-offs

- JSON не доказывает честность автора → независимый проход, raw evidence,
  идентичность артефакта и negative tests; не обещаем криптографическое доверие к агенту.
- Неполный перенос старого покрытия → инвентарь и явные пробелы блокируют release,
  не записываем старые тесты как текущий pass.
- Store build отличается от QA → зафиксированные artifact/API origin и отдельные
  реальные проверки; pipeline не требует готовности для самой сборки кандидата.
- Публичный Git → тестовые профили, без секретов/личных данных; большие evidence
  вне Git, для релиза долговременное хранение и проверка hashes.
- Параллельные задачи используют устройства → не перезапускать чужие сессии,
  фиксировать недоступность и продолжать независимую проверку инструментов.

## Migration Plan

Схемы и каталог → CLI/negative tests → навыки/SDD → Allure и реальные пилотные
прогоны → CI и gate выкатки. Пилот не утверждает непроверенные клиенты.
Откат tooling-коммита не удаляет результаты и не делает старый релиз принятым.

## Framework references

Сохраняем существующие Go/Vitest/Playwright/XCTest/Compose frameworks.
Для отчёта выбран [Allure Report](https://allurereport.org/docs/), каталог
остаётся в Git рядом с требованиями. [Testomat](https://docs.testomat.io/project/import-export/download-tests-as-files/download-manual-tests-as-files/)
поддерживает сценарии обмена ручными кейсами через файлы;
[Allure TestOps](https://docs.qameta.io/use-testops/test-plans-and-launches/test-plans/)
предлагает отдельные планы/запуски, но внешний сервер для текущего объёма не вводим.
[Playwright agents](https://playwright.dev/docs/test-agents) полезны для планирования
и генерации тестов; автоматическое лечение теста не получает права менять
продуктовые ожидания или маскировать дефект skip. Пирамида и независимая приёмка
остаются правилами проекта, независимо от конкретного runner/TMS.
