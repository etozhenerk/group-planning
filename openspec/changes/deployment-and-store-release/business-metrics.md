# Бизнес-панель somewhere

Дополнение по запросу владельца 25.10.2026. Затрагивает backend (SQL-адаптер,
команда миграций) и infra (закрытый exporter, панель Monium). API и интерфейсы
web/iOS/Android не меняются; отдельный UX приложения неприменим.

## Метрики

| Имя после `somewhere_business_` | Определение |
| --- | --- |
| `users` | Число сохранённых профилей `identity_users` |
| `meetings` | Все сохранённые встречи, включая прошедшие и отменённые |
| `chats` | Ленты встреч: сейчас одна лента на встречу, включая пустые |
| `chats_with_messages` | Встречи, где есть хотя бы одна запись `Kind=message` |
| `messages` | Пользовательские сообщения; системные события не входят |
| `logins_total` | Успешные создания сессий с момента включения учёта |
| `logins_today` | Успешные создания сессий за текущие сутки UTC |
| `tracking_started_timestamp_seconds` | Начало достоверной истории входов |
| `collection_success` | Успешно прочитан полный агрегированный снимок, 1/0 |

Первые пять — gauges, `logins_total` — постоянный counter; остальные — gauges.
Повторное использование сессии, logout, cleanup, отмена OAuth и откат транзакции
не добавляют вход. Повторный login того же пользователя добавляет вход, но
не новый профиль. Старые удалённые сессии восстановить нельзя: backfill входов
не выполняется. Реальный тестовый аккаунт владельца входит в общие числа.

## Хранение и совместимость

В отдельной схеме `observability` хранится один счётчик входов на сутки UTC
без user ID, IP, имени, provider subject или токена. `AFTER INSERT` на
`identity_sessions` обновляет счётчик в той же транзакции. `ON CONFLICT UPDATE`
существующей сессии не считается повторным входом. Это покрывает web, native
handoff и SDK без изменения клиентского контракта.

Телеметрия включается отдельным параметром команды миграций из backend-релиза.
Она имеет собственную checksum-запись и не меняет версию прикладной схемы 1:
прежний backend совместим с добавленной схемой и продолжает учитывать входы.
DDL выполняет только migrator. Функция триггера имеет фиксированный search_path
и полностью квалифицированные имена; runtime не получает прав на таблицы
агрегатов. Роль exporter получает SELECT только на агрегирующее представление.

Exporter читает единый SQL-снимок раз в минуту, timeout 3 секунды, без вывода
SQL-ошибок/данных в логи. При ошибке — collection_success=0, остальные бизнес-ряды
отсутствуют. Не подставлять нули. Максимум девять новых рядов без дополнительных
меток; общая оценка с техническими метриками — 363 из лимита 500.

Уточнение после подключения 25.10.2026: фактически в custom 470 рядов,
включая бизнес-метрики и HTTPS probe. Оценка 363 не подтвердилась; перед
добавлением API-метрик ограничить системный набор. Доказательства —
[отчёт](monitoring-live-verification.md).

## Проверки и выпуск

Проверить идемпотентность включения и checksum; повторный вход/UPSERT, rollback,
logout/cleanup, границу UTC, конкурентные сессии, restart/restore и отсутствие
доступа exporter к исходным таблицам. Интеграционные проверки выполняются
только на изолированной облачной БД; локальный PostgreSQL/Docker не поднимать.
Выпустить отдельный backend RC, проверить его артефакт, затем включить учёт,
обновить exporter и импортировать отдельную бизнес-панель. До live-проверки
не объявлять графики подключёнными.
