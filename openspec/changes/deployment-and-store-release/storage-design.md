# Постоянное хранение: проект для группы 14.2

Дата: 24.10.2026. Этот документ конкретизирует выбранную PostgreSQL перед
реализацией адаптера и размещением ресурсов. Поведение API и клиентов сохраняется.
Приёмка постоянного хранения остаётся задачами 14.3–14.4 основного изменения.

## Decisions

- PostgreSQL **16**, штатные пакеты Ubuntu 24.04 LTS; minor-версия фиксируется
  в отчёте установки и обновляется в рамках безопасности. Эта major-версия
  [поддерживается Managed PostgreSQL](https://yandex.cloud/ru/docs/managed-postgresql/concepts/update-policy).
- Go-драйвер **github.com/jackc/pgx/v5 v5.11.0**, проверен через официальный
  Go module proxy 24.10.2026. Внешняя зависимость допускается только в SQL-адаптере
  и точке сборки зависимостей; политика архитектуры обновляется вместе с кодом.
- Очередь — **собственные SQL-записи текущих задач**, без River и Message Queue.
  Существующие `TransitionJob` уже реализуют версию расписания, lease/fencing,
  повторы и окончательный отказ. `PollCloseJob` выполняется целиком в Update.
  Перенос этих записей сохраняет одну машину состояний. River потребовал бы
  согласовать вторую систему retries/lease; Message Queue — ещё и outbox.
  Для пилота эти зависимости не дают подтверждённого выигрыша.
- Адаптеры `meetings.Store` и `identity.Store` сохраняют текущие порты;
  доменные правила, auth-provider и HTTP DTO не зависят от PostgreSQL.
  Идентификаторы — text, даты/сроки — timestamptz, ревизии/sequence —
  numeric(20,0), чтобы не сузить существующий uint64 до signed bigint.

## Data model

Каждая запись содержит отдельные ключи/индексируемые поля и `document jsonb`
с серверной структурой. Это отдельные строки по сущностям, а не единый снимок
всего приложения. JSON не является HTTP-ответом и не попадает в публичный API.
Поля индексов и document записываются одним SQL-оператором; их соответствие
проверяется адаптером и интеграционными тестами. Новые обязательные поля требуют
миграции/backfill, даже если PostgreSQL допускает их отсутствие в JSON.

| Таблица | Ключи и ограничения | Индексы и назначение |
| --- | --- | --- |
| meetings | PK id | organizer_id; status/past_at/id для сверки просрочки |
| invitations | PK token; UNIQUE id и meeting_id; FK meeting_id | одно актуальное приглашение встречи |
| rsvps | PK (meeting_id, user_id); FK meeting_id | user_id/meeting_id для личного списка |
| feed_entries | PK id; UNIQUE (meeting_id, sequence); FK meeting_id | UNIQUE (meeting_id, actor_id, client_request_id) только для непустого client_request_id |
| request_receipts | PK (user_id, operation, request_key) | expires_at для очистки без кеширования прав |
| transition_jobs | PK (meeting_id, schedule_version); UNIQUE id; FK meeting_id | state/available_at и state/lease_until; очередь и просроченные lease |
| date_polls | PK id; FK meeting_id | meeting_id; состояние/available_at задачи завершения |
| place_polls | PK id; FK meeting_id | document с вариантами, голосами и состоянием завершения |
| preparation_tasks | PK id; FK meeting_id | индекс meeting_id/id; document с поручением |
| meeting_covers | PK/FK meeting_id | ограниченный доменом бинарный файл в JSONB/base64 (TOAST), версия и размеры |
| identity_users | PK id; UNIQUE provider_subject | стабильная привязка Яндекс subject → собственный user ID |
| identity_attempts | PK id | expires_at; короткоживущие PKCE/state/handoff |
| identity_sessions | PK secret_hash; UNIQUE id; FK user_id | user_id, expires_at для отзыва/очистки |
| schema_migrations | PK version, checksum, applied_at | проверка применённых миграций |

`date_polls.document` хранит варианты и бюллетени одного ограниченного опроса
как агрегат. Изменение голоса, итог, новая дата, новая задача и feed-событие
коммитятся вместе. Внешние ключи встреч/задач отложены до commit: существующая
операция может поставить задачу до первой записи новой встречи.
Внешние ключи между identity и meetings не вводятся: связывание модулей остаётся
на уровне прикладных операций. Секреты сессий хранятся только в виде хеша.

## Transactions

- View: read-only транзакция REPEATABLE READ, один согласованный снимок,
  независимые значения после декодирования. После callback Reader недействителен.
- Update встреч: READ COMMITTED и транзакционный advisory lock с постоянным
  отдельным ключом модуля до первого чтения. Update identity имеет другой ключ.
  Локальный mutex защищает использование одного tx внутри callback; SQL-ошибка
  вызывает rollback всего callback. Права/revision/lease проверяет доменный слой.
- Это намеренно последовательные записи внутри модуля для первого пилота.
  Чтения не берут этот lock, identity и meetings не блокируют друг друга.
  Контроль времени ожидания lock входит в нагрузочную проверку; при ограничении
  сначала перейти к блокировкам агрегатов/строк отдельным изменением.
- Блокировка имеет срок жизни транзакции
  ([PostgreSQL](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)).
  Никаких HTTP-вызовов, вложенных транзакций и неограниченного ожидания внутри callback.
  lock_timeout 3 с, statement_timeout 5 с; отмена context вызывает rollback.
- SQL-ошибки identity накапливаются внутри tx, поскольку часть методов Records
  не возвращает error. Store проверяет накопленную ошибку перед commit и перед
  возвратом доменного результата: сбой SELECT не становится «пользователь не найден».
- Не повторять произвольный callback автоматически после неизвестного результата
  commit. Повтор HTTP обрабатывается прежними идемпотентными ключами/receipts.
  Новый процесс восстанавливает истёкшие lease по существующим правилам.

## Configuration and migrations

`SOMEWHERE_STORAGE=postgres`; DSN и параметры пула вне Git. Начальный пул:
max 10, min 1, ограничение connect 5 с. На локальной ВМ допускается Unix socket
с peer-доступом непривилегированной роли приложения; TCP слушает только loopback.
Для managed используется тот же DSN с `sslmode=verify-full` и доверенным CA.
Пароли, если нужны для TCP, доставляются через Lockbox в закрытый env-файл.
Роль runtime не является superuser и не владеет схемой; отдельная роль миграций
имеет DDL-права. Никаких обязательных superuser-расширений, файловых путей сервера
БД или зависимости от локального часового пояса.

Миграции нумеруются и встраиваются в отдельную команду. Перед применением:
advisory lock миграций, проверка checksum ранее выполненных версий и SQL-транзакция.
Runtime только проверяет совместимую схему и Ping, сам не выполняет DDL.
Неподдерживаемая версия/недоступная БД дают неготовность `/readyz`; `/healthz`
продолжает проверять процесс. Успешные записи без commit запрещены.
Обновления выполняются expand → совместимый выпуск → отдельное удаление устаревших
полей; откат бинарника не выполняет разрушительный down.

## Acceptance

На реальной PostgreSQL на облачной ВМ, без локального Docker/БД:

1. Применение/повтор миграции, checksum mismatch, runtime без DDL/superuser.
2. Создать пользователя/сессию/встречу/опрос/сообщение/receipts/задачи; закрыть
   соединения, перезапустить API и PostgreSQL, проверить прежнее состояние.
3. Два независимых пула/worker: гонки RSVP, сообщений с одним ключом, голосов,
   переноса и истечения lease; один эффект, без потерянного обновления.
4. Ошибка перед commit откатывает все изменения; потеря БД не даёт ложного успеха
   или раскрытия DSN/SQL/пользовательских данных, readiness становится отрицательной.
5. Восстановить pg_dump в отдельную чистую БД, сверить права, сессии, receipts
   и просроченные задачи; отдельно проверить копию вне ВМ и шифрованный экспорт.
6. Проверить API-контракт, текущие клиенты и нагрузку с очередью/копиями/агентами.

Тесты на mock-provider Terraform и memory.Store эти сценарии не закрывают.
