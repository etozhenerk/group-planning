# Прикладной мониторинг somewhere

Дополнение по запросу владельца 24.10.2026: тайминги, ok/bad RPS, пинги,
трафик ботов и остальных клиентов. Это **план подключения к production-релизу**;
сейчас в облаке работают системные/PG-метрики, API ещё отвечает заглушкой 503.
Прикладные графики не заполнять искусственными нулями до появления источника.

## Первая очередь

| Панель/показатель | Определение и разрез | Зачем |
| --- | --- | --- |
| Входящие API RPS | Завершённые API-запросы/с, окна 1 и 5 мин; общий поток и группы операций | Видеть нагрузку, пики и чрезмерный polling |
| OK RPS | Ответы 2xx; 3xx показывать рядом отдельной линией, включая OAuth-редиректы | Отличать полезные ответы от переходов |
| Bad RPS | 5xx и серверные/upstream timeout; без двойного счёта 504 и того же timeout | Видеть именно сбой обслуживания |
| Отклонённые запросы | 4xx отдельно; 429 отдельно от прочих 4xx; отмены клиентом отдельно | 401/404 не означают падение сервера; 429 — давление на лимит |
| Error rate | Bad / (2xx + 3xx + Bad), плюс абсолютные ошибки/5 мин | Не прятать ошибки за ботами/404 и не поднимать шум из-за 1 запроса |
| Время ответа | Histogram p50/p95/p99 по чтению, записи, auth; успешные и ошибочные отдельно | Среднее скрывает медленные ответы |
| Операции в работе | Число одновременных запросов, завершения, отмены | Различать рост RPS и зависание запросов |
| Внешний HTTP-пинг | Readiness с отдельной функции: success, полный latency, DNS/TCP/TLS/TTFB, возраст результата | Видеть проблему снаружи, включая домен и сертификат |
| Трафик | RX/TX ВМ, request/response bytes HTTP, исходящие ГБ за сутки/месяц | Видеть нагрузку и источники расхода |
| Источник запросов | Подтверждённый бот, предполагаемый бот, preview, наш probe, неизвестно | Отделять автоматический трафик, не выдавая оценку за факт |

`OK RPS` в интерфейсе подписать «Успешные ответы (2xx)», `Bad RPS` — «Сбои
сервера и таймауты». Не объединять 4xx с Bad и не объявлять весь остаток
«успешными»: графики в сумме должны объяснять весь поток. Статику и health/probe
исключать из пользовательского API RPS, но оставлять в общих HTTP/traffic счётчиках.
Readiness ping не должен создавать аккаунт, сессию, сообщение или бизнес-задачу.

## Где измерять

- **Caddy:** все внешние HTTP-запросы, upstream failures и размеры ответа после
  сжатия, включая ответ до попадания в Go. Backend и proxy — разные источники,
  их счётчики не складывать: один пользовательский запрос проходит оба слоя.
- **Go middleware:** длительность обработчика, статус/исход, операция, in-flight.
  Экспорт на закрытом `/metrics`, без пользовательского токена в селекторе.
- **PostgreSQL/pgx:** время ожидания соединения, занятые/свободные соединения,
  latency операций БД, блокировки, deadlocks, long transactions. SQL-тексты
  и аргументы в метрики/уведомления не включать.
- **Worker:** длина очереди, возраст самой старой готовой задачи, длительность,
  retries, final failures, задержка выполнения относительно due_at, последнее
  успешное восстановление пропущенных задач.
- **Cloud Function:** внешний HTTPS-пинг раз в минуту; отдельно возраст последнего
  результата и ошибка самого probe. Выполнение в том же регионе не доказывает
  доступность при отказе региона. ICMP до VM — необязательная диагностика:
  успешный ICMP не доказывает работу API/БД.

Длительность HTTP в секундах; панели показывают мс. Использовать histogram,
не усреднять уже вычисленные p95 разных процессов/окон. При малом числе запросов
показывать число наблюдений и пометку недостаточной выборки. p99 для пилота из
шести человек диагностический; отдельный аварийный алерт на него не нужен.
Опорные соглашения: [OpenTelemetry HTTP metrics](https://opentelemetry.io/docs/specs/semconv/http/http-metrics/),
[Prometheus histograms](https://prometheus.io/docs/practices/histograms/).

## Боты и прочие запросы

Пять ограниченных классов: `verified_bot`, `suspected_bot`, `link_preview`,
`synthetic`, `unknown`. «Не бот» нельзя надёжно получить вычитанием ботов:
неизвестный браузер может оказаться скриптом. Отдельный признак авторизованной
сессии полезен, но не подтверждает человека. Названия в панели должны это отражать.

1. `synthetic` — только собственный probe, подтверждённый сервером по отдельной
   конфигурации; произвольный заголовок от клиента не даёт права исключить запрос.
2. `verified_bot` — allowlist с актуальными официальными диапазонами IP или
   корректной reverse **и** forward DNS-проверкой. Проверка асинхронная/с кешем,
   не DNS-запрос на каждый API request. IP из непроверенного X-Forwarded-For
   не доверять; учитывать только настроенную цепочку reverse proxy.
3. `link_preview` — робот предпросмотра приглашений (Telegram и т.п.); если
   проверка источника недоступна, это предполагаемая категория, явно подписанная
   на панели. Не блокировать такой трафик автоматически: он нужен Open Graph.
4. `suspected_bot` — известный UA/поведение без подтверждения источника.
5. Всё остальное — `unknown`, а не гарантированные люди.

UA может быть подделан, что прямо отмечает
[документация Googlebot](https://developers.google.com/search/docs/crawling-indexing/googlebot).
Никакого блокирования или CAPTCHA только по этой метке в данной задаче не вводится.
Собирать RPS, долю 4xx/429 и байты по классам; подозрительный рост сначала
сопоставлять с затратами CPU/трафика и пользовательскими ошибками.

## Ограничение кардинальности и цены

Никаких IP, user/meeting/message ID, полного URL/query, invite token, email,
сырого UA, произвольной версии клиента или SQL в метках. Routes — шаблоны,
не фактический путь. Для старта группировать до 8 операций: auth, meetings,
feed, poll, invites, profile, health, other. Разрезы не перемножать везде:

| Семейство | Верхняя оценка рядов |
| --- | ---: |
| Существующие система/PG/копии/агент | 116 (наблюдалось; перепроверить) |
| API requests: 8 групп × 7 взаимоисключающих исходов | 56 |
| Duration: 4 группы × 2 исхода × (10 конечных buckets + Inf + sum + count) | 104 |
| In-flight по 4 группам | 4 |
| HTTP requests/request bytes/response bytes: 5 классов × 3 scope × 3 семейства | 45 |
| Внешняя проверка и сертификат | 8 |
| Дополнительные PG pool/worker | 20 |
| **Ориентир суммарно** | **353**, запас до 500 |

10 конечных buckets: 0,01 / 0,025 / 0,05 / 0,1 / 0,25 / 0,5 / 0,75 / 1 /
2,5 / 5 секунд, плюс `+Inf`. Scope трафика: api/public/assets; это отдельное
семейство от route/outcome, без их полного произведения. Health/probe помечается
так, чтобы исключение было одинаковым в числителе и знаменателе error rate.

Это оценка схемы, не измеренная кардинальность будущей библиотеки. После подключения
проверить реальные buckets/labels, внутренние series экспортера, повторяющиеся
proxy/Go счётчики и правила alerting. При ≤500 рядов, 60 с и ≤20 условиях
укладываемся в уже заложенный Monium; отдельная Grafana или ВМ не нужны.
Логи по 5 ГБ/месяц и внешняя функция уже есть в смете, фактический расход сверить.

## Сигналы и проверка

- Внешний probe: 3 неуспеха подряд; нет свежего результата >3 мин — отдельная
  неисправность. Срок сертификата <14 дней Warning, <7 дней Alarm.
- API: Bad >1% за 5 мин при ≥100 eligible-запросах; для малого пилота отдельный
  сигнал ≥5 Bad/5 мин или неуспешный probe. Один 401 не вызывает аварийное письмо.
- p95 выше согласованного SLO операции 10 минут при ≥100 наблюдениях;
  SLO взять из design.md и проверить нагрузкой. Число RPS само по себе не авария.
- Всплеск bot/unknown и 429 — диагностический график; алерт только после
  базовой недели и при влиянии на latency/error rate/расход, без произвольного
  «нормального» процента ботов.
- Сценарии: 2xx, OAuth redirect, 401/404, 429, 500, proxy timeout, client cancel,
  перезапуск counters, отсутствие данных, малое число запросов, поддельный UA,
  preview приглашения, отказ DNS/TLS/probe. Сверить total и исключения; проверить,
  что один timeout не удваивает Bad, а private URL не оказался в логе/метке.

Реализация затрагивает backend/infra; UI мобильных клиентов для этого не меняется.
Web/native performance (LCP/INP, crash-free sessions и сетевые ошибки устройств)
можно добавить следующей очередью с отдельной схемой данных и бюджетом.
