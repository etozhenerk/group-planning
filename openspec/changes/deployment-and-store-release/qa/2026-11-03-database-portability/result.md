# 2.5 — переносимый адрес БД, TLS и безопасное восстановление

03.11.2026, основной агент, отдельная временная БД на существующей ВМ
somewhere-mvp. Семь реальных проверок PASS за7.907381с;
[receipt](receipt.json), [исходный вывод](final.txt), [driver](verify.py).

## Проверенное поведение

1. В новой пустой marker-guarded БД штатный уже установленный migrator применил
   все8 миграций. API работал от OS/SQL somewhere: superuser/createdb/createrole
   false. Установлено только штатное plpgsql, дополнительных расширений нет.
2. Использован неизменённый бинарник `/opt/somewhere/backend/releases/0.1.0-rc.6/`
   с SHA256 из receipt. Он подключился через `sslmode=verify-full` и явный
   sslrootcert к TLS1.2+ loopback-прокси перед реальным PostgreSQL16.15.
   Авторизованный Bearer-запрос `/api/v1/me` вернул200. Это синтетические записи
   identity в тестовой БД, не реальный Яндекс OAuth и не обход production-входа.
3. С посторонним CA тот же API завершил startup ненулевым кодом;
   в готовое состояние с недоверенным сертификатом не перешёл.
4. После реального commit создания встречи тело ответа201 намеренно отброшено
   клиентом. Сохранена ровно одна встреча. Это конкретно потерянное тело ответа,
   не выдаётся за обрыв до получения HTTP-заголовков.
5. У единственного тестового DB-прокси закрыты активные соединения и отклонены
   новые. `/healthz`200, `/readyz`503; запись вернула500, успешного ответа и
   новой встречи нет. После восстановления endpoint тот же процесс API
   снова получил readiness200 и авторизованный `/me`200 без перезапуска.
   Фактический500 не переименован в503:503 наблюдался только у readiness.
6. После штатной остановки тестового API изменён только адрес PostgreSQL
   в DSN: второй независимый loopback TLS-endpoint48505→55223. Тот же binary,
   schema, API и тестовая БД. Сессия сохранилась, повтор того же POST с исходным
   Idempotency-Key вернул201 и исходную встречу; count по-прежнему1.
7. В логах тестовых API не обнаружены токен сессии и synthetic provider secret.

Прокси нужен только для изолированного TLS/сетевого fault-теста: рабочий
PostgreSQL не перенастраивался, production-соединения не закрывались.

## Соответствие текущей реализации

[qualification.json](qualification.json): database.go, запуск persistent API,
auth config, go.mod/go.sum и все8 SQL-миграций побайтово совпадают с rc.6.
Единственная последующая правка server/config.go — дополнительный MetricsAddress
и его валидация; DSN/storage/address/auth-ветви не менялись. Это квалификация
именно переносимости БД, а не PASS всего текущего backend по старому binary.
Пул ограничен max10/min1; connect5с, statement5с, lock3с и idle-in-transaction30с
остались прежними. PostgreSQL-адрес, TLS и CA передаются конфигурацией,
суперпользователь не нужен runtime. Нового backend-кода/SQL-миграции нет.

PG16 остаётся поддерживаемой версией Managed PostgreSQL по
[официальной политике Yandex Cloud](https://yandex.cloud/ru/docs/managed-postgresql/concepts/update-policy),
проверенной03.11. Для используемого набора нет внешних/superuser-расширений.
Реальный managed-кластер не создавался; инфраструктурная миграция сейчас
не выполнялась и не объявляется пройденной.

## Будущий перенос и откат

Сохранён [действующий шаблон](../../../../../infra/host/templates/managed-postgresql-change.md):
репетиция dump/restore и ACL; пауза HTTP-записи/reconcile/worker; финальная копия,
один источник истины; переключение DSN/readiness и один worker. До новых записей
возможен согласованный возврат; после новых записей простой возврат DSN запрещён,
требуется обратный перенос новых данных либо исправление на новой БД. Копия
старого назначения хранится не менее7дней и до проверки нового восстановления.
Это сохранённая будущая процедура, не выполненный переезд.

## Очистка и исходный неудачный запуск

Первый запуск прошёл все7 проверок, но guard очистки ошибочно использовал
obj_description вместо shobj_description для общей pg_database. Он завершился
ошибкой и сохранён как [attempt1](attempt1.txt), не PASS. Его единственная
временная БД затем удалена после отдельной сверки точных owner/nonce:
[cleanup](attempt1-cleanup.json), без FORCE. Исправлена только метапроверка
тестового driver; полный повтор прошёл с автоматическим удалением своей БД.

Оба loopback-прокси и тестовые API завершены, временные TLS-ключи удалены
TemporaryDirectory. Production MainPID/ActiveState до/после совпали.
Не было release/deploy, restart production, Telegram, локальной БД/Docker
или изменений CI. Синтаксис driver, agent:check, OpenSpec strict и diff-check
проверены при фиксации. Для неизменённого продукта общий Go-набор не повторялся.
