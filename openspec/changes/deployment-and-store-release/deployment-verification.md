## Result

**Инфраструктура запущена, пользовательское приложение ещё не выпущено.**
После решения владельца «возьмём поменьше, потом расширим» создана обычная

В поддержку не писали, другие площадки и дополнительные ВМ не заказывали.

## Verified

- Первые 40 ГБ в зоне a отклонены; создавшиеся IP/SG/SA удалены, state сверён.
  По новому решению **20 ГБ в a** также отклонены с ResourceExhausted
  (request ID `dbe56c91-3008-411b-927a-e31f659d6528`), ресурсов не создали.
  **10 ГБ в d** успешно выделены в пределах её квоты, затем применены планы
  ВМ и сервисов без удаления или изменения чужих ресурсов.
- Ubuntu 24.04.5, официальный закреплённый образ; cloud-init завершён.
  PostgreSQL **16.15**: только Unix socket, runtime без superuser, отдельные
  роли миграций и статистики. Runtime peer-запрос выполнен успешно.
- SSH root/password отключены, public-key включён; security group разрешает
  SSH только текущему `/32` владельца. Проверены внешние подключения:
  **5432, 8080, 9108, 16241 недоступны**, HTTP возвращает ожидаемый **503**.
  Caddy admin и метрики слушают localhost. HTTPS ещё не обслуживается.
- Корневая ФС `/dev/vda1`, ext4: 9,1 ГиБ доступного размера, занято примерно
  2,5 ГиБ, свободно 6,6 ГиБ. Текущая конфигурация — подготовка без приложения,
  не замер ресурсов под пользовательской нагрузкой.
- Приватный S3 без anonymous read/list/config и без static-key auth;
  runtime имеет storage.uploader только на этот бакет. Retention `database/`
  7 дней, незавершённые multipart 1 день; локально последняя копия.
- Три контейнера Lockbox с deletion protection и адресным payloadViewer
  созданы; **значения пока не загружены**, получение секретов приложением
  не проверено. Роль записи метрик — monium.metrics.writer на каталог.
- `pg_dump -Fc → age → S3`: зашифрованная копия успешно загружена с IAM metadata,
  без plaintext dump. Ежедневный systemd timer 03:00 UTC + до 10 минут включён.
  Script/unit-файлы и повторяемая настройка сохранены в infra/host.
- **Restore drill механизма копий:** собственная синтетическая строка в отдельной
  тестовой схеме → копия → S3 → скачивание и SHA256 → отдельная чистая БД →
  чтение маркера. Тестовая БД/схема затем удалены, новая чистая копия сделана.
  Последняя зашифрованная копия скачана на компьютер владельца, проверен новый
  `pull-backup.py`. Identity age остаётся вне ВМ, с правами 0600.
  Этот тест **не** подтверждает прикладные сессии/receipts/задачи или RPO/RTO.
- Unified Agent **26.10.50** установлен из официального пакета; закреплённый
  SHA256 повторно проверен при воспроизводимой установке. Метрики раз в 60 с.

## Incident verification

Повторная проверка 24.10.2026: [инцидент 2136](https://status.yandex.cloud/ru/incidents/2136)
остаётся открытым («11 октября — Сейчас»). В браузере последнее сообщение
от 16 октября, 20:19 МСК указывает на ограниченный режим и направляет за
актуальными подробностями к рекомендациям по восстановлению.

[Рекомендации Яндекса](https://yandex.cloud/ru/recommendations), обновлённые
**23 октября 2026, 17:41 МСК**, сообщают о запуске новой площадки под прежним
именем `ru-central1-a`. Доступ открывают поэтапно; создание ресурсов остаётся
ограниченным. Возможность создавать ВМ и диски в принципе восстановлена,
но не означает доступности выделения ресурсов для каждого облака.

Для нашей попытки наиболее вероятная причина — ограничение размещения в ходе
восстановления после инцидента. Это вывод по совокупности официального сообщения,
выбранной зоны и отказа API при одобренной квоте SSD 40 ГБ и активном биллинге.
Точная связь конкретного request ID с инцидентом публично не подтверждена:
ошибка `Resource allocation is restricted` не содержит причины ограничения.
Исключить влияние инцидента или объявить причиной ошибку настройки аккаунта
по имеющимся данным нельзя. Одобрение квоты не подтвердило доступ к мощности.
При проверке инцидента ресурсов и обращений в поддержку не создавали;
позднейшее развёртывание в зоне d описано выше.
