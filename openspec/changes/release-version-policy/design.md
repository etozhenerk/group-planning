# Design

## Context

Мотивация — [proposal.md](proposal.md). Состояние проверено 25.10.2026:

- [docs/releases.md](../../../docs/releases.md) и `scripts/release/common.py`
  уже допускают `component/vX.Y.Z` и `component/vX.Y.Z-rc.N`, проверяют main,
  чистоту checkout, manifest, SHA256 и запрет замены Release. Проверки порядка
  версий и правил bump пока нет.
- После fetch самые новые локальные теги: backend `0.1.0-rc.3`, web `0.1.0-rc.2`,
  monitoring `0.1.0-rc.3`; тегов Android/iOS и окончательных тегов ещё нет.
  Наличие тега не доказывает, что он установлен на production или принят магазином.
- `build.py` знает release metadata, но `package_cloud.build` получает только
  component/output и вызывает обычный `web:build`, без передачи версии.
- В текущем незавершённом `meeting-experience-refresh` Vite читает
  `VITE_APP_VERSION` с fallback в package.json (`0.0.0`), а
  `shared/config/version.ts` сокращает номер до первых двух чисел. В футере
  используется сокращённая версия; справка называет полный SemVer «Сборкой».
  Это наблюдение рабочего дерева другого изменения, не проверка production.
- Пользователь выбрал полную подпись на сайте, включая PATCH и RC.
  [UX v1](ux.md) подготовлен до технического решения и уточняет прежний макет.
- Мобильные сборки уже получают числовую часть SemVer и GITHUB_RUN_NUMBER;
  проект ограничивает build number диапазоном 1–9999. Подписи и store-приёмка
  остаются отдельной незавершённой работой.

## Goals / Non-Goals

**Goals:** понятный выбор номера, короткое утверждение конкретного выпуска,
единое происхождение web-версии от тега до UI, проверяемые кандидат/финал/откат.

**Non-Goals:** общий синхронный номер всего монорепозитория, автоматический
деплой от каждого коммита, новый платный CI/сервис, выпуск текущих изменений,
расширение мобильных экранов и API версии сервера. Схема БД не меняется.

## Decisions

План принят пользователем 25.10.2026. При реализации карточка сохраняется
JSON-аннотацией Git-тега, подготовленной `scripts/release/prepare.py`.
Это связывает её с неизменяемым тегом без дополнительного сервиса; факт
разрешения остаётся в поручении владельца, а не автоматическом поле карточки.

### 1. SemVer и границы совместимости

Сохраняем пять независимых последовательностей и существующий синтаксис тегов.
`v` — часть оформления Git-тега; на сайте его и префикса `web/` нет.
В текущем процессе используем только окончательный выпуск и `-rc.N`;
alpha/beta и `+build` в теги не добавляем. Build number/SHA хранятся отдельно.
Это допустимое подмножество SemVer, совместимое с существующим парсером.

| Изменение | До 1.0.0: пример от 0.2.3 | После 1.0.0: пример от 1.2.3 |
| --- | --- | --- |
| Совместимое исправление, корректировка текста или сборки | 0.2.4 | 1.2.4 |
| Новая совместимая возможность, объявление deprecation | 0.3.0 | 1.3.0 |
| Несовместимое изменение контракта | 0.3.0 + явное предупреждение | 2.0.0 |
| Только документация, без нового артефакта | Выпуск не нужен | Выпуск не нужен |

Значение bump выбирается по наибольшему влиянию всего состава выпуска.
`feat`/`fix`/`BREAKING CHANGE` из Conventional Commits полезны как подсказки,
но пока не вводим автоматическое назначение номера по заголовкам: история
содержит смешанные изменения, а смысл совместимости требует проверки.
Изменения CI, зависимостей и refactor оцениваем по влиянию на поставляемый
артефакт; новый артефакт не может повторно использовать старый номер.

Публичный контракт backend — OpenAPI, auth и поведение, на которое опираются
поддерживаемые клиенты. Для клиентов — документированные сценарии, ссылки,
сохранённые данные и возможности обновления; перестановка UI сама по себе
не требует major. Для monitoring — контракт конфигурации/вызова и метрик.
Это проектное применение SemVer к приложениям, а не обещание, что стандарт
определяет значимость каждой визуальной правки.

Политика `0.x` — наше более строгое соглашение поверх свободной начальной фазы
SemVer. Ноль не освобождает от совместимости с установленными мобильными
версиями. Перед несовместимостью нужны переходный контракт и план поддержки.
`1.0.0` утверждается отдельно для каждого компонента: описан стабильный контракт,
принят целевой объём, пройдены его проверки и приёмка. Публичный домен или первый
RC не являются автоматическим основанием для 1.0.0.

Альтернатива CalVer полезна для календарных циклов, которых у проекта нет.
Общий номер продукта заставлял бы выпускать неизменившиеся приложения;
поэтому сохраняем принятую независимость.

### 2. Как выбираем и утверждаем выпуск

1. Из актуального main определяем компонент и весь diff после его предыдущего
   окончательного релиза. Если окончательного выпуска нет — фиксируем начальный
   объём `0.1.0`; расширение первого MVP допускается до его финальной приёмки.
2. Готовим карточку с точной версией и SHA; проверяем доступность номера,
   результаты CI, совместимость и ограничения. Для RC той же базы увеличиваем N.
3. Владелец принимает карточку либо действует уже выданное поручение с тем же
   составом/SHA. Не добавляем повторный запрос при уже согласованном выпуске.
   Если коммит или состав поменялся, карточка и решение обновляются.
4. Из чистого checkout создаём аннотированный тег на этот SHA; отправляем
   только этот тег. Тег остаётся триггером `Component releases`.
5. Workflow повторно проверяет происхождение, версию и артефакты. GitHub Release
   содержит человекочитаемые изменения и manifest с точным SHA/build number.
6. Деплой на ВМ или отправка в магазин — следующий шаг с проверками среды
   в границах поручения владельца. Номер не считается установленным по одному
   факту появления тега или зелёной сборки.

Карточка (в сообщении/отчёте подготовки, затем её факты входят в release notes):

```text
Компонент: web
Предыдущий окончательный: 0.1.0
Предлагаемый: 0.2.0-rc.1
Commit: <полный SHA из main>
Причина: новая возможность, MINOR
Изменения: <короткий перечень>
Совместимость: <проверенные API/клиенты; необходимость миграций>
Проверки: <конкретные результаты и ссылки>
Ограничения: <непроверенное>
Действие: создать артефакты / также развернуть в указанной среде
Решение владельца: <ссылка или запись уже данного поручения>
```

Смысл изменения и решение владельца проверяются процессом, не выдуманным CI
флагом `approved=true`. Автоматизация проверяет синтаксис, числовой порядок,
занятость номера, commit и согласованность метаданных. Для MVP одна линия на
компонент: версия должна быть выше последнего окончательного выпуска, новый
RC — выше предыдущего RC этой базы; закрытая стабильным тегом база не принимает
новые RC. Существующий тег, даже после неудачи CI, резервирует свой номер.
Preflight **до тега** отклоняет занятый номер. Проверка **в CI** ожидает наличие
своего тега и исключает его из сравнения с предшественниками: иначе она
заблокирует каждый выпуск. Повтор неизменённого тега до создания Release
может повторить неудавшуюся сборку; существующий Release/draft разбирается
по действующей инструкции без перезаписи. Номер уже принятой mobile-сборки
при таком повторе не становится новым. Подготовку выпусков одного компонента
выполняем последовательно; перед публикацией перечитываем состояние origin.

Release notes группируют пользовательские изменения по смыслу (добавлено,
исправлено, изменено/удалено), а не копируют весь git log. Для проверки номера
нужно видеть предыдущий тег и причину bump. Дополнительная база утверждений,
обязательный PR и новый сервис согласований не нужны.

### 3. RC, окончательный выпуск и артефакты

`0.2.0-rc.1 → rc.2 → rc.3 → 0.2.0`. RC — кандидат именно целевой базы;
исправления принятого RC увеличивают N, пока финал не выпущен. После финала
исправление идёт в `0.2.1[-rc.N]`. Если существенно меняется уже согласованный
объём серии, заново утверждаем карточку и при необходимости целевую базу.

У финала другой тег и встроенная версия: текущий pipeline создаёт **новую
финальную сборку** и проверяет её. Не переименовываем RC-архив и не выдаём его
manifest за финальный. При неизменном продуктовом коде теги могут указывать
на один commit, но manifest финала другой; web со встроенным номером также
меняется. Отдельные файлы других компонентов могут совпасть побайтово.
Правило «один артефакт между средами» относится к одному точному тегу.

Для mobile после финальной сборки `X.Y.Z` сначала проверяем именно её
в TestFlight/внутреннем треке, затем продвигаем этот build в магазин.
RC-маркетинговая версия остаётся числовой, стадия хранится в manifest.
Загруженный RC не превращается в новый финальный артефакт переименованием.
Откат установленного mobile обычно требует следующего исправляющего выпуска
и большего build number. Web/backend возвращают предыдущий сохранённый артефакт
при совместимой БД; действие записывается как откат, без повторной публикации тега.

### 4. От тега до номера на сайте

Источник истины — проверенный тег → объект release metadata → web-сборка
и manifest. Версия root/web package.json относится к пакетной обвязке;
автоматически синхронизировать её с пятью тегами не нужно.

В `scripts/release/` передать проверенные metadata из build в web-упаковщик.
Для релизного вызова явно задать доверенные version/tag/commit/build number;
не принимать унаследованный `VITE_APP_VERSION` как альтернативный источник.
Vite различает release-контекст, dev и demo. Обычный локальный запуск остаётся
доступен без тега; release-контекст с отсутствующими полями завершается ошибкой.

Из одного проверенного набора сгенерировать встроенные константы клиента
и `dist/build-info.json` с полями schema_version, component, version, tag,
commit, build_number. JSON находится **внутри** `web.tar.gz`; внешний набор
архив/manifest/SHA256SUMS сохраняется. В metadata только публичные идентификаторы,
никаких env dump, токенов, путей к ключам или контактов владельца.
Перед публикацией сверить внутренний JSON с manifest; проверить реальную
отрисовку константы из собранного клиента, а не только JSON-файл рядом с ним.

UI читает встроенные данные синхронно через `shared/config`; футер и справка
используют одну подпись. Никакого runtime-запроса `/version`, GitHub latest или
версии API. Поэтому старое открытое окно честно показывает свою старую сборку,
а откат не требует правки текста. После обновления страницы проверяем свежий
HTML и согласованные hash-assets; настройка cache HTML проверяется на реальном
деплое, не обещаем мгновенное обновление всех открытых вкладок.

Существующие FSD widgets/pages сохраняются; преобразования и проверка metadata
не помещаются внутрь TSX компонента. Конкретные тексты и эскизы — [ux.md](ux.md).
Новый API, таблицы и серверная бизнес-логика неприменимы.

### 5. Мобильная и инфраструктурная нумерация

Сохраняем versionName / CFBundleShortVersionString = числовая база тега,
versionCode / CFBundleVersion = существующий номер запуска workflow.
Номера между Android и iOS не обязаны совпадать; пропуски нормальны.
Действующий диапазон 1–9999 — ограничение нашей обвязки, не общий лимит Android.
Перед upload сверяем номер с уже принятыми магазином сборками. Rerun сохраняет
GITHUB_RUN_NUMBER: если этот build принят, создаём новый RC/релизный запуск.
При замене workflow или исчерпании диапазона сначала мигрируем счётчик,
не сбрасываем его. Переход на иной алгоритм в этот план не входит.

Backend/monitoring получают ту же политику выбора номера и остаются независимы;
публичную страницу со всеми версиями инфраструктуры не добавляем. Terraform,
host-конфиги, SQL migration ID и OpenAPI document version не равны версии сайта.

## Risks / Trade-offs

- Параллельная реализация футера → при apply сверить актуальные файлы и UX
  `meeting-experience-refresh`, заменить только источник/формат номера.
- Две независимые версии могут быть несовместимы → в карточке перечислять
  проверенные сочетания, соблюдать контракт старых native-клиентов.
- Релизный тест demo не доказывает правильность production bundle → отдельно
  тестировать распакованный web-артефакт с известным полным RC и manifest.
- Номер в UI расходится с JSON → оба получаются из одного источника, плюс
  браузерная проверка собранного UI; hashes сами по себе этого не доказывают.
- RC на production выглядит как окончательная версия → суффикс сохраняется
  полностью; стадия не определяется по домену.
- Автоматический bump по типу коммита ошибается → рекомендация по commits,
  итоговое решение по всему составу и совместимости.

## Migration Plan

1. Рассмотреть политику. Полный формат на сайте уже выбран; не считать сам
   этот план поручением создать очередные теги.
2. При apply синхронизировать `docs/releases.md` и уточнение формата в UX/specs
   `meeting-experience-refresh`; дополнить `component-releases` ссылкой на правила.
3. Внедрить preflight порядка версий, передачу web metadata, сверку архива и UI.
   Не менять существующие теги/артефакты; исключение для старых архивов остаётся
   только на пути отката, новый release обязан содержать build-info.
4. Проверить тестовые метаданные 0.1.0-rc.3, 0.1.0 и ошибочные варианты локально,
   не создавая production-тегов для тестов.
5. Когда будет поручение на выпуск, заново получить origin-теги и зафиксировать
   SHA/состав. Если web rc.2 всё ещё последний кандидат базы 0.1.0, свободный
   следующий номер — rc.3; это пример, а не резервирование или утверждение выпуска.
6. Развернуть проверенный web-артефакт, сверить manifest ↔ build-info ↔ UI
   на smwhere.ru. Backend при этом не получает новый релиз. Проверить откат
   в тестовой среде, не откатывать рабочий сайт ради демонстрации.

## Sources

Проверены 25.10.2026; правила 0.x и процесс утверждения — соглашения проекта:

- [SemVer 2.0.0](https://semver.org/): структура, совместимость, начальная фаза,
  приоритет RC и неизменяемость опубликованной версии.
- [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):
  смысл feat/fix/BREAKING CHANGE, не замена оценки состава.
- [Keep a Changelog](https://keepachangelog.com/en/1.1.0/): человекочитаемые заметки о выпуске.
- [Android versioning](https://developer.android.com/studio/publish/versioning):
  различие versionName и versionCode, защита от понижения.
- [Apple version number](https://developer.apple.com/help/glossary/version-number/)
  и [CFBundleVersion](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion):
  пользовательская числовая версия и отдельный номер сборки.
