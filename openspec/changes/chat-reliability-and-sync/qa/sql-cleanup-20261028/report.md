# Удаление большой SQL-истории, 28.10.2026

Исполнительский результат: исправлен `QA-SQL-CLEANUP-100K-001`;
независимая приёмка нового кандидата остаётся отдельным этапом. Production,
схема, timeout и глобальная блокировка записи не менялись. Коммита и деплоя
этой работой не выполнялось.

## Причина

В историческом PostgreSQL-журнале за исходный failed run найдена ошибка
`statement_timeout` в 22:34:54.371 UTC, PID 53746, для `somewhere_integration`.
Контекст ошибки — внутренний `DELETE FROM ONLY message_reactions` по `entry_id`:
построчный FK CASCADE при удалении большой ленты. Числовой SQLSTATE исходный
журнал не сохранил; конкретная причина timeout и таблица подтверждены журналом.
[Обезличенная выборка](old-db-log.json) содержит только классификацию и
разрешённые имена таблиц, без SQL-параметров, DSN и пользовательского содержимого.

Два новых диагностических прогона исходного кода прошли, поэтому прежнее
падение не переименовано в pass. Test-only pgx tracer измерил один
`DELETE 100000`: 3 609 мс в изолированном прогоне и 1 656 мс после полного
исходного набора при штатном statement timeout 5 000 мс. `request_receipts`
удалялся за 0,533–0,535 мс. Массовое удаление одним statement оставляло
зависимость от доступной производительности ВМ; увеличение timeout не требуется.

## Изменение

`DeleteMeeting` удаляет feed keyset-порциями до 1 000 строк. Границы выбираются
существующим индексом `(meeting_id, sequence)`; выборка не читает JSON истории.
Все порции и прочие зависимые данные остаются в той же транзакции и под прежним
write lock. Ошибка/отмена откатывает всю операцию. Пропуски sequence и максимальный
uint64 не требуют арифметического увеличения позиции. FK CASCADE и индекс реакций
сохранены; миграции не добавлялись.

Также уточнено описание memory.Store: View читает опубликованный неизменяемый
snapshot, Update копирует его перед записью, Reader возвращает отделённые данные.
