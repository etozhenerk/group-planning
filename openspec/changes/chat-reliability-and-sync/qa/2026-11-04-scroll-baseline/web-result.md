# Web baseline10k · 04.11.2026

Новый opt-in `playwright.baseline.config.ts`, не повтор прежних39/40/42 suites.
На каждой платформе отдельный локальный Go memory/HTTPS API: 10000 сообщений
с1…32 повторениями строки и10 реальных длинных карточек задач. HTTP браузера
задержан75мс до и после ответа. Полный проход страниц tail→oldest→tail,
сохраняется500 серверных записей; видимых DOM-строк в checkpoint максимум27.
Это scripted edge scroll с активацией штатных границ истории, не запись touch-жестов.

Chromium156.0.8078.4: PASS2.8мин; rAF p95≈16.70мс/p99≈16.80мс.
Mobile WebKit: PASS2.9мин; rAF p95=22мс/p99=32мс — хуже цели16.7мс;
это записанное ограничение, не performance PASS. Исходные значения, версии, viewport,
сырые интервалы и23 memory-checkpoint сохранены в baseline.json каждого клиента.
Hash в dataset относится к шаблону содержимого seed по номеру, не к случайным
серверным UUID или порядку завершения параллельных POST внутри пакета из10.

Ограничения измерения: requestAnimationFrame — JS heartbeat, не GPU presented
frames; поэтому целевой frame-budget7.9 этим не объявляется выполненным.
RSS — сумма потомков собственного QA browser worker, без worker/probe;
shared pages могут считаться повторно. На macOS WebKit часть XPC-процессов не
является такими потомками: этот показатель не выдаётся за полную память WebContent
или за сопоставимый с Chromium physical footprint. Chrome после прогрева
держит плато примерно730–750MiB на этой машине, без линейного роста на10k;
это весь отслеженный browser process tree, не JS live heap.
