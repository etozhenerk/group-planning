# Шифрование и границы защиты

Пользователь попросил сравнить варианты и предложить решение. Рекомендация
ниже не означает согласия пользователя на отказ от E2EE. Сейчас только
планирование: текущий код хранит доступный серверу текст, наличие шифрования
дисков и резервных копий этим исследованием не подтверждено.

## Сравнение

| Свойство | TLS/WSS + защищённое серверное хранение | Сквозное шифрование, E2EE |
| --- | --- | --- |
| Кто читает сообщения | Участники и сервер с доступом к данным/ключам | Устройства участников с ключами; сервер хранит шифротекст |
| Перехват сети | TLS защищает канал; обязательная проверка сертификата | TLS также нужен, содержимое дополнительно зашифровано на устройстве |
| Украденный диск/backup | Защита зависит от реально настроенного шифрования и отдельного управления ключами | Текст скрыт без ключей устройств/восстановления; метаданные могут остаться видимыми |
| Компрометация работающего сервера | Сервер способен раскрыть текст | Защищает содержимое при корректном протоколе, проверке устройств и доверенном клиенте; сервер может мешать доставке и видеть метаданные |
| Новое устройство | История доступна после входа и проверки прав | Нужны передача ключей, подтверждение устройством или защищённая резервная копия |
| Потеря устройств | Вход восстанавливает доступ к серверной истории | Без recovery-ключа/доверенного устройства история может быть утрачена |
| Исключение участника | Сервер прекращает выдачу данных | Дополнительно меняется доступ к будущим ключам; уже прочитанное удалить у получателя невозможно |
| Поиск, обработка, жалобы | Сервер может обрабатывать текст при наличии продуктового основания | Поиск обычно на клиенте; серверная обработка требует отдельного раскрытия содержимого |
| Цена для somewhere | Проверка инфраструктуры, доступа, журналов и локального outbox | Жизненный цикл устройств, ключей, восстановления, членства и миграция всех клиентов |

Шифрование диска защищает выключенный носитель, а не запрос легитимного
процесса к открытой БД. Envelope encryption с отдельными ключами также не
становится E2EE, если приложение сервера может запросить расшифровку.
Метаданные встречи, участников, времени и размеров сообщений требуют своей
модели защиты при любом варианте.

## Рекомендация для текущего этапа

Выбрать защищённый серверный чат: HTTPS/WSS, права на каждый запрос,
ограниченный доступ к БД, исключение текста/токенов из логов и подтверждённая
защита дисков/backup. Это сохраняет единый источник правил встреч и позволяет
закрыть наблюдаемые задержки, исходящие и прокрутку без переноса продукта.
Не писать в UI «сквозное шифрование» и не ставить соответствующий значок.

Проверка хранения — входной критерий заявления о его защите: фактическая
конфигурация, разделение доступа к ключам и backup, ротация, восстановление
и срок удаления копий. Если эксплуатация уже закрыла эти пункты, достаточно
ссылок на проверенные свидетельства; не создавать дублирующую инфраструктуру.
До такой проверки статус — «не подтверждено», а не «зашифровано по умолчанию».

Это рекомендуемая ветка плана. Если до реализации выбираем обязательное
E2EE, сначала пересматриваем design/specs: подмена криптомодели после готовых
клиентов и накопления открытой истории будет существенно дороже.

## Если E2EE обязательно

Кандидат — Matrix с поддерживаемыми SDK, а не собственная реализация ratchet.
[Документация Matrix](https://matrix.org/docs/matrix-concepts/end-to-end-encryption/)
описывает ключи устройств, их проверку и передачу ключей для расшифровки.
[Matrix Rust SDK](https://github.com/matrix-org/matrix-rust-sdk) используется
в Element X на iOS/Android и предоставляет нативные bindings; web имеет
свой SDK из [официального каталога](https://www.matrix.org/ecosystem/sdks/).
Это база для отдельного прототипа, не доказательство совместимости с нашим UI.

До выбора необходимо проверить:

- вход через существующий Яндекс-аккаунт, привязку устройств и выход со всех;
- создание комнаты и атомарное согласование доступа с RSVP somewhere;
- общую хронологию сообщений, карточек, системных событий и скрытых голосов;
- приглашение нового участника: доступ к прошлой истории и ключам;
- проверку нового устройства, восстановление, потерю всех устройств;
- смену членства, удаление аккаунта, остатки данных в backup и на чужих устройствах;
- migration старой открытой истории, клиентские версии, эксплуатацию и стоимость.

Полноценный E2EE чат не получается подключением одной crypto-функции.
[Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)
и [Sesame](https://signal.org/docs/specifications/sesame/) решают разные
части шифрования и асинхронных сессий нескольких устройств.
[libsignal](https://github.com/signalapp/libsignal) прямо предупреждает,
что использование вне Signal не поддерживается; наличие TypeScript bindings
не доказывает пригодности для браузера. Для этого проекта он не выбран.

## Обязательные границы независимо от варианта

- WebSocket принимает только разрешённый Origin и действующую сессию;
  нативный клиент проходит аутентификацию без токена в URL.
- Встреча доступна только по актуальным правам. При утрате доступа поток
  закрывается, незавершённые ответы старой сессии отбрасываются.
- Публичный push содержит только сигнал об изменении; приватные payload
  HTTP выдаёт заново после проверки доступа. Скрытые голоса не попадают в push.
- Локальные draft/outbox изолированы по аккаунту; logout/удаление аккаунта
  очищают их. При утрате доступа к встрече очищается её приватное состояние.
- Web IndexedDB не защищает от XSS/пользователя того же профиля браузера.
  Native storage использует защиту ОС и отдельные ключи в системном хранилище.
- Нельзя обещать уничтожение уже полученного текста на чужом устройстве
  или отсутствие метаданных у сервера.
- Read receipt означает продвижение видимой позиции по правилам клиента,
  а не доказательство, что человек понял текст. Отправитель видит только
  текущих участников; удалённые аккаунты в списке не раскрываются.

Сценарии проверки закреплены в [chat-security/spec.md](specs/chat-security/spec.md).
