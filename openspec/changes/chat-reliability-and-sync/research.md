# Исследование реализации чата

Проверено 25.10.2026. Задача — уменьшить задержки и исправить состояние,
прокрутку, дозагрузку и прочитанность во всех клиентах somewhere.
Это исследование и предложение, не отчёт об установленном стеке.
Аудит репозитория — [current-state.md](current-state.md).

Это разные масштабы и исторические версии систем. Приведённые ниже решения —
наш вывод с учётом кода somewhere, а не утверждение, что такая архитектура
целиком используется в перечисленных продуктах.

## Выбор транспорта и готового решения

| Вариант | Что получаем | Что остаётся нашим | Решение |
| --- | --- | --- | --- |
| Текущий polling | Простой HTTP, совместимость | Задержка интервала, фоновые запросы, всё восстановление | Только прежние клиенты и ограниченный запасной режим |
| SSE + HTTP | Односторонний поток; браузерный EventSource поддерживает reconnect и Last-Event-ID | Протокол восстановления, нативные адаптеры, доступ, outbox | Рабочий вариант для чата, но здесь больше собственного кода на трёх клиентах |
| Обычный WebSocket + HTTP | Поддержка браузером и нативными сетевыми библиотеками | Heartbeat, reconnect, подписки, recovery, backpressure, совместимость протокола | Слишком много вспомогательного кода для этой доработки |
| **Centrifuge внутри Go + официальные SDK** | Готовый протокол, жизненный цикл соединений, подписки, краткое recovery | Постоянная история, бизнес-права, read state, outbox и UI | **Рекомендуется для текущего этапа** |
| Отдельный Centrifugo | Самостоятельный сервер транспорта и его конфигурация | Те же прикладные гарантии плюс эксплуатация сервиса | Отложить до обоснованной необходимости нескольких API-узлов |
| Matrix + готовые SDK | Чат-протокол, синхронизация, устройства, инструменты E2EE | Связь с Яндексом, RSVP, общей лентой, миграция, UX и эксплуатация homeserver | Сильный кандидат, если E2EE становится обязательным требованием сейчас |

Источники сравнения: [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html),
[Centrifuge](https://github.com/centrifugal/centrifuge),
[транспорты](https://centrifugal.dev/docs/transports/overview),
[официальные SDK](https://centrifugal.dev/docs/transports/client_sdk),
[Matrix SDK](https://www.matrix.org/ecosystem/sdks/).

Centrifuge — библиотека Go, Centrifugo — отдельное приложение. Начинаем
с библиотеки и MemoryBroker в одном API-процессе, без Redis/Kafka. Это не
новый источник истины: серверный журнал PostgreSQL обеспечивает восстановление.
У библиотеки пока нет стабильного v1; версии Go и всех SDK нужно проверить
совместно и закрепить. Зависимость прячется за адаптерами приложения.

## Что взять из готовых реализаций

| Задача | Опора | Применение |
| --- | --- | --- |
| Пропуск/повтор события | [Telegram updates](https://core.telegram.org/api/updates): порядок и восстановление разрывов | Отдельный подтверждённый курсор. Максимальный номер в UI не доказывает, что всё до него получено. |
| Переподключение | [Centrifugo history/recovery](https://centrifugal.dev/docs/server/history_and_recovery): offset/epoch и ограниченная история | Быстрое recovery — оптимизация; неудача всегда ведёт к HTTP-синхронизации с БД. |
| Повтор отправки и read state | [Matrix Client-Server API](https://spec.matrix.org/latest/client-server-api/): transaction IDs, receipts, private receipts | Стабильный ID намерения; различать личную позицию и публичное подтверждение прочтения. Наше поведение описано отдельно в specs. |
| Сохранённая очередь | [Android offline-first](https://developer.android.com/topic/architecture/data-layer/offline-first) | UI читает локальную модель; намерение сохраняется до сети. Это не обещание полного offline всей системы. |
| Прокрутка web | [React Virtuoso API](https://virtuoso.dev/react-virtuoso/api-reference/virtuoso/) и [исходники](https://github.com/petyosi/react-virtuoso) | Проверить prepend, динамическую высоту, следование за хвостом и сохранение строки на наших карточках. |
| Разбудить обработчик после commit | [PostgreSQL NOTIFY](https://www.postgresql.org/docs/16/sql-notify.html) | Сигнал не заменяет журнал: после сбоя обработчик читает сохранённые недоставленные события. |

На web кандидат — бесплатный MIT-пакет `react-virtuoso`.
Коммерческий `@virtuoso.dev/message-list` — другой продукт с
[отдельной лицензией](https://virtuoso.dev/message-list/licensing/); он в план
не включён. iOS и Android сохраняют нативные lazy-списки, пока измерения
не покажут необходимость другого контейнера. Общего UI SDK для всех платформ
не вводим: он не заменит наши карточки опросов/задач и правила FSD.

## Итоговая рекомендация

1. Сначала устранить разрыв между курсором приёма и отображаемыми сообщениями,
   полное чтение SQL-истории и потерю исходящих при закрытии приложения.
2. Подключить готовый realtime-протокол, сохранив HTTP-команды и права сервера.
3. Добавить серверную прочитанность и списки прочитавших, подтверждённые пользователем.
4. Ограничить окно данных и рендер; проверить якорь, клавиатуру и загрузку
   в каждом клиенте на настоящих карточках.
5. Отдельно проверить защиту хранения. Сравнение с E2EE и рекомендация —
   [security.md](security.md); ни WebSocket, ни Centrifuge не делают чат E2EE.

Приёмочные бюджеты и эксперименты — [validation-plan.md](validation-plan.md).
Данных о production p95 и результатах нового SDK пока нет: их нельзя
подменить опытом Slack, VK или рекламным benchmark библиотеки.
