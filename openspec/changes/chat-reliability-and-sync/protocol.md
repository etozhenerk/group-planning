# Контракт синхронизации: реализация v1

Это контракт разрешённого 27.10.2026 расширения `/api/v1`, не утверждение
о доступности новых endpoints. Порядок внедрения и проверки — [testing.md](testing.md).
Существующие GET feed и POST messages сохраняют контракт. Поля sequence,
revision и счётчиков версий — decimal strings, не JavaScript Number.
Курсоры opaque, versioned, связаны с пользователем/встречей и проверяются
сервером; получение cursor не заменяет проверку прав.

## Три независимые позиции

| Позиция | Значение | Кто продвигает |
| --- | --- | --- |
| `feed_sequence` | Порядок записей ленты встречи | Сервер при создании записи |
| `change_cursor` | Подтверждённый диапазон журнала всех изменений встречи, включая изменение старой карточки | Клиент только по успешно применённому ответу sync |
| `read_through_sequence` | Общая фактическая позиция чтения пользователя | Сервер через max допустимых обновлений видимости |

`unread_baseline_sequence` отдельно от read-through: подавляет старую историю
при первом включении/вступлении, но не создаёт публичный receipt.
Для unread используется max(baseline, read-through), для списка прочитавших —
только фактический read-through. History cursor и смещение экрана тоже отдельны.
Получение POST ACK, `latest_sequence`, push-hint или старой страницы ни один
курсор приёма не продвигает. `offset/epoch` SDK — четвёртая, транспортная
позиция; она никогда не записывается как change_cursor.

## HTTP

| Операция | Запрос | Ответ и правила |
| --- | --- | --- |
| Возможности сервера | `GET /chat-capabilities` после проверки сессии | Версия sync-протокола и флаги sync/read-state/realtime. Старый сервер с 404 или отключённый флаг оставляет клиента на совместимом HTTP пути; отсутствующий read-state скрывает read UI. |
| Начальное окно | `GET /meetings/{id}/sync?limit=50`, опционально `around_entry_id` | Согласованный снимок: entries, актуальные metadata/my read state, `change_cursor`, `stream_epoch`, диапазон, `has_older/has_newer`, first_unread. По умолчанию вокруг первого непрочитанного, иначе хвост. |
| Изменения | `GET /meetings/{id}/sync?cursor=...&limit=100` | Ограниченные изменения/актуальные проекции, `next_cursor`, `has_more`, фиксированный `through_cursor`. Следующие страницы продолжают до этого барьера; новые события — следующим циклом. |
| История | Прежний `GET /meetings/{id}/feed?before=...` или `after=...`, новое `around_entry_id` взаимоисключающе | SQL-страница, limit 1–100, без обновления change_cursor. around возвращает диапазон и оба направления; неподдерживаемые параметры старого клиента не меняются. |
| Отправка | Прежний `POST /meetings/{id}/messages`, прежние body и Idempotency-Key | ACK после commit, canonical entry и ID исходящего. Повтор той же операции — прежняя запись, конфликт другого тела — прежняя семантика ошибки. |
| Чтение | `PUT /meetings/{id}/read-marker` с `read_through_sequence` | Проверка существующей доступной позиции, monotonic max; возвращает фактический marker и unread. Повтор безопасен без нового ID. |
| Кто прочитал | `GET /meetings/{id}/messages/{entry_id}/readers?cursor=...&limit=50` | Только автор подтверждённого сообщения; текущие участники, ID/имя/аватар, без контактов. Keyset-страницы и счётчик для текущего снимка; изменения состава требуют refresh. |
| Счётчики своих видимых сообщений | `POST /meetings/{id}/read-receipts/query` с максимум 100 entry IDs | Только собственные сообщения; агрегаты reader_count. Чужие ID отклоняются. Ограниченный batch вместо запроса на каждую строку. |
| Список встреч | Существующий GET списка с добавленными необязательными unread_count/first_unread | Старые клиенты игнорируют новые поля; доступа к чужой персональной позиции нет. |

Initial snapshot read-only repeatable-read фиксирует окно и change high-water
в одной транзакции. around берёт ограниченное число записей до/после якоря,
а не загружает все промежуточные сообщения. Поведение entry исчез/нет доступа:
404/403 по существующей политике сокрытия; клиент пробует разрешённую базовую
позицию только после проверки доступа.

Changes — `{kind, entry_id?, projection_version?, ...}`: `entry_upsert`,
`entry_removed`, `meeting_changed`, `receipts_changed`, `history_invalidated`.
Upsert содержит текущую разрешённую проекцию, а не неизменяемый приватный
payload из журнала. Применение idempotent; более старая projection_version
не перезаписывает новую. Invalidation сбрасывает затронутые старые диапазоны
и перечитывает видимое окно, например после обезличивания аккаунта.

`410 sync_reset_required` возвращается при истёкшем/чужом epoch или обрезанном
журнале; клиент получает новый снимок, повторно валидирует загруженное окно,
сохраняет допустимый outbox и якорь. Некорректный cursor — 400; 401/403/404
не превращаются в бесконечный retry. Все ошибки сохраняют общий envelope
с request_id. Значения скрытых голосов проходят существующие правила проекции.

Новые POST/PUT сохраняют действующую защиту HTTP-команд от CSRF и ограничения
частоты; доступ к WebSocket не заменяет защиту cookie-аутентифицированных команд.

## Поток и восстановление

`/api/v1/realtime` — endpoint Centrifuge. Web передаёт существующую HttpOnly
cookie и проходит exact Origin allowlist; native — Bearer в разрешённых
SDK connect credentials/заголовках, без URL query и логирования содержимого.
Верификация идёт существующим session service, не доверяет user_id клиента.
Окончательный механизм native header/connect data проверяется SDK spike.

Подписки: личный канал, выведенный сервером из сессии, и одна открытая встреча.
Канал встречи содержит только hint `{schema_version, meeting_id, stream_epoch,
latest_change_sequence}`. Личный канал сообщает invalidation списка/unread
и отзыва доступа, без тела сообщений и имён. Его после reconnect всегда
сверяем с текущим списком/сессией; он не является постоянной историей.

Последовательность подключения:

1. Проверить сессию и получить начальный HTTP snapshot.
2. Подписаться; после подтверждения подписки обязательно выполнить sync
   от snapshot cursor, даже если ни одного hint не пришло.
3. Применять страницы до зафиксированного through_cursor. Только после
   применения страницы сохранять next_cursor; merge и cursor атомарны в client store.
4. Hint ставит флаг необходимости следующего sync; coalesce до 100 мс,
   один активный запрос на встречу. Повтор/старый hint безопасен.
5. Reconnect всегда вызывает HTTP catch-up. Если SDK восстановил поток,
   это ускоряет обнаружение, но не отменяет сверку постоянной истории.
6. Background приостанавливает поток/опрос/авторетраи и не подтверждает чтение.
   Foreground повторяет проверку и catch-up, затем продолжает очередь.

Backoff reconnect берётся из SDK с jitter. После 10 с устойчивого отказа
realtime, если HTTP работает, fallback опрашивает sync 3→6→12→30 с с jitter;
один владелец и один таймер. Успешная подписка + catch-up выключают polling.
При доступном realtime нет постоянного GET feed. Нет отдельного опроса
каждой карточки встречи. Старая сборка продолжает прежний polling.

Сервер ограничивает число соединений/подписок и размер очереди отправки,
отключает медленного потребителя с восстановимым результатом. Отзыв RSVP
и сессии закрывает соответствующую подписку/соединение после commit;
expiry соединения привязан к сроку сессии, повторная проверка не реже минуты.
Даже запоздавший hint не даёт права получить HTTP payload. Каждый клиент
проверяет generation аккаунта/доступа прежде чем применять любой callback.

## Постоянные данные и атомарность

Предлагаемые таблицы/порты (имена уточняются миграцией, смысл закреплён):

- `meeting_streams`: meeting_id, epoch, latest_change_sequence; epoch устойчив
  при обычном рестарте, меняется при несовместимом сбросе/восстановлении данных.
- `meeting_changes`: `(meeting_id, change_sequence)`, kind, entry_id/version,
  created_at; без копий текста. Журнал покрывает создание и изменение записей.
- `realtime_outbox`: устойчивый event_id, целевой канал/ID, версия hint,
  retry/dispatch state; без текста/токенов. Один event может объединять несколько
  изменений. Запись создаётся в той же транзакции, что предметное изменение.
- `meeting_read_markers`: `(meeting_id, user_id)`, unread_baseline_sequence,
  read_through_sequence, updated_at. Read-through начинается с 0.

После commit dispatcher публикует hint и отмечает dispatch. Crash до отметки
даёт повтор; crash до публикации оставляет запись для следующего запуска.
Публикация не доказывает получение клиентом. MemoryBroker хранит только
краткое recovery; PostgreSQL остаётся источником восстановления.
Периодический drain outbox обязателен, NOTIFY — необязательное ускорение.
Для memory.Store те же транзакционные порты и mock dispatcher, данные
сбрасываются при перезапуске как сейчас. Локальную БД не поднимаем.

SQL Reader добавляет bounded `FeedPage`/`FeedAround`, lookup text intent
по существующему уникальному `(meeting, actor, client_request_id)` и lookup
по сохранённому `entry_id` для media publish retry. Оба повтора сохраняют
проверку текущего доступа, автора, встречи и прежнего содержимого после expiry
receipt; media hydration возвращает только разрешённое подтверждённое вложение.
Memory реализует те же границы с независимыми копиями и rollback. Полный
`Feed()` остаётся у не перенесённых потребителей и не вызывается ради страницы
или адресного повтора. `initial/before` выбирают ближайшие записи DESC и возвращают
ASC; `after` выбирает ASC. Tail и page принадлежат одному read-only снимку.
Индексы `(meeting_id, sequence)`, `(meeting_id, change_sequence)` и подходящие
индексы markers подтверждаются EXPLAIN. `LIMIT + 1` определяет продолжение.
Нельзя заменить полный SELECT скрытой полной десериализацией в другом слое.
Общий write-lock пока сохраняется: менять его только после замера и отдельной
проверки атомарности account removal, RSVP, опросов и worker.

Журнал хранится 7 суток; начальные лимиты — 100 000 изменений на встречу,
короткое SDK recovery — 120 с/1000 hints. Это конфигурация для пилотного теста,
не измеренный оптимум. Обрезка любого предела делает старый cursor явно
непригодным. Недоставленный outbox не удаляется с журналом молча: возраст
контролируется, а истёкший диапазон заменяется текущим invalidation hint.

Удаление аккаунта очищает его markers/outbox-получателей; обезличивание
истории создаёт history_invalidated в той же транзакции. Журнал содержит
ссылки, поэтому повтор не возвращает прежнее имя. Полное удаление встречи
удаляет её историю/markers/stream; личные invalidation текущим клиентам
публикуются из отдельного outbox без FK cascade на удалённую встречу.

## Read state и исходящие

### Wire-формат read state v1

Флаг `SOMEWHERE_CHAT_READ_STATE=false` по умолчанию. `read_state=true` требует
настроенной sync-подписи и завершённой атомарной активации до приёма HTTP.
Аддитивная миграция создаёт таблицы/индексы; baseline заполняется при активации
флага, а не заранее во время DDL. Для текущего организатора и участников «Приду»
сохраняется baseline=tail, actual=0, только если строки ещё нет. Создание встречи
и первое вступление задают baseline в той же транзакции; повторное включение
флага и повторное вступление не сбрасывают прежнюю позицию.

При включённом флаге snapshot и changes передают персональные поля:

```json
{
  "my_read_state": "150",
  "unread_baseline_sequence": "100",
  "unread_count": "3",
  "first_unread": "6ba2aca3-a232-4ad5-9934-9118c64c0edd"
}
```

`my_read_state` — фактический decimal marker, `first_unread` — UUID записи,
не sequence; при отсутствии непрочитанных — `null`. При выключенном флаге
новые необязательные поля могут отсутствовать, прежние null остаются допустимы.
Считаются только чужие сообщения после max(baseline, actual); системные события,
карточки и реакции не увеличивают число непрочитанных.

`PUT read-marker` принимает `{ "read_through_sequence": "150" }` и возвращает
`read_through_sequence`, `unread_baseline_sequence`, `unread_count`, `first_unread`,
`projection_version`. Все числовые значения — decimal strings. No-op marker
не меняет updated_at и не создаёт journal/outbox запись.

`POST read-receipts/query` принимает `{ "entry_ids": ["<uuid>"] }`, максимум100,
и возвращает `{ "receipts": [{ "entry_id": "<uuid>", "reader_count": "2" }],
"projection_version": "151" }`. Это собственные подтверждённые сообщения автора.
`GET messages/{entry_id}/readers` возвращает `readers` с `id`, `display_name`,
`avatar_url`, а также decimal `reader_count`, opaque/null `next_cursor` и decimal
`projection_version`. Только текущие организатор/«Приду» с достаточным actual
попадают в список; автор и удалённые аккаунты исключены. Персональные markers
других людей, контакты и время чтения не выдаются.


Read-through объединяется max; запись отправляется не чаще раза в секунду
и best-effort при уходе. Локально желаемая позиция изолирована аккаунтом,
после ошибки/401 не продвигает серверный счётчик. Первое вступление и база
фиксируются атомарно с RSVP; повторное вступление использует прежние значения.
Миграция существующих участников фиксирует хвосты без потери конкурентных
новых сообщений. Без отдельного фактического marker база не создаёт receipts.

Reader_count = число текущих участников кроме автора с actual read-through
не ниже sequence сообщения. Агрегаты для видимого окна пересчитываются batch
после `receipts_changed`, RSVP и удаления аккаунта. No-op marker не пишет
новое событие, чтобы не создавать цикл синхронизации.

Очередь: `queued → sending → accepted`, либо `uncertain → reconcile/retry`,
либо `rejected`. Сохранение intent предшествует очистке редактора. На встречу
один POST в работе, последующие намерения ждут; неопределённый первый результат
сначала сверяется повтором того же ID. Окончательно отклонённое не блокирует
остальную очередь. Серверный порядок является окончательным, ID повторов
никогда не меняется. ACK сверяет автора, встречу, ID и содержимое.

Стабильный ключ UI своих сообщений — `(actor_id, client_request_id)`, чужих —
server entry_id. Подтверждение меняет поля той же строки. Черновик, очередь,
display entries, receive cursor, read marker и viewport anchor — отдельные
состояния одного владельца, не побочные эффекты React/SwiftUI recomposition.
