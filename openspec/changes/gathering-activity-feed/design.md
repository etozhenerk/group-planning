# Design

## Context

19 октября 2026 года. В репозитории есть инструкции, семь delta specs и
одобренные [макеты v0.7](ux.md), Go-модуль и HTTP-сервер с анонимным preview.
Серверный identity и операции встреч проверены через HTTP с fake-provider.
Первый веб-срез проверяется Chromium с настоящим Go API; реальный Яндекс ID
и мобильные клиенты ещё не проверены, БД отложена.
Мотивация и полный состав MVP — в [proposal.md](proposal.md). Архитектура
клиентских интерфейсов принята в [ADR 0002](../../../docs/architecture/0002-client-ui.md).

Обновление 20 октября 2026 года: по решению пользователя создание БД отложено.
Первый этап использует mock-хранилище в памяти Go-процесса; API и авторизация
развиваются отдельными задачами. Go/web toolchain уже закреплён;
мобильные библиотеки ниже остаются предложением.
Пользователь согласовал порядок: **назначенная дата →
создание → приглашение → ответ → чат** на общем бэкенде и трёх клиентах.
Календарь, опрос даты, смена места и задачи остаются последующими этапами MVP.

## Goals / Non-Goals

**Goals:**

- Получить первый сквозной сценарий с реальными аккаунтами и данными.
- Использовать один контракт операций для web, iOS и Android; авторитетные
  права и бизнес-правила проверяет Go-сервер.
- Сохранять изменения встречи и записи истории атомарно, выдерживать повтор
  запроса после потери ответа и конкурентные действия участников.
- Реализовать одобренный UX средствами клиентов с общими смысловыми токенами.

**Non-Goals:**

- Текущий этап реализует сервер и первый веб-сценарий; реальный Яндекс OAuth
  и мобильные сценарии ещё требуют отдельной проверки.
- Первый срез не является выпуском всего MVP. Его приёмка не закрывает требования
  календаря, опросов и задач и не позволяет архивировать всё изменение.
- Поездки, платежи, AI-функции, уведомления ОС и автономная работа без сети
  не добавляются этим техническим решением.

## Decisions

### 1. Один Go-процесс и временное хранение в памяти

Архитектурная основа — [ADR 0003](../../../docs/architecture/0003-modular-monolith.md):
модульный монолит, явное владение данными и прикладные контракты между областями.
Сборка прикладных сервисов находится в `internal/server`; HTTP получает готовые
операции, web-превью — узкий контракт чтения приглашения. Зависимости проверяет
`go run ./cmd/check-dependencies` по политике `internal/architecture`;
подробности и границы будущих активаций/модерации описаны в ADR 0003.
Это рефакторинг бэкенда без изменения HTTP-контракта или интерфейсов клиентов.

Встреча, участие и лента остаются в `meetings`; обработчики фоновых задач
вызывают его операции. На моках обработчики и API разделяют один процесс.
Границы текущих пакетов закреплены в задаче 2.6; проверки и ограничения —
в [отчёте](monolith-boundaries-verification.md).
Критерии будущего выделения сервисов не меняют API или состав MVP.

На первом этапе используется Go без SQL, Docker и миграций. Прикладной код
работает с узким портом `meetings.Store`; адаптер `internal/storage/memory`
реализует его в памяти. Он хранит встречи, ответы, записи ленты и receipts.
Модуль и проверки можно создать до HTTP-контракта: публичные DTO не зависят
от устройства хранилища. Права, валидация полей, ревизии и бизнес-переходы
находятся в прикладных операциях и не подменяются ответами мока.

`View` читает согласованный снимок. `Update` сериализует записи, создаёт копию
состояния и публикует её только после успешного callback и проверки context.
Ошибка, отмена или panic оставляют прежнее состояние. Callback не выполняет
внешних HTTP-вызовов и не открывает вложенную транзакцию этого же Store.
Сессия чтения/записи закрывается после callback; полученные значения отделены
от внутренних map, срезов и указателей. Нельзя изменить хранилище через alias.

Mock запускается пустым, а примеры заполняются явно демонстрационной командой
или тестом. В каждом процессе своё состояние: запускать несколько экземпляров
сервера с независимыми mock-хранилищами нельзя. Перезапуск теряет все временные
данные, включая будущие профили и сессии; прежний вход после него недействителен.
Это режим локальной разработки, не обещание сохранности пользовательских данных.

PostgreSQL, pgx, goose, миграции и резервное копирование отложены до отдельного
заключительного этапа облака и расчёта стоимости (группа 14 в tasks.md).
Выбор и проектирование реальной БД также обсуждаются на этом этапе.
Тогда адаптер и его интеграционные тесты заменят
mock при сохранении поведения прикладных операций и общего HTTP API.
Тесты мока не доказывают SQL-блокировки или надёжность хранения на диске.
SQLite и файлы для временного этапа не требуются: они добавили бы ещё один
формат хранения, который затем пришлось бы переносить.

API — HTTP/JSON с префиксом `/api/v1`; описание OpenAPI 3.1 находится
в `contracts/openapi.yaml`. Добавлены сервер, безопасные ошибки и анонимный
preview из memory.Store, серверный вход и собственные сессии, операции создания,
RSVP, настроек и чата. Они проверены через HTTP с тестовым провайдером;
[результаты серверного среза](meetings-verification.md).
20 октября пользователь перенёс реальное подключение Яндекс ID в конец
разработки. Первый веб-сценарий реализован на общих fixtures и проверяется
с настоящим API и тестовым провайдером; [отчёт](web-verification.md).
Далее — iOS и Android. В runtime нет подставного user ID или обхода входа.
GET /healthz проверяет только процесс. Конфигурация и реальные команды —
в backend/README.md, контракт/fixtures проверяются в CI вместе с Go.
[api.md](api.md) задаёт семантику операций, ошибок, доступа и повторов. REST выбран вместо GraphQL
и gRPC: существующий путь состоит из небольшого набора операций, общих для
браузера и мобильных клиентов, без отдельного шлюза.

```mermaid
flowchart LR
    W[React + TypeScript] --> A[Go HTTP API]
    I[SwiftUI] --> A
    D[Jetpack Compose] --> A
    A --> P[(In-memory mock)]
    A --> Y[Яндекс ID]
```

Общий API передаёт встречи, ответы и записи ленты. Их типы описывают предметные
данные; дерево UI, имена клиентских компонентов и переходы сервер не присылает.

### 2. Модели и ограничения первого среза

| Модель | Основные поля | Ограничение и назначение |
| --- | --- | --- |
| `User` | `id`, `display_name`, `created_at` | Внутренний UUID; имя не является идентификатором входа. |
| `ExternalIdentity` | `provider`, `subject`, `user_id` | UNIQUE `(provider, subject)`; для Яндекса используется проверенный сервером `id`, не email. |
| `Session` | `id`, `user_id`, `secret_hash`, `client_kind`, `expires_at`, `revoked_at` | Одна сессия на вход/устройство; хранилище содержит хеш секрета сессии. |
| `AuthAttempt` | `id`, `state_hash`, `context`, `client_kind`, `status`, `expires_at` | Этапы `pending / provider_verified / session_issued`, отдельные отметки погашения state и кода передачи; подробности в [auth.md](auth.md). |
| `Meeting` | `id`, `organizer_id`, `title`, `description`, `starts_at`, `timezone`, `place`, `revision`, `feed_sequence`, `created_at` | Название и известное время обязательны; описание и текстовое место могут отсутствовать. |
| `InvitationLink` | `id`, `meeting_id`, `token`, `created_at` | Непредсказуемые 32 случайных байта в URL-safe формате; UNIQUE токен. В первом срезе одна ссылка на встречу. |
| `Rsvp` | `meeting_id`, `user_id`, `answer`, `revision`, `updated_at` | UNIQUE `(meeting_id, user_id)`; `going / maybe / not_going`. Отсутствие строки означает отсутствие ответа. |
| `FeedEntry` | `id`, `meeting_id`, `sequence`, `kind`, `actor_id`, `occurred_at`, `payload` | UNIQUE `(meeting_id, sequence)`; событие или сообщение с версией payload. |
| `RequestReceipt` | `user_id`, `operation`, `key`, `request_hash`, `resource_id`, `expires_at` | UNIQUE по пользователю, операции и ключу; защита от дублей при повторе. |

Связи: пользователь владеет встречами и ответами; у встречи есть ссылка, ответы
и лента. Организатор хранится отдельно от ответов приглашённых. Состав компании —
организатор и уникальные пользователи с текущим `going`; число не хранится
вручную в нескольких таблицах. Сам организатор не присоединяется по своей ссылке.
Выход организатора и передача владения не входят в первый путь.

Для создания Meeting дополнительно хранит `client_request_id` и исходный
`creation_request_hash`: повтор сравнивается с исходным запросом, даже если
организатор впоследствии изменил настройки. У сообщения постоянная уникальность
запроса задаётся `(meeting_id, actor_id, client_request_id)`.

Время хранится как UTC instant (`time.Time`) вместе с IANA timezone встречи.
При переходе на PostgreSQL ему будет соответствовать `timestamptz`.
Клиент передаёт выбранные дату/время, IANA-пояс и согласованное смещение;
сервер проверяет согласованность. На вебе поля даты и времени разделены,
пояс автоматически берётся из браузера при создании и из встречи при
редактировании; отдельного поля выбора пояса нет. Сохранённый черновик
сохраняет исходный пояс. Gravity DatePicker отображает календарные части
в UTC как условные значения полей; итоговый instant вычисляет Temporal
в настоящем поясе встречи, чтобы библиотека UI не переносила DST-время.
Компоненты Gravity UIKit 7.51.1 / date-components 4.1.0 / date-utils 2.7.2
подключаются через shared/ui и используют общую тёмную тему. Состояния и
эскиз изменения описаны в [ux.md](ux.md#уточнение-формы-даты-и-времени--20-октября-2026). Для неоднозначного или отсутствующего местного времени нужен
явный выбор/ошибка поля, а не молчаливый перенос на час. Календарные дни клиента
не вычисляются простым обрезанием UTC-строки.

Ответ API с первого среза допускает `starts_at: null` для будущих встреч
с выбором даты; клиенты проверяются на таком fixture и не выдумывают дату.
Само создание первого среза требует назначенного времени. Это позволяет позднее
добавить опрос даты без падения уже выпущенных декодеров; серверная модель
недатированной встречи расширяется на соответствующем этапе.

Будущие `PlacePoll`, `PlaceVote`, `PreparationTask`, варианты даты и обложки
появятся вместе со своими сценариями; структуры хранения не создаются пустыми
заранее. Известные
правила и оставшиеся условия следующих этапов перечислены ниже.

### 3. Права и атомарные изменения

Согласовано пользователем: настройки меняет организатор; участники видят состав
и ответы друг друга; смена `going` на `maybe / not_going` закрывает чат.
Публичная ссылка не является правом читать переписку.

| Операция | Кто может выполнить |
| --- | --- |
| Прочитать публичное приглашение | Обладатель действительной ссылки; только разрешённые публичные поля. |
| Создать встречу | Пользователь с действующей сессией. |
| Сохранить свой RSVP | Авторизованный приглашённый, доказавший знание ссылки, либо пользователь с собственным ранее сохранённым ответом. |
| Прочитать детали, состав и чужие ответы | Организатор или пользователь с текущим `going`. |
| Читать и писать ленту | Организатор или пользователь с текущим `going`; проверка при каждом запросе. |
| Изменить настройки | Организатор; `revision` защищает от перезаписи устаревшей формы. |

Создание одним атомарным `Update` сохраняет встречу, ссылку, запись `meeting_created`
и receipt запроса. Сохранение RSVP внутри `Update` сверяет права
и ожидаемую ревизию ответа, затем сохраняет ответ и событие изменения.
Повтор того же ответа ничего не меняет и не создаёт ещё одно присоединение.
Переход в `going` отражается как `participant_joined`; выход из него — как
`participant_left`; прочее изменение — `rsvp_changed`. Ответы `maybe/not_going`
не увеличивают состав компании. Пользователь может повторно выбрать `going`.

Отправка сообщения, изменение настроек и изменение RSVP выполняются внутри
одного механизма `Update`, который сериализует конкурентные записи. Это не позволяет конкурентной отправке обойти уже
сохранённую потерю доступа. Успех операции означает commit; потерянный сетевой
ответ не отменяет уже сохранённое действие. Идемпотентность не отменяет повторную
проверку текущего доступа перед выдачей результата.

### 4. Яндекс ID и собственные сессии

Выбран серверный обмен authorization code и собственная сессия Somewhere.
Яндекс-токен используется сервером для проверки личности и не становится
ключом доступа к нашему API. Подробная последовательность, возврат к приглашению,
cookie/Bearer, отмена и повтор — в [auth.md](auth.md).

Так один путь проверки личности обслуживает три клиента. Браузер использует
защищённую cookie; мобильные приложения — системный браузер и защищённое хранение
сессии. Альтернативы: отдельные LoginSDK на обеих платформах либо внешний
посредник авторизации. Они добавляют интеграции, которые не нужны для первого
провайдера. Серверный путь требуется проверить с реальным приложением Яндекс OAuth
на всех трёх клиентах до объявления входа готовым.

### 5. Лента с устойчивым порядком и догрузкой

`FeedEntry` — журнал пользовательских сообщений и предметных событий, не event
sourcing всей системы. Текущее состояние остаётся в моделях встречи и ответов;
история содержит снимок изменения, а не ссылку на изменяемый текущий текст.

При добавлении записи внутри `Update` адаптер назначает следующий sequence
одной встречи; номер и запись публикуются вместе. Время и глобальный счётчик
не используются как единственный курсор: конкурентное изменение не должно
поздно опубликовать запись, которую клиент уже пропустил. Удаление сообщения
не входит в первый срез; номера ленты повторно не используются.

Последние записи загружаются страницей; новые — по `after_sequence`, история —
по `before_sequence`. Для каждой догрузки проверяется доступ. Ответ содержит
текущую ревизию встречи, свой RSVP и счётчик состава, чтобы данные рядом с лентой
обновлялись вместе с наблюдаемыми событиями. Клиент сливает данные по ID/sequence,
сохраняет позицию при чтении истории и не прыгает вниз при каждом ответе.

Первая доставка — опрос HTTP каждые 3 секунды при открытой активной встрече;
при ошибке интервал увеличивается до 30 секунд, в фоне опрос останавливается.
Возврат на экран сразу догружает новые записи. Интервалы — настройки первого
среза, не обещание мгновенной доставки. WebSocket/SSE потребовали бы отдельного
восстановления соединений и контроля отозванного доступа. Их можно добавить
позже, сохранив журнал и курсоры HTTP.

Веб определяет сторону сообщения по `entry.actor.id === session.user.id`:
своё сообщение вместе с аватаром располагается справа, чужое — слева.
Системные события остаются по центру; CSS меняет раскладку, сохраняя DOM-порядок
истории, подписи и перенос длинного текста. Локальная отправка и ошибка
с повтором также показываются справа. Новые поля и операции API не нужны.

Сообщение показывается локально как отправляемое с `client_request_id`.
Неопределённый исход повторяется с тем же ID; черновик не теряется. При потере
доступа клиент закрывает разговор и очищает его кеш. Это предотвращает дальнейшее
чтение в приложении, но не отзывает уже сделанные снимки или прочитанное человеком.

### 6. Реализация клиентов и связь с UX

| Часть UX v0.7 | API и состояние | Клиентская реализация |
| --- | --- | --- |
| Онбординг и вход | Сессия, `AuthAttempt`, сохранённая точка входа | Общий вход; приглашение обходит онбординг. |
| Личные встречи | `GET /meetings`, загрузка/пусто/ошибка | Сначала список; календарь добавляется следующим этапом к тем же данным. |
| Создание | `POST /meetings`, локальный черновик и ID запроса | Форма, сохранение, повтор, подтверждение выхода с несохранённым вводом. |
| Передача ссылки | Ссылка из результата или API организатора | Web Clipboard с ручным копированием; системное Share в мобильных клиентах. |
| Приглашение и ответ | Публичный preview, собственный RSVP | Три ответа; чат открывается только после ответа API. |
| Лента и информация | Детали, участники, страница записей, локальная отправка | Сообщения, системные события, компактная шапка; на телефоне одна колонка. |

Веб: Vite, React + TypeScript, React Router для маршрутов и TanStack Query для
серверного кеша. Формы и небольшое UI-состояние — локальные хуки; дополнительный
глобальный store не нужен. Автоповторы мутаций выключены: явный повтор использует
сохранённый ключ запроса. Все конфигурации приложения — TypeScript.

FSD: `app` связывает маршруты, провайдеры и QueryClient; `pages` содержит экраны
landing, meetings, meeting-create, invitation, meeting и auth-return;
`widgets` — самостоятельную композицию ленты/деталей;
`features` — sign-in, create-meeting, respond-to-invitation, send-message,
share-invitation и edit-meeting; `entities` — user, meeting, rsvp, feed-entry;
`shared` — независимые UI, transport, примитивы контрактов и config.
DTO маппятся в предметных slices; features не импортируют друг друга.
Файл компонента содержит только импорты, компонент и Props, ориентир —
до 100 содержательных строк. Все внутренние импорты идут через `@/` и публичные API.

iOS: SwiftUI, владельцы состояния на `MainActor`, `URLSession` + `Codable`,
`ASWebAuthenticationSession` для входа, Keychain для сессии. Навигация и черновик
формы принадлежат приложению; сетевые задачи отменяются по жизненному циклу.

Android: Compose, ViewModel + StateFlow, Repository и coroutines, OkHttp +
kotlinx.serialization для сети; системная авторизация через Custom Tabs.
Секрет сессии шифруется ключом Android Keystore и хранится в закрытой области
приложения. Сбор состояния учитывает жизненный цикл; Back не теряет приглашение.

Точные версии и toolchain закрепляются при инициализации в lock-файлах,
Go module, Xcode project и Gradle version catalog; плавающих зависимостей нет.
Для iOS закреплены минимум 17.0 и Xcode 26.0.1 (17A400): Swift 6.2 в режиме
Swift 6, swift-format 6.2.0, SDK iOS Simulator 26.0. Обычный Xcode project
с синхронизированной группой и общей схемой `Somewhere` не требует генератора
или внешних Swift-пакетов. Build settings находятся в `.xcconfig`;
`clean build analyze` для generic simulator работает без подписи.
CI выбирает тот же Xcode на `macos-15`, версии проверяет отдельный скрипт.
На этом этапе root view показывает бренд с двумя цветами из общих токенов;
API, состояния, вход и пользовательские экраны относятся к следующим задачам.

Основа Android и её закреплённые инструменты описаны в
[android-bootstrap.md](android-bootstrap.md): minSdk 26, SDK 36, JDK 17,
Compose, Gradle wrapper и отдельная проверка CI. Результаты сборки фиксируются
после выполнения реальных команд; следующий этап — данные и состояние 7.2.

| --- | --- | --- |

| Смена места | Автор задаёт срок; автозакрытие; один открытый опрос; голос можно менять; без кворума; ничья/0 не меняют место. | Определить учёт пришедших/вышедших и ручного изменения места во время опроса; закрыть соответствующие сценарии. |
| Подготовка | Предложение адресату и отдельное принятие; состояние видно в ленте. | Решить принятие чужой задачи, отказ/передачу/отмену и необходимость завершения; дополнить UX. |
| Обложка | Необязательна, принадлежит встрече. | Выбрать хранение, ограничения загрузки и обработку ошибок; реализовать до выпуска полного MVP. |

Для автозакрытия опросов планируется фоновый цикл в том же Go-приложении:
просроченный открытый опрос закрывается внутри `Update`; результат, место
и записи ленты публикуются вместе. Повтор/перезапуск фонового цикла в том же
процессе не применяет результат дважды. Перезапуск самого mock-сервера сбрасывает
состояние; восстановление просроченных опросов после него потребует постоянного хранения. Это не зависит
от того, открыт ли у кого-нибудь экран. Точная операция уточняется после
перечисленных продуктовых решений, до кода этапа.

### 8. Проверка и совместимость

OpenAPI и общие JSON-fixtures проверяют запросы, ответы, nullable, ошибки и типы
записей во всех клиентах. DTO и transport остаются внутри приложений; общий
исполняемый UI/SDK трёх языков не создаётся. Клиенты терпимы к дополнительным
полям; неизвестный тип записи отображается безопасной заглушкой без исполнения
действий и не ломает остальную историю. Новые обязательные поля/смена семантики
требуют совместимого расширения либо новой версии API.

Первые серверные тесты используют новый memory.Store на каждый тест, управляемые
часы и подставной OAuth-provider. Состояние между тестами не разделяется;
`go test -race` проверяет конкурентную запись и чтение. Production-путь не содержит
обхода входа; тесты реального SQL-адаптера появятся при подключении PostgreSQL.
Проверяются гонки
RSVP/сообщения, повтор после commit, приватность публичного DTO, закрытие доступа
и восстановление приглашения. UI сравнивается с [макетами](ux.md) отдельно
на web, iOS и Android; структура OpenSpec не заменяет эти проверки.

## Risks / Trade-offs

- [Три реализации UI] → Общие UX, контракт и сценарии приёмки, отдельная проверка платформ.
- [Задержка обновления при polling] → Догрузка при возврате, устойчивые курсоры; смена транспорта при реальной потребности.
- [Последовательная запись и копирование mock-состояния] → Короткие callbacks без внешних запросов; подходит для локального объёма, масштабирование требует постоянного хранилища.
- [Сброс данных и сессий при перезапуске] → Явный режим разработки; перед постоянным использованием нужен другой адаптер.
- [OAuth ещё не проверен] → Первый интеграционный этап проверяет весь вход и возврат на трёх платформах с реальным Яндекс OAuth.
- [Часть MVP ещё требует продуктовых решений] → Задачи следующих этапов имеют явные условия старта; их нельзя выполнять по умолчаниям агента.
- [Уже прочитанные сообщения нельзя отозвать] → Прекратить новые запросы и убрать приватный кеш при выходе/потере доступа.

## Migration Plan

Это новый проект: перенос существующих пользовательских данных не требуется.
Сначала создаётся модуль Go и mock-адаптер; затем API запускается с этим Store
без сервисов базы данных. Веб будет обращаться к API через dev proxy того же origin.
Для реального OAuth нужен зарегистрированный HTTPS callback,
конфигурация домена и секреты вне Git. Подробности — в [auth.md](auth.md).

Порядок: контракт и окружение → серверный вход/данные/лента → web → iOS → Android
→ проверка одного сценария между всеми клиентами. Это последовательность
поставки, а не отказ от любой платформы. Каждое приложение получает реальные
команды запуска, форматирования, сборки и тестов в своём AGENTS.md.

На временном этапе миграций и переноса данных нет. В заключительной группе 14
сначала рассчитываются облачные ресурсы и стоимость, затем выбираются постоянные
хранилище и очередь, проектируются схема и миграции. После подключения выполняются
те же проверки поведения репозитория, интеграционные проверки и восстановление
из резервной копии.
Перенос mock-данных не обещается. Выпуск первого среза не равен готовности полного MVP.

### Короткие приглашения и Open Graph

Новые токены приглашений содержат 128 случайных бит (22 символа base64url);
старые 256-битные токены принимаются. URL интерфейса — `/i/{token}`, старый
`/invitations/{token}` поддерживается. API `/api/v1/invitations/` не меняет путь.
Описание становится явным публичным полем preview; остальные приватные данные
по-прежнему исключены. Изменение обратно совместимо для старых токенов/клиентов.

Пакет Go `internal/webui` обслуживает собранный frontend и вставляет экранированные
метатеги в HTML приглашения по публичному snapshot. Базовый HTML перечитывается
при запросе, чтобы обновление сборки не требовало перезапуска памяти. Абсолютные
URL берутся из доверенной конфигурации, не Host запроса. Авторизация остаётся
отдельной и отложенной; web-origin можно настроить без Яндекс ID. Публичный
сервер опционально подключается через `SOMEWHERE_WEB_DIST`/`SOMEWHERE_WEB_ORIGIN`.
Тестовый стенд использует тот же обработчик, подменяя только OAuth-provider.

[Open Graph](https://ogp.me/) задаёт title/type/image/url и description.
Изображение — статическая PNG 1200×630 с существующим знаком; новые Go-зависимости
не нужны. Проверяются заголовки, raw HTML, экранирование, 404, HEAD, старые ссылки
и отсутствие персональных данных. Внешние crawler/кеши проверяются после выкладки.

## Календарь и история: план этапа 9 от 21.10.2026

Согласованы граница истории и сохранение текущего поведения прошедших встреч.
UX — в [entry-home.md](entry-home.md), требования —
в [personal-meetings/spec.md](specs/personal-meetings/spec.md), расширение
API — в [api.md](api.md). Содержание следующей итерации истории неизвестно
и не входит в этот план.

Пользователь согласовал сохранённый статус и отложенные задачи 21.10.2026.
Встреча хранит `upcoming`, `past` или `undated`; API и статистика читают это
значение. Чтение встречи или списка не меняет статус. Срок перехода — начало
следующего календарного дня в `meeting.timezone`, с учётом смены UTC-смещения.

Для каждой датированной предстоящей встречи ставится задача `mark_meeting_past`
с ID встречи, версией расписания и временем выполнения. При наступлении срока
фоновый обработчик атомарно проверяет текущий статус, версию расписания и срок,
затем сохраняет `past`. Повторная доставка не повторяет изменение. Перенос даты
или пояса сохраняет актуальный статус и новое расписание; старая задача с иной
версией завершается без изменения встречи. Изменение заголовка или RSVP само
по себе не отменяет задачу перехода. Встречи без даты не получают такую задачу.

Сохранение встречи и постановка задачи должны быть согласованы: успешная запись
встречи не должна оставлять её без задачи. Конкретный механизм (единая транзакция
с хранилищем очереди либо доставка через outbox) зависит от ещё не выбранных
хранилища и библиотеки. Успех задачи подтверждается после сохранения статуса;
ошибки допускают повтор. Просроченные задачи после простоя должны выполняться
без пользовательского запроса. Срок задаёт самое раннее время выполнения;
задержка очереди или недоступность обработчика не означают потерю задачи.

Контроль выполнения задач и сверка просроченных встреч согласованы пользователем
21.10.2026. Это серверная часть этапа 9.2; новый интерфейс клиентов не требуется.

- Наблюдаем количество повторов, окончательных ошибок и зависших задач,
  задержку выполнения и возраст самой старой просроченной встречи. Сохраняем
  время последней успешной сверки и её ошибки: остановка самой проверки тоже
  должна обнаруживаться. Пороги задержки и интервал сверки настраиваются;
  конкретные значения закрепляются вместе с реализацией.
- Диагностика задачи содержит её ID, ID встречи, версию расписания, номер
  попытки и безопасный код ошибки. Тексты встреч, переписки, токены приглашений
  и содержимое сессий в эти логи не попадают. Окончательные ошибки и превышение
  порогов дают сигнал оператору; канал доставки выбирается при подключении
  мониторинга. Исчерпанные попытки остаются доступными для разбора и управляемого
  повторного запуска. Повтор использует те же проверки срока и расписания.
- Зависшая задача возвращается в обработку после истечения срока владения
  исполнителем. Пока срок не истёк, контроль не создаёт конкурирующую задачу.
  Повторная доставка сохраняет атомарную проверку и идемпотентность перехода.
- Сверка запускается при старте обработчиков и периодически, без пользовательских
  запросов. Ограниченными порциями выбирает `upcoming` с наступившим сроком
  перехода. Перед восстановлением заново проверяет актуальные статус, срок
  и версию расписания в транзакции. Перенесённые, недатированные и уже прошедшие
  встречи пропускаются. Сверка восстанавливает работу через обычный обработчик
  перехода и не вводит отдельные правила сохранения статуса.
- Если задача текущего расписания отсутствует, сверка согласованно создаёт её
  с защитой от дублей по ID встречи и версии расписания. Параллельные сверки
  не создают дополнительные задачи. Задачу, которая уже выполняется или ожидает
  повтора, не дублируем и не сбрасываем её задержку/счётчик попыток. При
  окончательной ошибке сохраняем сигнал и возможность управляемого повтора;
  каждый проход сверки не запускает новый бесконечный цикл попыток.

Приёмка включает остановку исполнителя, исчерпание попыток, потерянную задачу,
ошибку/простой самой сверки, одновременные сверки и гонку с переносом даты.
Логи и метрики проверяются на отсутствие чувствительных данных. Логику
проверяем на моке с управляемыми часами; сохранность и восстановление после
перезапуска БД/процессов — отдельно на постоянном хранилище, без запуска БД локально.

Права доступа сохраняются независимо от статуса. Переход не добавляет сообщение
в чат и не закрывает редактирование. Надёжность после перезапуска требует
постоянного хранения и встреч, и задач. Последнее решение пользователя от
21.10.2026 переносит все вопросы реальной БД и очереди в заключительную группу 14:
выбор технологии, SQL-схему, миграции, подключение и проверки рассматриваем вместе
с облачными ресурсами и стоимостью. До этого используем memory.Store и мок
очереди; реализуем переходы статуса, повторы, контроль сбоев и сверку просроченных
встреч. Их поведение сохраняется при замене адаптеров. Тесты мока не подтверждают
сохранность после остановки процесса. Выбор постоянного хранилища не блокирует
календарь и следующие пользовательские сценарии.

Кандидат для обсуждения в группе 14 — PostgreSQL + River для Go. Запись
встречи и `InsertTx` выполняются в одной транзакции общей БД; отдельный outbox
для постановки этой задачи тогда не нужен. River предоставляет отложенное
выполнение и повторы, а предметный обработчик сохраняет проверки расписания
и идемпотентность. Библиотека пока предложена, а не установлена или проверена
в проекте. Версии и параметры повторов закрепляются при подключении адаптера.
Публичные основания: [транзакционная постановка](https://riverqueue.com/docs/transactional-enqueueing)
и [возможности River](https://github.com/riverqueue/river).

API получает фильтры раздела и локальных дат, полные счётчики и отметки дней,
устойчивую пагинацию и момент следующего обновления. Фильтрация выполняется
до пагинации. Прежний запрос без фильтров сохраняет поведение и курсоры.
Контракт и общие fixtures обновлены с бэкендом в задаче 9.2;
[результаты проверки](calendar-backend-verification.md). Решение от 22.10.2026: если состав или состояние личного набора меняются
между страницами, сервер возвращает `409 calendar_changed`; клиент начинает
загрузку заново, сохраняя раздел, месяц и день. Курсор содержит отпечаток
доступного набора (ID, ревизия встречи, статус и ревизия своего RSVP), профиль,
фильтры и позицию. Отпечаток рассчитывается заново в одной read-транзакции;
чужие встречи не влияют на него. `as_of` — время текущего чтения, без заморозки
статуса. Старые курсоры списка без `period` сохраняют семантику.

Фоновый переход увеличивает общую `meeting.revision` ровно один раз, не меняет
версию расписания и не добавляет событие ленты. Конфликт редактирования проходит
обычную обработку `meeting_revision_conflict`. `schedule_version` меняется лишь
при фактическом изменении времени/пояса; на создании равна 1. Уже прошедшая дата
при создании или переносе сохраняется как `past`, без лишней отложенной задачи.
Встреча без даты имеет `undated` и не получает задачу. Перенос в будущее сохраняет
`upcoming` и новое расписание. Заголовок и RSVP не отменяют действующую задачу.

Мок хранит задачу в том же атомарном `Update`, что и встречу. Её ключ — ID встречи
и версия расписания. Получение задачи фиксирует попытку и lease с уникальным
токеном; старый исполнитель не может подтвердить работу после повторного захвата.
Запись статуса и подтверждение задачи атомарны. Задачи старого расписания
завершаются без изменений. Ошибки хранилища не раскрываются в диагностике.

Начальные настройки: опрос очереди 1 с, lease 30 с, максимум 5 попыток,
задержка повтора 5 с с удвоением до 5 минут, размер порции 100; сверка раз в
минуту, сигнал при задержке перехода более минуты или отсутствии успешной
сверки более 5 минут. Значения настраиваются сервером. Сверка ограничивает
число записей за проход и сохраняет позицию до окончания полного обхода;
после ошибки возобновляется без сброса существующих попыток. Метрики и
операционные сигналы передаются в структурированный серверный лог;
облачная доставка и панель оператора остаются в группе 14. Прикладная операция
повтора окончательно упавшей задачи проверяет актуальное расписание и
сохраняет счётчик ручных повторов; публичного HTTP-доступа к ней нет.

Ответ календаря содержит `refresh_after_seconds=5`. Клиент обновляет данные
на `next_transition_at`; если срок уже наступил, повторяет запрос через этот
интервал, без цикла нулевых таймеров. На открытом экране опрос раз в 5 с замечает
и изменения других участников. Ошибки сети используют обычный backoff клиента.
Это политика обновления отображения, а не механизм смены статуса.

Веб хранит переключатели и выбранный день в модели страницы личных встреч;
запросы и DTO остаются в соответствующих FSD-слоях. iOS использует владельца
состояния экрана и SwiftUI-компоненты, Android — ViewModel/repository и Compose.
Ключ запроса включает профиль, раздел и диапазон; ответ старого запроса
не заменяет новый. Смена даты/RSVP сбрасывает соответствующие страницы и
счётчики. Возврат на экран и серверный момент обновления заново запрашивают
данные. Часы клиента не являются источником классификации.

Проверки строятся на управляемых серверных часах: начало и конец дня,
разные IANA-пояса, день смены UTC-смещения, отсутствие даты, смена года,
пагинация и изменение доступа между страницами. Для UI на каждой платформе
сверяются макеты, Back, несколько событий, пустота и ошибка, доступность
и отсутствие повторов кнопки создания. Только уже открытые устройства,
не более одного симулятора/эмулятора каждой платформы.
