# Задачи подготовки

Этап 12 для общего API, web, iOS и Android. Основание — согласованный
пользователем набор действий от 24.10.2026. Постоянное хранение и облако
не входят в реализацию этого этапа.

## Правила и состояния

Участник с доступом к разговору (организатор или текущий going) предлагает
задачу с названием 1–200 символов после обрезки внешних пробелов. Адресат —
текущий участник или «Любой участник». Можно предложить задачу себе;
создание всё равно не означает принятие.

| Состояние | Доступные переходы |
| --- | --- |
| `offered`, указан адресат | Адресат принимает или отказывается; автор/организатор отменяет |
| `offered`, общая задача | Любой текущий участник принимает; автор/организатор отменяет |
| `accepted` | Только исполнитель отмечает выполнение или отказывается; автор/организатор отменяет |
| `completed` | Итоговое состояние, повтор с прежним ключом не создаёт новое событие |
| `declined` | Итоговое состояние; новое предложение создаётся отдельно |
| `cancelled` | Итоговое состояние; новое предложение создаётся отдельно |

Общую непринятую задачу нельзя отклонить за всю компанию: у неё ещё нет
адресата или исполнителя. Отказ после принятия снимает ответственность,
не назначает другого человека и сохраняет прежнюю карточку в истории.
Передача выполняется существующими действиями: отказ от своей задачи или её отмена и новое
предложение выбранному человеку. Согласие нового адресата требуется отдельно.
Автоматической передачи, редактирования принятой задачи, сроков и повторного
открытия итоговых задач этот этап не добавляет.

При выходе из состава никто не назначается автоматически. Карточка сохраняет
состояние и историю; у вышедшего нет доступа к действиям. Организатор/автор
может отменить предложение, в том числе принятое. Возвращение с going
восстанавливает доступ к действиям по текущему состоянию задачи. Адресат
проверяется на момент создания, права действующего пользователя — в каждой
операции, включая повтор. Последующее завершение/отказ доступны только
текущему исполнителю с доступом к встрече.

## UX

Меню «+» рядом с сообщением: «Предложить дату», «Предложить место»,
«Предложить задачу». Форма задачи:

```text
Предложить задачу                       ×
Что нужно сделать
[ Заказать пиццу                       ]
Кому предложить
[ Любой участник                     v ]

                   [ Предложить задачу ]
```

Список адресатов загружается из состава встречи, включает организатора
и going. Имя не заменяет идентификатор пользователя. Загрузка — скелетон,
ошибка — «Не удалось загрузить участников» с повтором; отправка до загрузки
недоступна. Предложение себе показывается в списке как «Вы».

После успешной записи форма закрывается, карточка появляется в разговоре.
При ошибке поля сохраняются; неизвестный результат повторяется с тем же
ключом и телом. Во время отправки вместо текста кнопки показывается спиннер,
повторные нажатия блокируются, доступное название кнопки сохраняется.

```text
Саша
Заказать пиццу
Предложено Лене
[ Принять задачу ] [ Отказаться ]
```

Автор карточки и сторона следуют существующим сообщениям. Одна строка статуса
сообщает отдельный факт; нет повторного абзаца с тем же смыслом.

| Состояние / зритель | Карточка и действия |
| --- | --- |
| Предложено конкретному человеку | «Предложено Лене»; адресату — «Принять задачу», «Отказаться» |
| Общая задача | «Пока никто не взял задачу»; «Взять на себя» |
| Принято | «Исполняет Лена»; исполнителю — «Отметить выполнение», «Отказаться» |
| Выполнено | «Выполнила Лена» либо нейтральное «Выполнено · Лена», без кнопок |
| Отказ | «Отказался: Тимофей» либо нейтральное «Отказ · Тимофей», без назначения нового исполнителя |
| Отмена | «Отменено · Саша», без кнопок |
| Право отмены у зрителя | «Отменить задачу» для offered/accepted, отдельно от принятия/выполнения |

В коде использовать нейтральные формы «Выполнено · имя», «Отказ · имя»:
пол пользователя не известен и не выводится из имени.

Карточка ждёт подтверждения сервера: нажатие не меняет исполнителя или итог
оптимистично. Ошибка чтения сохраняет уже загруженную карточку; до первого
ответа показывается скелетон. Ошибка действия — «Не удалось сохранить действие»
и повтор. При конфликте — «Задача изменилась. Проверьте её состояние»;
карточка перечитывается, недоступные действия исчезают. Старый повтор не
откатывает более позднее действие. При 401/403 приватные данные очищаются.

Создание отображается карточкой; принятие, отказ, отмена и выполнение —
отдельными системными строками с человеком и названием задачи. Текущая карточка
обновляется через существующее периодическое чтение, при возврате приложения
и после действий. Две вкладки/устройства видят одного исполнителя.

Web: адаптивный диалог с закреплённой кнопкой, Escape/Back/возврат фокуса,
черновик формы при закрытии, 320/390/1440 px и reduced motion.
iOS: sheet/Form, Dynamic Type и VoiceOver-подписи; Android: Material sheet,
клавиатура/insets, Back, восстановление Activity и TalkBack-подписи.
Сетевые чтения привязаны к жизненному циклу; старый ответ не восстанавливает
закрытый экран или сессию. Неопределённое действие сохраняется для точного повтора.

## API

Префикс `/api/v1/meetings/{id}`; права организатор/current going.

| Метод и путь | Тело | Результат |
| --- | --- | --- |
| `POST /preparation-tasks` | `{title, recipient_id: UUID|null}` | 201 PreparationTask |
| `GET /preparation-tasks/{task_id}` | — | 200 PreparationTask |
| `POST /preparation-tasks/{task_id}/accept` | `{expected_revision}` | 200 PreparationTask |
| `POST /preparation-tasks/{task_id}/decline` | `{expected_revision}` | 200 PreparationTask |
| `POST /preparation-tasks/{task_id}/cancel` | `{expected_revision}` | 200 PreparationTask |
| `POST /preparation-tasks/{task_id}/complete` | `{expected_revision}` | 200 PreparationTask |

`PreparationTask`: `id`, `meeting_id`, `title`, `author`, `recipient` nullable,
`assignee` nullable, `updated_by`, `state`, `revision`, `created_at`, `updated_at`,
`can_accept`, `can_decline`, `can_cancel`, `can_complete`. Пользователь —
существующий `{id, display_name}`; ревизия — десятичная строка, время RFC3339.
Прежний assignee сохраняется в истории отказа/отмены, но UI не называет его
действующим исполнителем. Эти четыре флага определяет сервер для читателя.

Все записи требуют `Idempotency-Key`, web — также CSRF. На создании ключ
сохраняется в задаче, чтобы повтор не создавал вторую карточку после очистки
временных receipts. Повтор действия возвращает актуальную проекцию и никогда
не возвращает задачу назад. Права проверяются до повторного ответа.
Несовпадающее тело прежнего ключа — 409 `idempotency_key_reused`;
устаревшая ревизия — 409 `task_revision_conflict`;
неподходящее текущее состояние — 409 `task_state_conflict`;
неправомочный адресат/исполнитель — 403 `forbidden`.
Неверный title/recipient_id — 422; выбранный человек вне состава —
422 `recipient_id: unavailable`, клиент обновляет список и сохраняет название.

Имена записей ленты: `preparation_task_created`, `preparation_task_accepted`,
`preparation_task_declined`, `preparation_task_cancelled`,
`preparation_task_completed`. `payload_version: 1`, `payload: {task_id, title}`.
Автор записи — действовавший человек. Неизвестные события остаются безопасными
данными у прежних мобильных клиентов; существующие маршруты не меняются.

## Хранение и проверки

Задачи принадлежат области meetings; новый модуль или инфраструктура не нужны.
Операция обновляет задачу, ревизию и ленту одной `Store.Update`. Одновременные
принятия общей задачи дают одного исполнителя и одно событие. Сбой любой записи
откатывает всё. Сохраняются независимые копии nullable-профилей.

Сервер: адресат/общая/самому себе; запрет принятия чужого предложения; принятие,
отказ до/после, отмена, завершение; потеря/возврат доступа; неверный адресат;
два одновременных принятия, повтор ключа, конфликт ревизии, поздний повтор,
откат при ошибке ленты и сохранения. OpenAPI сверяется с реальными HTTP-ответами,
fixtures декодируют все клиенты.

Каждый клиент: форма/состав/ошибка, предложение и принятие разными людьми,
общая задача и конфликт, отказ/отмена/выполнение, точный повтор, потеря доступа,
итог без активных кнопок, навигация/клавиатура/крупный текст. Результаты и снимки
сохраняются в отдельном отчёте; memory.Store сбрасывается при перезапуске процесса.
