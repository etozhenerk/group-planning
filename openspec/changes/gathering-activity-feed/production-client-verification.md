# Проверка клиентов с smwhere.ru

Дата: 25.10.2026. Продолжение [функциональной проверки MVP](mvp-functional-verification.md)
и [проверки мобильного входа](auth-native-verification.md). Деплой в этот проход
не выполнялся. Изменение кода касается только web; локальные обычные мобильные
сборки настроены на `https://smwhere.ru` без тестового провайдера.

## Подтверждено на настоящем окружении

| Клиент | Результат | Граница проверки |
| --- | --- | --- |
| Web | Настоящий вход Яндекс ID, список существующих встреч; выход, открытие публичного приглашения и повторный вход вернули ту же ссылку и профиль | Проверялось собственное приглашение организатора, без второго аккаунта |
| iOS | Обычная Debug-сборка установлена в iPhone Simulator; пользователь вошёл через Яндекс и увидел свои встречи, включая «Проверка запуска somewhere» | Физическое устройство, отмена входа и вход по приглашению в этом проходе не проверены |
| Android | Обычная Debug-сборка собрана и установлена с правильным API origin | Вход на smwhere.ru не подтверждён: запрос начала авторизации не завершает HTTPS-соединение |

Для iOS использованы Xcode 27.1, SDK iphonesimulator27.1, схема `Somewhere`,
Debug и существующий симулятор. Для Android — JDK 17, закреплённый wrapper,
`:app:assembleDebug -PsomewhereApiOrigin=https://smwhere.ru` и существующий
единственный AVD Android 36. Конфигурации сохранены в игнорируемых
`frontend/ios/Config/Local.xcconfig` и `frontend/android/local.properties`.
Исходный код нативных приложений не менялся; их полные проверки предыдущего
прохода перечислены в функциональном отчёте и здесь не выдаются за новые.

## Android: локализация сбоя

Временная instrumentation-проверка использовала production `ApiClient`,
`AuthRequests.start` и новый PKCE challenge без пользовательских credentials.
Она зафиксировала сбой до вызова Яндекс LoginSDK:

1. Изначально DNS эмулятора не разрешал `smwhere.ru` (`unknown host`).
2. Тот же AVD перезапущен без сброса данных с явным DNS текущей сети. Имя стало
   разрешаться в `158.160.246.254`, ICMP-проверка получила ответ.
3. После исправления DNS: `TLS started` → `SocketTimeoutException`; HTTP-ответа нет.
4. На Mac `curl https://smwhere.ru/healthz` также зависал на TLS после успешного
   TCP-соединения. Проверка TLS 1.2 получила `Connection reset by peer`.
   `http://smwhere.ru/healthz` отвечал редиректом 308 на HTTPS;
   `https://oauth.yandex.ru/` отвечал 302 с успешным TLS.
5. SSH к той же ВМ не завершил обмен banner. Это не доказательство причины
   на сервере или в VPN: другую сеть проверить не удалось, пользователь пока
   не может переключить подключение.

Это локализует текущую ошибку до соединения с API, но не подтверждает успешность
последующих стадий Android-входа. Обход сертификатов, HTTP вместо HTTPS и смена
SDK не применялись. Диагностический тест убран из исходников; сетевые параметры
не записаны в репозиторий. После восстановления доступа требуется новая попытка
в обычном somewhere, затем проверка возврата и списка встреч.

## Исправление собственного приглашения в web

Реальный возврат из Яндекса выявил дефект: организатору показывались три варианта
RSVP. Нажатие «Приду» правильно отклонялось сервером, но интерфейс выдавал
ошибку доступа к переписке. Теперь web проверяет роль по защищённым деталям:
организатор получает «Открыть встречу», приглашённый — прежние варианты ответа.
Во время проверки показан скелетон; при сетевой ошибке можно повторить запрос.
Состав встречи, серверные права и API не меняются.

Карта текстов: нейтральная надпись «Приглашение на встречу» описывает страницу;
строка профиля позволяет заметить вход не в тот аккаунт; строка организатора
объясняет доступное действие; кнопка называет переход. Название и факты встречи
сохранены. Технические подробности проверки в интерфейс не добавлены.

Проверено автоматически с настоящим Go API и тестовым OAuth-провайдером:

- вход из собственной ссылки и возврат без записи RSVP, перезагрузка страницы;
- отсутствие трёх вариантов ответа, один участник, прежняя ревизия встречи;
- переход к разговору клавишей Enter;
- задержанная проверка роли, ошибка сети и успешный повтор;
- сохранение сценариев обычного приглашённого в полном наборе E2E.

Снимки локальной сборки: [320 px](assets/production-client-verification/own-invitation-320.png),
[390 px](assets/production-client-verification/own-invitation-390.png),
[1440 px](assets/production-client-verification/own-invitation-1440.png).
Визуально проверены узкий и широкий варианты: нет горизонтального переполнения,
главное действие доступно. Исправление ещё не установлено на smwhere.ru.

## Проверки кода

| Проверка | Результат |
| --- | --- |
| `npm run web:check` | Типы, линтеры, FSD, форматирование; 62 unit-теста в 18 файлах прошли |
| `npm run web:build` | Production-сборка прошла |
| Полный `npm run web:test:e2e` | 89 passed, 1 failed, 1 skipped; единственное падение было в подготовке даты существующего теста скелетонов |
| Повтор `tests/18-loading-logout.spec.ts` | После перехода на дату через 7 дней и согласованный UTC: 5 passed |
| Повтор `tests/25-own-invitation.spec.ts` после финального текста | 2 passed |
| `npm run agent:check`, OpenSpec strict, `git diff --check` | Прошли; структура, ссылки и оформление проверены |

Старый тест скелетонов опирался на фиксированное 24 октября: после этой даты
созданная встреча переставала быть предстоящей. Тест теперь устанавливает будущую
дату через API с согласованными `starts_at`, `starts_on` и `timezone`. Первый
прогон нового setup без последних двух полей получил ожидаемый 422; окончательный
вариант прошёл. Это правка тестовых данных, поведение календаря не менялось.
Единственный пропуск полного набора — отдельный межплатформенный тест без
запущенного мобильного fixture; его предыдущий успешный прогон описан в
[cross-platform-verification.md](cross-platform-verification.md).

## Что требуется для завершения приёмки

1. Восстановить HTTPS-доступ к API с Android и пройти реальный LoginSDK-цикл.
2. Проверить два настоящих аккаунта: приглашение, явный RSVP, один профиль на
   разных клиентах и обмен сообщениями. Собственное приглашение не заменяет
   проверку приглашённого.
3. Пройти отмену авторизации, повтор и восстановление контекста приглашения
   после завершения процесса на обычных мобильных сборках.
4. Проверить VoiceOver/TalkBack и физические устройства. Автоматические проверки
   крупного текста и подписей из прошлых отчётов не закрывают ручную приёмку.
5. Подготовить проверенное открытие HTTPS-приглашений в приложениях: сейчас
   поддержаны собственные URI-схемы; для домена ещё нужны Universal Links /
   Android App Links и файлы ассоциаций на хосте. Серверную часть согласовать
   с отдельной работой по деплою.
6. Для тестовой раздачи собрать артефакты по [процессу релизов](../../../docs/releases.md).
   На этом Mac обнаружен только сертификат Apple Development; Distribution
   не подтверждён. Подпись и магазинные настройки Android в этом проходе
   не проверялись. Ключи и новые сертификаты не создавались.

Задачи 5.3, 6.3, 7.3, 8.1, ручная доступность и окончательная приёмка остаются
открытыми. Этот отчёт не является подтверждением готовности store-релизов.
