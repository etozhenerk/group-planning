# API первого рабочего среза

Дополнение этапа 10b: [контракт списка приглашений](invitations-tab.md#api).
`GET /api/v1/invitations` возвращает только текущие собственные ответы `maybe`
и публичные preview; прежний список встреч и права чата остаются прежними.

20 октября 2026 года: на первом этапе сервер использует memory-адаптер. Данные
и будущие сессии сбрасываются при перезапуске; API-контракт от этого не меняется.

Часть [технического плана](design.md). Машинный контракт находится в
[contracts/openapi.yaml](../../../contracts/openapi.yaml), примеры и проверки —
в [contracts/README.md](../../../contracts/README.md). Таблицы ниже задают
поведение первого среза. Сейчас зарегистрированы только GET /healthz и
анонимный GET /api/v1/invitations/{token} и пять маршрутов входа/сессий.
Операции встреч ещё не реализованы; OAuth выключен без конфигурации
по [инструкции](../../../backend/docs/auth.md), реальный вход пока не проверен.
Preview пока возвращает my_rsvp: null и my_rsvp_revision: "0";
собственный ответ после входа добавляется с задачей 4.3.

## Общие правила

- HTTPS, HTTP/JSON, `/api/v1`, `snake_case`, UUID в виде строк.
- Время — RFC 3339 с offset/UTC; у встречи отдельно IANA `timezone`.
  Номера sequence/revision передаются десятичными строками без потери точности JS.
- Отсутствующее необязательное значение обозначается явно `null`, если поле
  входит в DTO; дополнительные поля клиент пропускает. Пустой массив отличается от ошибки.
- Авторизованные web-запросы используют cookie + CSRF для мутаций;
  мобильные — Bearer. Эти два способа не смешиваются в одном запросе.
- Неизвестные поля, повторяющиеся имена, неверный регистр имени поля и несколько
  JSON-значений в теле отклоняются с 400; ошибки семантики обрабатывает операция.
- ID пользователя/автора берётся из сессии. Клиент не выбирает его в теле операции.
- Ошибка — `{ "error": { "code": "…", "field_errors": {}, "request_id": "…" } }`.
  Клиент показывает согласованный текст по code, не сырой стек/текст SQL.
- Коды HTTP: 400 — формат запроса; 401 — нет/истекла сессия; 403 — нет права;
  404 — ресурс недоступен; 405 — метод не поддержан; 409 — конфликт ревизии/ключа;
  413 — тело больше 64 KiB; 415 — нужен application/json; 422 — ошибка полей;
  429 — ограничение запросов; 5xx — временный/внутренний сбой.
  Для недоступной публичной ссылки — одинаковый 404 без сведений о встрече.
- Ответы с приватными данными и приглашениями не кешируются общими proxy;
  токены, cookie и URL приглашения не попадают в access/application logs.

## Авторизация

Последовательность — в [auth.md](auth.md).

| Метод и путь | Вход | Успех |
| --- | --- | --- |
| `POST /auth/yandex/start` | `client_kind`, типизированный `return_context`; для native `app_challenge` | `attempt_id`, `authorization_url`, `expires_at`; для web — cookie привязки. |
| `GET /auth/yandex/callback` | Provider code/state либо provider error | Проверка и редирект web / одноразового кода native, без RSVP. |
| `POST /auth/mobile/exchange` | `attempt_id`, `handoff_code`, `app_verifier` | Собственный `session_token`, `expires_at`, безопасный контекст возврата. |
| `GET /me` | Собственная сессия | `user: {id, display_name}`, срок сессии; web CSRF-token. |
| `POST /auth/logout` | Собственная сессия, CSRF для web | 204 и отзыв текущей сессии. |

Контекст возврата имеет вид `{kind: "home"}` либо
`{kind: "invitation", token: "…"}`. Сервер проверяет действительность ссылки
и создаёт разрешённый локальный маршрут; внешние URL не принимаются.
Нельзя получить данные профиля/сессию только по `attempt_id`.

## Встречи и приглашения

| Метод и путь | Доступ | Результат |
| --- | --- | --- |
| `POST /meetings` | Сессия | 201: `Meeting`, собственная роль, `invitation_url`. |
| `GET /meetings?cursor=…&limit=…` | Сессия | Свои созданные + текущие `going`, страница `MeetingSummary`, следующий cursor. |
| `GET /meetings/{id}` | Организатор / текущий `going` | `Meeting` и собственный ответ. |
| `PATCH /meetings/{id}` | Организатор | Обновлённая встреча; обязательна ожидаемая `revision`. |
| `GET /meetings/{id}/invitation` | Организатор | Та же ссылка для повторного Share. |
| `GET /invitations/{token}` | Обладатель ссылки | Только `InvitationPreview`; с сессией — также собственный ответ. |
| `PUT /invitations/{token}/rsvp` | Сессия + ссылка | Сохранённый `Rsvp`, доступ к чату и текущая ревизия встречи. |
| `PUT /meetings/{id}/rsvp` | Свой ранее сохранённый ответ | Изменение своего ответа без повторного получения ссылки. |
| `GET /meetings/{id}/participants` | Организатор / текущий `going` | Организатор, профиль и ответ каждого ответившего; никто без ответа не выдумывается. |

Оба PUT вызывают одну прикладную операцию. Встречи `maybe/not_going` не
включаются в личный список по существующей спецификации; сохранённый ответ
остаётся виден при повторном открытии приглашения. Человек, снявший `going`,
попадает на подтверждение своего ответа; чат и список участников закрываются.

Начальное `GET /meetings` сортирует по времени и ID с устойчивым cursor.
Деление на предстоящие/прошедшие и диапазон календаря запланированы ниже
в разделе «Календарь: расширение API этапа 9». Продуктовая граница согласована
21.10.2026; новые параметры пока не реализованы. Первый список не выдаёт произвольную
классификацию за готовую реализацию спецификации `personal-meetings` целиком.

`Meeting`: `id`, `organizer_id`, `title`, `description`, `starts_at`,
`timezone`, `place`, `cover_url: null` на первом срезе, `participant_count`,
`revision`, `my_rsvp`, `my_rsvp_revision`, `created_at`.
`starts_at` в ответах nullable с первого контракта, чтобы будущая встреча
с выбором даты не ломала старый клиент. Клиент показывает отсутствие итоговой
даты, а не подставляет сегодня. Создание первого среза по-прежнему требует
назначенного времени. Этап 10 ниже расширяет контракт полем `starts_on` и
необязательным временем; это описание первоначального формата, а не запрет
создания без часа в новом API.
`MeetingSummary` содержит только нужные списку поля, без сообщений/токенов.
`InvitationPreview` содержит ID встречи, название, полное публичное описание, дату/зону, место, необязательную
обложку и собственный ответ с его ревизией при входе; переписка, чужие ответы
и профили в него не входят.
Наличие действующей сессии само по себе не расширяет preview до приватных деталей.

Пример создания; дата согласована заранее, время указано по Москве:

```json
{
  "title": "Суббота без спешки",
  "description": null,
  "starts_at": "2026-10-24T19:00:00+03:00",
  "timezone": "Europe/Moscow",
  "place": "Лофт «Квартал»"
}
```

Предлагаемые ограничения первого контракта: название 1–120 символов после
обрезки внешних пробелов; описание до 4000; место до 500; сообщение 1–4000.
Они проверяются одинаково на сервере и клиентах. Это параметры технического
предложения, не отдельно подтверждённые продуктовые лимиты. Формат места
в первом срезе — текст; поля карты/геокодера не добавляются автоматически.

PUT RSVP принимает `answer: going|maybe|not_going` и `expected_revision`.
При первом ответе revision равна `"0"`. Последующие ответы используют полученную
ревизию; устаревшее значение возвращает `409 rsvp_revision_conflict` и текущий
собственный ответ, не переписывая более новый выбор со второго устройства.
Успех — `200 {meeting_id, rsvp, rsvp_revision, can_access_feed, meeting_revision}`.
Ошибка не выдаёт `can_access_feed: true`. В `409 current_response` собственный
ответ может быть `null`, если человек ещё не отвечал (`rsvp_revision: "0"`).
Для такого снимка используется RsvpSnapshot; успешный RsvpResult всегда
содержит один из трёх ответов. После конфликта клиент перечитывает состояние;
снимок ошибки не служит разрешением на чат. Повтор того же ответа без нового
изменения возвращает текущее состояние, не добавляя событие присоединения.
Даже для повтора старого успешного запроса `rsvp` и `can_access_feed`
определяются по текущему состоянию, а не по когда-то сохранённому разрешению.

PATCH принимает изменяемые поля и `expected_revision`; не принимает
`organizer_id`, счётчик участников, системные даты или записи ленты.
При конфликте клиент получает текущие данные для повторного решения, а не
автоматически отправляет старую форму поверх них.

## Лента и сообщение

| Метод и путь | Доступ | Результат |
| --- | --- | --- |
| `GET /meetings/{id}/feed?limit=50` | Организатор / текущий `going` | Последняя страница в порядке возрастания sequence. |
| `GET /meetings/{id}/feed?after_sequence=…&limit=50` | Тот же | Новые записи строго после курсора; ascending, `has_more`. |
| `GET /meetings/{id}/feed?before_sequence=…&limit=50` | Тот же | Ближайшие более ранние записи; результат ascending, `has_more`. |
| `POST /meetings/{id}/messages` | Организатор / текущий `going` | 201: подтверждённая запись сообщения. |

`after_sequence` и `before_sequence` взаимно исключают друг друга. Limit 1–100.
При `has_more` клиент догружает оставшиеся записи до следующего интервала опроса;
курсором становится последняя реально полученная sequence. `latest_sequence`
из метаданных не заменяет этот курсор: в ответ могли попасть не все записи.

Страница содержит `entries`, `has_more`, `meeting_revision`,
`participant_count`, `my_rsvp`, `my_rsvp_revision`, `latest_sequence`.
Метаданные и записи читаются в согласованном snapshot. При изменении
`meeting_revision` клиент перечитывает детали; состав обновляет отдельным запросом
при открытом списке людей. При потере доступа — 403 без приватного payload.

Запись: `id`, `meeting_id`, `sequence`, `kind`, `payload_version`,
`actor: {id, display_name}`, `occurred_at`, `payload`, `client_request_id: null|string`.
В первом срезе kind: `meeting_created`, `meeting_updated`, `participant_joined`,
`participant_left`, `rsvp_changed`, `message`. Текст сообщения — обычный текст,
не доверенный HTML. Payload события хранит конкретное изменение на тот момент.
Будущие опросы/задачи имеют предметные типы, а не универсальную схему UI.

POST сообщения принимает `{text, client_request_id}`. Сервер отвечает полной
записью; клиент заменяет локальное отправляемое сообщение по client_request_id.
Потерянный ответ не вызывает создание нового ID для повтора.

## Повторы, ревизии и порядок

POST создания, POST сообщения, PATCH настроек и PUT RSVP требуют
`Idempotency-Key` — случайный UUID, постоянный на время одного намерения.
Для сообщения он совпадает с `client_request_id`. Receipt связывает ключ
с пользователем, операцией/ресурсом и хешем нормализованного тела.
Повтор того же тела не повторяет изменение и находит прежний ресурс;
метаданные доступа и собственный RSVP вычисляются заново. Другое тело с тем же ключом —
`409 idempotency_key_reused`. Receipt сохраняется атомарно с операцией
через Store.Update.

Ключ проверяется до сравнения expected_revision для повтора уже сохранённой
операции, но после проверки сессии и текущих прав. Поэтому потеря ответа на
успешный RSVP не становится ложным конфликтом ревизии, а снятая роль не даёт
достать старый приватный ответ из receipt. Клиент не повторяет 4xx вслепую.

Receipts первого среза сохраняются до 30 дней в пределах жизни mock-процесса.
Прикладная запись удаляет истёкшие receipts в своей транзакции; при ошибке
очистка тоже откатывается. Проверка срока не зависит от момента удаления.
Перезапуск сбрасывает и receipts, и сами ресурсы; повтор между перезапусками
не имеет гарантии идемпотентности до подключения постоянного хранилища. У сообщений дополнительно действует
постоянная уникальность `(meeting_id, actor_id, client_request_id)`, у создания —
`(organizer_id, client_request_id)`; ID создания сохраняется в Meeting.
Одинаковое тело после истечения receipt находит прежний ресурс, другое — конфликт.
Для RSVP/настроек устаревшую доставку после TTL останавливает expected_revision;
изменённый выбор пользователя получает новый ключ.

## Приёмка контракта

Общие fixtures покрывают новое приглашение без сессии, все три ответа,
повтор `going`, переход `going → maybe`, чужую попытку редактирования,
истёкшую сессию и поздний повтор сообщения. Серверные тесты доказывают:

1. Preview/ошибка/неавторизованный запрос не раскрывают сообщения и чужие профили.
2. Вход не создаёт RSVP; `maybe/not_going` не открывают чат и не увеличивают состав.
3. RSVP, событие и receipt коммитятся вместе; гонка не создаёт два присоединения.
4. После снятия `going` нельзя читать новые страницы или писать сообщение.
5. Конкурентные commit не теряют записи при догрузке по sequence.
6. Потерянный ответ + повтор не создают вторую встречу или сообщение.

Расширение API следующих этапов начинается с их product/spec/UX условий из
[design.md](design.md). План календаря дополнен после решений 21.10.2026;
правила опроса даты, задачи завершения и отзыва приглашений остаются вне
реализованного контракта.

## Уточнения реализованного первого среза

Организатор всегда учитывается один раз, не имеет гостевого RSVP и получает
403 при попытке ответить на собственное приглашение. Открытие своей ссылки
ничего не меняет. Его выход и передача владения отложены.

Поля title/place нормализуются обрезанием пробелов по краям. Description
сохраняется как передан; null очищает его в PATCH, пропуск сохраняет прежнее
значение. То же различие действует для place. Текст сообщения сохраняется
целиком, включая переносы и пробелы, но не может состоять только из пробелов.
Title, starts_at и timezone в PATCH не принимают null; пустая правка отклоняется.
Мутация без фактического изменения настроек/RSVP не повышает ревизию и не создаёт
событие. Сообщение повышает только sequence, а не meeting_revision.

Личный список сортируется по starts_at и ID, недатированные записи идут в конце.
Cursor — непрозрачная позиция последнего элемента; он не фиксирует весь набор
между запросами. Если настройки времени изменились, клиент обновляет список.
Границы и календарь описаны в плане этапа 9 ниже; действующий контракт первого среза пока их не реализует.
Новая ссылка организатора имеет путь `/i/{token}` на настроенном HTTPS origin.
Токен — 16 случайных байт, 22 символа канонического base64url. Старые
32-байтные токены и `/invitations/{token}` поддерживаются. Публичный HTML
содержит серверные Open Graph/canonical и не требует JavaScript или входа.

## Календарь: расширение API этапа 9

Продуктовые решения 21–22.10.2026; сервер и контракт реализованы в 9.2.
[Проверки и ограничения](calendar-backend-verification.md).
Ниже описаны изменения существующего `GET /api/v1/meetings`.

| Параметр | Поведение |
| --- | --- |
| `period` | Необязательный `upcoming`, `past` или `undated`; без него сохраняется старый общий список |
| `from`, `to` | Пара локальных дат `YYYY-MM-DD`, начало включительно, конец исключительно; только с `upcoming`/`past` |
| `limit`, `cursor` | Прежние пределы 1–100 и непрозрачный курсор; фильтрация предшествует пагинации |

Диапазон — от одного до 42 календарных дней: он покрывает сетку месяца вместе
с соседними днями. Для выбранного дня используются его дата и следующий день.
Это не UTC-интервал: принадлежность вычисляется по дате `starts_at` в поясе
каждой встречи. `period=undated` не принимает диапазон. Одна граница без второй,
невалидная дата, неизвестный/повторный параметр или несовместимое сочетание
возвращают `400 invalid_query`.

`period` отражает сохранённый статус встречи. Задача перехода в `past`
планируется на начало следующего дня по `meeting.timezone`; фоновый обработчик
записывает статус независимо от чтений API. GET не вычисляет и не записывает
новый статус. `starts_at=null` соответствует `undated`.
Согласованы модель отложенных задач и безопасные повторы. Этап 9 использует
мок хранилища и очереди. Все вопросы постоянной БД/очереди перенесены в группу 14
вместе с выбором облака и расчётом стоимости; они не блокируют этот API.
PostgreSQL + River остаются кандидатом для будущего обсуждения.
`upcoming` сортируется по времени начала и ID по возрастанию, `past` — по
убыванию времени и ID. При заданном диапазоне порядок для календаря — по
локальной дате, локальному времени начала и ID по возрастанию; это позволяет
последовательно догружать список дня без пересортировки всех страниц.
Встречи без даты имеют стабильный порядок по ID. Прежний запрос без `period`
сохраняет текущий порядок.

Для запросов с `period` ответ `MeetingsPage` дополнится:

| Поле | Назначение |
| --- | --- |
| `as_of` | Серверное время чтения сохранённого состояния; не запускает переход статуса |
| `counts` | `{upcoming, past, undated}` для всего доступного личного набора, до диапазона и пагинации |
| `days` | Для диапазона: отсортированные `{date, count}` непустых дней выбранного раздела; для запроса без диапазона — `[]` |
| `refresh_after_seconds` | Интервал обновления открытого экрана и повтора после наступившего срока; 5 секунд |
| `next_transition_at` | Плановый срок ближайшей задачи перехода доступной встречи; `null`, если задач нет. Срок не подтверждает её выполнение |

`MeetingSummary` в новых выборках дополнится `local_date` (`YYYY-MM-DD` либо
`null`) и `period`. Раздел берётся из сохранённого серверного статуса;
клиент не переводит встречу по локальным часам. Счётчики `days` не обрезаются
`limit`. Сетка запрашивает
сводку диапазона, список выбранного дня — отдельную выборку со всеми страницами.
Отсутствующие страницы не означают отсутствие событий. Новые клиенты берут
метаданные первой страницы; при обновлении сбрасывают весь набор страниц.

Новый cursor должен учитывать раздел, диапазон и порядок; несовпадение фильтров
остаётся ошибкой `422 validation_failed` с полем `cursor`. Старые cursor для
запроса без фильтров остаются валидными. Каждая страница проверяет текущий доступ,
включая снятый ответ «Приду». Полного snapshot изменяемых данных между запросами
не обещаем; после изменения даты или участия клиент начинает загрузку заново.

Уточнение 22.10.2026: курсор привязан к профилю и отпечатку всего доступного
набора ID/ревизий/статусов/своих RSVP. Если набор изменился, включая фоновый
переход, ответ — `409 calendar_changed`, без приватных данных в ошибке.
Клиент сбрасывает страницы и обновляет список, сохраняя раздел, месяц и день.
Повреждённый курсор или несоответствие профиля/фильтров — `422 validation_failed`.
`as_of` относится к текущему чтению. `refresh_after_seconds=5` задаёт период
обновления открытого экрана и ожидание после уже наступившего `next_transition_at`;
GET никогда не выполняет переход.

Запрос без новых фильтров сохраняет прежнюю схему ответа и семантику, поэтому
старые приложения продолжают работать. Для новых клиентов сервер поставляется
первым. Старый сервер не поддерживает календарь: ошибку новых параметров нельзя
выдавать за пустой месяц.

Первая страница, `counts` и `days` вычисляются в одной read-транзакции mock.
Перед повторным чтением после `next_transition_at`, изменения встречи или
RSVP клиент сбрасывает cursor. Все существующие операции чтения/редактирования/
приглашения/RSVP/отправки сообщений сохраняют права и проверки первого среза.
Фоновый переход не пишет сообщение в ленту и сохраняет действующие права.
Фоновый переход увеличивает `meeting.revision` один раз; версия расписания
меняется только при изменении даты/пояса. Прежние конфликты ревизии сохраняются.

Проверки: граница полуночи и разных поясов; DST; две встречи одного дня;
больше 100 событий диапазона; история в обратном порядке; недатированная встреча;
совпадающие времена; неизменный старый запрос/cursor; запрет чужого доступа,
смена ответа между страницами; полные счётчики при ограниченной странице.

## Уточнение этапа 10: дата без времени и настраиваемые опросы

Правила согласованы 22.10.2026. Дата обязательна, время необязательно.
Большинство — строго больше половины текущих пользователей с доступом к чату:
организатор и `going`. Бот, `maybe/not_going` и их бюллетени не учитываются.
Возвращение к `going` восстанавливает прежний голос. Изменение состава
пересчитывает открытый видимый опрос в той же операции, что и RSVP.

Видимый опрос применяет большинство сразу. Скрытый ждёт закрытия. Из дат с
большинством выбирается максимальное число голосов; равенство лидеров требует
выбора организатора. После применения опрос закрыт навсегда. Одновременно
активен один опрос, включая ожидание выбора организатора. Ручная смена дня
закрывает его; смена времени, названия или места сама по себе не закрывает.
Опрос меняет только день, сохраняет местное время либо его отсутствие и RSVP.

Только уведомления о голосовании отправляются от бота. Обычные системные
события сохраняют прежний вид и исходного человека в `actor`.
Подписка и AI для уведомлений не требуются.
Двухчасовой таймер и подтверждение обычного большинства отменены.

Вкладка «Приглашения» для текущих `maybe` проектируется отдельно в 10b.1.
Она не предоставляет доступ к чату или опросам.

### Техническая подготовка этапа 10 · 22.10.2026

Сервер и машинный OpenAPI реализуют описанный ниже контракт на memory.Store.
Чтение новых полей и интерфейсы клиентов проверяются отдельно в 10.3–10.5;
успешное декодирование старым клиентом не означает поддержку нового сценария.

#### Дата без часа

Добавляем `starts_on: YYYY-MM-DD|null` в детали, список, приглашение и снимки
встречи в событиях. Это календарный день в `timezone`. `starts_at` сохраняет
прежнее назначение: конкретный момент с известным временем либо `null`.
При известном моменте `starts_on` обязан совпадать с его датой в поясе встречи.
Два отсутствующих значения допустимы только при чтении прежней недатированной
записи. Новое создание требует даты явно или через прежний `starts_at`.

Пример нового запроса создания без времени:

```json
{
  "title": "Настолки",
  "starts_on": "2026-10-24",
  "starts_at": null,
  "timezone": "Europe/Moscow"
}
```

- Старое создание с одним `starts_at` принимается: сервер выводит дату в
  указанном поясе. Неверный день, пояс или противоречащие друг другу значения
  отклоняются с ошибкой соответствующего поля.
- Новые клиенты при изменении расписания передают согласованные `starts_on`,
  `starts_at` и `timezone` вместе. PATCH различает отсутствие поля и `null`:
  отсутствие сохраняет значение, явный `starts_at: null` удаляет только время.
  Для удаления часа обязательно передаётся известная `starts_on`; дату
  существующей датированной встречи обнулить нельзя.
- Прежний PATCH с непустым `starts_at` обновляет и календарный день. Изменение
  только пояса у встречи с точным временем сохраняет момент, как сейчас;
  при неизвестном времени сохраняется выбранный календарный день.
- Если передана только другая `starts_on`, а точное время уже задано, запрос
  требует согласованный `starts_at` или явное удаление часа. Сервер не выбирает
  смещение при неоднозначном местном времени за пользователя.
- Внутри `Meeting` день хранится явно. Календарный `local_date` выводится из
  него; `starts_at == null` больше не означает автоматически `undated`.
  `schedule`, календарная выборка, сортировка и snapshots обновляются вместе.
- `past_at` остаётся началом следующего календарного дня в IANA-поясе,
  включая дни смены смещения. Это внутренний срок задачи, а не час встречи.
  Изменение дня/момента/пояса меняет версию расписания. GET остаётся read-only.

Старые DTO всех трёх клиентов уже принимают nullable `starts_at`, но отображают
его как отсутствие даты. Поэтому успешное декодирование не доказывает
корректное отображение новой встречи. Сначала обновляем чтение `starts_on`
во всех клиентах, затем включаем создание без часа. Новый клиент при отсутствии
поля на старом сервере выводит день из `starts_at` и пояса; при двух пустых
значениях сохраняет прежнее состояние «Без даты».
Новые поля запросов нельзя отправлять на старый сервер: его строгий декодер
отклоняет неизвестные поля. Сервер расширяется до включения новых форм.

#### Отправитель и автор действия

Добавляем к записи ленты `sender: {kind, id, display_name}`. `kind` различает
`user` и `bot`; ID бота — стабильный технический UUID, не его отображаемое имя.
`actor` и прежние payload существующих событий сохраняются: это человек,
который создал встречу, изменил её или ответил на приглашение.
Для автоматического результата опроса `actor` — бот, действие не приписывается участнику.

`sender` передаётся у сообщений пользователей, создания карточки опроса и
уведомлений о голосовании. У обычных системных событий поле отсутствует.
Клиенты определяют вид записи по `kind`: сообщения и карточки сохраняют автора,
`date_poll_applied`, `date_poll_no_majority`, `date_poll_choice_required`,
`date_poll_time_required`, `date_poll_cancelled` показываются от бота слева.
Создание встречи, настройки, RSVP и напоминание о времени остаются системными
строками по центру даже при старом `sender.kind=bot`. Неизвестные типы показывают
безопасную заглушку. `actor` сохраняет инициатора действия.
Бот не создаёт RSVP, не входит в roster или знаменатель опроса и не может
использовать пользовательские операции. Переименование не меняет его ID.
Системные события не зависят от AI, подписки и будущих лимитов помощника.

#### Операции опроса

Все пути ниже имеют префикс `/api/v1/meetings/{meeting_id}` и требуют
текущего доступа к чату. Публичное приглашение не содержит опросы или голоса.

| Операция | Назначение |
| --- | --- |
| `POST /date-polls` | Создание с вариантами, пятью настройками и `closes_at`; автор берётся из сессии. |
| `GET /date-polls/{poll_id}` | Персонализированный снимок опроса с собственным выбором и разрешёнными результатами. |
| `PUT /date-polls/{poll_id}/vote` | Полный набор выбранных ID и ожидаемая ревизия собственного голоса. |
| `POST /date-polls/{poll_id}/options` | Добавление варианта, если разрешено настройкой. |
| `POST /date-polls/{poll_id}/resolve` | Выбор организатором одного из лидеров либо явное уточнение неоднозначного местного времени. |

Закрытие по сроку — внутренняя операция, вызванная фоновым обработчиком.
Досрочное закрытие и изменение/удаление опубликованных вариантов не добавлены.
Создание принимает 2–20 различных календарных дат; добавление ограничено теми же
20 вариантами. Даты сортируются по возрастанию. Это защитные ограничения API.
Срок задаётся timestamp со смещением и должен быть в будущем. Даты вариантов
не ограничены будущим, как и обычная форма встречи; несуществующий календарный
день в её поясе отклоняется. Пять настроек неизменны после публикации: несколько
ответов, переголосование и новые варианты включены по умолчанию; анонимность
и скрытие результатов выключены.
Все мутации используют `Idempotency-Key`; повторы сначала проверяют текущий
доступ, затем возвращают разрешённое актуальное представление результата.
Тот же ключ с другим телом — конфликт. Запоздавший голос не открывает закрытый
опрос. Доступ, срок и применимость действия проверяются внутри `Store.Update`.

Снимок содержит ID, автора, настройки, срок, варианты с устойчивыми ID,
собственный выбор и его ревизию, состояние и применённый вариант при наличии.
Количество голосов и чужие профили исключаются на сервере до закрытия скрытого
опроса. В анонимном опросе чужие профили исключаются и после закрытия.
Отсутствующие итоги не подменяются нулями.

Промежуточные голоса не становятся отдельными записями общей ленты. Скрытые
ответы не должны утекать через payload, ревизию публичного опроса, метаданные
ленты, сообщения бота или ответы мутаций. Собственная ревизия не раскрывает
чужие голоса. Клиент обновляет видимую карточку отдельным чтением снимка.

#### Атомарность и фоновое выполнение

Опрос, бюллетени, задача закрытия, перенос встречи и лента принадлежат
`meetings`; HTTP не считает большинство. Мок хранит их через существующий
порт, без новой БД и отдельного сервиса. Публикация опроса и постановка задачи
закрытия выполняются одним `Update`.

После голоса либо изменения RSVP операция пересчитывает текущий допустимый
состав внутри той же транзакции. Для видимого опроса она применяет однозначный
результат с большинством сразу; скрытый ждёт срока. Итог, календарный день,
версия расписания, новая задача перехода в историю и уведомление бота
публикуются вместе. При ошибке всё откатывается.

Обработчик закрытия проверяет актуальное состояние в транзакции. Конкурентный
голос, повторная доставка и старый срок не создают второй перенос или сообщение.
Наступление срока закрывает приём голосов независимо от задержки обработчика;
GET не закрывает опрос. Мок очереди получает повтор, безопасную диагностику
сбоев и сверку просроченных открытых опросов по принципам действующих задач
перехода в историю. В логах нет вариантов, бюллетеней или текста переписки.

#### Проверки до включения интерфейсов

1. Старые запросы/fixtures и чтение новых полей; дата без часа во всех DTO,
   календаре, приглашении и переходе в историю, включая смену смещения UTC.
2. Два одновременных голоса, голос против закрытия, повтор после потерянного
   ответа, гонка RSVP с голосом, откат на ошибке записи уведомления.
3. Запрет для `maybe/not_going`, пересчёт от текущего состава, отсутствие бота
   в знаменателе, сохранение и восстановление прежнего голоса при возврате.
4. Матрица анонимность × скрытые итоги × собственный голос × срок;
   отсутствие утечек через все ответы API и историю.
5. Смена даты обновляет детали, счётчики и календарь; старое расписание не
   переносит встречу в историю. Пользовательский демостенд не перезапускается.

#### Состояния и конфликт местного времени

`open` принимает голоса до `closes_at`. После закрытия фиксируются состав,
бюллетени и лидеры; дальнейший RSVP не меняет исторические цифры.

- `applied`: выбранная дата применена, никаких новых голосов или вариантов.
- `no_majority`: срок закончился, большинства нет, прежняя дата сохранена.
- `awaiting_choice`: несколько лидеров с одинаковым максимальным большинством;
  только организатор выбирает один из них через `resolve`.
- `awaiting_time`: сохранение местного часа невозможно или неоднозначно
  при смене UTC-смещения. Опрос уже не принимает голоса. Дата встречи пока прежняя;
  организатор передаёт выбранный `starts_at` со смещением либо явно `null`.
  Это обработка ошибки времени, а не повторное утверждение большинства.
- `cancelled`: организатор вручную изменил день. Старый результат и задача
  больше не меняют встречу. Отменённый скрытый опрос не раскрывает голоса.

`revision` меняется при добавлении варианта или смене состояния; чужой голос
не меняет её. `my_vote_revision` защищает замену собственного набора вариантов.
Пустой набор снимает прежний голос при разрешённом переголосовании. Клиент
передаёт `expected_revision` и уникальный ключ операции; после конфликта читает
актуальный снимок, сохранив ввод для повторной попытки. `CanVote/CanAddOptions`
в ответе учитывают срок независимо от задержки фоновой задачи.

События `date_poll_created` и итоговые записи содержат `poll_id`. Для карточки
клиент читает отдельный персонализированный снимок; видимая карточка обновляется
с тем же интервалом, что лента. Скрытые цифры и профили передаются как `null`.
Вызов создания/голоса не записывает сырой текст уведомления: клиент формирует
согласованный текст из события и его снимка даты. `meeting_time_unspecified`
публикуется при создании без времени и при явном удалении ранее заданного часа.
Повтор запроса не дублирует уведомление. Если выбран прежний день, текст сообщает
о подтверждённой дате, а не о переносе.

#### Контроль фонового закрытия

Задача хранится внутри опроса и создаётся атомарно с ним. Worker запускается
при старте сервера, обрабатывает просроченные задачи и продолжает по интервалу
действующих настроек очереди. Одна попытка — короткий `Store.Update` без внешнего
I/O; конкурентные обработчики повторно проверяют состояние в транзакции.

При ошибке весь результат откатывается, отдельная операция записывает попытку
и задержку. Повтор после достижения лимита запрещён, сверка его не сбрасывает.
`RetryDatePollClose` — внутренняя операция оператора: обнуляет текущую серию,
сохраняет общее число попыток и учитывает ручной повтор. Публичного HTTP-метода нет.
Сверка восстанавливает отсутствующую задачу открытого опроса, не обходя backoff.
Диагностика сообщает безопасный ID, код ошибки, число упавших задач и наибольшую
просрочку; бюллетеней, адресов и текста чата в ней нет. Перезапуск процесса
теряет данные мока — сохранность реальной очереди проверяется только в группе 14.
