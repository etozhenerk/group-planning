# Вход через Яндекс ID

Часть [технического плана](design.md). Серверная реализация первого среза
добавлена и проверена с fake-provider; [конфигурация и проверки](../../../backend/docs/auth.md).
Для локального запуска подготовлены OAuth-настройки и HTTPS-туннель ngrok.
Пользователь подтвердил настоящий web-вход; состояния интерфейса и результаты
проверок описаны в [auth-web-verification.md](auth-web-verification.md).
Мобильные интеграции отслеживаются отдельно.

## Граница ответственности

Яндекс подтверждает личность; Go-сервер сопоставляет её с профилем Somewhere
и выдаёт собственную отзываемую сессию. Сервер вызывает API информации Яндекса
с `Authorization: OAuth …` и проверяет ответ; присланные клиентом `user_id`,
email или имя не подтверждают личность. Связь задаётся `(yandex, id)`.
Имя берётся из профиля с запасным вариантом login. Первый успешный вход создаёт
один профиль; UNIQUE внешней личности предотвращает дубль при конкурентных входах.

Запрашивается `login:info`; email, телефон и фото для первого среза не нужны.
Провайдер может вернуть дополнительные поля — мы их не сохраняем без потребности.
Аватар без фото показывается инициалами. Яндекс access/refresh tokens не используются для запросов к API Somewhere
и не сохраняются для долгой работы после получения профиля: сессия нашего сервиса живёт отдельно.

## Серверная последовательность web и прежнего mobile handoff

1. Клиент создаёт `AuthAttempt`: тип `web/ios/android`, точка возврата
   `home` либо `invitation`, контекст ссылки и привязка инициатора.
   В ответ получает `attempt_id` и URL начала авторизации.
2. Сервер создаёт случайный `state` и PKCE verifier для обмена с Яндексом.
   `state` — непрозрачная ссылка на попытку, а не JSON с приглашением.
   Время жизни попытки — 10 минут; она одноразовая.
3. В браузере открывается Яндекс OAuth с `response_type=code`, зарегистрированным
   callback, `state` и PKCE `S256` challenge.
4. Серверный callback проверяет `state`, срок и одноразовость; для web также
   cookie привязки, для native привязка проверяется при обмене кода передачи.
   Сервер обменивает code на токен по HTTPS и получает профиль.
   Сетевой обмен с Яндексом идёт вне транзакций встречи.
   Дополнительные параметры провайдера, включая `cid`, игнорируются согласно
   [RFC 6749 §4.1.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2):
   они не участвуют в проверке личности или выборе адреса возврата. Повторные
   параметры и повреждённое URL-кодирование отклоняются; проверки state,
   cookie привязки и PKCE остаются обязательными.
5. После проверки личности сервер находит/создаёт профиль, затем завершает
   соответствующий путь сессии. Вход не пишет RSVP и не добавляет участника.
6. Клиент возвращается к той же встрече и показывает актуальный собственный
   ответ. Без ответа чат закрыт. `Приду` сохраняется отдельным запросом API.

Использование authorization code + PKCE поддержано
[документацией Яндекса](https://yandex.ru/dev/id/doc/ru/codes/code-url).
Отдельный обмен мобильного кода ниже — проектное решение Somewhere, а не
недокументированный метод API Яндекса.

## Web

При старте сервер ставит короткую HttpOnly-cookie привязки попытки.
Callback без совпадающей привязки не выдаёт сессию, даже если `state` существует.
Параллельные попытки различаются по ID; завершение одной не подменяет другую.
Возврат выбирается по сохранённому типизированному контексту; произвольный
внешний `return_url` не принимается.

Успех создаёт новый случайный 256-битный секрет сессии и cookie
`__Host-somewhere_session`: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`,
без `Domain`. Клиентский JavaScript не получает секрет. После callback
перенаправление убирает code/state из рабочего адреса; на auth-ответах
`Cache-Control: no-store` и `Referrer-Policy: no-referrer`.

Web и API доступны с одного origin; в разработке используется proxy.
Реальный web-вход проверяется через один HTTPS origin для SPA и API: cookie
на localhost не должна ожидаться в callback другого домена. До появления сессии
web-start проверяет Origin и создаёт привязку попытки. Для изменяющих запросов
с сессией сервер проверяет точный Origin и CSRF-токен, полученный с этой сессией. CORS с произвольным origin и credentials
не включается. OAuth callback — исключение с отдельной проверкой state/binding.

## iOS и Android

Новые сборки используют официальный LoginSDK для iOS/Android. Он выбирает
установленное приложение Яндекса или собственный веб-сценарий. Конфигурация
содержит публичный Client ID, Bundle ID/App ID и Android package/fingerprint;
секрет OAuth в приложение не включается.

1. Приложение создаёт attempt через `/auth/yandex/start` с `client_kind` и S256
   challenge случайного app verifier; сохраняет attempt/verifier/контекст защищённо.
   URL из ответа используется только прежними клиентами; SDK запускается своим API.
2. LoginSDK выполняет авторизацию и возвращает OAuth-токен. Отмена оставляет
   исходный экран; ошибка допускает новый вход без потери приглашения.
3. Приложение отправляет `attempt_id`, `app_verifier`, `oauth_token` в
   `POST /api/v1/auth/mobile/sdk/exchange`. Сервер погашает attempt, проверяет
   токен через `https://login.yandex.ru/info?format=json`, включая `client_id`.
4. Проверенный `yandex:id` соответствует тому же профилю, что и web-вход.
   Сервер выдаёт собственную сессию, не создавая RSVP. Приложение сохраняет её
   перед `/me`; ошибка сети на `/me` допускает повтор без нового входа.

Повтор SDK-обмена, чужой verifier, web-attempt, просроченная попытка и токен
другого OAuth-клиента отклоняются. Старый `/auth/mobile/exchange` и его callback
с handoff остаются доступны для совместимости. SDK-токены не попадают в логи,
обычные настройки, аналитику и серверное хранилище.

Секрет сессии передаётся как `Authorization: Bearer …`. iOS хранит его в Keychain;
Android — в приватном файле, зашифрованном ключом Android Keystore. В URL,
обычных настройках, логах и аналитике секретов нет. При уходе приложения в фон
сохраняется минимальный контекст попытки в защищённом хранилище до её истечения.

Для обычных приглашений используются HTTPS-ссылки с браузерным запасным путём.
Universal Links/App Links привязываются к выбранному домену и проверенным
идентификаторам приложений. Без установленного приложения ссылка открывает web.
Callback входа регистрируется отдельно от маршрута обычного приглашения.

## Хранение и срок сессии

В серверном адаптере хранится хеш случайного секрета, пользователь, тип клиента,
время окончания и отзыва. Временный memory-адаптер модуля identity
теряет профили, попытки и сессии при перезапуске: потребуется повторный вход.
Memory-адаптеры встреч и identity раздельны; HTTP-сервер и вход/сессии добавлены.
Операции встреч и локальный web-вход с Яндексом реализованы; реальные мобильные
циклы остаются в задачах 6.3/7.3.
Начальный абсолютный срок — 30 дней в пределах жизни процесса, настраиваемый
параметр сервера. Первый срез обходится без JWT и refresh-цепочки:
истёкшая сессия требует нового входа с сохранением приглашения.

`POST /auth/logout` отзывает текущую сессию и удаляет cookie/локальный секрет.
401 очищает приватный кеш клиента и предлагает войти; 403 на встрече закрывает
разговор, но не завершает действительную сессию всего сервиса. При обычном
logout приватный кеш очищается. Черновик сообщения не отправляется автоматически
от другого профиля после повторного входа.

`InvitationLink.token` хранится сервером для повторной выдачи ссылки организатору.
Он даёт доступ к публичной карточке и возможности ответить после входа;
его нельзя публиковать в логах. Контекст ссылки и PKCE-данные попытки —
короткоживущие чувствительные данные, удаляемые после завершения/истечения.
Секрет сессии и одноразовый код передачи хранятся только в виде хешей.

## Отмена, ошибки и проверка

- Отмена в браузере/системном окне оставляет исходное приглашение и не создаёт RSVP.
- Неверный, истёкший или повторный state/code не выдаёт сессию; попытку можно начать заново.
- Сбой API Яндекса не создаёт частично подтверждённый профиль/вход.
- Изменение приглашения во время входа не возвращает устаревшие детали:
  после входа они запрашиваются снова. Недоступная ссылка показывает своё состояние.
- Callback не принимает внешний URL возврата; пользовательские строки ошибок
  провайдера не вставляются в HTML и не показываются как доверенный код.
- Проверки включают подмену state/verifier, повтор callback/exchange, два
  одновременных первых входа, отмену и восстановление приглашения, истечение
  собственной сессии и реальный цикл на web/iOS/Android.

Для интеграционных тестов нужен отдельный fake-provider в тестовой конфигурации.
Ни dev-user header, ни пароль обхода Яндекса не должны работать в production.

Перед интеграцией нужны зарегистрированный Яндекс OAuth client, минимальный
scope, HTTPS callback и конфигурация мобильного возврата. Client secret
расположен только на сервере и не попадает в Git или сборки приложений.
Этот план не создаёт OAuth-приложение и не требует передачи секрета в чат.
