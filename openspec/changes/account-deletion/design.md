# Design

## Context

Мотивация и границы — [proposal.md](proposal.md), экраны и тексты —
[UX v1](ux.md). Сейчас identity и meetings используют независимые транзакции.
В memory это разные gates, в PostgreSQL — разные advisory locks одной БД.
Связанные таблицы не имеют ON DELETE CASCADE. В RSVP хранится последнее время
ответа; первое вступление достоверно сохраняется в упорядоченной ленте.
Имя есть не только в identity, но и в FeedEntry.ActorName, авторах/голосах
опросов и авторах/исполнителях задач.

## Goals / Non-Goals

**Goals:** атомарная операция между двумя областями; отсутствие записей от
удалённого пользователя после commit; безопасный повтор при отозванной сессии;
совместимость прежних клиентов и стандартных событий ленты.

**Non-Goals:** модерация, удаление аккаунта Яндекса, распознавание личных данных
в свободном тексте, деплой, store upload, изменение обычного выхода из аккаунта.

## Decisions

### Граница атомарной операции

Небольшой координатор `accounts` вызывает узкие прикладные операции identity
и meetings. Он не получает их Store/Writer и не изменяет чужие модели.
Composition root server связывает его с техническим Unit of Work двух хранилищ:
адаптер создаёт transaction-bound stores, server строит на них те же сервисы.
Все операции короткие, без сетевых вызовов внутри транзакции.

Memory захватывает identity, затем meetings, работает с копиями и публикует
обе только после успеха и проверки context. PostgreSQL берёт те же два locks
в том же порядке и использует один pgx.Tx. Обычные операции берут только свой
lock. Ошибка, отмена и panic откатывают весь результат. Раздельные commit или
очередь удаления отвергнуты: они оставляли бы частично обработанные встречи.

### Identity и повторы

Новый `DELETE /api/v1/me` требует `X-Deletion-Token`: канонические 32 случайных
байта base64url, созданные и сохранённые клиентом до первого запроса. Первое
выполнение проверяет актуальную сессию и web Origin/CSRF внутри транзакции.
После commit возвращает 204 и удаляет web-cookie. Только SHA-256 ключа и тип
клиента сохраняются на 24 часа как квитанция. Повтор по этой квитанции возвращает
204 без сессии (для web всё равно требуется свой Origin), не раскрывает профиль
и не затрагивает новый аккаунт. Квитанция не содержит user ID или provider subject.
401 без квитанции не трактуется как подтверждение удаления.

Удаляются профиль, provider mapping, все сессии и связанные выданные handoff.
Для provider subject сохраняется короткая SHA-256 метка момента удаления
на срок живущих попыток входа (10 минут): callback/SDK не создаёт профиль из
попытки, начатой до удаления. Поздний новый вход разрешён. Очистка identity
удаляет истёкшие квитанции и метки. Сырой subject в этих метках не хранится.

### Встречи и конкурентность

В каждом сохранённом собрании текущие going-кандидаты сортируются по первому
`participant_joined` в ленте; fallback для технически неполных старых записей —
RSVP.UpdatedAt и UserID. Удаляемый организатор заменяется первым кандидатом;
Meeting.Revision увеличивается. При отсутствии кандидата DeleteMeeting явно
удаляет все связанные записи и индексы, включая отложенные задания и квитанции
операций этой встречи. Ответ удаляемого человека удаляется.

Opaque user ID остаётся только как обезличенная ссылка истории и tombstone
для запрета старых in-flight запросов; имя/связь с провайдером удаляются.
Любая пользовательская мутация проверяет tombstone внутри meetings.Update,
включая создание встречи и RSVP. Чтения проверяют доступ по актуальному составу.
Missing-профиль исторического ID отображается как «Удалённый аккаунт».

Открытые голоса удаляются; дата пересчитывается как при выходе участника.
Закрытые ballots/FinalEligible сохраняют результат с обезличенным именем.
Предложенная удаляемому адресату или принятая им задача отменяется через те же
правила состояний и стандартное событие отмены. Авторство других задач меняет
имя, но не действия других людей. Тексты сообщений/названий не редактируются.
Существующие kind/payload ленты сохраняются для совместимости старых клиентов.

### Клиенты

Web: `features/delete-account` владеет подтверждением и запросом; storage ключа
и API принадлежат entities/session. Восстановление незавершённой операции выше
SessionGate. После 204 использовать общую очистку сессии/доступа/черновиков,
затем публичный экран с результатом; прежний logout остаётся отдельным действием.
iOS: отдельные View/owner, операция SessionStore и ключ в защищённом credential
storage; корневой экран выбирает состояние удаления раньше приватной навигации.
Android: отдельные Compose-компоненты, состояние ViewModel, операция repository,
ключ в encrypted credential storage. Перезапуск сохраняет возможность повтора.
Во всех клиентах ordinary 401 не подменяет подтверждённый результат удаления.

### Контракт и совместимость

DELETE добавляется к существующему GET /me; новые ошибки используют прежний
error envelope. Нет новой обязательной формы старых ответов. Старые mobile
клиенты получают обычный 401 на отозванные сессии и стандартные профили/события
в сохранённых встречах. Проверки включают fixtures и реальный HTTP, затем
сборки/тесты трёх клиентов. Новые приложения требуют новый сервер только
для самой кнопки удаления; старый сервер должен давать видимую ошибку операции.

## Risks / Trade-offs

- Большое число встреч → одна транзакция дороже обычной операции; для текущего
  MVP это сознательный выбор целостности. Timeout откатывает всё и допускает повтор.
- Личные данные в тексте сообщения → UI явно обещает удаление профиля, имя
  скрывается в структурированных полях; свободный текст не анализируется.
- Потеря ключа/истечение 24 часов → не объявлять успех на основании одного 401;
  показывать необходимость новой проверки сессии.
- Недоступность облачной тестовой БД → SQL-код и тесты подготовить, результат
  интеграционного прогона отмечать отдельно; не поднимать локальную БД/Docker.
- Произвольное число устройств → отзыв выполняется на сервере, очистка чужих
  локальных данных происходит при следующей проверке сессии, не по push.

## Migration Plan

Добавить следующую версионную SQL-миграцию с tombstones, deletion receipts и
короткими subject fences. Не переписывать уже применённый 001_initial.sql.
Обновить проверку версии/контрольных сумм на последовательность миграций.
Облачное применение выполняет отдельная задача деплоя; в этой работе оно
не запускается. Старый сервер с точной проверкой схемы не поддерживает новую
версию: откат требует совместимого серверного артефакта, не удаления квитанций.
Удалённые пользователем данные программным откатом не восстанавливаются.
