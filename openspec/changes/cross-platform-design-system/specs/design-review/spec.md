# Spec Delta

## Purpose

Обеспечивает независимую проверку реализованных экранов somewhere
по утверждённым макетам и дизайн-системе до завершения UI-задачи.

## ADDED Requirements

### Requirement: Independent screen review
После реализации экрана и его состояний процесс MUST запускать независимого
субагента, проверяющего визуальное соответствие и взаимодействия на заявленных
платформах. Ревьюер MUST не изменять приложение или эталоны для получения pass.

#### Scenario: Mismatch
- **WHEN** проверяющий обнаружил неверную композицию или поведение
- **THEN** он возвращает needs-fixes с состоянием, платформой, правилом и доказательством; исполнитель исправляет и повторяет проверку

### Requirement: Complete current evidence
Отчёт MUST связывать результат с входными UI-исходниками, версией системы,
эталонами и файлами доказательств. Пропущенная платформа, отсутствующие файлы,
изменение входов или доказательств MUST запрещать зачёт готовности.

#### Scenario: Stale report
- **WHEN** после pass изменился компонент, токен, контракт или эталон
- **THEN** проверка готовности отклоняет старый отчёт

#### Scenario: Missing platform
- **WHEN** манифест включает Android, а доказательства есть только для web и iOS
- **THEN** задача не получает общий pass

### Requirement: Honest blocked state
При недоступных инструментах или несопоставимых данных процесс MUST сохранять
blocked с причиной; сохранённый скриншот сам по себе MUST не означать pass.
Явная пауза пользователя MUST останавливать работу без принудительного продолжения.

#### Scenario: Different fixture
- **WHEN** эталон и фактический экран показывают разные данные
- **THEN** ревью различает подтверждённые структурные ошибки и непроверенное пиксельное соответствие

#### Scenario: User pause
- **WHEN** пользователь просит приостановить работу при незавершённом ревью
- **THEN** процесс сохраняет незавершённость и позволяет закончить ответ без ложного pass или бесконечного цикла

### Requirement: Workflow enforcement
Новые UI-изменения MUST объявлять затронутые экраны и состояния до реализации.
Проверка завершения MUST требовать актуальный pass; CI MUST проверять структуру,
генерацию и актуальность заявленного завершения. Непроверенный checkpoint
MUST оставаться возможным без представления его как принятого интерфейса.

#### Scenario: Checkpoint versus completion
- **WHEN** сохранён промежуточный коммит с незавершённым экраном
- **THEN** структурная проверка допускает checkpoint, но проверка готовности и выпуск затронутого UI требуют pass

### Requirement: Review after a design revision
При смене согласованного дизайна процесс MUST сохранить прежние отчёты и evidence
с исходными hash, заново открыть задачи с утратившей актуальность приёмкой и
повторить независимое ревью после реализации новой ревизии. Старые результаты
MUST не переноситься в новый отчёт без новой проверки. Начатое по отменённой
ревизии ревью MUST не подтверждать текущую готовность.

#### Scenario: Completed screen changes
- **WHEN** пользователь меняет дизайн экрана после успешного ревью
- **THEN** его приёмка снова становится незавершённой, manifest возвращается в checkpoint, а закрытие задачи требует свежего независимого pass и design:ready
- **AND** явная пауза пользователя сохраняется до разрешения продолжить

#### Scenario: Design changes during review
- **WHEN** новая подтверждённая коррекция поступает во время работы ревьюера
- **THEN** исполнитель прекращает приёмку по прежней ревизии, публикует новую и после реализации передаёт независимому ревьюеру новый контекст
- **AND** отчёт со старым hash остаётся историческим результатом и не переименовывается в актуальный

#### Scenario: Implementation error does not change authority
- **WHEN** ревью выявляет расхождение приложения с действующим утверждённым макетом без нового решения пользователя
- **THEN** исполнитель исправляет приложение и повторяет ревью, сохраняя действующий эталон
