# Design

## Context

См. [proposal](proposal.md) и [UX](ux.md). В актуальном main есть отдельные
палитры CSS/Swift/Compose, HTML-макеты и screenshot runners. Основа v0.7
устарела; Playwright сохраняет пары, но не делает pixel assertion. Уточнения
26.10.2026 отменяют часть старых оболочек. Реализация экранов на паузе.

## Goals / Non-Goals

**Goals:** воспроизводимая публикация общих решений, платформенные адаптеры,
контроль новых значений, независимое ревью и проверяемая актуальность результатов.

**Non-Goals:** замена React/SwiftUI/Compose, новый визуальный стиль, массовая
переделка экранов, автоматическое утверждение golden images, изменения API,
облака или юридических документов. CI не заменяет визуальное суждение ревьюера.

## Decisions

1. `design-system/tokens.json` использует проверяемое подмножество DTCG:
   явные типы, sRGB, размеры px, длительности ms, алиасы. Style Dictionary
   закрепляется точной версией после пробы. Собственные форматы создают CSS/TS,
   SwiftUI и Compose; px преобразуются в pt/dp, текст — в масштабируемый sp/стиль.
   JSON остаётся переносимым; не заявляем полную поддержку DTCG 2025.10.
2. В `design-system` хранятся версия, каталог, реестр эталонов и ограничения.
   Документы компонентов/паттернов связывают роли токенов с композицией,
   состояниями и реализацией. Общая база не превращается в web-only UI kit.
3. Проверка ручных значений использует явный исходный инвентарь старых строк.
   Новые литералы запрещены; перенос строки в другой файл не наследует исключение.
   Лексический контроль не является полноценным анализом произвольных выражений:
   вычисляемые обходы проверяет ревью. Сгенерированные файлы проверяются побайтно.
4. UI-изменение содержит `design-manifest.json`: экраны/состояния/платформы,
   входные каталоги, эталоны, contracts, статус работы. Отдельный отчёт ревью
   содержит SHA-256 входов и файлов evidence, окружение, наблюдения и результат
   каждой пары платформа/состояние. Hash не включает сам отчёт или tasks.md,
   чтобы избежать самоссылки. Неизвестные поля и неполное покрытие отклоняются.
5. Навык публикации читает подтверждение, обновляет систему/версию, генерирует
   адаптеры и регистрирует manifest. Навык ревью запускает независимого субагента
   с read-only поручением. Ревьюер может писать только отчёт/evidence; родитель
   исправляет код. Без доступного субагента или инструмента проверки — blocked.
6. OpenSpec остаётся `spec-driven`; config/AGENTS задают обязательный вызов
   навыков. Сгенерированные навыки OpenSpec не редактируются вручную.
   Проверка `design:check` входит в CI; `design:ready` — перед закрытием UI-задач
   и выпуском. Состояние checkpoint допускает неполный отчёт, complete — нет.
7. Stop hook проверяет только явно зарегистрированный завершённый UI-этап.
   Он не запускает субагента сам: возвращает агенту причину продолжить ревью.
   При повторном stop-hook продолжении или явной паузе не зацикливает работу.
   Файл hooks — опциональная локальная интеграция: требуется поддержка клиента
   и доверие точной конфигурации, автоматическое включение не предполагается.
8. Pixel regression: существующие runners остаются основой, одинаковые fixture,
   шрифты, время и viewport обязательны. Playwright toHaveScreenshot применяется
   к утверждённым web baselines; Swift Snapshot Testing/Roborazzi — кандидаты
   следующей миграции компонентов после проверки совместимости. В этом изменении
   не добавляем библиотеки в приостановленные native UI-тесты ради формального шага.
9. Коррекция дизайна во время apply/review возвращает затронутую работу к
   публикации по [циклу ревизии](../../../docs/design/revisions.md). Агент
   обновляет сам макет и проверяет его отображение, согласует только оставшиеся
   открытыми решения, синхронизирует UX/specs/design/tasks и публикует изменение
   через `design-system-publish`. Существующие manifest обновляются; прошлые
   отчёты и evidence сохраняются с исходными hash. Задачи с утратившей актуальность
   приёмкой открываются заново. После разрешённой реализации обязателен новый
   `design-review` с субагентом и `design:ready`. Ошибка реализации исправляется
   по действующему дизайну; переписывать эталон ради устранения ошибки нельзя.

## Risks / Trade-offs

- Несогласованные legacy-значения → исходный инвентарь долга и постепенное
  удаление; каталог не утверждает каждую существующую строку автоматически.
- Ложный pass от формального заполнения JSON → независимый агент, реальные
  evidence, негативные тесты, понятное различие валидации и визуального ревью.
- Исходные screenshots с другими fixtures → blocked для точного сравнения,
  отдельно подтверждённые наблюдения; не обновлять эталон из actual.
- Смена источника после ревью → hash включает исходники, реестр, contracts,
  генератор и эталоны; любое изменение инвалидирует результат.
- CI после push в main не отменяет коммит → локальная проверка перед завершением
  и отдельный gate выпуска, без навязывания PR-процесса.

## Migration Plan

Сначала источник/публикация, затем адаптеры и проверка, навыки/SDD/CI, пилот
независимого ревью на существующих материалах. Полный перенос UI происходит
в задачах соответствующих изменений с новым manifest; старые незавершённые
изменения явно зарегистрированы как legacy. Откат — обычный revert связанного
коммита источника и генерации, без ручного изменения generated-файлов.
