# Spec Delta

## Purpose

Находить неожиданные проблемы работающего приложения через независимое
исследование пользовательского опыта без чтения приёмочных тест-кейсов.

## ADDED Requirements

### Requirement: Explicit exploration request
Процесс MUST запускать исследование только по явному запросу пользователя
на `exploratory-test` или независимый поиск неожиданных проблем без кейсов.
Автоматический выбор навыка MUST быть отключён. Обычная проверка фичи,
релиза, изменение кода и создание самого навыка MUST не запускать исследование.

#### Scenario: Routine verification
- **WHEN** пользователь просит проверить готовую фичу или подготовить релиз
- **THEN** применяются соответствующие обязательные проверки без exploratory-test

#### Scenario: Explicit invocation
- **WHEN** пользователь просит исследовать приложение как новый пользователь без тест-кейсов
- **THEN** основной агент готовит ограниченный бриф и независимую сессию

### Requirement: Unbiased runtime session
Исследователь MUST работать в отдельном контексте без истории разработки,
кейсов, specs, макетов, исходников, diff и прежних баг-репортов. Он получает
только назначение приложения, адрес/сборку, доступ, роли, границы, бюджет,
инструкции инструментов и путь отчёта. При попадании запрещённого контекста
MUST начинаться новая независимая сессия.

#### Scenario: Existing test cases are available
- **WHEN** основной агент имеет доступ к тест-кейсам и известным дефектам
- **THEN** он не передаёт их исследователю и не формирует из них маршрут проверки

#### Scenario: Missing independent runner
- **WHEN** свежий субагент или средство взаимодействия с заявленной платформой недоступны
- **THEN** ограничение записывается как blocked без имитации прохода по исходникам

### Requirement: Adaptive bounded exploration
Исследователь MUST выбирать действия по пользовательской цели и результатам
взаимодействия с работающим интерфейсом, меняя гипотезы по наблюдениям.
Сессия ограничена заявленными платформами, данными, действиями и бюджетом.
Исследователь MUST писать только собственный отчёт/evidence; изменения кода,
ожиданий, автоматическое исправление и сообщения реальным людям не входят в запуск.

#### Scenario: Surprising transition
- **WHEN** пользовательский путь даёт неожиданный результат
- **THEN** исследователь сохраняет наблюдение и уточняет воспроизведение в пределах сессии

#### Scenario: Time or access is exhausted
- **WHEN** закончился бюджет или отдельный путь недоступен
- **THEN** отчёт сохраняет фактическое покрытие, незавершённые области и ограничения

### Requirement: Evidence without finding quota
Отчёт MUST разделять подтверждённые дефекты, нерегулярные наблюдения,
неудобства и вопросы к ожидаемому поведению. Каждая находка содержит действия,
expected/actual, основание ожидания в UI/цели, воспроизводимость, влияние,
уверенность и evidence. Квота ошибок MUST отсутствовать; неудачный повтор
MUST не удалять первоначальное наблюдение.

#### Scenario: Intermittent behavior
- **WHEN** проблема наблюдалась один раз из трёх попыток
- **THEN** отчёт сохраняет 1/3, исходное evidence и неопределённость

#### Scenario: No observed defects
- **WHEN** за отведённую сессию дефекты не обнаружены
- **THEN** отчёт описывает проверенные и непроверенные области без выдуманных находок и гарантии отсутствия ошибок

### Requirement: Separate triage and acceptance
Основной агент MUST сопоставлять находки со specs, кейсами и известными
дефектами только после фиксации независимого отчёта. Исходный отчёт сохраняется,
решения разбора — отдельно. Подтверждённым дефектам назначается регрессионное
покрытие по пирамиде. Исследование MUST не давать функциональный/design pass,
не менять статусы автоматизации и не заменять обязательные gates.

#### Scenario: Documented restriction looks unexpected
- **WHEN** после фиксации отчёта обнаружено согласованное ограничение
- **THEN** разбор объясняет решение отдельно, сохраняя первоначальное наблюдение

#### Scenario: Fix requires implementation
- **WHEN** найдена подтверждённая ошибка
- **THEN** исправление и test-spec выполняются в разрешённой задаче, затем обычная функциональная и при необходимости дизайн-приёмка
