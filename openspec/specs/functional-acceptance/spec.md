# functional-acceptance Specification

## Purpose

Подтверждать работу пользовательской задачи на реальном приложении и API,
связывая независимый проход и доказательства с проверяемым состоянием кода.

## Requirements

### Requirement: Independent functional verification
После реализации пользовательской задачи процесс MUST выполнить подходящие
автотесты и независимый проход новых/изменённых сценариев на работающей сборке.
Основной ручной исполнитель — агент; недоступное действие передаётся человеку
с причиной. Проверяющий MUST не исправлять продукт или ожидания во время приёмки.

#### Scenario: Mockup is not the product
- **WHEN** открыт статический HTML-макет вместо приложения с API
- **THEN** проход не подтверждает функциональную готовность

### Requirement: Complete current run
Прогон MUST фиксировать кейсы, платформы, окружение, сборку, исполнителя,
время, фактический результат и evidence. Пропуск, blocked, failed, отсутствие
доказательств или устаревший контекст MUST запрещать закрытие связанной задачи.

#### Scenario: Changed sources
- **WHEN** после проверки изменились исходники или требования
- **THEN** прежний pass сохраняется в истории и не закрывает новую версию задачи

#### Scenario: Missing device
- **WHEN** для требуемой платформы нет доступного устройства
- **THEN** результат остаётся blocked с причиной, а общий pass не выдаётся

### Requirement: Observable manual procedure
Ручной проход MUST проверять предусловия, выполнить действия, сопоставить
ожидаемое и фактическое поведение, сохранить доказательства и очистить данные.
Ошибка MUST фиксироваться с воспроизведением; независимые кейсы продолжаются,
зависимые получают blocked. Повтор MUST сохранять историю предыдущего результата.

#### Scenario: Persistence or synchronization
- **WHEN** сценарий требует сохранения или передачи данных другому участнику
- **THEN** проверяется повторное открытие или второй аккаунт, а не только появление уведомления об успехе

### Requirement: SDD task gate
Пользовательская задача MUST ссылаться на спецификацию тестирования и текущий
прогон; её завершение требует актуального функционального pass. UI дополнительно
требует независимой дизайн-приёмки. Документационные задачи без продуктового
поведения MUST иметь явную неприменимость пользовательского прохода.

#### Scenario: Checkbox without acceptance
- **WHEN** связанная задача отмечена выполненной без полного актуального прогона
- **THEN** проверка репозитория отклоняет готовность

#### Scenario: Independent tasks in a shared feature plan
- **WHEN** checkpoint-план содержит несколько задач, а закрывается только одна из них
- **THEN** проверка требует все case/platform/environment результаты этой задачи и все обязательные suites исходного плана с актуальными hashes, временем и evidence
- **AND** незавершённые остальные проверки сохраняются в плане и отчёте, готовность всего прогона остаётся false
- **AND** частичная готовность не допускает complete/release и не выдаёт release receipt

#### Scenario: Independent platform acceptance records
- **WHEN** задача принимается параллельно на нескольких платформах
- **THEN** каждая платформа может ссылаться на свой текущий feature-план и результат без переписывания других записей
- **AND** закрытие требует все заявленные case/platform/environment пары и обязательные suites каждого плана; повторные и посторонние платформы отклоняются
