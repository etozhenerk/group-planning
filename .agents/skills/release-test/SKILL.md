# Приёмка релиза

Прочитай [процесс](../../../testing/README.md), [окружения](../../../testing/environments.md)
и [правила выпуска](../../../docs/releases.md). Сначала собери кандидат;
публикация файлов для проверки не означает выкатку пользователям.

1. Зафиксируй реальные файлы артефакта, manifest/SHA256, API origin/конфигурацию,
   поддерживаемые версии клиентов и все обязательные профили releaseProfiles.
   Backend проверяется также с поддерживаемыми клиентами; QA не равен store build.
   Исходники должны соответствовать commit кандидата; source-runners не освобождают
   автоматизированный кейс от ручного прохода точного релизного артефакта.
2. Создай release-план через qa:plan. Все действующие применимые кейсы выбираются
   из каталога; старые функции не исключаются по отсутствию изменений в diff.
3. Выполни обязательные автоматические suites. Передай независимому субагенту
   полный manual-набор и raw-кейсы для прохода по алгоритму feature-test.
   Это явное разрешение делегировать QA; проверяющий не редактирует код/ожидания.
4. Пройди все manual/planned/partial/flaky/quarantined кейсы. Непроверенное,
   skipped/blocked и отсутствующее evidence не дают pass. Разбери ошибки
   обязательных автотестов; ручной успех не отменяет их. Человек нужен только
   для действий, которые агент выполнить не может, с указанием причины.
5. Исправление создаёт новый кандидат и новый прогон; историю сохраняй.
   Перед выкаткой запусти qa:release-ready на текущем каталоге и тех же файлах,
   получи receipt. Не создавай/не редактируй receipt вручную, не меняй artifacts.
6. Сохрани план/результат/evidence/receipt долговременно, без секретов и личных
   данных. Верни готовность либо список блокеров по кейсам/платформам.

Навык не даёт нового разрешения на production/store/внешние сообщения.
При уже разрешённой выкатке продолжай её только после pass, затем smoke-test.
Отсутствующее окружение/аккаунт сохраняет blocked и не позволяет объявить релиз готовым.
