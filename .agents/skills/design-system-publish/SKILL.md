# Публикация дизайна somewhere

Прочитай `docs/design/README.md`, `design-system/README.md`, authority и UX
текущего OpenSpec-изменения. Решение пользователя в разговоре уже является
подтверждением: не проси одобрить то же повторно. Если визуальное изменение
ещё не согласовано, подготовь конкретный макет и запроси только отсутствующее
решение; не публикуй гипотезу как утверждённую.

1. Сопоставь макет и последние коррекции с действующими контрактами. Сохрани
   ревизию эталонов и область отменённых решений. При конфликте более поздняя
   подтверждённая коррекция имеет приоритет над старым PNG/HTML.
2. Повторно используй смысловые роли. Недостающие роли добавь в
   `design-system/tokens.json` вместе с назначением. Платформенную адаптацию
   укажи в `docs/design/platforms.md`/контракте компонента. Не извлекай случайные
   значения из текущей реализации как будто пользователь их утвердил.
3. Обнови `version.json`, `CHANGELOG.md`, `authority.json` и нужные contracts.
   Hash эталона обновляется только из подтверждённого дизайна, никогда из actual
   ради устранения расхождений. Изменённая версия инвалидирует прежние ревью.
4. Запусти `npm run design:generate`, `npm run design:check`, `npm run design:test`.
   Если нужны новые типы токенов, сначала расширь валидатор и платформенные
   форматы с тестами. Не правь generated-файлы вручную.
5. До кода создай `design-manifest.json` внутри изменения по
   `docs/design/review.md`: все экраны, состояния, платформы, реальные входные
   UI-каталоги, fixture/build-конфигурацию, связанные картинки/шрифты, contracts
   и эталоны. Разные формы и viewport фиксируй отдельными состояниями; общего
   `open` для всех действий и `default` для всех web-размеров недостаточно.
   Зарегистрируй его в registry. Не пропускай
   платформу из-за отсутствующего симулятора: она позже получит blocked.
6. Сохрани ссылки в ux/design/tasks; задачи содержат реализацию и отдельную
   независимую проверку на каждой платформе. Передай исполнителю опубликованную
   версию и точный manifest. Публикация дизайна не означает готовности клиента.

Для интерфейсных текстов применяй проектный `product-copy-editor`.
Не переписывай сгенерированные OpenSpec-навыки; порядок задаётся config/AGENTS.
