# Спецификация тестирования

Прочитай [правила](../../../testing/README.md), требования/UX текущего OpenSpec
и существующие кейсы. Новые ожидания выводи из согласованного поведения, не из
текущего кода. Учитывай уже данное решение пользователя.

1. Создай/обнови testing.md: объём, риски, платформы, окружения, ID кейсов,
   нужные автотесты и ручной проход. Для документации без продукта укажи неприменимость.
2. Выбирай минимальный достоверный уровень пирамиды: unit для правил/границ,
   integration для взаимодействий, небольшой E2E-набор для ключевых путей.
   Не навязывай проценты и дублирование комбинаций во всех клиентах.
3. В testing/cases обнови реальные предусловия/шаги/expected/cleanup, source
   и платформы. Новый source добавь в config.sources; инфраструктурные исключения
   должны иметь причину в excludedSources. Сохраняй стабильные ID;
   при смене требования пересмотри кейс до обновления hash. Не скрывай конфликт.
4. Отдельно оцени automation/health каждой платформы. automated требует
   воспроизводимого теста того же уровня, проверенных assertions и регулярного
   runner. Файл/компиляция/разовый проход агентом не доказывают автоматизацию.
5. Зарегистрируй testing-manifest.json с case/platform mapping каждого task ID,
   обоснованными exemptTasks и путями плана/результата
   по схеме scripts/testing/schema.mjs. Незавершённая работа — checkpoint;
   явная пауза — paused. Legacy-запись удаляется при регистрации manifest.
6. Выполни qa:check. При изменении требований/дизайна открой утратившие приёмку
   задачи и запланируй новый feature-test. Старые отчёты не переписывай.

Публикация кейсов не означает, что они пройдены. В пределах разрешённой реализации
продолжай apply; запрос только подготовить план не запускает приложение/деплой.
