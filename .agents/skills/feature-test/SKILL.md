# Функциональная приёмка задачи

Прочитай [процесс](../../../testing/README.md), testing.md, cases и manifest.
Сверь API/UI окружение по [правилам](../../../testing/environments.md).
Запусти подходящие unit/integration и E2E: пирамида не заменяется ручным кликаньем.
Создай feature-план с фактическими сборкой/окружением, актуальным каталогом и ID.

**Поручи независимому субагенту проход работающей фичи.** Это явное поручение
проекта на делегирование. Передай raw requirements/cases, план, URL/сборку,
fixture, доступные инструменты и отдельные пути отчёта/evidence. Не передавай
ожидаемый вердикт или собственное объяснение, почему код должен работать.

Ревьюер не меняет продукт, кейсы или source hash; пишет только отчёт/evidence.
Он проверяет предусловия, проходит действия, сравнивает expected/actual, проверяет
сохранение/второй аккаунт, когда нужно, и очищает собственные данные. Для pass
нужны фактические доказательства; screenshot без действий недостаточен.
Статический макет, исходники и прежние screenshots не являются работающей фичей.

Ошибка → failed с воспроизведением и дефектом. Нет инструмента/доступа → blocked
с конкретной причиной; человеку передаются только недоступные действия.
Зависимые кейсы блокируются, независимые продолжаются. Тестовые обращения
и уведомления направляются только в изолированные тестовые каналы; разрешение
на QA не разрешает сообщения реальным людям. Основной ручной исполнитель — агент.

Родитель проверяет diff ревьюера, исправляет приложение и повторяет независимый
проход. Учитывай изменившийся hash; не переносите старый pass в новый прогон.
До checkbox выполни qa:ready, для UI также design-review/design:ready.
При отсутствии субагента не подменяй независимую приёмку собственной.
Явная пауза прекращает работу и сохраняет незавершённость.
