# Вложения и альбом

API принимает отдельный файл в три этапа: резервирование metadata, бинарная
загрузка, публикация. `client_request_id` сохраняет идентичность файла после
потери ответа; повтор публикации возвращает прежнюю запись. Системные события
не заменяются вложениями. Сообщение с файлом сохраняет `kind: message`, версию 1
и текст «Фото»/имя файла для прежних клиентов; новые получают `attachments`.
Фото чата не попадают в альбом автоматически.

Фото: JPEG/PNG/WebP до 10 MiB; файлы: PDF/plain text/ZIP и эти фото до 20 MiB.
Выбор ограничен 10 элементами, незавершённые резервы — 50 на автора во встрече,
суммарный объём резервов/готовых файлов — 1 GiB на встречу. Лимиты возвращает
`GET /meetings/{id}/media/limits`. Проверяются заявленный и фактический тип,
размер и имя. Сервер декодирует изображения с ограничениями 8192 на сторону и
16 млн пикселей, применяет EXIF orientation и заново кодирует без метаданных.
WebP нормализуется в PNG. Анимация не поддерживается. Декодер WebP — официальный
[`golang.org/x/image/webp` v0.47.0](https://pkg.go.dev/golang.org/x/image/webp).
PDF/ZIP не исполняются и не распаковываются сервером, отдаются как attachment.

Текущие права проверяются на каждом этапе, повторно после записи/чтения bytes.
Публичное приглашение, обложка и Open Graph не раскрывают вложения. Ссылки
относительные и требуют текущую сессию; ответы `no-store`/`nosniff`. Внешний
URL загрузки не принимается. Альбом доступен для сохранённого сервером `past`.
Порядок альбома — время публикации и ID; cursor привязан к конкретной встрече.

## Локальный режим

`memory.Store` хранит metadata, `internal/storage/files` — bytes в отдельном
каталоге `somewhere-media-*` внутри системного временного каталога. Директория
имеет права 0700, файлы 0600; имена состоят из UUID и digest, не из имени клиента.
Обычная остановка сервера удаляет каталог целиком. Аварийная остановка может
оставить каталог до очистки временных файлов ОС; не используйте этот режим
для данных, которые должны пережить перезапуск.

Ежечасно незавершённые резервы старше суток удаляются; неподтверждённые bytes
старше часа без живой ссылки очищаются отдельно. Повтор загрузки обновляет
время bytes, чтобы очистка не удалила файл между проверкой и commit metadata.
Публикация metadata и записи ленты атомарна; файловый I/O идёт вне транзакции.
В unit/HTTP fixtures применяется самостоятельный memory-адаптер bytes.

## Подготовка постоянного режима

Миграция `003_meeting_experience.sql` добавляет metadata, реакции и ограниченные
`bytea`-объекты отдельно от JSON. Runtime PostgreSQL получает именно этот
адаптер и не заменяет его памятью. Удаление встречи каскадно удаляет объекты;
удаление пользователя снимает реакции и обезличивает автора общей истории.
Миграцию применяет отдельная DDL-роль; приложение по-прежнему только проверяет
схему. Резервное копирование должно включать новые таблицы.

До облачного выпуска нужны отдельная проверка миграции/GRANT, сохранности после
рестарта, восстановления backup, миниатюр и квот на реальных объёмах. Бинарник,
поддерживающий только миграции 001–002, не запустится после 003: нельзя обещать
откат заменой файла без совместимого бинарника и проверенной процедуры.
Облачные проверки и выпуск остаются в задачах 7.2–7.3; локальные тесты их не заменяют.

## Сохранение полного альбома

`GET /api/v1/meetings/{id}/memories/snapshot` возвращает все опубликованные
memory-фото одним авторизованным снимком в порядке `created_at/id`:
`{photos: [...], next_cursor: null}`. Мобильный клиент фиксирует этот набор,
скачивает каждый `download_url` последовательно и проверяет актуальность своей
сессии/встречи перед передачей подготовленного пакета системной галерее.
Снимок не создаёт публичных ссылок и не отменяет проверку доступа к каждому фото.

Web отправляет `{}` в `POST /api/v1/meetings/{id}/memories/exports` с
`Idempotency-Key`, а для cookie-сессии также Origin/CSRF. Ответ 202 содержит
`id`, `state`, `count`, `expires_at`. Повтор ключа возвращает удерживаемую
операцию. `GET .../exports/{id}` возвращает preparing/ready/failed;
`DELETE .../exports/{id}` отменяет подготовку/выдачу и удаляет файл.
После ready браузер открывает `GET .../exports/{id}/download` штатным скачиванием.
Ответ — `application/zip`, `Content-Disposition: attachment`, полный
`Content-Length`. Диапазоны игнорируются; прерванное/повторное скачивание требует
новой подготовки. Факт передачи браузеру не подтверждает запись на диск.

`internal/albumexport` получает только прикладные операции meetings.
Подготовка идёт последовательно, удерживает bytes одного фото до 10 MiB и
записывает ZIP Store без повторного преобразования фотографий. Качество и
ориентация соответствуют нормализованным серверным bytes, а не первоначальному
файлу до загрузки. Имена очищаются от путей/управляющих символов и получают
уникальный порядковый префикс. Новые фото после старта не включаются.

На процесс разрешены два удерживаемых архива, на пользователя один.
Фото ограничены существующей квотой 1 GiB, запись ZIP дополнительно ограничена
этой квотой плюс 2048 bytes на фото и 1024 bytes на каталог/ZIP64.
Metadata снимка и ZIP-каталог занимают память пропорционально числу фото;
содержимое всего альбома в память не собирается. Каталог `somewhere-album-*`
имеет права 0700, файлы 0600. Подготовка ограничена двумя минутами, ready —
десятью минутами, передача — оставшимся сроком ready (и максимум десятью минутами).
Отмена сохраняет занятый слот до завершения I/O, включая уже открытый файл.

Создавшая экспорт сессия и участие проверяются до/после подготовки, при выдаче,
далее не реже очередной проверки фонового обслуживания (тик раз в секунду,
проверка каждого из максимум двух заданий с deadline в секунду). Передача
проверяет отмену на каждом чтении, сессию/участие — также раз в секунду.
Выход, отзыв, DELETE и TTL прерывают активную передачу; отправленные ранее bytes
вернуть нельзя. Чужой ID не раскрывает состояние. После передачи, ошибки,
отмены и Close временные файлы очищаются. При аварийной остановке файлы остаются
до очистки ОС; production использует systemd PrivateTmp. После рестарта ID
недействительны. Миграций БД нет, прежние media API сохраняют совместимость.

Ошибки: 409 `album_empty` для пустого набора; 429 `album_export_busy`
с `Retry-After: 5` при занятости; 409 `album_export_pending` для неготового
или неуспешного архива; 404 для чужого, истёкшего или использованного ID.
При failed клиент удаляет экспорт и запускает новую попытку.
