# Настройка и проверка входа

Сервер реализует Яндекс authorization code + PKCE, собственные профили и сессии.
Реальный вход настраивается отдельно для локального и production origin. Автоматические проверки
используют provider только из `_test.go`; runtime не имеет входа по вымышленному
пользователю. Готовность мобильных обработчиков входа описана отдельно ниже.

Веб получает Secure/HttpOnly-cookie; iOS и Android используют LoginSDK и
обменивают его токен на собственную сессию с отдельным app verifier. Вход не меняет RSVP.
В локальном режиме memory попытки, профили и сессии теряются при перезапуске;
в production PostgreSQL сохраняет их. См. [postgres.md](postgres.md).

## Необязательные данные профиля

`GET /api/v1/me/profile` возвращает владельцу имя, аватар, почту, телефон и
`provider: yandex`. Недоступные дополнительные поля равны `null`; отсутствие
разрешения не мешает входу. При повторном входе сервер обновляет полученные
поля, сохраняя прежние значения для полей, пропущенных провайдером.
Явное отсутствие аватара удаляет прежнюю картинку.

Используются `default_avatar_id`/`is_avatar_empty`, `default_email` и
`default_phone.number`. Аватар строится только на `avatars.yandex.net`, почта
и телефон проверяются перед сохранением. Дополнительные разрешения
`login:avatar`, `login:email`, `login:default_phone` требуются для соответствующих
данных; текущий web-запрос продолжает использовать `login:info` и не расширяет
доступ без отдельной настройки. См. [официальные поля Яндекс ID](https://yandex.ru/dev/id/doc/ru/user-information).

Публичные представления участников/авторов содержат только ID, имя и
необязательный аватар. Контакты не входят в состав, реакции, ленту, карточки
или анонимное приглашение. Клиент загружает публичный аватар без Bearer-токена
нашего API; приватные вложения требуют отдельной авторизации нашего сервера.

## Что заполнить в Яндекс OAuth

Поля сверены с официальной документацией 24.10.2026. Production origin —
`https://smwhere.ru`; callback — `/api/v1/auth/yandex/callback`. Для локальной
разработки используется отдельный зарегистрированный HTTPS-туннель.
Client ID приложения: `43a1ba4507214901a5c08a0d090c6e30`; секрет сохранён только
в защищённом окружении сервера вне Git. Для локального OAuth нужен фактический
HTTPS-origin запуска. Его обеспечивает локальный TLS proxy с доверенным сертификатом
или временный HTTPS-туннель. Адрес нельзя придумывать заранее.
Контактную почту владельца нужно указать самостоятельно.

Открой [создание приложения для авторизации](https://oauth.yandex.ru/client/new/id/)
под аккаунтом, которому будет принадлежать приложение.

| Шаг / поле | Что указать |
| --- | --- |
| Тип приложения | **Для авторизации пользователей**. Тип «Для доступа к API» не подходит для входа пользователей. |
| Название вашего сервиса | `somewhere` |
| Иконка | [somewhere-oauth.png](assets/somewhere-oauth.png), 512 × 512, меньше 1 МБ; экспорт существующего знака. |
| Контактная почта | Действующий адрес владельца проекта; выбрать вручную. |
| Платформы | **Веб-сервисы**, **iOS-приложение** и **Android-приложение**; параметры мобильных сборок ниже. |
| Redirect URI | `<локальный HTTPS-origin>/api/v1/auth/yandex/callback` — сохранить точный путь без завершающего `/`. |
| Доступ к данным | **Логин, имя и фамилия, пол** (`login:info`). Сервер сохраняет идентификатор и отображаемое имя; остальные поля этой группы не использует. |
| Завершение | Проверить карточку и нажать **Всё верно**. Сохранить Client ID и Client Secret из карточки приложения. |

Типы приложений описаны в [правилах регистрации](https://yandex.ru/dev/id/doc/ru/register-client),
поля — в [инструкции создания](https://yandex.ru/dev/id/doc/ru/register-auth).
Email, телефон, портрет и дата рождения пользователей для текущего входа не нужны.
Контактная почта владельца в форме не является разрешением читать почту пользователей.

Если кабинет показывает поле «Хост страницы, на которой разместится кнопка
или виджет авторизации», укажи фактический HTTPS-origin локального запуска,
без пути callback. Если схема `https://` уже задана формой, введи только хост
и порт. Этот хост должен совпадать с адресом страницы, открытой в браузере.
Если появляется поле описания, готовый текст:

> somewhere — сервис для встреч с друзьями: создавайте встречу, делитесь приглашением и обсуждайте детали в общем чате.

Верификация относится к владельцу сервиса. Для личного проекта документация
описывает путь **Снять ограничения → Подтвердить аккаунт через Госуслуги**.
Без подтверждения пользователи видят предупреждение; это не следует путать
с настройкой DNS или callback. Подтверждение владелец выполняет самостоятельно
в [кабинете Яндекса](https://oauth.yandex.ru/).
Источник: [верификация сервиса](https://yandex.ru/dev/id/doc/ru/confirm-account).

### Один профиль на трёх платформах

Web использует HTTPS callback сервера. iOS и Android подключают официальный
LoginSDK; он выбирает установленное приложение Яндекса или штатный веб-вход.
Клиенты отправляют токен SDK в `/api/v1/auth/mobile/sdk/exchange`; сервер проверяет
личность и `client_id` через Яндекс, затем выдаёт сессию somewhere. Все платформы
сопоставляются по одному `yandex:id`. Токен Яндекса не заменяет сессию нашего API.

| Адрес | Где используется |
| --- | --- |
| `<локальный HTTPS-origin>/api/v1/auth/yandex/callback` | **Redirect URI веб-входа в Яндекс OAuth**. |
| `<локальный HTTPS-origin>/auth/return` | Внутренняя страница возврата веба после серверного callback; в Redirect URI Яндекса не добавляется. |
| `group-planning-ios://auth/callback` | Совместимость с прежним серверным handoff, `SOMEWHERE_IOS_AUTH_CALLBACK`; в Redirect URI Яндекса не добавляется. |
| `group-planning-android://auth/callback` | Совместимость с прежним серверным handoff, `SOMEWHERE_ANDROID_AUTH_CALLBACK`; в Redirect URI Яндекса не добавляется. |

Один фактический origin должен обслуживать собранный web, `/api/v1`, `/auth/return`
и приглашения `/i/`. Все клиенты используют этот же локальный Go-процесс с
memory.Store. Для проверки с телефона origin должен быть доступен телефону
и иметь доверенный TLS-сертификат. `localhost` на физическом телефоне указывает
на сам телефон, а не на Mac. Временный HTTPS-туннель даёт всем клиентам один
адрес без покупки домена и удалённого хостинга; при остановке туннеля он перестаёт
работать. Локальный TLS proxy без туннеля требует настройки доверия сертификату
и сетевого доступа на каждом устройстве. Выбор способа не меняет OAuth-протокол.

### Регистрация мобильных платформ / LoginSDK

Значения обычных targets для LoginSDK. QA hosts используют другие идентификаторы
и не должны авторизовываться с production-регистрацией.

| Поле Яндекса | Значение / откуда взять |
| --- | --- |
| iOS AppId | `KMGUVHBG8T.dev.groupplanning.ios` для текущей Personal Team. Prefix `KMGUVHBG8T` подтверждён профилем Apple и entitlement `application-identifier` подписанной Debug-сборки 24.10.2026. |
| iOS AppStore URL | Реальная ссылка на опубликованное приложение. В репозитории такой ссылки нет. |
| Android package name | `dev.groupplanning.android` из `app/build.gradle.kts`. |
| Android Google Play URL | Реальная ссылка из Google Play после публикации. В репозитории такой ссылки нет. |
| SHA256 Fingerprints | SHA-256 сертификата подписи устанавливаемой сборки. Для локальной отладки — debug-сертификат этого компьютера; для версии из Play — app signing certificate из Play Console. |

App ID `dev.groupplanning.ios` зарегистрирован через автоматическую подпись Xcode
в Personal Team; созданы сертификат Apple Development и профиль для подключённого
iPhone. Текущий профиль действует до 31.10.2026. Бесплатная Personal Team подходит
для локальной разработки: её профили имеют срок 7 дней; это не регистрация выпуска
в App Store. Ограничения описаны у [Apple](https://developer.apple.com/help/account/basics/about-your-developer-account).
При смене команды подписи перепроверь Prefix по новому профилю и подписи приложения.

Проверка полного App ID у собранного приложения:

```sh
codesign -d --entitlements - \
  frontend/ios/.build/SigningVerification/Build/Products/Debug-iphoneos/Somewhere.app
```

Используй значение `application-identifier`, а не предположение по Team ID.
Ссылки магазинов нельзя заменять шаблонами; для неопубликованного приложения
оставь их пустыми, если форма разрешает.
Если кабинет требует эти данные, прямую SDK-регистрацию нужно завершить после их
получения. Она не является условием регистрации серверного OAuth-клиента.

Получить отпечаток уже собранного Android Debug APK из корня репозитория:

```sh
"$ANDROID_HOME/build-tools/36.0.0/apksigner" verify --print-certs \
  frontend/android/app/build/outputs/apk/debug/app-debug.apk
```

Нужна строка `certificate SHA-256 digest`, не SHA-1 и не хеш файла APK.
Debug-отпечаток не подходит для распространения сборки с другой подписью.
Документация: [мобильные поля](https://yandex.ru/dev/id/doc/ru/register-auth),
[сертификаты Android](https://developer.android.com/studio/publish/app-signing).

## Окружение

По умолчанию `SOMEWHERE_AUTH_ENABLED=false`: сервер запускается без секретов,
`/me` отвечает 401, начало входа — 503 `auth_unavailable`. Для реального входа
нужно зарегистрировать приложение в [Яндекс OAuth](https://oauth.yandex.ru/).
Права: только `login:info`, без email, телефона и аватара.

| Переменная | Значение |
| --- | --- |
| `SOMEWHERE_AUTH_ENABLED` | `true`, чтобы включить серверный вход. |
| `SOMEWHERE_PUBLIC_ORIGIN` | Один HTTPS origin web и API, без завершающего `/`, пути, query или fragment. |
| `SOMEWHERE_YANDEX_CLIENT_ID` | Client ID зарегистрированного приложения. |
| `SOMEWHERE_YANDEX_CLIENT_SECRET` | Серверный секрет, только в локальном окружении/хранилище секретов. |
| `SOMEWHERE_IOS_AUTH_CALLBACK` | Точный callback iOS: HTTPS либо схема `group-planning-ios`. Без query/fragment/userinfo. |
| `SOMEWHERE_ANDROID_AUTH_CALLBACK` | Точный callback Android: HTTPS либо схема `group-planning-android`. |
| `SOMEWHERE_SESSION_TTL` | Абсолютный срок, Go duration от `1h` до `720h`; по умолчанию `720h`. |

Callback провайдера вычисляется строго как
`SOMEWHERE_PUBLIC_ORIGIN + /api/v1/auth/yandex/callback`; клиент не передаёт его
в запросе. Мобильный callback настраивается отдельно для каждой платформы.
Если он не задан, вход этой платформы не начинается; веб при этом работает.
Частичная конфигурация при выключенном входе и небезопасные адреса отклоняются
при запуске. Вход через plain HTTP не включается даже для разработки.

Конфигурация окружения локального запуска (фактический HTTPS-origin нужно
взять у работающего локального TLS proxy или туннеля):

```sh
export SOMEWHERE_AUTH_ENABLED=true
# SOMEWHERE_PUBLIC_ORIGIN задаётся фактическим адресом локального запуска.
export SOMEWHERE_YANDEX_CLIENT_ID=43a1ba4507214901a5c08a0d090c6e30
# SOMEWHERE_YANDEX_CLIENT_SECRET задаётся вне Git; не вставляй его в чат.
export SOMEWHERE_IOS_AUTH_CALLBACK=group-planning-ios://auth/callback
export SOMEWHERE_ANDROID_AUTH_CALLBACK=group-planning-android://auth/callback
export SOMEWHERE_SESSION_TTL=720h
go run ./cmd/server
```

Для этого примера разрешены ровно следующие адреса:

- В настройках Яндекс OAuth: `<локальный HTTPS-origin>/api/v1/auth/yandex/callback`.
- Возврат web: `<локальный HTTPS-origin>/auth/return?kind=home` либо
  тот же путь с `kind=invitation&token=<исходный токен>`.
- Возврат iOS: `group-planning-ios://auth/callback`.
- Возврат Android: `group-planning-android://auth/callback`.

Старый native callback передаёт только attempt/handoff; протокол остаётся
совместимым. Новые приложения используют callback схемы `yx<Client ID>` внутри
официального SDK, зарегистрированный его конфигурацией. iOS также обрабатывает
Universal Links доменов `yx<Client ID>.oauth.yandex.ru` и `.com`.
Клиентская обработка и реальная проверка отслеживаются в задачах 6.3 и 7.3.

Web-страница `/auth/return` и начало входа уже реализованы. Страница получает
`/me`, обрабатывает безопасный `auth_error` и открывает исходный контекст.
Настоящий цикл Яндекс ID ещё нужно проверить на выбранном HTTPS origin.

Web и API должны находиться на одном HTTPS origin через proxy. Cookie,
созданная на localhost, не переносится в callback другого домена. Не выставляй
client secret в Vite/мобильную сборку и не коммить `.env`; Go не загружает его
автоматически. Сервер сам слушает HTTP на loopback; TLS завершается на proxy.

### Локальный запуск через HTTPS-туннель

Свой домен, удалённый сервер и деплой не требуются. Запуск использует
[ngrok через официальный Node.js SDK](https://github.com/ngrok/ngrok-javascript):
он передаёт HTTPS-запросы серверу на Mac. SDK устанавливается вместе с `npm ci`;
отдельный ngrok CLI не требуется. Любой, кто знает ссылку, может открыть приложение,
пока работает туннель. При остановке приложение становится недоступно извне.

Нужен аккаунт ngrok. Бесплатный тариф выдаёт один dev-домен аккаунта, который
сохраняется между запусками. Трафик и число запросов ограничены
[условиями тарифа](https://ngrok.com/docs/pricing-limits/free-plan-limits).
Скопируй корневой [.env.ngrok.example](../../.env.ngrok.example) в `.env.ngrok.local`,
задай права `600` и вставь Authtoken из личного кабинета ngrok.
Файл игнорируется Git; вместо файла можно задать переменную `NGROK_AUTHTOKEN`.
Токен передаётся только SDK, секрет Яндекса — только серверу.

После заполнения секретов выполни из корня:

```sh
npm run auth:local
```

Команда подключает туннель, собирает обычный web и Go-сервер, запускает сервер
на `127.0.0.1:8080` с memory.Store и проверяет `/healthz` через HTTPS. При занятом
порте она останавливается и не завершает чужие процессы. Рабочий URL и точные
значения для полей Яндекса выводятся в терминале; они также находятся в
игнорируемом `.cache/local-auth/registration.json`, пока команда работает.
Укажи выведенные значения:

- **Redirect URI** — адрес с `/api/v1/auth/yandex/callback`.
- **Хост страницы** — тот же origin без пути.

Не используй сторонний домен вместо выданного адреса. Прежний неподходящий
Redirect URI нужно удалить из карточки приложения. Веб открывай по HTTPS-адресу
туннеля: открытый напрямую `http://localhost:8080` не подходит для OAuth-cookie.

Адрес автоматически записывается в `.env.yandex.local`, iOS `Config/Local.xcconfig`
и Android `local.properties`. Все три файла игнорируются Git. После каждого
нового адреса обнови поля Яндекса и пересобери мобильные приложения в IDE.
Остановка всего запуска — Ctrl+C. Сессии и данные сервера при этом теряются.

При первом открытии бесплатного ngrok-адреса браузер может показать промежуточную
страницу ngrok: нажми **Visit Site**. Это не экран входа somewhere.
Если подключение отклонено, причина записана в `.cache/local-auth/tunnel.log`.
В частности, [ERR_NGROK_9040](https://ngrok.com/docs/errors/err_ngrok_9040)
означает запрет подключения с текущего IP; замена настроек Яндекс OAuth его
не исправит. Команда прекращает запуск и не выдаёт старый адрес за рабочий.

### Куда записать полученные значения

Готовый шаблон — [backend/.env.yandex.example](../.env.yandex.example).
На текущем компьютере `.env.yandex.local` уже заполнен и имеет права `600`.
Для другого окружения из `backend/` скопируй шаблон в `.env.yandex.local`, задай
права `600` и заполни `SOMEWHERE_YANDEX_CLIENT_SECRET` в локальном редакторе.
Публичный Client ID записан в шаблоне; при смене приложения замени и его.
`.env.yandex.local` игнорируется Git. Секрет не нужен в чате, мобильных настройках,
`VITE_*` или URL. Шаблон без секрета намеренно не запускает OAuth.

Текущие GitHub Actions выполняют сборки и тесты с тестовым provider и не
развёртывают сервер. Настоящий секрет Яндекса им не требуется, поэтому в Actions
он не добавлен. При появлении deployment workflow передавай его серверу через
секрет окружения развёртывания `SOMEWHERE_YANDEX_CLIENT_SECRET`; не включай
значение в workflow, клиентские bundles, артефакты сборки или логи.

Для своего TLS proxy вместо встроенного запуска вручную задай фактический
origin в локальном файле и запусти сервер:

```sh
# Из корня: обычный web bundle с настоящим провайдером.
npm run web:build
cd backend
set -a
. ./.env.yandex.local
set +a
go run ./cmd/server
```

Локальный TLS proxy или туннель должен вести фактический HTTPS-origin на этот
сервер; Go раздаёт web из `SOMEWHERE_WEB_DIST`. Proxy не должен записывать query
callback в access log: там находятся краткоживущие `code`/`state`. Сервер продолжает
работать на компьютере разработчика; удалённое развёртывание не требуется.

| Клиент | Настройка общего API |
| --- | --- |
| Web | Сборка `npm run web:build`, открывается по фактическому HTTPS-origin локального запуска; API вызывается на том же origin. |
| iOS | `npm run auth:local` заполняет `SOMEWHERE_API_ORIGIN` в игнорируемом `Config/Local.xcconfig`. Синтаксис `https:/$()/` сохраняет `//` внутри xcconfig. Bundle ID остаётся `dev.groupplanning.ios`. |
| Android | `npm run auth:local` заполняет `somewhere.api.origin` в игнорируемом `local.properties`. При необходимости переопредели через `-PsomewhereApiOrigin="$SOMEWHERE_PUBLIC_ORIGIN"`. Application ID остаётся `dev.groupplanning.android`. |

Эти настройки задают адрес API. Публичный Client ID SDK закреплён в приложениях;
iOS допускает переопределение `SOMEWHERE_YANDEX_CLIENT_ID` через Local.xcconfig,
Android — `somewhere.yandex.client.id` в local.properties или
`-PsomewhereYandexClientId=...`. Секрет в клиенты не передаётся. Проверяются
первый и повторный вход одним аккаунтом, отмена, возврат к приглашению,
logout/истечение сессии и отказ повторному SDK-обмену. Сам вход не сохраняет RSVP.

## Запросы

`POST /api/v1/auth/yandex/start`: JSON с `client_kind` и `return_context`.
Для web обязателен точный `Origin`, а `app_challenge` запрещён. Для native
обязателен base64url S256 challenge от отдельного verifier длиной 43–128 символов.
Контекст — `{ "kind": "home" }` либо
`{ "kind": "invitation", "token": "..." }` для действительной ссылки.
`return_url`, callback URL и чужой user ID не принимаются.

Web получает cookie привязки `__Host-somewhere_auth_<attempt UUID>` на 10 минут;
разные попытки не подменяют друг друга. После callback она удаляется.
Успех устанавливает `__Host-somewhere_session`: Secure, HttpOnly, SameSite=Lax,
Path=/, без Domain. `/me` возвращает профиль, expires_at и CSRF-token, но не секрет
web-сессии. Мутации с cookie требуют точные Origin и `X-CSRF-Token` этой сессии.

LoginSDK-клиент выполняет `POST /api/v1/auth/mobile/sdk/exchange` с attempt_id,
app_verifier и oauth_token. Попытка одноразовая, живёт 10 минут; проверка токена
происходит на сервере по фиксированному HTTPS endpoint Яндекса. Сервер проверяет
client_id и не сохраняет токен провайдера. Прежний `/auth/mobile/exchange` с
handoff_code остаётся совместимым; handoff живёт 60 секунд.
Далее используется `Authorization: Bearer <session_token>`. Bearer и cookie
не смешиваются; web-секрет не работает как Bearer и наоборот.
`POST /api/v1/auth/logout` отзывает текущую сессию, для web проверяет CSRF
и удаляет cookie. 401 означает недействительную сессию; 403 — нарушение привязки/CSRF.

Callback с неверным/истёкшим state даёт 400, с чужой web-привязкой — 403.
После допустимой отмены или сбоя провайдера выполняется 303 к сохранённому
контексту с `auth_cancelled` / `auth_unavailable`; произвольный текст ошибки
Яндекса не отражается в ответе. Повтор callback не выдаёт ещё один код/сессию.

Яндекс-токен используется только для немедленной проверки профиля по HTTPS.
Проверяются subject и client_id. Access/refresh tokens не сохраняются;
секреты собственных сессий, state, binding и коды передачи хранятся как хеши.
Серверный PKCE verifier временно хранится до обмена/истечения попытки и удаляется.

## Очистка и проверки

Процесс каждые 60 секунд удаляет истёкшие попытки/коды и сессии. Проверка срока
выполняется при каждом обращении: задержка очистки не продлевает доступ.
В PostgreSQL профили и сессии сохраняются после перезапуска. В memory
профили сохраняются только до перезапуска; отдельный CLI-процесс не может
очистить память работающего сервера.

Команды из `backend/`:

```sh
go test -race ./internal/identity/... ./internal/httpapi ./internal/storage/memory ./internal/server
go test ./internal/storage/memory -run '^TestIdentityCleanup$' -v
go test ./internal/identity -run '^TestExpiredHandoffAndInvitationContext$' -v
```

Из корня: `npm run api:test` сравнивает реальные auth/session ответы с OpenAPI,
включая пустые 303/204. Тестовый web и API используют один локальный TLS origin
`https://127.0.0.1:<случайный порт>`, которому доверяет только тестовый клиент.
Тестовый provider внедряется программно из `_test.go`; runtime всегда использует
фиксированные HTTPS endpoints Яндекса и не следует внешним HTTP-редиректам.
Переменных подмены provider URL нет; `SOMEWHERE_DEV_USER`, `SOMEWHERE_AUTH_BYPASS`
и известные override-переменные отклоняются при запуске.

Проверены конкуренция первых входов, привязки state/binding/verifier, отмена,
сетевая ошибка, повторы, сроки, отзыв и очистка, отсутствие открытых секретов
сессий в хранилище/логах и отсутствие автоматического RSVP. Эти проверки
не заменяют реальный вход Яндекс ID: он требует настроенного приложения,
HTTPS-окружения и клиентов и пока не выполнен.

Основа адаптера: [код и PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url),
[проверка профиля](https://yandex.ru/dev/id/doc/ru/user-information).
