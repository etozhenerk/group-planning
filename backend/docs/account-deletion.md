# Удаление аккаунта

`DELETE /api/v1/me` удаляет профиль somewhere и отзывает все его сессии.
Яндекс-аккаунт пользователя остаётся у провайдера. Полный контракт находится
в [OpenAPI](../../contracts/openapi.yaml); UX — в
[изменении account-deletion](../../openspec/changes/account-deletion/ux.md).

## Запрос и повтор

Клиент перед отправкой сохраняет случайные 32 байта в base64url без padding
и передаёт их в `X-Deletion-Token`. Первый запрос требует действующую сессию:
web — cookie, свой Origin и X-CSRF-Token; native — Bearer. Ответ об успехе —
только 204. 401 не подтверждает удаление.

Если ответ потерян, повторить тот же запрос с тем же ключом. Сервер хранит
SHA-256 ключа и тип клиента 24 часа без user ID. Такая квитанция позволяет
вернуть 204 после отзыва сессии; web-повтор по-прежнему проверяет Origin.
Повтор не удаляет новый профиль, созданный последующим самостоятельным входом.
Ключ нельзя записывать в журналы, аналитику, URL или Git.

Клиенты хранят незавершённую операцию до подтверждения и очистки локальных данных:
web в sessionStorage текущей вкладки, iOS в Keychain, Android в encrypted credentials.
При восстановлении сначала показывается повтор удаления. При потере ключа
или истечении квитанции клиент предлагает новый вход, не заявляя об успехе.

## Встречи и данные

- Организатором становится текущий участник «Приду» с самым ранним первым
  вступлением. Выход и повторное вступление не меняют этот порядок.
- Если кандидатов нет, встреча целиком удаляется вместе с приглашением,
  лентой, ответами, обложкой, опросами, поручениями и отложенными заданиями.
  Правило действует также для прошедших встреч.
- В сохранённых встречах удаляется RSVP, структурированное авторство заменяется
  подписью «Удалённый аккаунт». Свободный текст сообщений сохраняется.
- Открытые голоса удаляются. Закрытые результаты сохраняются обезличенными.
  Поручения удаляемому адресату и принятые им задачи отменяются; чужие задачи остаются.
- Профиль, связь с провайдером, сессии и выданные handoff удаляются атомарно
  с изменениями встреч. Короткая метка SHA-256 subject на 10 минут блокирует
  входы, начатые до удаления; новый самостоятельный вход создаёт новый профиль.

Операция использует одну транзакцию memory/PostgreSQL. Opaque ID остаётся
в общей истории и запрете старых запросов; персональные имена и provider mapping
не сохраняются в этих метках. Таймаут/ошибка до commit откатывают обе области.

## Выпуск

Нужна миграция `002_account_deletion.sql`. Она добавляет три таблицы, не изменяя
checksum миграции 001 и существующие документы. Команда `somewhere-migrate`
проверяет всю последовательность. Runtime требует версию 2; предыдущий backend,
проверяющий ровно версию 1, после миграции несовместим. Down-миграции нет;
откат возможен только на совместимый бинарник. Удалённые данные не восстанавливаются.

До выпуска проверить `TestAccountDeletionAtomicityAndPersistence` и
`TestAccountMigrationUpgradesVersionOne` в отдельной `somewhere_integration`
по [инструкции PostgreSQL](postgres.md). Первый проверяет rollback двух областей,
удаление дочерних записей, повторное чтение другим пулом и очистку квитанций;
второй проверяет переход с версии 1 в отдельной временной схеме и сохранность профиля.
Без тестового DSN они явно пропускаются. Успех обычного Go-набора не заменяет
этот прогон. Default privileges `somewhere_migrator` из `infra/host/prepare.sh`
выдают runtime DML-права на новые таблицы; при другой установке права проверить явно.

Старые клиенты продолжают читать прежние ответы и события. Удалённые сессии
получают обычный 401. Новым клиентам для удаления нужен новый backend;
неподдерживаемая операция на старом backend отображается ошибкой без ложного успеха.
