# Бэкенд Somewhere

Сервер работает в одном Go-процессе. Локальный режим использует память без БД;
облачный — PostgreSQL 16 через pgx v5.11.0. Go **1.27.2** закреплён в `go.mod`;
установка — с [go.dev](https://go.dev/dl/). Инструменты оформления закреплены
отдельно в `tools/go.mod`/`tools/go.sum` и скачиваются при первом запуске.

## Запуск

Из корня репозитория:

```sh
cd backend
go run ./cmd/server
```

По умолчанию сервер слушает `127.0.0.1:8080`:

```sh
curl -i http://127.0.0.1:8080/healthz
```

Ответ — 200 и `{"status":"ok"}`. Ctrl+C/SIGTERM прекращает приём новых
соединений и даёт активным запросам до 5 секунд на завершение.
Для выбора адреса и срока остановки экспортируй переменные из
[.env.example](.env.example); Go не загружает `.env` автоматически.
Например:

```sh
SOMEWHERE_HTTP_ADDR=127.0.0.1:8081 SOMEWHERE_SHUTDOWN_TIMEOUT=10s go run ./cmd/server
```

`SOMEWHERE_STORAGE` принимает `memory` (по умолчанию) или `postgres`.
Для PostgreSQL обязательна `SOMEWHERE_DATABASE_URL`; миграции применяет
отдельная команда `somewhere-migrate` под DDL-ролью. Runtime проверяет схему
и не создаёт таблицы. `/readyz` возвращает 503 при недоступной/несовместимой БД;
`/healthz` проверяет процесс. Процедура выпуска — [postgres.md](docs/postgres.md). Адрес требует явного host и порта;
доступ извне включается явно, например через `0.0.0.0:8080`. По умолчанию вход
выключен. Для локального запуска с настоящим Яндекс ID используй из корня
`npm run auth:local`: сервер остаётся на loopback, а временный HTTPS-туннель
обслуживает web и API по одному адресу. Подготовка OAuth-файла, установка
ngrok и поля регистрации — в [docs/auth.md](docs/auth.md#локальный-запуск-через-https-туннель).
Автоматические тесты используют тестовый provider без runtime-обхода входа.

## Что доступно

Все пути API имеют префикс `/api/v1`.

| Операция | Доступ |
| --- | --- |
| `GET /healthz` (вне префикса) | Состояние процесса. |
| `GET /invitations/{token}` | Публичные поля и, при действительной сессии, свой RSVP. |
| `POST /meetings`, `GET /meetings` | Создание и личный список вошедшего пользователя. |
| `GET /meetings/{id}`, `GET /meetings/{id}/participants` | Организатор или текущий going. |
| `GET /meetings/{id}/invitation`, `PATCH /meetings/{id}` | Только организатор. |
| `PUT /invitations/{token}/rsvp` | Вошедший гость по ссылке. |
| `PUT /meetings/{id}/rsvp` | Изменение собственного сохранённого ответа. |
| `GET /meetings/{id}/feed`, `POST /meetings/{id}/messages` | Организатор или текущий going. |
| `GET /me/profile` | Личный профиль; контакты доступны только владельцу. |
| `POST /support/feedback` | Публичное идемпотентное обращение; локальная очередь, [доставка и ограничения](docs/support.md). |
| `GET /meetings/{id}/reactions`, `PUT /meetings/{id}/messages/{entry_id}/reactions` | Подтверждённые реакции текущих участников. |
| `GET /meetings/{id}/media/limits`, `POST /meetings/{id}/media/uploads`, `PUT /meetings/{id}/media/{media_id}/content`, `POST /meetings/{id}/media/{media_id}/publish` | Выбор, проверка и публикация приватного вложения. |
| `GET /meetings/{id}/media/{media_id}/content`, `GET /meetings/{id}/memories` | Приватные файлы и альбом прошедшей встречи. |
| `POST /meetings/{id}/place-polls`, `GET /meetings/{id}/place-polls/{poll_id}`, `PUT /meetings/{id}/place-polls/{poll_id}/vote` | Организатор или текущий going. |

Также зарегистрированы POST auth/yandex/start, GET auth/yandex/callback,
POST auth/mobile/exchange, GET me и POST auth/logout. Вход не создаёт RSVP.
Тела, заголовки идемпотентности, ревизии и ошибки описаны в
[OpenAPI](../contracts/README.md). Событие и данные операции сохраняются вместе;
поздний повтор сообщения/создания не создаёт второй ресурс даже после TTL receipt.

Новое «Приду» закрывается за час до точного начала; дата без времени не получает
выдуманной отсечки. Повтор текущего подтверждённого участия сохраняет доступ.
Приглашение возвращает причину закрытия и `join_closes_at` для интерфейса.
Хранение, ограничения и очистка вложений — в [media.md](docs/media.md).

Сервер запускается **пустым**. Случайное приглашение даёт JSON 404, приватные
операции без сессии — 401. Публичного seed-endpoint и обхода входа нет.
По умолчанию Go-сервер обслуживает API. Собранный web подключается опционально:

```sh
# Сначала из корня: npm run web:build
SOMEWHERE_WEB_DIST=../frontend/web/dist SOMEWHERE_WEB_ORIGIN=https://somewhere.example go run ./cmd/server
```

HTTPS завершается на proxy перед Go; web и API должны быть доступны на одном
origin. Если включён OAuth, его `SOMEWHERE_PUBLIC_ORIGIN` должен совпадать
с `SOMEWHERE_WEB_ORIGIN`. Настройка web не включает OAuth и не требует его ключей.
На локальном TLS-стенде используется тот же `internal/webui`, а fake-provider
остаётся исключительно в тестах. Запуск — в [инструкции веба](../frontend/web/README.md).

Новые приглашения имеют путь `/i/{token}` и 22 символа канонического base64url
из 16 случайных байт. Прежние 32-байтные токены принимаются; старый путь
`/invitations/{token}` перенаправляет на короткий, сохраняя контекст. Секреты
сессий, state и PKCE остаются прежней длины.

Для открытия HTTPS-приглашений в iOS/Android сервер выдаёт файлы ассоциаций
по явно заданным идентификаторам и подписям: [настройка App Links](docs/app-links.md).

Название, дата, место и полное описание публичны по ссылке приглашения. HTML
содержит Open Graph/canonical и PNG 1200×630, без выполнения JavaScript.
Состав, чужие ответы и переписка не входят в метаданные. Пустое описание
заменяется датой/местом, неизвестный токен даёт 404 без данных встречи.
Метаданные читают текущий snapshot; absolute URL берётся из конфигурации,
а не Host запроса. Для реального превью в мессенджере нужен публичный HTTPS;
localhost проверяется через HTTP/HTML и браузер без JavaScript.
Неверный и неизвестный токены возвращают одинаковую ошибку без данных встречи.
Ответы имеют `Cache-Control: no-store`, `Referrer-Policy: no-referrer` и новый
`X-Request-ID`; ошибки не показывают текст хранилища или panic. Логи содержат
только ID, статус и длительность, без URL, body, cookie или токенов.

## Проверки

Из `backend/`:

```sh
go test -race ./...
go vet ./...
go run ./cmd/check-dependencies
go build ./...
sh scripts/format.sh --check
gofmt -l .
go run ./cmd/storage-demo
```

`go run ./cmd/check-dependencies` проверяет границы пакетов и доступ к портам
хранения по [ADR 0003](../docs/architecture/0003-modular-monolith.md).
Команда должна завершиться без нарушений; тот же контроллер запущен отдельным
шагом Checkers в Backend CI. Правила и тесты — в `internal/architecture`.

`sh scripts/format.sh --check` проверяет gofumpt и wsl (разделение блоков
пустыми строками); исправление — `sh scripts/format.sh --write`.
`gofmt -l .` дополнительно должен давать пустой вывод. Демонстрация отдельно создаёт встречу,
ответ друга и две записи ленты и печатает:
`Вечер с друзьями: ответов — 1, событий — 2`.
Она не наполняет другой работающий сервер.

Из корня с установленными `npm ci` инструментами:

```sh
npm run api:test
npm run agent:check
```

Тесты проверяют память/атомарность/конкуренцию, приватность HTTP, JSON-ошибки,
строгий декодер запросов, ограничения полей/времени/зон, ревизии и повторы,
права и страницы ленты, контракт и запуск/остановку через TCP.
CI выполняет те же команды без БД и Docker.
Тестовый OAuth-provider проверяет конкурентный вход, state/PKCE, cookie/CSRF,
мобильный handoff, отзыв/сроки и очистку сессий. Сквозной HTTP-сценарий проверяет
встречу с отдельными профилями, web-cookie и native Bearer. Реальный Яндекс ID
и мобильные приложения ещё не проверены. Веб проверяется Chromium
с этим же Go API и отдельным test-only provider.

### Первый серверный сценарий без настройки Яндекса

Из `backend/`:

```sh
go test -count=1 -run '^TestMeetingOpenAPIResponses$' -v ./internal/httpapi
go test -race ./internal/meetings ./internal/storage/memory
```

Первая команда поднимает временный TLS-сервер и независимые браузерные cookie-jar:
организатор входит, создаёт встречу, получает ссылку; друг входит по приглашению
без RSVP, отвечает «Приду», отправляет сообщение, меняет ответ и теряет доступ.
Проверяются повторы, настройки, ответы участников и тот же профиль через Bearer.
Вторая команда проверяет конкуренцию, откаты и повторы после TTL receipts.
Это автоматизированная проверка API; не интерактивный вход в работающий процесс.
Результаты — в [отчёте](../openspec/changes/gathering-activity-feed/meetings-verification.md).

## Устройство и ограничения

- `cmd/server` — конфигурация, сигналы и сборка зависимостей.
- `internal/server` — конфигурация и HTTP lifecycle с таймаутами.
- `internal/httpapi` — маршруты, отдельные DTO, JSON, ошибки и безопасные логи.
- `internal/meetings` — модели, порт Store, правила доступа и прикладные операции.
- `internal/storage/memory` — временные адаптеры встреч и identity.
- `internal/storage/postgres` — постоянные адаптеры, SQL и встроенные миграции.
- `cmd/migrate` — отдельный процесс применения миграций.
- `internal/identity` — попытки входа, профили и собственные сессии.
- `internal/identity/yandex` — HTTPS-адаптер реального провайдера.
- `cmd/storage-demo` — явный отдельный пример с вымышленными данными.

`memory.New()` создаёт пустое независимое хранилище. Перезапуск теряет записи;
это же касается профилей, сессий и receipts. Все клиенты должны обращаться к одному
экземпляру: независимые процессы не разделяют состояние. Перенос временных данных
при подключении постоянного хранилища не обещается.

`View` возвращает согласованный снимок и независимые копии. `Update` сериализует
записи, копирует состояние и публикует связанные изменения вместе; ошибка,
отмена context до публикации или panic оставляют прежнее состояние. Reader/Writer
закрываются после callback. Нельзя сохранять их, вызывать вложенный View/Update
того же Store или выполнять внешние запросы внутри callback.

Адаптер проверяет ссылки/уникальность и назначает sequence; права, ревизии,
идемпотентность, TTL и страницы реализованы в прикладных операциях.
Истёкшие receipts удаляются при следующей успешной прикладной записи;
ошибка откатывает и эту очистку. Проверка срока не зависит от удаления.
Копирование состояния подходит для небольшого локального объёма. Тесты памяти
не доказывают надёжность на диске; SQL-адаптер и его проверки — отдельный этап.

## Календарь и отложенный переход в историю

`GET /api/v1/meetings?period=upcoming|past|undated` возвращает раздел,
полные счётчики и метаданные обновления. Датированные разделы принимают пару
`from=YYYY-MM-DD&to=YYYY-MM-DD`: локальные даты встречи, правая граница
исключается, максимум 42 дня. `limit` и `cursor` ограничивают список,
но не `counts`/`days`. Без `period` сохраняются прежние ответ и курсоры.

Если набор изменился между страницами, ответ `409 calendar_changed` требует
перечитать список с первой страницы. Клиент сохраняет выбранные раздел и день.
`next_transition_at` сообщает плановый срок, `refresh_after_seconds` — интервал
повторного чтения, в том числе если обработчик ещё не успел выполнить задачу.
GET никогда не меняет статус.

Сервер запускает обработчик вместе с API. Встреча и её задача сохраняются
атомарно в выбранном Store. Статус меняется на `past` с начала следующей
локальной даты; старая задача после переноса не влияет на новое расписание.
Переход повышает ревизию встречи, сохраняет права и не добавляет сообщение в чат.

Настройки `SOMEWHERE_TRANSITION_*` перечислены в [.env.example](.env.example).
По умолчанию очередь опрашивается раз в секунду, lease действует 30 секунд,
допускается 5 попыток с задержкой от 5 секунд до 5 минут. Сверка при старте
и раз в минуту восстанавливает отсутствующие задачи порциями по 100 записей.
Она не сбрасывает текущие lease, backoff и окончательные ошибки.

Структурированные события `transition_health` содержат размеры очереди,
повторы, зависшие задачи, просроченные встречи и время последней успешной сверки.
Окончательные ошибки, задержка более минуты и отсутствие успешной сверки
более 5 минут дают уровень ERROR и флаги сигнала. Отдельный сбой сверки тоже
логируется как ошибка. В диагностике нет текстов встреч, токенов и raw-ошибок.

Управляемый повтор предоставляет прикладная операция
`Service.RetryFailedTransition(ctx, meetingID, scheduleVersion)`. Она заново
проверяет актуальность расписания, сохраняет общий счётчик попыток, последнюю
ошибку и число ручных повторов. Публичного HTTP-маршрута для неё нет;
операторский интерфейс и доставка облачных сигналов проектируются с инфраструктурой.

Это мок очереди: перезапуск обработчика с тем же Store сохраняет задачи,
остановка процесса теряет и задачи, и встречи. Порции ограничивают прикладную
работу, но memory-адаптер по-прежнему копирует состояние целиком; его поведение
не является оценкой масштабирования постоянного хранилища.

## Опрос места

Создание принимает `place` (1–500 символов после обрезки внешних пробелов)
и будущий `closes_at`; голос — `answer: for|against` и ревизию собственного
голоса `expected_revision`. Один открытый опрос на встречу; место меняется
только по сроку при строгом большинстве «За». Ничья и отсутствие голосов
сохраняют место. Учитывается текущий состав организатор/going; повторное
вступление до закрытия возвращает прежний голос. Ручная смена места отменяет
открытый опрос. Подробные ответы и ошибки — в OpenAPI.

Обработчик `PlacePollWorker` запускается вместе с API, сверяет отсутствующие
задачи при старте и закрывает просроченные опросы. Итог, место и события
фиксируются одной `Update`; ограниченные повторы используют
`SOMEWHERE_TRANSITION_*`. Диагностика `place poll jobs` не содержит текстов
мест или голосов. Окончательная ошибка требует операторской операции
`Service.RetryPlacePollClose`; публичного HTTP-маршрута для неё нет.
Это тот же мок очереди: перезапуск процесса сбрасывает опросы и задачи.

### Обложки встреч

Создание и настройки принимают необязательное поле `cover` с `media_type` и
base64 `data`. Поддерживаются JPEG/PNG до 5 MiB, 16 миллионов пикселей и
8192 px по стороне; метаданные удаляются при повторном кодировании. Для этих
двух операций лимит JSON — 7 MiB. В PATCH отсутствие поля сохраняет фото,
`null` удаляет. Изменение фото, встречи и ленты атомарно.

`cover_url` указывает на бинарный GET/HEAD `/api/v1/meetings/{id}/cover?v=…`
с текущим доступом к разговору или `/api/v1/invitations/{token}/cover?v=…`
по приглашению. Старые версии дают 404; ответы не кешируются. Изображения
хранятся в выбранном Store: память сбрасывается при перезапуске, PostgreSQL сохраняет данные.

Проверка сброса отдельного mock API при перезапуске (из корня репозитория,
Go 1.27.2 в PATH): `python3 scripts/test-mock-restart.py`. Она создаёт два
временных тестовых процесса и проверяет потерю прежней сессии и встречи;
запущенный пользовательский API не затрагивается.
