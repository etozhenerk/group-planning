# Бэкенд Somewhere

Сервер работает в одном Go-процессе с временным хранилищем в памяти.
PostgreSQL, Docker и миграции не нужны. Go **1.27.2** закреплён в `go.mod`;
установка — с [go.dev](https://go.dev/dl/). Внешних Go-зависимостей нет.

## Запуск

Из корня репозитория:

```sh
cd backend
go run ./cmd/server
```

По умолчанию сервер слушает `127.0.0.1:8080`:

```sh
curl -i http://127.0.0.1:8080/healthz
```

Ответ — 200 и `{"status":"ok"}`. Ctrl+C/SIGTERM прекращает приём новых
соединений и даёт активным запросам до 5 секунд на завершение.
Для выбора адреса и срока остановки экспортируй переменные из
[.env.example](.env.example); Go не загружает `.env` автоматически.
Например:

```sh
SOMEWHERE_HTTP_ADDR=127.0.0.1:8081 SOMEWHERE_SHUTDOWN_TIMEOUT=10s go run ./cmd/server
```

`SOMEWHERE_STORAGE` принимает только `memory`. Адрес требует явного host и порта;
доступ извне включается явно, например через `0.0.0.0:8080`. Для реального OAuth
в дальнейшем нужен один HTTPS origin для web и API, с proxy перед сервером.
Сейчас OAuth не подключён; переменные/секреты Яндекса ещё не требуются.

## Что доступно

- `GET /healthz` — состояние процесса, без проверки внешних сервисов.
- `GET /api/v1/invitations/{token}` — анонимная карточка из memory.Store:
  ID, название, время/зона и место. Обложка и собственный RSVP пока `null`,
  ревизия ответа `"0"`. Сеансы ещё не реализованы.

Сервер запускается **пустым**. Запрос случайного приглашения даёт общий JSON 404.
Тесты явно создают вымышленные данные и проверяют успешный preview; публичного
seed-endpoint и обхода входа нет. Создание встреч, Яндекс ID, сохранение ответа
и сообщения будут добавлены следующими задачами. Наличие их описания в
[OpenAPI](../contracts/README.md) не означает готовый маршрут.

Токен приглашения — 32 случайных байта в каноническом base64url без padding.
Неверный и неизвестный токены возвращают одинаковую ошибку без данных встречи.
Ответы имеют `Cache-Control: no-store`, `Referrer-Policy: no-referrer` и новый
`X-Request-ID`; ошибки не показывают текст хранилища или panic. Логи содержат
только ID, статус и длительность, без URL, body, cookie или токенов.

## Проверки

Из `backend/`:

```sh
go test -race ./...
go vet ./...
go build ./...
gofmt -l .
go run ./cmd/storage-demo
```

`gofmt -l .` должен давать пустой вывод. Демонстрация отдельно создаёт встречу,
ответ друга и две записи ленты и печатает:
`Вечер с друзьями: ответов — 1, событий — 2`.
Она не наполняет другой работающий сервер.

Из корня с установленными `npm ci` инструментами:

```sh
npm run api:test
npm run agent:check
```

Тесты проверяют память/атомарность/конкуренцию, приватность HTTP, JSON-ошибки,
строгий декодер тел будущих операций, контракт и запуск/остановку через TCP.
Декодер проверяет DTO с именованными полями; проверка обязательности и бизнес-лимитов
добавляется в самих операциях. CI выполняет те же команды без БД и Docker.
Полный сценарий двух вошедших пользователей ещё не реализован и этими проверками
не подтверждается.

## Устройство и ограничения

- `cmd/server` — конфигурация, сигналы и сборка зависимостей.
- `internal/server` — конфигурация и HTTP lifecycle с таймаутами.
- `internal/httpapi` — маршруты, отдельные DTO, JSON, ошибки и безопасные логи.
- `internal/meetings` — модели, порт Store и операция публичного preview.
- `internal/storage/memory` — временный адаптер Store.
- `cmd/storage-demo` — явный отдельный пример с вымышленными данными.

`memory.New()` создаёт пустое независимое хранилище. Перезапуск теряет записи;
это же касается будущих профилей и сессий. Все клиенты должны обращаться к одному
экземпляру: независимые процессы не разделяют состояние. Перенос временных данных
при подключении постоянного хранилища не обещается.

`View` возвращает согласованный снимок и независимые копии. `Update` сериализует
записи, копирует состояние и публикует связанные изменения вместе; ошибка,
отмена context до публикации или panic оставляют прежнее состояние. Reader/Writer
закрываются после callback. Нельзя сохранять их, вызывать вложенный View/Update
того же Store или выполнять внешние запросы внутри callback.

Адаптер проверяет ссылки/уникальность и назначает sequence; права, ревизии,
идемпотентность, TTL и страницы реализуются в прикладных операциях.
Копирование состояния подходит для небольшого локального объёма. Тесты памяти
не доказывают надёжность на диске; SQL-адаптер и его проверки — отдельный этап.
