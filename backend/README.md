# Бэкенд Somewhere

Сервер работает в одном Go-процессе с временным хранилищем в памяти.
PostgreSQL, Docker и миграции не нужны. Go **1.27.2** закреплён в `go.mod`;
установка — с [go.dev](https://go.dev/dl/). Внешних runtime-зависимостей Go нет. Инструменты оформления закреплены
отдельно в `tools/go.mod`/`tools/go.sum` и скачиваются при первом запуске.

## Запуск

Из корня репозитория:

```sh
cd backend
go run ./cmd/server
```

По умолчанию сервер слушает `127.0.0.1:8080`:

```sh
curl -i http://127.0.0.1:8080/healthz
```

Ответ — 200 и `{"status":"ok"}`. Ctrl+C/SIGTERM прекращает приём новых
соединений и даёт активным запросам до 5 секунд на завершение.
Для выбора адреса и срока остановки экспортируй переменные из
[.env.example](.env.example); Go не загружает `.env` автоматически.
Например:

```sh
SOMEWHERE_HTTP_ADDR=127.0.0.1:8081 SOMEWHERE_SHUTDOWN_TIMEOUT=10s go run ./cmd/server
```

`SOMEWHERE_STORAGE` принимает только `memory`. Адрес требует явного host и порта;
доступ извне включается явно, например через `0.0.0.0:8080`. Для реального OAuth
в дальнейшем нужен один HTTPS origin для web и API, с proxy перед сервером.
По умолчанию вход выключен. Серверный OAuth и сессии реализованы;
реальное подключение Яндекс ID пользователь отложил до конца разработки.
Инструкция сохранена в [docs/auth.md](docs/auth.md). До этого серверный сценарий
проверяется тестовым OAuth-provider, внедрённым только в тесты, без runtime-обхода.

## Что доступно

Все пути API имеют префикс `/api/v1`.

| Операция | Доступ |
| --- | --- |
| `GET /healthz` (вне префикса) | Состояние процесса. |
| `GET /invitations/{token}` | Публичные поля и, при действительной сессии, свой RSVP. |
| `POST /meetings`, `GET /meetings` | Создание и личный список вошедшего пользователя. |
| `GET /meetings/{id}`, `GET /meetings/{id}/participants` | Организатор или текущий going. |
| `GET /meetings/{id}/invitation`, `PATCH /meetings/{id}` | Только организатор. |
| `PUT /invitations/{token}/rsvp` | Вошедший гость по ссылке. |
| `PUT /meetings/{id}/rsvp` | Изменение собственного сохранённого ответа. |
| `GET /meetings/{id}/feed`, `POST /meetings/{id}/messages` | Организатор или текущий going. |

Также зарегистрированы POST auth/yandex/start, GET auth/yandex/callback,
POST auth/mobile/exchange, GET me и POST auth/logout. Вход не создаёт RSVP.
Тела, заголовки идемпотентности, ревизии и ошибки описаны в
[OpenAPI](../contracts/README.md). Событие и данные операции сохраняются вместе;
поздний повтор сообщения/создания не создаёт второй ресурс даже после TTL receipt.

Сервер запускается **пустым**. Случайное приглашение даёт JSON 404, приватные
операции без сессии — 401. Публичного seed-endpoint и обхода входа нет.
Обычный Go-сервер обслуживает API. Запуск веб-клиента и test-only демо —
в [инструкции веба](../frontend/web/README.md); API не поднимает UI сам.

Токен приглашения — 32 случайных байта в каноническом base64url без padding.
Неверный и неизвестный токены возвращают одинаковую ошибку без данных встречи.
Ответы имеют `Cache-Control: no-store`, `Referrer-Policy: no-referrer` и новый
`X-Request-ID`; ошибки не показывают текст хранилища или panic. Логи содержат
только ID, статус и длительность, без URL, body, cookie или токенов.

## Проверки

Из `backend/`:

```sh
go test -race ./...
go vet ./...
go build ./...
sh scripts/format.sh --check
gofmt -l .
go run ./cmd/storage-demo
```

`sh scripts/format.sh --check` проверяет gofumpt и wsl (разделение блоков
пустыми строками); исправление — `sh scripts/format.sh --write`.
`gofmt -l .` дополнительно должен давать пустой вывод. Демонстрация отдельно создаёт встречу,
ответ друга и две записи ленты и печатает:
`Вечер с друзьями: ответов — 1, событий — 2`.
Она не наполняет другой работающий сервер.

Из корня с установленными `npm ci` инструментами:

```sh
npm run api:test
npm run agent:check
```

Тесты проверяют память/атомарность/конкуренцию, приватность HTTP, JSON-ошибки,
строгий декодер запросов, ограничения полей/времени/зон, ревизии и повторы,
права и страницы ленты, контракт и запуск/остановку через TCP.
CI выполняет те же команды без БД и Docker.
Тестовый OAuth-provider проверяет конкурентный вход, state/PKCE, cookie/CSRF,
мобильный handoff, отзыв/сроки и очистку сессий. Сквозной HTTP-сценарий проверяет
встречу с отдельными профилями, web-cookie и native Bearer. Реальный Яндекс ID
и мобильные приложения ещё не проверены. Веб проверяется Chromium
с этим же Go API и отдельным test-only provider.

### Первый серверный сценарий без настройки Яндекса

Из `backend/`:

```sh
go test -count=1 -run '^TestMeetingOpenAPIResponses$' -v ./internal/httpapi
go test -race ./internal/meetings ./internal/storage/memory
```

Первая команда поднимает временный TLS-сервер и независимые браузерные cookie-jar:
организатор входит, создаёт встречу, получает ссылку; друг входит по приглашению
без RSVP, отвечает «Приду», отправляет сообщение, меняет ответ и теряет доступ.
Проверяются повторы, настройки, ответы участников и тот же профиль через Bearer.
Вторая команда проверяет конкуренцию, откаты и повторы после TTL receipts.
Это автоматизированная проверка API; не интерактивный вход в работающий процесс.
Результаты — в [отчёте](../openspec/changes/gathering-activity-feed/meetings-verification.md).

## Устройство и ограничения

- `cmd/server` — конфигурация, сигналы и сборка зависимостей.
- `internal/server` — конфигурация и HTTP lifecycle с таймаутами.
- `internal/httpapi` — маршруты, отдельные DTO, JSON, ошибки и безопасные логи.
- `internal/meetings` — модели, порт Store, правила доступа и прикладные операции.
- `internal/storage/memory` — временные адаптеры встреч и identity.
- `internal/identity` — попытки входа, профили и собственные сессии.
- `internal/identity/yandex` — HTTPS-адаптер реального провайдера.
- `cmd/storage-demo` — явный отдельный пример с вымышленными данными.

`memory.New()` создаёт пустое независимое хранилище. Перезапуск теряет записи;
это же касается профилей, сессий и receipts. Все клиенты должны обращаться к одному
экземпляру: независимые процессы не разделяют состояние. Перенос временных данных
при подключении постоянного хранилища не обещается.

`View` возвращает согласованный снимок и независимые копии. `Update` сериализует
записи, копирует состояние и публикует связанные изменения вместе; ошибка,
отмена context до публикации или panic оставляют прежнее состояние. Reader/Writer
закрываются после callback. Нельзя сохранять их, вызывать вложенный View/Update
того же Store или выполнять внешние запросы внутри callback.

Адаптер проверяет ссылки/уникальность и назначает sequence; права, ревизии,
идемпотентность, TTL и страницы реализованы в прикладных операциях.
Истёкшие receipts удаляются при следующей успешной прикладной записи;
ошибка откатывает и эту очистку. Проверка срока не зависит от удаления.
Копирование состояния подходит для небольшого локального объёма. Тесты памяти
не доказывают надёжность на диске; SQL-адаптер и его проверки — отдельный этап.
