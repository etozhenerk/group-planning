# Бэкенд

Применяй [общие правила](../AGENTS.md). Эта область отвечает за API,
бизнес-логику, доступ к данным и фоновые задачи Somewhere.
Также применяй [общие соглашения кода](../docs/development.md).

## Текущее состояние

Выбран Go. Бэкенд предоставляет предметные данные и операции через общий API;
экраны реализуются в клиентах. См. [ADR 0002](../docs/architecture/0002-client-ui.md).
Добавлен Go-модуль 1.27.2 и mock-адаптер memory.Store для данных встреч.
Внешних Go-зависимостей нет; БД, Docker и миграции отложены пользователем.
Добавлены cmd/server, анонимный preview и модуль identity с Яндекс OAuth,
web-cookie и native Bearer-сессиями. Вход выключен без конфигурации;
[настройка и ограничения](docs/auth.md). Реализованы создание, личный список,
приглашение, RSVP, настройки, состав и лента с сообщениями. Реальное подключение
Яндекс ID пользователь отложил до конца разработки; runtime-обхода входа нет.
Запуск, текущие маршруты и ограничения —
в [README.md](README.md).

## Оформление Go

- Форматируй исходники через `gofmt`. Имена пакетов — короткие, строчными
  буквами. Идентификаторы — `MixedCaps` для экспортируемых объявлений
  и `mixedCaps` для неэкспортируемых; локальные имена — `mixedCaps`.
- Давай экспортируемым объявлениям документацию по их назначению. Избегай
  общих пакетов `utils`, `common` и `helpers` без определённой ответственности.
- Обрабатывай возвращаемые ошибки; при передаче выше добавляй полезный контекст,
  сохраняя исходную причину. Ожидаемые ошибки запроса не обрабатываются через `panic`.
- В операциях ввода-вывода передавай `context.Context` первым аргументом;
  соблюдай отмену и дедлайны. Для запускаемой goroutine определяй срок жизни
  и способ завершения.
- Интерфейсы делай небольшими и определяй у потребителя по реальной потребности.
  Конкретный тип не требует отдельного интерфейса только ради единообразия.

Основа: [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments).

## Архитектура приложения

Для Somewhere начинаем с одного модульного серверного приложения.
Точки входа и сборка зависимостей находятся в `cmd/`, внутренние пакеты —
в `internal/`; это согласуется с [руководством Go по серверным проектам](https://go.dev/doc/modules/layout#server-project).
Фактические пакеты создавай по мере появления функциональности.

- Группируй пакеты по предметной области. Внутри области отделяй прикладные
  операции и бизнес-правила от HTTP, хранения и внешних SDK.
- HTTP-обработчик разбирает запрос, вызывает прикладную операцию и формирует
  ответ. Бизнес-правила не зависят от HTTP-фреймворка, SQL-драйвера или внешнего SDK.
- Доступ к хранилищу и внешним сервисам реализуется адаптерами. Прикладная
  операция получает нужные зависимости явно; связывание происходит при запуске.
- API возвращает данные предметной области и результаты операций. Формат ответа
  отделён от моделей хранения; композиция экранов и навигация принадлежат клиентам.
  Права и бизнес-решения проверяются в серверной операции.
- Выделяй отдельный сервис, общий пакет или дополнительный слой по конкретной
  необходимости. Пустые слои и интерфейсы для каждой структуры не требуются.

## Правила изменений

- Для новой операции сначала опиши поведение, данные, ошибки и права доступа.
  Согласуй изменение API с затронутыми клиентами через общий контракт.
- Клиенты выпускаются независимо от сервера. При изменении API учитывай
  поддерживаемые выпущенные версии web, iOS и Android. Опиши совместимость,
  миграцию и необходимые проверки затронутых клиентов.
- Храни модели БД и детали хранения внутри бэкенда. Представление API должно
  оставаться устойчивым к внутренним изменениям хранения.
- Для совместных действий учитывай повторные запросы и конкурентные изменения:
  например, повторное принятие приглашения или одновременное голосование.
  Решение и проверяемые сценарии фиксируй в проектировании конкретной фичи.
- Изменения схемы данных сопровождай способом миграции и проверкой совместимости.
- Разделяй код по обязанностям внутри приложения. Выделение нового сервиса
  обосновывай отдельной потребностью в проектировании.

## Проверки

Запуск из `backend/` с Go 1.27.2: `go run ./cmd/server` (остановка — Ctrl+C).
Команды проверок:

```sh
go run ./cmd/storage-demo
go test -race ./...
go vet ./...
go build ./...
gofmt -l .
```

Последняя команда должна давать пустой вывод. Для исправления — `gofmt -w .`.
Тесты проверяют память, атомарность, копии, конкурентность, публичный HTTP,
приватность ошибок, JSON-декодер и запуск/остановку сервера. Из корня запускай
`npm run api:test`: реальные HTTP-ответы сравниваются с OpenAPI. При изменении
документации также запускай `npm run agent:check`. Эти команды повторяются в CI.
Identity проверяется с fake-provider: state/PKCE, параллельные входы, web-cookie,
CSRF, handoff, Bearer, отзыв/сроки и очистка. Реальный Яндекс ID, клиентские
приложения и SQL-адаптер пока не проверены. Серверный сценарий встреч проверен
с несколькими профилями тестового OAuth-provider, включая потерю доступа.
Fake-provider допустим только в тестах: runtime использует фиксированные
HTTPS endpoints Яндекса и не принимает dev-user/bypass или provider URL из env.

На временном этапе не подключай PostgreSQL/pgx/goose и не создавай миграции.
В прикладных операциях используй порт `meetings.Store`; память — его адаптер.
Права и бизнес-правила проверяются до изменения данных внутри Update.
Новый Store пустой; примеры добавляются явно. Перезапуск теряет состояние.
Не выдавай успешные тесты мока за готовый продукт или проверенную сохранность данных.
