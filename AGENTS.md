# Правила агента: group-planning

Техническое имя репозитория — `group-planning`, продукт — `somewhere`
со строчной буквы; в подписи знак стоит слева. См. [брендинг](docs/design/branding.md).
Это самостоятельный пет-проект. Используй Git и оригинальный OpenSpec.
Используй проектные навыки и публичные источники. Внутренние корпоративные
навыки, поиск и инфраструктура не являются основой этого проекта.

## Начало работы

Исключение для субагента-исследователя `exploratory-test`: он получает только
нейтральный бриф и инструкцию исследователя, не выполняет стартовое чтение
продуктовых документов, specs, кейсов, исходников или Git. Подготовку окружения
и чтение этих правил выполняет основной агент. Ограничения доступа и безопасности
сохраняются; исключение нужно для согласованного исследования без подсказок.

1. Прочитай [README](README.md), [контекст продукта](docs/product/overview.md),
   [решения по устройству проекта](docs/architecture/decisions.md) и
   [процесс разработки](docs/workflow.md).
2. Проверь рабочее дерево и активные изменения:
   `git status --short --branch` и
   `npm run --silent openspec -- list --json`.
3. Перед редактированием приложения прочитай его правила:

   | Область | Инструкция |
   | --- | --- |
   | Бэкенд | [backend/AGENTS.md](backend/AGENTS.md) |
   | Веб | [frontend/web/AGENTS.md](frontend/web/AGENTS.md) |
   | iOS | [frontend/ios/AGENTS.md](frontend/ios/AGENTS.md) |
   | Android | [frontend/android/AGENTS.md](frontend/android/AGENTS.md) |

   Это необходимо и при запуске агента из корня: локальные инструкции должны
   быть прочитаны для каждой затронутой области. В `frontend/AGENTS.md`
   дополнительного уровня правил нет.
4. Перед первым кодом и при изменении соглашений прочитай
   [общие правила кода](docs/development.md). Для фичи с интерфейсом прочитай
   [правила дизайна](docs/design/README.md) и её UX/UI-материалы.

## Инструменты и OpenSpec

- Корневой Node.js используется для инструментов разработки. Бэкенд — Go,
  веб — React + TypeScript, мобильные приложения — Swift + SwiftUI и
  Kotlin + Jetpack Compose. Каждый клиент реализует свой интерфейс в коде;
  сервер предоставляет данные и операции через общий API. См.
  [ADR 0002](docs/architecture/0002-client-ui.md). Библиотеки и команды Go/web закреплены в локальных инструкциях.
  Команды сборки и проверки каждого клиента — в его локальной инструкции.
- Установка: `nvm use`, `npm ci`. Проверка обвязки: `npm run agent:check`.
- Запускай CLI через `npm run --silent openspec -- <аргументы>`.
  Если готовый навык показывает `openspec ...`, используй этот префикс.
  Он выбирает закреплённую версию и локальный профиль проекта.
- Готовые навыки находятся в `.agents/skills/openspec-*/SKILL.md`.
  Проработка — `openspec-explore`; подготовка изменения — `openspec-propose`;
  правка плана — `openspec-update-change`; реализация — `openspec-apply-change`;
  проверка — `openspec-verify-change`; синхронизация — `openspec-sync-specs`;
  завершение — `openspec-archive-change`.
- Для создания и проверки текстов интерфейса, макетов и онбординга применяй
  [product-copy-editor](.agents/skills/product-copy-editor/SKILL.md). Он проверяет
  назначение текста и повторы между блоками, затем формулировки и состояния.
  Это проектный навык; он не генерируется OpenSpec.
- Выбирай навык по запросу пользователя. Запрос на обсуждение или предложение
  остаётся в границах планирования. Для реализации используй apply и учитывай
  уже данное пользователем разрешение на конкретную работу.
- Перед работой над фичей прочитай её артефакты и соответствующие актуальные
  спецификации. Сценарии содержат критерии приёмки; `tasks.md` — ход выполнения.
- Создавай изменения CLI, сохраняй стандартную схему `spec-driven`.
  Файлы готовых навыков генерируются OpenSpec: изменения процесса задаются
  в `openspec/config.yaml`, а состав навыков — в `scripts/openspec-profile.json`.
- Небольшую техническую правку можно выполнить непосредственно, если она
  не меняет описанное поведение. При изменении поведения синхронизируй требования.

## Дизайн-система и независимая приёмка

- После одобрения UI пользователем, до реализации, примени
  [design-system-publish](.agents/skills/design-system-publish/SKILL.md): токены,
  контракты, версия и manifest состояния. Уже данное одобрение не спрашивай повторно.
- При изменении дизайна во время реализации или ревью сам пройди
  [цикл ревизии](docs/design/revisions.md): обнови реальные макеты и UX/specs/tasks,
  повторно вызови design-system-publish, обнови затронутые токены/контракты и
  манифесты, затем разрешённую реализацию и независимый design-review.
  Задачи с устаревшей приёмкой открой заново; прежние отчёты/evidence сохрани
  с исходными hash. Не жди отдельной команды на эти связанные этапы.
- Источник значений — [design-system](design-system/README.md), композиция и
  платформенные различия — [контракты](docs/design/components/README.md).
  Новые цвета, размеры, шрифты и движение берутся из системы; расширения
  публикуются вместе с согласованным дизайном. Старый literal-инвентарь не расширяй
  ради зелёной проверки. Generated-файлы меняются только генератором.
- После реализации экрана/состояний **обязательно вызови
  [design-review](.agents/skills/design-review/SKILL.md) и запусти отдельного
  субагента для независимой проверки**. Ревьюер читает приложение и эталоны,
  пишет только evidence/отчёт; исполнитель исправляет код и повторяет ревью.
- До закрытия UI-задачи выполни `npm run design:ready -- --manifest <путь>`.
  Непроверенная платформа, старый hash и screenshot-only запуск не дают pass.
  `npm run design:check` проверяет обвязку, но не заменяет визуальную приёмку.
  При явной паузе сохраняй `phase=paused`, не продолжай против воли пользователя.
- Порядок и формат доказательств — [design review](docs/design/review.md).
  Документационные и серверные изменения без UI не требуют визуального ревью.

## Границы и проверка результата

- Для продуктовой задачи примени [test-spec](.agents/skills/test-spec/SKILL.md):
  подготовь testing.md, кейсы и task/case/platform mapping по
  [процессу тестирования](testing/README.md). Пирамида: правила — unit,
  границы — integration, важные сквозные пути — немного E2E; без квот по процентам.
- После реализации поведения вызови [feature-test](.agents/skills/feature-test/SKILL.md)
  с независимым субагентом: работающая фича на каждой заявленной платформе,
  затем qa:ready до checkbox. Основной ручной проход выполняет агент.
  Макеты и зелёная сборка не являются функциональной приёмкой; нет доступа — blocked.
- Перед выкаткой примени [release-test](.agents/skills/release-test/SKILL.md):
  полный набор применимых кейсов, включая прежние nonautomated/partial/flaky,
  обязательные автотесты и точный кандидат. Выполни qa:release-ready и сохрани
  receipt; кандидат можно собрать и опубликовать для проверки до приёмки.
  Изменение поведения/дизайна обновляет кейсы и открывает утратившие приёмку задачи;
  повтори функциональную и, для UI, дизайн-проверку. Старый pass не переносится.
  Для каталога и правил выполняй qa:check и qa:test; они также проверяются в CI.

- Только по явной просьбе пользователя исследовать приложение без кейсов
  используй [exploratory-test](.agents/skills/exploratory-test/SKILL.md).
  Он запускает свежего субагента без истории разработки и продуктовых подсказок;
  пишет отчёт/evidence, не исправляет приложение. Сопоставление с требованиями
  и кейсами делает основной агент после фиксации независимого отчёта.
  Обычная просьба проверить фичу, apply, CI, релиз и создание навыка не запускают
  исследование; его отчёт не заменяет обязательные приёмочные gates.

- Одна фича может затрагивать четыре приложения; в плане явно укажи затронутые
  платформы. Готовность одной платформы не означает готовность остальных.
- Для интерфейсной фичи до реализации подготовь `ux.md` с переходами,
  состояниями, макетами и отличиями платформ; сошлись на него из `design.md`.
  Техническое проектирование не заменяет UX/UI. Для изменения без UI укажи
  неприменимость. Учитывай уже данное разрешение без повторного согласования этапов.
- Соглашения кода действуют и для прототипа. При инициализации приложения
  добавь реальные настройки инструментов и команды проверок в его инструкции.
- Веб обязан следовать локальным требованиям: строгий FSD, алиасы импортов,
  только TypeScript, один небольшой компонент и тип его пропсов в файле. Компоненты, хуки
  и остальные функции веба объявляются через `const` со стрелочной функцией.
  Учитывай эти ограничения при выборе инструментов и разборе сторонних примеров.
- Для интерфейсной фичи запланируй реализацию и проверку в каждом затронутом
  клиенте. Экраны, навигация и формы находятся в клиентском коде; их изменения
  поставляются выпуском соответствующего клиента.
- До заключительного этапа облака и расчёта стоимости используй memory.Store
  и мок очереди. Все вопросы реальной БД/очереди — выбор, SQL-схема, миграции,
  подключение и проверки сохранности — перенесены в группу 14 плана.
  Не возвращай их как условие начала пользовательских функций и не поднимай
  локальную БД/Docker. Прикладные правила, фоновые задачи и их контроль
  реализуются на моках; их сброс при перезапуске описан в
  [backend/README.md](backend/README.md).
- Клиенты взаимодействуют с сервером через API-контракт. Серверные модели БД
  остаются внутри бэкенда. Учитывай ранее выпущенные мобильные клиенты.
- Открытые продуктовые вопросы собраны в
  [docs/product/open-questions.md](docs/product/open-questions.md).
  Не представляй гипотезу или предложенный стек как принятое решение.
- При правках обвязки, инструкций или документации запускай `npm run agent:check`.
  Для кода запускай реальные проверки затронутого приложения, описанные в его
  инструкции. Go и веб имеют сборку/тесты и проверки оформления в CI.
  iOS проверяется через swift-format и чистую simulator-сборку по своей инструкции;
  Android проверяется Gradle wrapper, ktlint, Debug/Release-сборками и Android Lint.
- Отмечай задачу выполненной после реализации её поведения и нужных проверок.
  Структурная валидация OpenSpec не доказывает работоспособность продукта.
- Перед завершением просматривай diff, запускай `git diff --check` и сообщай,
  что проверено, а что осталось непроверенным. Сохраняй чужие изменения.
- По договорённости с пользователем коммить и пушь изменения прямо в `main`,
  без PR. Перед записью обновляй чистый `main` из `origin` без переписывания истории.
- README описывает назначение, структуру и запуск; не добавляй туда текущий
  статус, историю доработок и следующий шаг. Прогресс веди в `tasks.md` изменения,
  результаты проверок — в его отчётах.
- Документы проекта пиши по-русски; сохраняй обязательные структурные заголовки
  и ключевые слова формата OpenSpec на английском. Не добавляй секреты в Git.
