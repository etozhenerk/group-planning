# Подготовка интерфейса

Для фичи с интерфейсом UX/UI готовится после определения сценария и до
завершения технического проектирования и начала реализации. `design.md`
в стандартном OpenSpec описывает техническое решение; макеты и поведение
экранов описываются отдельно. Общий порядок — в [workflow.md](../workflow.md).

## Результат проработки фичи

В созданном через CLI изменении OpenSpec сохраняй дополнительный `ux.md`.
Это документ проекта, а не новый обязательный артефакт стандартной схемы.
Из `design.md` должна вести ссылка на него. Для интерфейсной фичи в нём нужны:

1. **Путь пользователя.** Точка входа, шаги, результат, возврат назад и выход
   из сценария. Для приглашений — прямая ссылка и возврат после авторизации.
2. **Экраны и состояния.** Основное содержимое и действия, загрузка, пустое
   состояние, ошибки, повторная попытка и сохранение ввода. Неприменимые
   состояния отмечай явно.
3. **Макеты.** Проверяемое изображение или интерактивный прототип и его версия.
   Для небольшого изменения достаточно эскиза или существующего компонента
   с описанием правки. Одного списка названий экранов недостаточно.
4. **Три платформы.** Что общее, как экран адаптируется к браузеру и телефонам,
   какие системные переходы и отличия нужны iOS и Android. Учитывай клавиатуру,
   системный размер текста, доступные подписи и управление с клавиатуры в вебе.
5. **Компоненты и данные.** Какие блоки используются, что они показывают,
   какие действия вызывают и что происходит при недоступности действия.
6. **Статус.** Какие решения приняты, что остаётся гипотезой и какие вопросы
   мешают реализации. При изменении поведения синхронизируй specs и задачи.

Масштаб документа соответствует фиче: небольшая правка существующего экрана
может иметь короткий `ux.md` со ссылкой на прежний макет и описанием отличий.
Для изменения без UI укажи неприменимость UX/UI в `design.md`; макеты не нужны.

## Хранение и проверка макетов

- Материалы конкретной фичи храни рядом с `ux.md`, например в каталоге
  `assets/` изменения, и добавляй относительные ссылки. Они сохранятся
  вместе с остальными материалами при архивации изменения.
- Допускается внешний инструмент дизайна. Запиши ссылку на конкретную версию
  или ревизию и сохрани доступный экспорт ключевых экранов в репозитории,
  если ссылка не позволяет воспроизводимо проверить согласованный вид.
- Не описывай ещё не созданный макет как готовый. Не называй дизайн
  согласованным без соответствующего решения пользователя.
- Перед реализацией должны быть определены необходимые экраны, состояния
  и действия. Учитывай уже данное разрешение пользователя на работу;
  эти правила не требуют повторного подтверждения каждого этапа.
- В проверке фичи сопоставь работающий интерфейс с указанной версией макета
  на затронутых платформах. Различай просмотр макета и проверку приложения.

## Общая основа дизайна

В этой папке по мере появления первых макетов сохраняются общие токены
и каталог компонентов. Фича ссылается на них, а новые общие решения
добавляются в эту основу вместе с фичей.

Токены задают смысловые роли цветов, типографику, отступы, размеры и скругления.
Имена должны отражать назначение, например основной текст или опасное действие.
Конкретные значения выбираются на макетах и переносятся в используемый
формат проекта. Не создавай три независимых набора значений по платформам;
необходимые различия фиксируй явно.

Для компонента нужны назначение, входные данные, варианты, состояния, действия
и требования доступности. Связывай описание с макетом, компонентами в коде
затронутых клиентов и нужными данными API по мере их появления. Не заводи каталог всех возможных компонентов
до появления реального сценария.

## Мобильный онбординг

Для iOS и Android принято общее [знакомство по слайдам](mobile-onboarding.md):
визуальные примеры функций, плавное перелистывание и вход на последнем экране.
Документ определяет навигацию, доступность, Reduce Motion и оформление нативных панелей.

## Клиентские интерфейсы и API

Следуй [ADR 0002](../architecture/0002-client-ui.md). Интерфейсы реализуются
на React + TypeScript, SwiftUI и Jetpack Compose в соответствующих клиентах.

- Сценарий, смысл действий и продуктовые состояния общие для web, iOS и Android.
  Каждый клиент реализует состав экранов, навигацию и формы в своём коде.
- Общие токены и описание компонентов служат основой для платформенных
  реализаций. Различия платформ фиксируй в UX/UI и техническом решении.
- Действие пользователя вызывает предметную операцию API. Права доступа
  и бизнес-валидацию проверяет сервер; клиент отражает подтверждённый результат.
- Разделяй данные сервера и локальное состояние: черновик формы, загрузку,
  ошибку, повтор и навигацию. Для каждого состояния укажи владельца.
- Изменения UI поставляются выпуском соответствующего клиента. При изменении
  API сохраняй совместимость с поддерживаемыми выпущенными клиентами.
- Проверяй интерфейс на каждой затронутой платформе; для изменения общего API
  проверяй затронутые сценарии клиентов, включая поддерживаемые старые сборки.
  В результатах указывай, какие версии действительно проверены.

## Действующая система

Начинайте с [дизайн-системы](../../design-system/README.md), её
[каталога токенов](../../design-system/catalog.md),
[контрактов](components/README.md) и [процесса приёмки](review.md).
После одобрения UI применяется `design-system-publish`, после реализации
экрана — `design-review` с независимым субагентом и проверкой `design:ready`.

Действующий пакет — [meeting-experience-refresh](../../openspec/changes/meeting-experience-refresh/ux.md),
одобренный 25.10.2026 с последующими коррекциями 26.10.2026. Реестр authority
показывает источники и приоритет решений. [Основа v0.7](foundations.md)
сохранена как историческая; она не заменяет текущие tokens/контракты.
Проверенные правила текста остаются в [content.md](content.md), бренд —
в [branding.md](branding.md). Публикация системы не означает, что все старые
экраны уже мигрированы и приняты.
