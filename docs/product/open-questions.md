# Открытые решения

Этот список помогает продолжить проработку. Открытые пункты не являются
утверждёнными требованиями. Границы MVP заданы в [описании сценария](mvp-gathering.md),
готовность реализации — в [tasks.md](../../openspec/changes/gathering-activity-feed/tasks.md).

## Решено для первой версии

| Вопрос | Решение |
| --- | --- |
| Для кого делаем продукт? | Для компании друзей. Один человек создаёт встречу или поездку и приглашает остальных ссылкой. |
| Какой сценарий берём первым? | «Собраться». Поездки остаются следующим направлением. |
| Что входит в MVP? | Встреча с обязательной датой и необязательным временем, приглашение, опрос переноса даты, ответы участников, общая лента с чатом, голосования за смену места и задачи подготовки. |
| Что открывается при общем первом входе? | Онбординг с объяснением возможностей и кнопкой «Попробовать», затем Яндекс ID и личные встречи. Прямое приглашение сохраняет свой путь. |
| Как смотреть свои встречи? | Списком или календарём, с предстоящими и прошедшими. Все встречи выбранного дня видны рядом; без итоговой даты — отдельно. |
| Когда встреча становится прошедшей? | Отложенная задача сохраняет статус со следующего календарного дня по часовому поясу встречи, независимо от запросов; согласовано 21.10.2026. |
| Меняются ли действия в истории? | Нет, пока сохраняем существующие права и действия. Воспоминания с фото и видео отложены до следующей итерации; календарный этап их не добавляет. |
| Как пользователь входит? | Через Яндекс ID, с автоматическим созданием профиля при первом входе и возвратом в исходную встречу. Сам вход не подтверждает участие. |
| Что видно до входа по приглашению? | Название, дата, место и полное описание встречи. Для ответа нужен вход; переписка до принятия приглашения закрыта. |
| Когда друг получает переписку? | После успешно сохранённого «Приду». Смена на «Возможно»/«Не смогу» закрывает доступ; повторное «Приду» снова открывает. |
| Кто меняет настройки и видит ответы? | Настройки меняет организатор; участники с доступом видят состав и ответы друг друга. |
| Что означает фото в макете? | Это обложка конкретной встречи. Она не служит общим декором сервиса и не используется для аватаров. Обложка необязательна. |
| Что откладываем? | Подарки, расходы, платежи, воспоминания с фото/видео и планирование поездок. |
| Как выглядит основной экран встречи? | Общая лента действий, карточек голосований и задач, результатов и сообщений участников. Актуальные детали находятся в компактной шапке. |
| Когда голосование меняет место? | Автор задаёт срок, закрытие автоматическое; нужно большинство проголосовавших, без кворума. Ничья/0 сохраняют место. До закрытия голос меняется; одновременно открыт один опрос о месте. |
| Как создаём встречу по решению 22.10.2026? | Дата обязательна, время необязательно; если время не задано, в чате появляется системное сообщение. |
| Кто создаёт опрос даты и задаёт срок? | Любой пользователь с доступом к чату; автор опроса выбирает дату и время окончания. |
| Кого учитываем в опросе даты? | Организатора и текущих участников с ответом «Приду». Только они могут голосовать и входят в большинство/единогласие. «Возможно»/«Не смогу» и их прежние голоса не учитываются. |
| Где найти ответ «Возможно»? | В отдельной вкладке «Приглашения»: открыть приглашение и изменить ответ, без доступа к чату. После «Приду» встреча переходит в «Мои встречи». |
| Как применяется опрос даты? | Большинство от текущего состава с доступом к чату сразу автоматически переносит дату. Двухчасовое ожидание и подтверждение организатора отменены. Скрытый опрос применяет результат при закрытии. Без большинства дата сохраняется. |
| Какие настройки у опроса даты? | Несколько ответов, переголосование и добавление вариантов включены по умолчанию; анонимность и скрытие итогов выключены. Даты идут по порядку. |
| Что меняет скрытие итогов? | Итоги, предложение применить результат и автоматический перенос ждут закрытия; досрочных объявлений результата нет. |
| Как подводим итог при закрытии? | Сразу: большинство — автоматический перенос, без большинства — прежняя дата. Для скрытых итогов то же правило; ожидания нет. |
| Как уведомляем о дате и времени? | Системными строками по центру чата, без имени и аватара. Они бесплатны; будущий AI-помощник относится к подписке. Пуши ещё предстоит проработать. |
| Как показываем число голосов? | Рядом с вариантом «3 голоса», «4 голоса» без повторяющегося «из 6». Общий счётчик проголосовавших этим решением не добавляется. |
| В каком порядке реализуем? | Сначала назначенная дата → создание → приглашение → ответ → чат на web/iOS/Android; календарь, опрос даты, смена места и задачи — следующие этапы того же MVP. |
| Что означает предложение задачи человеку? | Ему предлагают ответственность; принятие — отдельное явное действие. |
| Какое визуальное направление выбрано? | Направление ленты v0.4 одобрено: графит, мягкие формы и живой разговор. Ориентиры — Telegram, Instagram, Discord. Дизайн v0.6 с онбордингом, списком и календарём одобрен. Новый знак предложен отдельно. |
| Какие основные технологии выбраны? | Go для бэкенда, React + TypeScript для веба, Swift + SwiftUI и Kotlin + Jetpack Compose для мобильных приложений. |
| Как согласуем три клиента? | Общие сценарии, UX и API; каждый клиент реализует интерфейс в собственном коде. API учитывает поддерживаемые выпущенные клиенты. |
| Используем ли BDUI? | Нет. По решению пользователя интерфейс поставляется с клиентом; изменения мобильного UI требуют новой сборки. См. ADR 0002. |

Источник принятых продуктовых решений — согласованный
[MVP «собраться»](mvp-gathering.md). Общий контекст — в
[overview.md](overview.md). Технологии и ответственность сервера и клиентов —
в [ADR 0002](../architecture/0002-client-ui.md).

## Пилот и дальнейшее развитие продукта

Согласовано 21.10.2026: первый пилот — друзья автора проекта, примерно шесть
человек, которые собираются время от времени. Встреча — общее пространство
с инструментами, доступными в нужном компании порядке. Следующие направления —
бюджет вместе с учётом покупок и воспоминания после встречи.

Для будущего учёта переводов принято: участник отмечает «Перевёл», получатель
один раз подтверждает «Вся сумма собрана», без ответного подтверждения каждого
перевода. Подробности согласованного направления — в [overview.md](overview.md).

Предлагаемые метрики, критерии и ход проверки — в [плане пилота](validation-plan.md).
Остаётся определить:

- Какую ближайшую реальную встречу проверяем, когда и с каким доступным набором
  функций? Расходы и воспоминания не становятся условием первого пилота
  автоматически; его состав отдельно не согласован.
- Как провести следующую проверку с компанией, не знакомой с автором проекта?
- Как выбирать участников расходов, делить и округлять суммы; что происходит
  при изменении покупки, состава участников или отметки о переводе?
- Как устроены доступ, загрузка и хранение воспоминаний?
- Какие дополнительные функции люди готовы оплачивать? Платность расходов
  и воспоминаний не определена; вопросы подписки и партнёров собраны
  в [бизнес-модели](business-model.md).

## Подписка и безопасность

22.10.2026 согласованы N активаций помощника за оплаченный период подписки
и ограниченный срок каждой от момента включения. Перенос даты, переименование
или изменение участников срок не продлевают. После окончания обычный чат
остаётся, повторное включение расходует новую активацию. Доступ к платным функциям
зависит от подписки организатора, вызывать помощника могут все участники с доступом
к чату. Принято направление косметики подписчика, например значок у имени.

Прежняя общая отсрочка лимитов заменена этим принципом; N, длительность,
тариф и пограничные случаи пока не выбраны. Их список — в
[бизнес-модели](business-model.md). Ограничения по запросам к AI не согласованы.

Также согласована [система безопасности](trust-and-safety.md): жалобы,
автоматические сигналы, проверка медиа, разбор, блокировки и обжалование,
независимо от подписки. Базовая модерация нужна до публичного запуска.
Открыты возрастная политика, юрисдикция и правовой порядок действий,
объём анализа частных чатов, средства проверки, сроки реакции и ответственные.
Это вопросы подготовки отдельного изменения, а не уже реализованные функции.

## Уточнить перед реализацией сценария

- Как отзывать ссылку, удалять участника и передавать владение встречей?
  Смена собственного «Приду» уже определена: она закрывает переписку.
- Нужна ли отдельная сущность компании или достаточно участников одной встречи?
- Для «Приглашений» подготовить размещение вкладки, пустое состояние, загрузку,
  ошибки и переходы на трёх платформах. Состав уже определён: только «Возможно».
- Правила даты закрыты ответами 22.10.2026: один активный опрос, прежний голос
  возвращается вместе с доступом к чату; максимум голосов, выбор организатора
  при равенстве; закрытие после переноса, сохранение времени и RSVP. Ручная смена
  дня отменяет опрос. См. [MVP](mvp-gathering.md). Осталась проверка интерфейсов.
- Что происходит при отмене встречи и нужно ли повторное подтверждение?
- Какие ограничения нужны срокам голосования? Календарная дата и граница
  истории уже определены по часовому поясу самой встречи.
- Как задаётся место: текст, адрес, ссылка, карта? Что видно, пока место не задано?
- Какие уведомления о дате/времени дополнительно отправлять пушами на
  iOS/Android? Системные сообщения в чате уже согласованы.
- Как учитывать вступивших или вышедших участников в опросе места? Для даты
  используются только текущие пользователи с доступом к чату.
- Что происходит при ручном изменении места организатором во время опроса?
  Одновременные активные опросы одного типа уже запрещены для места и даты.
- Кто может принять задачу, адресованную другому, как отказаться и передать её?
- Нужны ли в первой версии завершение, сроки и отмена задач?
- Нужны ли редактирование/удаление сообщений и непрочитанное? Отправка, повтор
  и догрузка первого среза описаны в техническом плане.

## Технический план первого среза

Подготовлены [проектирование](../../openspec/changes/gathering-activity-feed/design.md),
[операции API](../../openspec/changes/gathering-activity-feed/api.md),
[авторизация](../../openspec/changes/gathering-activity-feed/auth.md) и
[задачи](../../openspec/changes/gathering-activity-feed/tasks.md).
По решению пользователя от 20 октября создание БД отложено: сначала mock
в памяти Go-процесса. Данные теряются после перезапуска; постоянное хранение —
отдельный этап. HTTP/JSON + OpenAPI и серверный обмен Яндекс OAuth остаются в плане. Дальнейшие
продуктовые условия не мешают началу первого среза, но блокируют свои этапы.

## Что закрепить при реализации

- Превратить описанный API в OpenAPI и проверяемые fixtures на Go и в клиентах.
- Реализовать описанные компоненты, состояние и навигацию первого сценария;
  проверить адаптацию и доступность на каждой платформе.
- Совместимость API между независимыми выпусками сервера и клиентов;
  период поддержки старых сборок и порядок миграции при изменении контракта.
- Закрепить версии Vite и средств проверки контракта. Вопросы реальной БД
  и очереди собраны в заключительном этапе ниже.
- Проверить предложенные минимумы iOS 17 / Android API 26 и закрепить среду сборки.
- Проверить Яндекс ID на целевых платформах и собственные сессии по auth.md.
- Локальное окружение и настройка приложения в Яндекс OAuth; выбор хостинга —
  в заключительном этапе облака.
- Средства сборки, тестирования и CI; необходимость хранения файлов в MVP.
- Загрузка и хранение обложек, ограничения форматов и размеров; отдельные данные
  аватара профиля и вариант с инициалами, если фотографии нет.
- Поставка обновлений ленты, порядок событий, хранение сообщений и связь
  результата голосования с изменением места без дублирования событий.

## Заключительный этап: облако, БД и стоимость

По решению пользователя от 21.10.2026 эти вопросы обсуждаются после реализации
сценариев на моках и не блокируют их разработку. План — группа 14 tasks.md
изменения `gathering-activity-feed`.

- Каковы стартовая нагрузка, объём данных/файлов и сценарий роста?
- Какое облако, размещение и конфигурация нужны; сколько в месяц стоят
  вычисления, БД, очередь, диски, трафик, резервные копии и мониторинг?
- Какую БД и библиотеку очереди выбираем? PostgreSQL + River пока только кандидат.
- Как устроить SQL-схему, транзакции, миграции, сроки хранения и очистку истории?
- Как проверить сохранность встреч и задач, пропущенные сроки и восстановление
  после сбоя/из резервной копии на целевой инфраструктуре?

Принятое продуктовое решение переносится в документ MVP и затем в спецификации
конкретного изменения. Технические решения фиксируются в
[архитектурных документах](../architecture/decisions.md) или соответствующем
изменении OpenSpec. Закрытый вопрос отмечается здесь с указанием источника.
