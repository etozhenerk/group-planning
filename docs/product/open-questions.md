# Открытые решения

Этот список помогает продолжить проработку. Открытые пункты не являются
утверждёнными требованиями. Продуктовые границы согласованы 19 октября 2026 года;
пользовательские функции ещё не реализованы.

## Решено для первой версии

| Вопрос | Решение |
| --- | --- |
| Для кого делаем продукт? | Для компании друзей. Один человек создаёт встречу или поездку и приглашает остальных ссылкой. |
| Какой сценарий берём первым? | «Собраться». Поездки остаются следующим направлением. |
| Что входит в MVP? | Встреча, приглашение, дата или опрос времени, ответы участников, общая лента с чатом, голосования за смену места и задачи подготовки. |
| Что открывается при общем первом входе? | Онбординг с объяснением возможностей и кнопкой «Попробовать», затем Яндекс ID и личные встречи. Прямое приглашение сохраняет свой путь. |
| Как смотреть свои встречи? | Списком или календарём, с предстоящими и прошедшими. Все встречи выбранного дня видны рядом; без итоговой даты — отдельно. |
| Когда встреча становится прошедшей? | С начала следующего календарного дня по часовому поясу встречи; решение пользователя от 21.10.2026. |
| Меняются ли действия в истории? | Нет, пока сохраняем существующие права и действия. Новую механику прошедших встреч пользователь перенёс на следующую итерацию; подробности ещё не заданы. |
| Как пользователь входит? | Через Яндекс ID, с автоматическим созданием профиля при первом входе и возвратом в исходную встречу. Сам вход не подтверждает участие. |
| Что видно до входа по приглашению? | Название, дата и место встречи. Для ответа нужен вход; переписка до принятия приглашения закрыта. |
| Когда друг получает переписку? | После успешно сохранённого «Приду». Смена на «Возможно»/«Не смогу» закрывает доступ; повторное «Приду» снова открывает. |
| Кто меняет настройки и видит ответы? | Настройки меняет организатор; участники с доступом видят состав и ответы друг друга. |
| Что означает фото в макете? | Это обложка конкретной встречи. Она не служит общим декором сервиса и не используется для аватаров. Обложка необязательна. |
| Что откладываем? | Подарки, расходы, платежи и планирование поездок. |
| Как выглядит основной экран встречи? | Общая лента действий, карточек голосований и задач, результатов и сообщений участников. Актуальные детали находятся в компактной шапке. |
| Когда голосование меняет место? | Автор задаёт срок, закрытие автоматическое; нужно большинство проголосовавших, без кворума. Ничья/0 сохраняют место. До закрытия голос меняется; одновременно открыт один опрос о месте. |
| В каком порядке реализуем? | Сначала назначенная дата → создание → приглашение → ответ → чат на web/iOS/Android; календарь, опрос даты, смена места и задачи — следующие этапы того же MVP. |
| Что означает предложение задачи человеку? | Ему предлагают ответственность; принятие — отдельное явное действие. |
| Какое визуальное направление выбрано? | Направление ленты v0.4 одобрено: графит, мягкие формы и живой разговор. Ориентиры — Telegram, Instagram, Discord. Дизайн v0.6 с онбордингом, списком и календарём одобрен. Новый знак предложен отдельно. |
| Какие основные технологии выбраны? | Go для бэкенда, React + TypeScript для веба, Swift + SwiftUI и Kotlin + Jetpack Compose для мобильных приложений. |
| Как согласуем три клиента? | Общие сценарии, UX и API; каждый клиент реализует интерфейс в собственном коде. API учитывает поддерживаемые выпущенные клиенты. |
| Используем ли BDUI? | Нет. По решению пользователя интерфейс поставляется с клиентом; изменения мобильного UI требуют новой сборки. См. ADR 0002. |

Источник принятых продуктовых решений — согласованный
[MVP «собраться»](mvp-gathering.md). Общий контекст — в
[overview.md](overview.md). Технологии и ответственность сервера и клиентов —
в [ADR 0002](../architecture/0002-client-ui.md).

## Уточнить перед реализацией сценария

- Кто первые тестировщики и какую конкретную встречу они организуют?
- Как отзывать ссылку, удалять участника и передавать владение встречей?
  Смена собственного «Приду» уже определена: она закрывает переписку.
- Нужна ли отдельная сущность компании или достаточно участников одной встречи?
- Какие ответы допустимы в опросе? Как голоса по датам связаны с ответами
  «Приду», «Возможно», «Не смогу» после выбора итогового времени?
- Как менять ответы и варианты опроса даты? Что происходит при переносе,
  смене места или отмене встречи и нужно ли повторное подтверждение?
- Какие ограничения нужны срокам голосования? Календарная дата и граница
  истории уже определены по часовому поясу самой встречи.
- Как долго хранить историю после появления постоянного хранилища?
  Сейчас действует прежнее ограничение mock: перезапуск удаляет данные.
- Какую новую механику прошедших встреч добавить в следующей итерации?
  Пользователь сообщил об идее, но пока её не описал; текущий календарь
  не вводит новых действий или ограничений истории.
- Как задаётся место: текст, адрес, ссылка, карта? Что видно, пока место не задано?
- Как уведомлять об итоговом времени и изменениях: внутри продукта,
  письмом, push-уведомлением или другим способом?
- Как учитывать вступивших или вышедших участников при подсчёте голосов?
- Что происходит при ручном изменении места организатором во время опроса?
  Одновременные опросы уже запрещены согласованным правилом.
- Кто может принять задачу, адресованную другому, как отказаться и передать её?
- Нужны ли в первой версии завершение, сроки и отмена задач?
- Нужны ли редактирование/удаление сообщений и непрочитанное? Отправка, повтор
  и догрузка первого среза описаны в техническом плане.

## Технический план первого среза

Подготовлены [проектирование](../../openspec/changes/gathering-activity-feed/design.md),
[операции API](../../openspec/changes/gathering-activity-feed/api.md),
[авторизация](../../openspec/changes/gathering-activity-feed/auth.md) и
[задачи](../../openspec/changes/gathering-activity-feed/tasks.md).
По решению пользователя от 20 октября создание БД отложено: сначала mock
в памяти Go-процесса. Данные теряются после перезапуска; постоянное хранение —
отдельный этап. HTTP/JSON + OpenAPI и серверный обмен Яндекс OAuth остаются в плане. Дальнейшие
продуктовые условия не мешают началу первого среза, но блокируют свои этапы.

## Что закрепить при реализации

- Превратить описанный API в OpenAPI и проверяемые fixtures на Go и в клиентах.
- Реализовать описанные компоненты, состояние и навигацию первого сценария;
  проверить адаптацию и доступность на каждой платформе.
- Совместимость API между независимыми выпусками сервера и клиентов;
  период поддержки старых сборок и порядок миграции при изменении контракта.
- Закрепить версии Vite и средств проверки контракта. PostgreSQL, pgx/goose
  и миграции отложены вместе с созданием БД.
- Проверить предложенные минимумы iOS 17 / Android API 26 и закрепить среду сборки.
- Проверить Яндекс ID на целевых платформах и собственные сессии по auth.md.
- Хостинг, локальное окружение и настройка приложения в Яндекс OAuth.
- Средства сборки, тестирования и CI; необходимость хранения файлов в MVP.
- Загрузка и хранение обложек, ограничения форматов и размеров; отдельные данные
  аватара профиля и вариант с инициалами, если фотографии нет.
- Поставка обновлений ленты, порядок событий, хранение сообщений и связь
  результата голосования с изменением места без дублирования событий.

Принятое продуктовое решение переносится в документ MVP и затем в спецификации
конкретного изменения. Технические решения фиксируются в
[архитектурных документах](../architecture/decisions.md) или соответствующем
изменении OpenSpec. Закрытый вопрос отмечается здесь с указанием источника.
