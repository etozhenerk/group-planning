# Решения по устройству проекта

## Принято

### Один монорепозиторий

`backend/` содержит серверную часть. Клиенты находятся в `frontend/web/`,
`frontend/ios/` и `frontend/android/`. Корневой `AGENTS.md` задаёт общие правила,
каждое из четырёх приложений содержит собственную инструкцию.
Дополнительный `frontend/AGENTS.md` не используется.

У каждого приложения будут самостоятельные сборка, проверки и выпуск.
Единое изменение может согласованно затронуть сервер и несколько клиентов.

### Стандартный SDD

Оригинальный OpenSpec находится в `openspec/`. Постоянные спецификации
хранятся в `openspec/specs/`, работа над изменениями — в `openspec/changes/`.
Готовые навыки устанавливаются в `.agents/skills/` и коммитятся вместе с кодом.
AIFF и корпоративная инфраструктура не входят в этот проект.

### Инструменты воспроизводимы

Версии корневых инструментов зафиксированы в `package.json` и `package-lock.json`.
`.nvmrc` задаёт проверенную версию Node.js для них. Это не выбор стека приложений.
Пакеты устанавливаются из публичного npm registry.

Состав навыков задаёт `scripts/openspec-profile.json`. Обёртка
`scripts/openspec.mjs` запускает официальный CLI, передавая профиль через
игнорируемую `.cache/openspec/`. Настройки профиля и данные CLI изолированы
от пользовательской конфигурации. При запуске обёртки телеметрия и предложения
самообновления CLI отключены; обновление версии выполняется явным изменением проекта.

### Основные технологии и клиентские интерфейсы

Бэкенд пишем на Go, веб — на React + TypeScript со строгим FSD. Для мобильных
приложений выбраны Swift + SwiftUI и Kotlin + Jetpack Compose.

Каждый клиент реализует экраны, навигацию, формы и состояние интерфейса
в собственном коде. Сервер предоставляет предметные данные и операции через
общий API, проверяет права и обеспечивает согласованность бизнес-операций.
Сценарии, UX и основа дизайна общие; детали реализации учитывают платформу.

Решение описано в [ADR 0002](0002-client-ui.md), который заменяет прежний выбор
BDUI. Изменения мобильного интерфейса требуют выпуска новой сборки.
API должен сохранять совместимость с поддерживаемыми выпущенными клиентами.
HTTP-сервер с анонимным preview и OpenAPI-контрактом добавлен;
вход, приватные операции и клиентские приложения ещё не реализованы.
Go и контракт проверяются по backend/AGENTS.md.

## Предложено для первого рабочего среза

В [техническом плане](../../openspec/changes/gathering-activity-feed/design.md)
описаны HTTP/JSON + OpenAPI, серверный обмен Яндекс OAuth,
собственные сессии, атомарные изменения ленты и реализация клиентов.
20 октября 2026 года пользователь отложил БД: первый этап использует
mock-адаптер в памяти одного Go-процесса. Перезапуск сбрасывает состояние.
PostgreSQL и его инструменты вернутся на отдельном этапе постоянного хранения.
Go-модуль, memory-адаптер, HTTP-сервер и анонимный preview добавлены.
OAuth и приватные операции остаются следующими задачами.
Порядок, подтверждённый пользователем: назначенная дата → создание → приглашение
→ ответ → чат на трёх клиентах. Следующие возможности остаются в объёме MVP.

## Что закрепить и проверить при реализации

- Превратить проект API в машинный контракт и общие проверяемые fixtures.
- Реализовать описанное состояние, навигацию и компоненты первого сценария
  в каждом клиенте, затем проверить его с реальным API.
- Закрепить совместимые версии предложенных библиотек, сборки и окружение;
  проверить выбранное хранение, транзакции и интеграцию Яндекс ID.
- Начать серверную часть одним приложением с модулями; появление дополнительных
  сервисов обосновывать конкретными задачами.
- Вынести общий код только при наличии реального использования несколькими частями.

Принятые решения фиксируются здесь либо отдельным ADR в этой папке.
При подготовке технического изменения OpenSpec ссылайся на соответствующий ADR
и описывай в артефактах изменения конкретную реализацию и проверки.
