# ADR 0003: модульный монолит и условия выделения сервисов

Статус: Monolith First принят пользователем 21.10.2026.
Ниже закреплены границы развития и критерии рассмотрения отдельных сервисов.
Это архитектурное решение; соответствие всего существующего кода этим границам
ещё нужно проверить. Оно не запускает разделение или новые функции.

## Решение

Бэкенд развивается как модульный монолит: одно серверное приложение,
один прикладной Go-модуль и явные границы предметных областей.
Вспомогательный модуль `backend/tools` сохраняет отдельные зависимости инструментов.
Web остаётся одним приложением; три клиента продолжают использовать общий API.
Монорепозиторий сохраняется и при возможном выделении сервисов.

Пакеты создаются по мере реализации функций. Заранее создавать пустые сервисы,
сетевые вызовы между локальными модулями или отдельные хранилища не требуется.
Все вопросы реальной БД/очереди и облачных ресурсов остаются в группе 14
[плана MVP](../../openspec/changes/gathering-activity-feed/tasks.md).

## Границы модулей

| Модуль | Ответственность и данные | Состояние |
| --- | --- | --- |
| `identity` | Профиль пользователя, внешняя идентичность, вход и сессии. Возвращает проверенного пользователя, не меняет встречи. | Существует. |
| `meetings` | Встреча, приглашение, участие, права в плане, лента, расписание; сюда добавляются голосования и задачи подготовки. | Существует, часть функций в плане MVP. |
| `notifications` | Доставка уведомлений, попытки и результат отправки. Получает событие или поручение, не решает бизнес-правила встречи. | Будущий модуль. |
| `assistant` | Запросы к помощнику, контекст разрешённого плана, поиск/сравнение и предложения действий. Обращается к операциям встречи с проверкой прав. | Гипотеза после MVP. |
| `billing` | Подписка пользователя, её состояние и платёжные операции. Не владеет встречами или доступом к их переписке. | После MVP. |
| `bookings` | Партнёрские предложения, ссылки и учёт бронирований/вознаграждения. Не хранит собственную изменяемую копию плана встречи. | После MVP. |

Это логические области, а не обещание выделить шесть сервисов.
Внутренние подпакеты вводятся по объёму и обязанностям кода.
Встреча, участие и её лента остаются в одной области: изменение прав,
состояния встречи и соответствующая запись ленты требуют согласованности.

Структура прикладного кода развивается внутри существующего `backend/`:

```text
backend/
  go.mod
  cmd/server/
  internal/
    server/          # запуск и связывание зависимостей
    httpapi/         # HTTP transport
    webui/           # веб-оболочка и публичные метаданные
    identity/
    meetings/
    storage/memory/  # временные адаптеры хранения
```

Будущие `notifications`, `assistant`, `billing`, `bookings` добавляются рядом
в `internal/`, когда для них появляется реализация. Каталог `services/`
и отдельные сборки появляются при обоснованном выделении конкретного модуля.
Структура каталогов сама по себе не обеспечивает изоляцию.

## Правила взаимодействия

- Модуль владеет изменениями своих данных. Другие области обращаются к его
  прикладным операциям через узкие контракты; не получают чужой `Store`,
  `Writer` или доступ к изменяемому состоянию.
- Контракты описывают входные данные, результат, ошибки и правила повторов.
  Интерфейс определяется у потребителя по реальной необходимости; зависимости
  связываются при запуске. Циклические зависимости исключаются.
- Прикладные правила не зависят от HTTP, конкретного хранения или SDK
  внешнего провайдера. Transport и адаптеры вызывают правила своей области.
  Общий пакет предметных моделей всех модулей не вводится.
- Нужные изменения встречи и ленты сохраняются атомарно в `meetings`.
  Постановка задания на переход в историю согласована с сохранением встречи.
  Обработчик вызывает операцию `meetings`, а не повторяет её бизнес-логику.
- Уведомления и другая последующая работа запускаются после успешного изменения.
  Для требуемой надёжной доставки согласованно сохраняются изменение и поручение;
  повторы безопасны. Конкретный механизм постоянного хранения обсуждается в группе 14.
- Внешние вызовы не выполняются внутри транзакции встречи. Задачи помощника
  и доставки имеют управляемое время выполнения и параллелизм, чтобы сохранять
  ресурсы для основного API. Это техническая изоляция работ; продуктовые лимиты
  использования помощника сейчас не проектируются.
- `assistant` получает состояние подписки через `billing`, а организатора
  и разрешённый контекст — через операции `meetings`. Правило доступа соответствует
  [бизнес-модели](../product/business-model.md): подписка организатора открывает
  помощника всем участникам с доступом к чату. Основные операции встречи
  не должны требовать доступности AI-провайдера.

В текущем коде ещё есть сборка прикладных зависимостей внутри `httpapi`
и передача порта хранения для публичного preview. Ревизия этих мест входит
в подготовку границ, а не считается уже выполненной. Архитектурная проверка
импортов и тесты контрактов запланированы в задаче 2.6; сейчас отдельного
автоматического контроллера границ нет. `internal/` в Go не запрещает
произвольные зависимости между соседними пакетами внутри бэкенда.

## Фоновые задачи и процессы

Пока используется память, API и обработчики работают в одном процессе
с одними экземплярами хранилища и мока очереди. Перезапуск теряет состояние.
Второй процесс с отдельной памятью не получает данные первого.

При подключении постоянного хранения можно отдельно запускать API и воркеры
из того же приложения для разного масштабирования и изоляции ресурсов.
Это ещё не выделение самостоятельного предметного сервиса. Для перехода
нужны проверки совместной работы процессов и сохранности из группы 14.
Очередь задач сама по себе не требует микросервисной архитектуры.

## Когда начинаем рассматривать выделение

Достаточен один подтверждённый сигнал из таблицы. Он запускает разбор конкретного
модуля, а не автоматическое разделение всего приложения. Доказательством
может быть инцидент, измерения в эксплуатации или воспроизводимый тест
на ожидаемой нагрузке; ждать отказа у пользователей не требуется.

| Сигнал | Что измеряем | Что проверяем до выделения сервиса |
| --- | --- | --- |
| Основные операции выходят за согласованные цели качества из-за помощника или фоновых работ. | Задержки p95/p99 и долю ошибок основных операций с этой нагрузкой и без неё, потребление CPU/памяти, задержку готовых к запуску задач. | Дедлайны, управление параллелизмом, отдельные исполнители/процессы. Если они обеспечивают цели качества, отдельный сервис не нужен. |
| Масштабирование всего приложения ради одного модуля дороже его отдельного запуска с учётом сопровождения либо не обеспечивает нужную производительность. | Профили нагрузки, скорость поступления/обработки задач и стоимость масштабирования всего приложения против нужной части. | Оптимизацию узкого места и масштабирование воркеров. Сравниваем полную стоимость двух вариантов, включая сопровождение. |
| Изменения одной области регулярно задерживают или нарушают независимые выпуски других. | Заблокированные выпуски, причины откатов, время от готовности изменения до поставки. | Разделение проверок, исправление зависимостей и локальное упрощение кода. Отдельный сервис полезен, если сохраняется потребность в самостоятельном выпуске. |
| Области нужны отдельная среда выполнения, доступы или уровень изоляции. | Конкретное требование и сценарий, который текущая схема не обеспечивает. | Возможность решить требование настройками или отдельным процессом. Проверяем, что сервисная граница действительно обеспечивает изоляцию. |

Число пользователей, файлов или наличие очереди не задают универсальный порог.
В группе 14.1 определяем измеримые цели качества (SLO) для основных операций
и допустимую задержку задач, ожидаемую нагрузку и окно наблюдения. В 14.4
снимаем исходные показатели и проверяем их под нагрузкой и при сбоях.
Произвольные значения миллисекунд, RPS или числа пользователей здесь не назначены.

## Условия решения о выделении

Выделяем один модуль, когда одновременно выполнены три условия:

1. Есть подтверждённая потребность и показано, почему более простые меры
   недостаточны или дороже. Заранее определена проверяемая цель выделения.
2. Граница устойчива: понятны операции и владелец данных; не нужна общая
   атомарная запись в хранилища двух сервисов. Если она нужна, сначала
   уточняем границу и правила согласованности.
3. Подготовлены самостоятельные сборка, выпуск, мониторинг и откат;
   определён ответственный за работу сервиса. План покрывает сетевые сбои,
   повторы, совместимость контрактов и перенос данных. Польза оправдывает
   дополнительную стоимость эксплуатации.

Извлечение функции в сервис требует нового проектирования её сетевого
контракта и отказов: перенос папки не делает локальный вызов надёжным сетевым.
При общей записи в одни данные несколькими сервисами граница не завершена.

## Порядок перехода

Для каждого выделения создаётся отдельное изменение OpenSpec с измерениями,
альтернативами, целью и ожидаемой стоимостью. Сначала закрепляются контракты
и тесты, затем выполняется постепенное переключение на сервис с одним владельцем
записи данных. План миграции определяет сверку данных, действия при повторах
и откат; несогласованная двойная запись недопустима.

После переключения повторяются измерения цели и проверяется независимость
сборки/выпуска. Веб и мобильные клиенты сохраняют внешний API, пока отдельным
контрактным изменением не обосновано другое поведение.

Первые кандидаты на такой разбор — помощник и уведомления при появлении
соответствующих сигналов. Их выделение не запланировано автоматически.
Сбой помощника должен оставлять доступными встречи и обычную переписку;
это проверяемый сценарий изоляции, а не гарантия одного лишь выбора архитектуры.

## Основания

- [Martin Fowler: Monolith First](https://martinfowler.com/bliki/MonolithFirst.html)
  — подход к уточнению границ до разделения на сервисы.
- [Martin Fowler: Microservice Prerequisites](https://martinfowler.com/bliki/MicroservicePrerequisites.html)
  — необходимость наблюдаемости, выпуска и сопровождения.
- [Go: Organizing a module](https://go.dev/doc/modules/layout#server-project)
  — `cmd/` и `internal/` для серверного приложения.

Конкретные границы и критерии выше — решение somewhere, основанное на нашем
коде и сценариях, а не универсальный стандарт из этих источников.
