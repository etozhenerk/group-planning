# ADR 0002: интерфейсы в клиентах и общий API

Статус: принято 19 октября 2026 года по решению пользователя.
Заменяет [ADR 0001](0001-bdui.md). Реализация приложений ещё не начиналась.

## Контекст

Somewhere развивается для web, iOS и Android. Сценарии и UX первой встречи
согласованы в [материалах изменения](../../openspec/changes/gathering-activity-feed/ux.md).
Ранее выбранный BDUI предполагал общую серверную композицию экранов.
Пользователь решил отказаться от этого подхода и реализовывать интерфейсы
непосредственно в клиентах. Для пет-проекта это убирает отдельную работу над
движком, описанием UI и его поддержкой на трёх платформах.

## Решение

| Область | Ответственность |
| --- | --- |
| Go, `backend/` | Авторизация и сессии, права, предметные данные, бизнес-операции, хранение и согласованность совместных действий. |
| React + TypeScript, `frontend/web/` | Экраны и компоненты по строгому FSD, маршрутизация, формы, состояние UI и браузерные интеграции. |
| Swift + SwiftUI, `frontend/ios/` | Нативные экраны, навигация, формы, состояние UI и системные интеграции iOS. |
| Kotlin + Jetpack Compose, `frontend/android/` | Нативные экраны, навигация, формы, состояние UI и системные интеграции Android. |

Сервер предоставляет общий API предметных данных и операций. Например,
клиент получает данные встречи и ленты, отправляет ответ на приглашение
и показывает подтверждённое состояние. API не задаёт дерево компонентов,
раскладку экрана или клиентскую навигацию. Модели БД остаются внутри бэкенда.

Каждый клиент отвечает за композицию UI, черновики, загрузку, ошибки и повтор
действия. Сервер остаётся источником подтверждённых данных и проверяет права
и бизнес-правила независимо от клиента.

Сценарии, критерии приёмки и основа дизайна общие. Компоненты реализуются
средствами каждой платформы с явным описанием отличий в UX/UI. Общая семантика
и токены не требуют одного исполняемого UI-кода для трёх технологий.

BDUI, DivKit и прототип серверной доставки интерфейса исключены из плана.
Согласованные продуктовые возможности и макеты v0.7 сохраняются.

## Выпуск и совместимость

Изменение экранов или навигации поставляется выпуском соответствующего клиента.
Для мобильного интерфейса нужна новая сборка приложения. Прежняя цель менять
его с сервера при недоступности выпуска через магазин больше не обеспечивается
архитектурой.

Сервер и клиенты выпускаются независимо. Изменения API должны сохранять работу
поддерживаемых выпущенных клиентов; период поддержки и способ миграции контракта
предстоит определить. При изменении общего API проверяются затронутые сценарии
клиентов, включая поддерживаемые старые сборки. Для UI нужна отдельная проверка
реализации по макетам на каждой затронутой платформе.

## Последствия и дальнейшая работа

У каждой платформы будет собственная реализация UI, поэтому общую фичу нужно
планировать и проверять в трёх клиентах. Нативные возможности и поведение
интерфейса можно развивать средствами выбранного стека каждой платформы.

В текущем изменении обновляются решения, инструкции и планирование;
приложения, API и миграции исполняемого кода не создаются. Следующий шаг —
технический план и задачи первого сквозного пути: создание встречи,
передача приглашения и ответ друга после входа через Яндекс ID.
Формат API, библиотеки, версии, база данных и среда выпуска пока не выбраны.
