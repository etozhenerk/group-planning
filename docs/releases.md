# Независимые релизы somewhere

Сборка выпускается из существующего Git-тега на коммите, входящем в `origin/main`.
Новый production-выпуск проходит опубликованный тег → `Component releases` →
GitHub Release с исходным набором файлов → установка именно этого набора.
Локальный тег, готовый dist и разрешение выпустить с ограничениями приёмки
не заменяют этот путь. Не переключать production на локально собранный пакет,
обходя публикацию тега и выпуск артефактов.
Версии пяти компонентов независимы; backend и web не пересобирают друг друга.
[Workflow](../.github/workflows/releases.yaml) создаёт GitHub Release с готовыми
файлами. Деплой в Yandex Cloud и отправка в магазины — отдельные действия над
этими же файлами. Terraform и настройки хоста хранятся в Git и меняются отдельно.

## Состав

| Тег (пример) | Файлы релиза | Назначение |
| --- | --- | --- |
| `backend/v1.0.0` | `backend-linux-amd64.tar.gz` | Go API и worker в одном процессе, systemd unit, пример env; SQL migrations включаются при наличии каталога |
| `web/v1.0.0` | `web.tar.gz` | Production static bundle React, API того же origin |
| `monitoring/v1.0.0` | `monitoring-functions.zip` | Vendored исходники двух закрытых Cloud Functions: `handler.Handler` и `probe.Probe` |
| `android/v1.0.0` | `somewhere.aab`, `somewhere.apk`, `mapping.txt` | AAB для Play, подписанный release APK для проверки/магазина, R8 mapping |
| `ios/v1.0.0` | `Somewhere.xcarchive.zip`, `Somewhere.ipa`, `dSYMs.zip` | Архив Xcode, App Store Connect export и символы |

Каждый выпуск также содержит `manifest.json` и `SHA256SUMS`. Манифест фиксирует
компонент, версию, тег, commit SHA, build number, проверки, параметры сборки,
имена/размеры/SHA-256 файлов. Контрольные суммы покрывают и манифест.
Неполный набор, лишний файл, symlink или несовпадение хеша запрещают публикацию.
Манифест не заменяет доверие к репозиторию и правам записи в GitHub.

Описание каждого GitHub Release следует [единому шаблону](release-description.md).
Изменения и причина номера берутся из карточки, результаты CI и список файлов —
из manifest. Описание не приравнивает публикацию файлов к деплою или выходу в стор.

## Выпуск

### Выбор номера

Используем [SemVer](https://semver.org/) отдельно для каждого компонента:
`MAJOR.MINOR.PATCH`, кандидат — `-rc.N`, где N начинается с 1.
В начальной фазе `0.x` исправления увеличивают PATCH, новые возможности
и несовместимые изменения — MINOR. Несовместимость всегда описывается явно
и не разрешает ломать поддерживаемые мобильные клиенты. После 1.0.0
несовместимый контракт увеличивает MAJOR; младшие числа обнуляются.

| Состав выпуска | До 1.0.0 | Начиная с 1.0.0 |
| --- | --- | --- |
| Исправление, оптимизация или обновление зависимости без изменения контракта | PATCH: `0.2.0 → 0.2.1` | PATCH: `1.2.0 → 1.2.1` |
| Новая совместимая возможность | MINOR: `0.2.1 → 0.3.0` | MINOR: `1.2.1 → 1.3.0` |
| Несовместимый контракт или удаление поддерживаемой возможности | MINOR с явным описанием несовместимости | MAJOR: `1.2.1 → 2.0.0` |
| Следующий кандидат той же версии | Увеличить только `rc.N` | Увеличить только `rc.N` |
| Документация без изменения поставляемого артефакта | Выпуск не нужен | Выпуск не нужен |

При смешанном составе выбираем самый высокий необходимый уровень.
Для backend контракт включает API и совместимость миграций; для web/mobile —
пользовательские возможности и поддержку API; для monitoring — события,
конфигурацию и интеграции. Исправление CI само по себе не выпускает все компоненты.

Примеры: `0.1.0 → 0.1.1` — исправление, `0.1.1 → 0.2.0` — новая возможность,
`0.2.0-rc.1 → 0.2.0-rc.2 → 0.2.0` — кандидаты и окончательный выпуск.
Первую линию компонента начинаем с `0.1.0`. Переход к `1.0.0` утверждается
отдельно после приёмки объёма и стабильного контракта. В MVP у компонента одна
активная линия; новый номер старше всех уже зарезервированных его тегов.

Номер определяется по всему составу выпуска. `feat`/`fix`/`BREAKING CHANGE`
помогают его предложить, но не заменяют оценку совместимости. Правка документов
без нового артефакта выпуска не требует. Версия API, SQL migration ID,
версии других клиентов и package.json обвязки не являются версией сайта.

### Карточка и тег

1. Завершить проверки приложения на нужном коммите `main`. Старые установленные
   мобильные версии должны продолжать работать с новым API.
2. Из чистого актуального main после `git fetch --tags origin main` подготовить
   карточку. Команда проверяет номер и сохраняет JSON, не создавая тег:

   ```sh
   python3 scripts/release/prepare.py \
     --tag web/v0.1.0-rc.3 --bump initial \
     --reason 'Первый выпуск с полной версией сайта' \
     --change 'Полный номер в справке и футере десктопного онбординга' \
     --check 'Укажите фактические результаты проверок и ссылки' \
     --compatibility 'API не меняется' \
     --limitations 'Укажите непроверенные сценарии либо отсутствие ограничений' \
     --output /tmp/somewhere-web-release.json
   ```

   Номер примера не зарезервирован: выбрать свободный по актуальным тегам.
   Bump: `initial` до первого финала, затем `patch`, `minor` или `major`;
   базовая версия должна быть следующим соответствующим номером. Для RC той же
   базы увеличивается N, а сравнение bump идёт от предыдущего финала.
   `--change` и `--check` можно повторять. Не включать секреты в карточку:
   аннотация тега и release notes публичны.

3. Проверить карточку: компонент, предыдущий/новый номер, SHA, причину,
   изменения, совместимость и ограничения. Зафиксировать решение владельца
   в сообщении/отчёте; учитывать уже выданное поручение без повторного запроса.
   При смене SHA или состава обновить карточку и решение. Создать аннотированный
   тег **на SHA из карточки** и отправить только его:

   ```sh
   git tag -a web/v0.1.0-rc.3 <COMMIT_ИЗ_КАРТОЧКИ> -F /tmp/somewhere-web-release.json
   git push origin web/v0.1.0-rc.3
   ```

4. Смотреть **Actions → Component releases**. Ручной запуск принимает уже
   существующий тег, а не имя ветки. Workflow проверяет ancestry, совпадение
   checkout с тегом и чистоту исходников, запускает проверки выбранной платформы.
   Новые теги требуют JSON-карточку в аннотации. CI исключает свой тег из
   сравнения предшественников, сверяет карточку с SHA и повторяет проверку
   актуальных тегов перед публикацией. Карточка документирует решение;
   CI не выдаёт введённый текст за подтверждение владельцем.
5. Build имеет только read-доступ. Только отдельный Publish получает
   `contents: write`, скачивает артефакт этого запуска и повторно проверяет hashes
   и тег. GitHub CLI загружает полный набор через draft и затем публикует его.
6. Скачать полный набор из Releases и выполнить `shasum -a 256 -c SHA256SUMS`
   перед развёртыванием/загрузкой. Файлы не пересобирать для переноса окружения.

Нельзя двигать/пересоздавать использованные теги и заменять файлы готового релиза.
Повторный запуск останавливается, если Release уже существует, включая draft.
После сбоя сначала проверить draft и причину; частичный draft разбирается вручную,
автоматического удаления нет. Для исправленного кода нужна новая версия.
Нативная подпись не обещает побайтовую воспроизводимость при повторной сборке.
Временный Actions artifact хранится 14 дней; долговременный источник — GitHub Release.
Список обязательных проверок записан в [build.py](../scripts/release/build.py).
UI/device-тесты Android остаются отдельной приёмкой, как в обычном CI.

Однократное исключение владельца для `web/v0.1.0-rc.13` позволяет собрать
и опубликовать этот кандидат без завершения приёмки design 4.1 и полного
ручного прохода. Ответ «Да, выпустить web с этим исключением» зафиксирован
29.10.2026 в 11:24:07 UTC, вопрос `call_2a2f63af01c644578b31221353c38006`.
[Ограничение сборщика](../scripts/release/web_rc13_exception.py) требует точного
совпадения деревьев `frontend/web`, `backend`, `contracts`, `design-system` и
`docs/design` с `e813f45e5c126b062b528e51fb1e826e33c873aa`; любое изменение
отменяет исключение. Manifest сохраняет отдельный `owner_exception` со статусом
`incomplete`, без записи design-acceptance в успешно пройденные checks.
Все автопроверки обязательны; исключение не создаёт passed receipt и не меняет
`qa:release-ready` или установщик хоста. Это не общий флаг обхода приёмки.

Отдельный допуск `web/v0.1.0-rc.14` закреплён ответом «Да, только исключение
rc.14 и выкладка» (вопрос `call_a44a9b66cf6541fd80108e62530a3742`,
29.10.2026 12:32:18 UTC). [Ограничение rc14](../scripts/release/web_rc14_exception.py)
проверяет те же пять деревьев по `b072fc0e8685b82655bcc7a3e29b59f92c2fc2be`.
Design 4.1.1 и полный ручной проход остаются `incomplete`; все автоматические
проверки обязательны. Только явно перечисленные точные теги имеют отдельный допуск;
остальные выполняют прежний design gate.

Окончательная версия собирается и проверяется отдельно от RC: её встроенная
версия и manifest отличаются. Нельзя переименовать RC-архив в финальный.
Между окружениями переносится неизменённый артефакт одного точного тега.
Повтор неудачного CI до создания Release допустим с тем же неизменённым тегом;
наличие более высокого тега остановит устаревший выпуск. Выпуски одного
компонента готовятся последовательно.

## Версия на сайте

Футер десктопного онбординга (`/`) и «О somewhere» показывают полный номер web-клиента:
`Версия 0.1.0` или `Версия 0.1.0-rc.3`. Отдельный CI-номер виден в справке
как `Сборка 42`. Версия встраивается в JavaScript и не запрашивается
у API или GitHub. Старая вкладка сохраняет номер своего клиента;
после отката и свежей загрузки виден номер возвращённого артефакта.
На внутренних страницах и mobile web футера нет; версия и номер сборки
остаются в «О somewhere», доступном через профиль или прямой адрес `/about`.

Release packager передаёт доверенные `SOMEWHERE_RELEASE_BUILD=1` и
`SOMEWHERE_BUILD_INFO` в Vite. Из этих данных создаются константы UI и
`build-info.json` внутри `web.tar.gz`: component, version, tag, commit,
build_number и schema_version. Отсутствие данных, противоречие tag/version
или несовпадение с manifest блокируют новую публикацию. Произвольный
`VITE_APP_VERSION` не используется; package.json не служит fallback.

Обычный `web:dev` / локальный `web:build` показывает «Локальная сборка»,
`web:demo` — «Демо». Они работают без тегов и облачных секретов.
«Версия недоступна» — аварийное отображение неполных старых данных, а не
допустимый результат нового релиза. Новые manifest имеют schema 2;
установщик хоста сохраняет чтение старых manifest для существующих артефактов
и отката. Старые опубликованные файлы не переписываем.

Проверка `build.py` открывает именно распакованный архив в Playwright с
недоступным API и сверяет отображение с `build-info.json`. Локальное сравнение
кандидата, предыдущей версии и длинного RC:

```sh
python3 scripts/release/validate_web_builds.py --output .cache/release-version-check
```

Каталог должен быть новым. Команда собирает тестовые варианты, сохраняет
manifest и снимки, проверяет открытую вкладку, обновление и возврат старого
архива на loopback-сервере. Она не создаёт тегов и не меняет production.
Для отдельного готового набора: `python3 scripts/release/check_web.py --directory <каталог>`.
Ошибка `identity does not match manifest` означает несовпадение данных внутри
архива: исправить источник сборки и выпустить новую версию, не править JSON вручную.

## Версии мобильных приложений

`MARKETING_VERSION` / `versionName` берутся из числовой части тега без `-rc.N`.
`CURRENT_PROJECT_VERSION` / `versionCode` — `GITHUB_RUN_NUMBER` этого workflow.
Политика проекта ограничивает его диапазоном 1–9999. Перед **каждой загрузкой**
сверить manifest и номера, уже принятые Google Play/App Store Connect (включая
тестовые треки/TestFlight): новый build number должен быть больше. CI не имеет
доступа к истории магазинов и не заменяет эту проверку. При смене workflow,
сбросе счётчика или достижении 9999 остановить upload и отдельно перенести
нумерацию; не обнулять её и не править уже собранный manifest/пакет вручную.
Повтор попытки того же запуска использует тот же номер: такой файл нельзя
загружать повторно, если магазин уже принял предыдущий. Создать новую версию/RC.

В **Repository settings → Secrets and variables → Actions** задать variable
`SOMEWHERE_API_ORIGIN`, например `https://smwhere.ru` после подключения DNS/TLS/API.
Это один HTTPS origin без пути; отсутствие значения блокирует мобильный релиз.
Замена origin требует нового мобильного артефакта. Примеры с `example.invalid`
предназначены только для локальной проверки сборочной обвязки.

### Android

| Secret | Значение |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | Base64 файла upload keystore |
| `ANDROID_STORE_PASSWORD` | Пароль keystore |
| `ANDROID_KEY_ALIAS` | Alias upload key |
| `ANDROID_KEY_PASSWORD` | Пароль ключа |

Если ключа ещё нет, владелец создаёт отдельный **upload key** в Android Studio
(Build → Generate Signed Bundle / APK → Android App Bundle → Create new).
Сохранить keystore и пароли в менеджере секретов с резервной копией.
Для Google Play включить Play App Signing; это отличает upload key от ключа,
которым Google подписывает приложение для пользователей. Для другого магазина
сначала проверить его требования к ключу и совместимость обновлений.
Не заменять ключ уже опубликованного APK произвольным новым.

Pipeline декодирует keystore во временный файл с правами 0600 и удаляет его
после сборки. Gradle получает пароли через env; обычная локальная unsigned
`assembleRelease` остаётся доступна. Store-путь включает minify/shrink, Lint,
unit-тесты, проверку APK/AAB подписей и R8 mapping. Тестовый локальный ключ не
должен использоваться для публикации. Аккаунт Google Play создаётся отдельно.

### iOS

| Настройка | Значение |
| --- | --- |
| Variable `IOS_TEAM_ID` | Apple Developer Team ID |
| Secret `IOS_CERTIFICATE_P12_BASE64` | Distribution certificate **с private key**, экспортированный в P12 |
| Secret `IOS_CERTIFICATE_PASSWORD` | Пароль P12 |
| Secret `IOS_PROVISION_PROFILE_BASE64` | App Store distribution provisioning profile |

Apple-аккаунт уже есть; наличие подписей нужно проверить в Xcode → Settings →
Accounts → Manage Certificates. Если подходящего сертификата нет, создать
Apple Distribution и экспортировать вместе с private key из Keychain Access.
В Developer portal создать App Store profile для `dev.groupplanning.ios`
и этой команды, с необходимыми capabilities, включая Associated Domains.
Идентификатор приложения также должен совпасть с записью App Store Connect.
Если существующее приложение зарегистрировано под другим Bundle ID, сначала
согласовать и изменить ID в проекте; не маскировать это параметрами экспорта.

Сборка использует закреплённый Xcode, Release, generic iOS archive, manual signing
и `app-store-connect` export. Проверяются срок/назначение profile, team/bundle ID,
подпись archive, наличие dSYMs, версия/build/origin и сохранение версии в IPA.
App ID prefix проверяется по provisioning profile отдельно от Team ID.
В archive и IPA должен сохраниться точный Associated Domain host API origin;
локальное отключение entitlements для Personal Team не допускается в выпуске.
Проверенный `associated_application_id` включён в manifest для
[серверной настройки ссылок](../backend/docs/app-links.md).
Временные keychain/profile удаляются в `finally`, прежний список keychain
восстанавливается. Принудительная потеря runner требует его штатной утилизации;
на общей рабочей машине подписанную сборку предпочтительно не запускать.
Без действующего сертификата и profile IPA не создаётся.

## Развёртывание и откат

- **Backend:** распаковать в `/opt/somewhere/backend/releases/<version>`, создать
  непривилегированного пользователя `somewhere`, конфигурацию поместить в
  `/etc/somewhere/application.env` (root:somewhere, 0640). Unit запускает бинарник через
  `/opt/somewhere/backend/current`. Переключать symlink атомарно, перезапускать
  службу и проверять readiness/API. Откат — предыдущий каталог, если схема БД
  совместима. Будущие миграции требуют backup и плана совместимого отката.
  Backend начиная с `v0.1.0-rc.2` содержит постоянный PostgreSQL-адаптер
  и `somewhere-migrate`. Миграции применяет отдельная DDL-роль; runtime
  использует ограниченную роль. Порядок — [PostgreSQL](../backend/docs/postgres.md).
- **Web:** отдельные `/opt/somewhere/web/releases/<version>` и `web/current`.
  Caddy завершает TLS и проксирует запросы Go webui/API: так сохраняется
  серверный Open Graph приглашений. При смене web current backend перезапускается
  для проверки нового dist; бинарник API остаётся прежним.
- **Monitoring:** из одного ZIP создаются две версии функций с разными SA и env.
  После проверки переключить стабильные теги функций; откатить теги на предыдущие
  version IDs. Реальные уведомления направлять только в настроенный владельцем чат.
  Точная схема — [инструкция бота](../infra/telegram-bot/README.md).
- **Android/iOS:** сначала загрузить готовые AAB/IPA в внутренний трек/TestFlight,
  проверить вход и основные сценарии с API, затем отдельно публиковать в магазине.
  Откат установленной версии обычно означает новый исправляющий выпуск с большим
  build number, а не замену старого файла в Releases.

Release workflow только публикует артефакты. Установщик для подготовленной ВМ —
`infra/host/deploy-release.py`: проверка функциональной приёмки и manifest/SHA256, безопасная распаковка,
миграция backend, атомарный symlink, restart/readiness и возврат прежнего symlink
при неудаче. Выпуск в магазины остаётся отдельным действием.
Домен, постоянное хранилище и реальные уведомления проверяются отдельно перед
первым production-развёртыванием; наличие зелёного CI не закрывает эти условия.

Источники: [GitHub CLI release create](https://cli.github.com/manual/gh_release_create),
[Android app signing](https://developer.android.com/studio/publish/app-signing),
[Apple archive/export](https://help.apple.com/xcode/mac/current/en.lproj/deva1f2ab5a2.html).

## Функциональная приёмка перед выкаткой

Сборка и публикация кандидата для тестирования не выкатывают его пользователям.
После получения точных артефактов примени [release-test](../.agents/skills/release-test/SKILL.md)
по [процессу тестирования](../testing/README.md): все применимые кейсы из каталога,
обязательные suites, ручной проход агентом. Не ограничивай регрессию diff релиза.
Тесты demo/QA не принимают production/store-сборку. Перед продвижением в App Store
или Google Play действует тот же процесс; пока продвижение ручное, это обязательный
шаг оператора, а не автоматическая интеграция со store API.

`qa:release-ready` повторно проверяется в актуальном checkout непосредственно
перед выкаткой. Сохранить plan/run, evidence и созданный `acceptance.json` вместе
с результатами выпуска. Receipt передаётся с доверенной рабочей машины, отдельно
от неизменяемого набора артефактов. Он не является криптографической аттестацией:
не принимай его от произвольного отправителя и не составляй вручную.

```sh
npm run qa:release-ready -- --plan <plan.json> --run <run.json> \
  --artifact-dir <candidate-directory> --receipt <acceptance.json>
# На ВМ, только после разрешённой выкатки:
sudo python3 deploy-release.py <candidate-directory> --acceptance <acceptance.json>
```

Host deployer отказывает до изменения файлов сервиса, если receipt отсутствует,
неполон или относится к другому manifest/артефакту/окружению. Его копия сохраняется
рядом с установленным выпуском. Старые версии deployer на ВМ нужно обновить
вместе с этим процессом; данный change сам по себе production не изменяет.
Сохранённый receipt не заменяет повторную локальную проверку актуальности каталога.
После выкатки проверь smoke/readiness и доступность; это дополняет, а не заменяет
предрелизную приёмку. Публикация артефактов GitHub Releases остаётся доступной
для организации тестирования до этого шага.
