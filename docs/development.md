# Общие правила кода

Эти соглашения действуют с первого кода приложения, включая прототип.
Правила каждого стека и ссылки на исходные руководства находятся в инструкциях:

- [Go](../backend/AGENTS.md): Go Code Review Comments и организация модулей Go.
- [React + TypeScript](../frontend/web/AGENTS.md): строгий FSD и требования пользователя.
- [Swift](../frontend/ios/AGENTS.md): Swift API Design Guidelines, swift-format и модель данных SwiftUI.
- [Kotlin](../frontend/android/AGENTS.md): Android Kotlin Style Guide и рекомендации Android по архитектуре.

Общий процесс описан в [workflow.md](workflow.md), подготовка интерфейса —
в [правилах дизайна](design/README.md). Внешние руководства служат основой;
конкретные правила Somewhere приведены в инструкциях приложений. Не переноси
сюда чужой шаблон архитектуры целиком без связи с задачами проекта.

## Общие соглашения

- Идентификаторы кода называй по-английски, используя продуктовые термины
  из [контекста](product/overview.md). Избегай неочевидных сокращений.
- Отделяй бизнес-правила, сетевой обмен, хранение и отображение. Правила
  конкретной архитектуры определяет локальная инструкция; для веба обязателен FSD.
- Используй небольшие модули с одной понятной ответственностью. Не уплотняй
  выражения ради сокращения числа строк. Новая абстракция, общий пакет
  или зависимость должны решать конкретную задачу.
- Передавай зависимости явно. Не скрывай изменяемое состояние и сетевые вызовы
  в глобальных объектах. У изменяемого состояния должен быть владелец.
- На внешних границах проверяй данные. Различай пользовательскую ошибку,
  сетевую недоступность и внутренний сбой; не скрывай ошибку пустым результатом.
- Не записывай в логи токены, сессии и полные приватные приглашения. Сообщение
  об ошибке должно помогать установить причину без раскрытия этих данных.
- Покрывай проверками изменяемое поведение и существенные риски: права доступа,
  повторные действия, потерю состояния, совместимость. Не добавляй тест только
  ради повторения устройства функции.
- Сгенерированный код обновляй через источник и генератор. Не добавляй ручные
  изменения в файлы, которые следующая генерация перезапишет.

## Где живут правила

| Место | Содержимое |
| --- | --- |
| Этот документ | Общие соглашения для четырёх приложений |
| Локальный `AGENTS.md` | Правила языка, архитектура приложения и команды проверки |
| Конфигурация инструментов в приложении | Форматирование, линтинг, проверки типов и сборки |
| `design.md` изменения OpenSpec | Решения, специфичные для фичи |

Автоматически проверяемое правило закрепляй конфигурацией инструмента.
Инструкция объясняет правило и команду запуска; она не заменяет конфигурацию.
При противоречии приведи документы и настройки к одному решению, сохраняя
согласованные требования и чужие изменения. Пользовательские ограничения
не ослабляй ради удобства инструмента или стороннего примера.

## Инициализация каждого приложения

До реализации первого сценария добавь в задачи инициализации:

1. Зафиксировать версии языка, SDK, зависимостей и минимальных платформ,
   необходимые именно этому приложению.
2. Описать фактическую структуру модулей и границы с другими приложениями
   в соответствии с его локальными правилами.
3. Добавить настройки форматирования, статического анализа и проверки типов,
   применимые к стеку. Сохранять версии внешних инструментов в проекте.
4. Добавить команды установки, запуска, сборки, форматирования, проверки
   форматирования без записи, анализа и нужных тестов в локальный `AGENTS.md`.
5. Выполнить доступные команды на начальном приложении. Указать среду и причины
   недоступности остальных проверок; не записывать предположение как результат.

Это касается и технического прототипа. Не создавай пустые конфигурации
для ещё не выбранных инструментов. Когда появится CI, он должен использовать
те же команды, что и локальная проверка.

## Текущее состояние

В backend добавлены Go-модуль, mock-адаптер и HTTP-сервер с анонимным preview;
команды форматирования, анализа, сборки и тестов приведены в его AGENTS.md.
Контракт и реальные HTTP-ответы проверяются через `npm run api:test` из корня;
CI повторяет команды Go, контракта и обвязки. Серверный identity проверяется
с fake-provider; реальный Яндекс ID, операции встреч и клиенты ещё не проверены.
`npm run agent:check` проверяет обвязку и документы; он не заменяет проверки Go.
