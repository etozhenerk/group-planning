# Шаблон описания релиза

Используется для каждого независимого выпуска somewhere. Заголовок GitHub
Release — полный тег, например `web/v0.2.0-rc.1`. Содержание формирует
`scripts/release/version_policy.py` из JSON-карточки тега и manifest сборки.
Это описание поставленных изменений, не обещание будущих функций.

```markdown
Компонент: **{{component}}** · Версия: **{{version}}**

Предыдущая окончательная версия: {{previous_version или «нет»}}

Причина повышения: **{{bump}}** — {{reason}}

Коммит: `{{полный SHA}}` · Сборка: {{build_number}}

## Изменения

- {{Что изменилось для пользователя или эксплуатации и какой результат это даёт.}}
- {{Следующее изменение, если оно есть.}}

## Совместимость

{{Проверенные API/клиенты, необходимые миграции и условия отката.
Для несовместимости — что перестало поддерживаться и как перейти.}}

## Проверки

До создания тега:

- {{Фактически выполненная проверка и результат/ссылка.}}

Проверки артефакта в CI:

- {{Проверка из manifest.checks.}}

## Ограничения

{{Известные проблемы и непроверенные сценарии, либо «Не выявлены».}}

## Артефакты

- `{{имя файла}}` — {{размер в байтах}} байт.
- `manifest.json` — состав, версия, коммит, сборка и проверки.
- `SHA256SUMS` — контрольные суммы файлов, включая manifest.

Публикация артефактов не выполняет деплой и не загружает приложение в стор.
```

Не вставлять весь git log, токены, приватные URL приглашений или персональные
данные. Для RC явно сохранить суффикс в версии; наличие GitHub Release не
называть установкой на production. Проверки до тега берутся из карточки
ответственного, CI добавляет свои результаты отдельно. Фраза «Не выявлены»
не заменяет перечисления реально непроверенных сценариев.

Порядок выбора номера и подготовки карточки — [релизы](releases.md).
