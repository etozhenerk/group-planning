# Работа с агентом и OpenSpec

## Подготовка

Открой корень `group-planning` как проект или рабочую папку агента. Для
инструментов нужен Node.js >=20.19.0; проверенная версия указана в `.nvmrc`.
При использовании nvm:

```sh
nvm use
npm ci
npm run agent:check
```

Готовые навыки уже хранятся в репозитории. Для их первоначальной генерации
или восстановления используй `npm run agent:setup`. После установки новых
навыков начни новую сессию Codex, если текущая сессия их не обнаружила.

Команды проверки приложений и контракта собраны в
[общих соглашениях кода](development.md); CI использует те же команды.

## Точки входа

В Codex CLI/IDE навык можно вызвать по имени с `$`; в приложении Codex —
выбрать в интерфейсе Skills. Обычный запрос также может выбрать подходящий навык.

| Задача | Готовый навык |
| --- | --- |
| Отредактировать тексты интерфейса и онбординга | `product-copy-editor` |
| Опубликовать одобренный дизайн для всех клиентов | `design-system-publish` |
| Независимо проверить реализованный экран | `design-review` |
| Разобрать идею и открытые вопросы | `openspec-explore` |
| Подготовить proposal, требования, design и tasks | `openspec-propose` |
| Изменить согласованный план | `openspec-update-change` |
| Реализовать задачи изменения | `openspec-apply-change` |
| Проверить реализацию по артефактам | `openspec-verify-change` |
| Синхронизировать требования отдельно от архивации | `openspec-sync-specs` |
| Синхронизировать требования и архивировать изменение | `openspec-archive-change` |

## Путь новой фичи

1. **Проработка.** Выяснить пользователя, проблему, основной сценарий и
   границы. Свериться с [контекстом продукта](product/overview.md),
   [открытыми решениями](product/open-questions.md) и текущими спецификациями.
2. **UX/UI.** Для интерфейсной фичи определить переходы, экраны, состояния,
   макеты и различия платформ по [правилам дизайна](design/README.md).
   Применить [редактор текстов](../.agents/skills/product-copy-editor/SKILL.md):
   проверить смысл и повторы между блоками, затем подписи, ошибки и подсказки.
   Для рассказа о возможностях использовать примеры интерфейса, когда они
   объясняют действие лучше описания.
   После одобрения применить `design-system-publish`: общий источник токенов,
   контракты, версия и manifest экранов/состояний по [процессу](design/review.md).
   Сохранить UX/UI-материалы в `ux.md` внутри созданного через CLI изменения OpenSpec.
   Для правки без интерфейса отметить неприменимость в техническом решении.
3. **Техническое предложение.** `openspec-propose` создаёт изменение и артефакты
   стандартной схемы: `proposal.md`, delta specs, `design.md`, `tasks.md`.
   Создать само изменение можно при начале UX/UI; завершать техническое решение
   и задачи нужно с учётом подготовленного дизайна. Из `design.md` сослаться
   на `ux.md`, связать экраны с клиентскими компонентами, состоянием и API.
   Разделить серверные операции и реализацию в каждом затронутом клиенте.
   Указать критерии приёмки и затронутые приложения. При уточнении использовать
   `openspec-update-change`; наличие файлов ещё не означает готовность плана.
4. **Реализация.** После рассмотрения артефактов перейти к
   `openspec-apply-change`, учитывая уже данное пользователем разрешение.
   Сам запрос на предложение кода не запускает. До первого кода приложения,
   включая прототип, применить [общие соглашения](development.md) и локальные
   правила. Инициализация должна включать настройки инструментов и реальные
   команды проверок. Выполнять задачи по зависимостям.
5. **Проверка.** Выполнить реальные проверки затронутых частей и
   `openspec-verify-change`. Сверить требования, сценарии, код, задачи
   и интерфейс с версией макетов на затронутых платформах. После каждого
   реализованного экрана вызвать `design-review` с независимым субагентом;
   до закрытия UI-задачи выполнить `design:ready` по её manifest. Для изменения API
   проверить совместимость затронутых клиентов, включая поддерживаемые прежние
   сборки. Сохранить результаты и ограничения.
6. **Завершение.** Архивировать завершённое и проверенное изменение с обновлением
   актуальных спецификаций. Прогресс по всем затронутым платформам должен быть
   отражён честно; непроверенные сценарии не считаются пройденными.

При изменении требований корректировать артефакты через `openspec-update-change`.
Если пользователь меняет дизайн уже во время реализации или ревью, агент сам
проходит [цикл ревизии](design/revisions.md): реальные макеты → UX и связанные
артефакты SDD → `design-system-publish` → разрешённая реализация → новый
`design-review` с субагентом → `design:ready`. Уже принятое решение не требует
повторного согласования. Утратившие приёмку задачи открываются заново, предыдущие
отчёты сохраняются как история. Этот переход действует и внутри apply;
сгенерированные OpenSpec-навыки не редактируются.

Технические правки без изменения поведения могут проходить сокращённый путь,
с проверками и синхронизацией затронутой документации.
Для чисто технического изменения OpenSpec допускает `skip_specs: true`
в метаданных изменения: требования продукта остаются без изменений.

## Команды CLI

Всегда запускай CLI через обёртку проекта. Если готовый навык предлагает
`openspec status ...`, эквивалент здесь — `npm run --silent openspec -- status ...`.
Обёртка использует официальный CLI закреплённой версии и локальный профиль.

```sh
npm run --silent openspec -- list --json
npm run --silent openspec -- list --specs --json
npm run --silent openspec -- status --change <change-name> --json
npm run --silent openspec -- validate --all --strict
```

`validate` проверяет структуру требований и изменений, а не работу приложения.
`npm run agent:check` также допускает новый проект без спецификаций: он
явно сообщает об этом, не выдавая пустой набор за проверенные продуктовые сценарии.

## Что где хранится

| Место | Назначение |
| --- | --- |
| `docs/product/` | Общий контекст и ещё не принятые продуктовые решения |
| `docs/architecture/` | Устройство проекта и принятые технические решения |
| `docs/design/` | Правила UX/UI, общие токены и каталог компонентов по мере появления |
| `docs/development.md` | Общие соглашения кода и порядок подключения инструментов |
| `openspec/specs/` | Актуальные спецификации после завершённых изменений |
| `openspec/changes/<name>/` | Требования к изменению, проектирование и задачи |
| `ux.md` и материалы в папке изменения | Переходы, состояния и версия макетов конкретной фичи |
| `openspec/changes/archive/` | История завершённых изменений |
| `AGENTS.md` и инструкции приложений | Правила выполнения работы |

README содержит назначение проекта, структуру и инструкции запуска.
Текущий статус, следующий шаг и результаты отдельных прогонов записывай
в `tasks.md` и отчёты соответствующего изменения OpenSpec. Не дублируй
эти сведения в README и правилах агента.

## Обновление инструментов

Изменение версии OpenSpec выполняется через `package.json` и lock-файл.
После него запусти `npm run agent:update`, просмотри diff сгенерированных
навыков и выполни `npm run agent:check`. Не редактируй сгенерированные навыки OpenSpec вручную.
Проектный product-copy-editor хранится отдельно и редактируется как исходник;
его наличие, метаданные и ссылки проверяет agent:check.
Локальные требования к артефактам и операциям задаются в `openspec/config.yaml`.
Набор генерируемых навыков OpenSpec задаётся в `scripts/openspec-profile.json`.

Лицензия исходных навыков OpenSpec сохранена в `.agents/skills/LICENSE.openspec`.
Установка и команды обёртки используют `.cache/openspec/`; это локальное
игнорируемое состояние. При его удалении обёртка создаст его заново.

## Проверка начала новой работы

Агент должен найти продуктовый контекст, назвать открытые решения, прочитать
инструкции затронутого приложения и увидеть активные изменения OpenSpec.
Проверить это можно запросом: «Изучи репозиторий и предложи следующий шаг,
перечислив принятые и открытые решения. Код пока не меняй».
