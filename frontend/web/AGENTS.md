# Веб-клиент

Применяй [общие правила](../../AGENTS.md). Эта область отвечает за браузерный
клиент Somewhere, в том числе открытие приглашений по ссылке.
Также применяй [общие соглашения кода](../../docs/development.md) и
[правила UX/UI](../../docs/design/README.md).

## Текущее состояние

Выбраны React + TypeScript. Экраны, навигация и состояние интерфейса реализуются
в коде веб-клиента по FSD; данные и результаты операций приходят из API.
См. [ADR 0002](../../docs/architecture/0002-client-ui.md). Рабочий срез включает онбординг, личный список, создание, приглашение, RSVP,
ленту, сообщения, состав и настройки. Версии закреплены в `package.json`;
команды и ограничения — в [README.md](README.md). Локальный вход через Яндекс ID
запускается из корня через `npm run auth:local`; настройки — в
[инструкции сервера](../../backend/docs/auth.md).

## Обязательные требования пользователя

Эти правила действуют с первого кода, включая прототип. Сторонний пример
адаптируй к ним. Инструменты выбирай с учётом всех ограничений.

1. Строгий Feature-Sliced Design.
2. Алиасы во внутренних импортах.
3. Только TypeScript, без поддерживаемых вручную JavaScript-файлов.
4. В файле компонента только импорты, один компонент и тип его пропсов.
5. Небольшие компоненты и файлы с одной ответственностью.
6. Компоненты, хуки и обычные функции — стрелочные функции, объявленные через `const`.
7. Один компонент на каталог: `Component/Component.tsx`, собственный
   `Component.module.css` при необходимости и `index.ts` с явным реэкспортом.
   Имена каталога, TSX и CSS Module совпадают с регистром. Других компонентов
   или файлов стилей в этом каталоге нет.

## Архитектура FSD

Следуй [правилам слоёв FSD](https://feature-sliced.design/docs/reference/layers)
и [публичного API](https://feature-sliced.design/docs/reference/public-api).

- Порядок зависимостей: `app → pages → widgets → features → entities → shared`.
  Импорты идут в нижележащие слои. Не создавай новые слои или `processes`.
  Используй только нужные слои, без пустых каталогов ради структуры.
- Внутри `pages`, `widgets`, `features` и `entities` выделяй slices по предметной
  области. Разные slices одного слоя изолированы. Для отношений сущностей
  допустим только явный API `@x` по правилам FSD; обычные cross-import запрещены.
- `app` и `shared` состоят из segments без slices. В slices разделяй код по
  назначению: `ui`, `model`, `api`, `lib`, `config` по необходимости.
- Внешний потребитель slice использует его `index.ts`. Deep-import во внутренние
  файлы другого slice запрещён. Экспорты перечисляй явно, без `export *`.
  В `shared` выделяй API самостоятельных модулей без единого общего barrel-файла.
- Внутри своего slice можно обращаться к его внутренним модулям напрямую.
  Не импортируй собственный публичный API из его же реализации.
- Маршруты, провайдеры и связывание приложения находятся в `app`; экраны —
  в `pages`. Переиспользуемые действия относятся к `features`, предметные
  модели — к `entities`, независимая инфраструктура и UI — к `shared`.
- Разделяй крупную композицию на небольшие локальные компоненты внутри её slice.
  Мелкий файл не требует нового slice или переноса кода в `shared`.

## Импорты и TypeScript

- Алиас `@/` указывает на `src/`. Все внутренние импорты и реэкспорты, включая
  обращения внутри собственного slice, используй через `@/`; пути `./` и `../`
  в этих импортах запрещены. Зависимости импортируются по именам пакетов.
- Настрой одинаковое разрешение алиаса в TypeScript, сборщике, тестах и линтере.
  Типы импортируй через `import type`. Алиас не отменяет границы публичного API.
- Исходники, тесты, скрипты и конфигурации веб-приложения пиши на TypeScript.
  Ручные `.js`, `.jsx`, `.mjs`, `.cjs` в `frontend/web` запрещены. Выбирай
  инструменты с поддержкой TS-конфигурации. Выход сборки и установленные
  зависимости хранятся в игнорируемых каталогах, отдельно от исходников.
- При инициализации включи `strict: true`, `allowJs: false` и проверку типов
  всех поддерживаемых TS-файлов. Не обходи типизацию через `any`, `@ts-ignore`
  или двойные приведения. Внешние данные принимай как `unknown` и проверяй
  на границе. Основа — [TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html).
- Компоненты и их файлы называй `PascalCase`, хуки — `useSomething`, обычные
  функции — `camelCase`, slices — `kebab-case`. Форматирование закрепи инструментом
  при инициализации, сохранив приведённые ограничения.

## Оформление

- Компонент объявляй как `export const MeetingCard = (...) => { ... };`.
  Хуки и вспомогательные функции также объявляй через `const`; не используй
  `function` или изменяемую переменную для хранения функции.
- Отделяй импорты, типы и объявления пустой строкой. Разделяй условия, циклы,
  обработку ошибок, многострочные объявления и итоговый `return`.
  Связанные короткие присваивания могут идти подряд.
- У `if`, `else` и циклов всегда ставь фигурные скобки. Отступ в TS/TSX/CSS —
  два пробела; форматтер задаёт переносы, кавычки и завершающие запятые.
- `npm run format --workspace @somewhere/web` применяет Prettier, ESLint autofix и проверку CSS на AST PostCSS.
  CSS-правила и группы `@media` также разделяй пустыми строками.
  `npm run web:check` из корня проверяет тот же стиль вместе с типами, FSD и тестами.
  Не уплотняй код для прохождения ограничения размера.

## Состав и размер компонента

- В `.tsx`-файле компонента разрешены импорты, тип `<ComponentName>Props`
  и объявление одного компонента. Других верхнеуровневых объявлений нет.
  Если пропсов нет, пустой тип создавать не нужно.
- Каталог компонента содержит только его TSX, одноимённый CSS Module и
  `index.ts`. Личные хуки, функции и тесты этих функций размещай в `hooks/`,
  `lib/` или `utils/` внутри этого каталога. Другой компонент — отдельный
  соседний каталог в `ui`, даже если его использует только этот компонент.
- `index.ts` каталога явно реэкспортирует только свой компонент и при
  необходимости его Props. Импорт компонента ведёт на этот каталог, стили —
  прямо на его собственный `Component.module.css`, оба через алиас.
- Доменные модели, API и разделяемое состояние остаются в segments FSD.
  Локальное размещение UI-хука не переносит туда бизнес-логику всего slice.
- Собственные классы подключай через CSS Modules. Не импортируй стили другого
  компонента и не оформляй его по селектору родителя. Различия внешнего вида
  передавай явным пропсом варианта; внешний блок оформляй собственным wrapper.
  `:global(.g-...)` разрешён только для Gravity UI внутри локального класса.
- Глобальные `app/styles/tokens.css` и `base.css` содержат токены, reset,
  типографику, базовое оформление HTML-контролов и reduced motion. Компонентные
  классы, раскладка экранов, диалогов и формы в них не добавляются. Тема Gravity
  принадлежит `App/App.module.css`. Пустой CSS-файл для компонента без стилей
  создавать не нужно.
- Компонент собирает представление из пропсов и подключённых хуков. Сетевые
  запросы, преобразование данных и побочные эффекты выноси в соответствующие
  модули. Соблюдай [правила чистоты React](https://react.dev/learn/keeping-components-pure).
- Разбивай UI на небольшие смысловые части. Рабочий ориентир — до 100
  содержательных строк файла компонента; растущий компонент разделяй заранее.
  Численный порог автоматической проверки закрепи при инициализации.
  Не уплотняй строки и не прячь несколько компонентов в один файл.

## Экраны в FSD

Экраны собираются из React-компонентов в `pages`; маршрутизация и провайдеры
подключаются в `app`. Самостоятельные составные блоки относятся к `widgets`,
переиспользуемые пользовательские действия — к `features`, предметные модели —
к `entities`. В `shared` находятся независимые UI-примитивы и инфраструктура.
Используй только те слои, которые нужны конкретному сценарию.

Состояние, запросы к API и преобразование данных размещай в соответствующих
модулях отдельно от файла компонента. Состав экрана и переходы определяются
клиентским кодом, а права и результат бизнес-операции подтверждает сервер.

## Правила изменений

- Привязывай экран к пользовательскому сценарию и общему API-контракту.
  Правила доступа проверяются сервером, а интерфейс отражает их результат.
- Изменения экранов, компонентов и навигации поставляются выпуском веб-клиента.
  Проверяй, что используемый API совместим с клиентом и обновление страницы
  загружает корректное состояние сценария.
- Продумывай открытие прямой ссылки, обновление страницы и возврат назад.
  Доступ гостя и переход после авторизации должны следовать согласованным
  спецификациям приглашений и входа; открытые правила не придумывай.
- Для сетевых операций предусматривай загрузку, пустой результат, ошибку
  и повторную попытку. Сохраняй введённые пользователем данные при ошибке.
- Используй семантические элементы и доступные подписи; проверяй клавиатурную
  навигацию и адаптацию к узкому экрану для затронутых сценариев.

## Проверки

Из корня с Node.js 22.22.3 (`nvm use`), Go 1.27.2 и зависимостями `npm ci`:

```sh
npm run web:dev
npm run web:check
npm run web:build
npx --no-install playwright install chromium webkit
npm run web:test:e2e
npm run agent:check
```

`web:check` выполняет TypeScript, ESLint, проверку пустых строк CSS, FSD/AST,
Prettier и Vitest. `web:test:e2e` собирает отдельный demo build и запускает
Chromium с настоящим Go API и test-only OAuth-provider на loopback TLS.
Сценарии мобильной прокрутки дополнительно выполняются в WebKit с эмуляцией
телефона. Тот же набор выполняется в CI; на Linux браузеры ставятся с `--with-deps`.
Для интерактивной проверки всех действий без Яндекса — `npm run web:demo`;
это тестовый процесс, он не меняет production-настройки авторизации.

Форматирование: `npm run format --workspace @somewhere/web`.
Отдельная проверка: `npm run format:check --workspace @somewhere/web`;
полный стиль проверяй через `web:check` (Prettier не проверяет все пустые строки).

Инициализация включает автоматические проверки FSD и публичного API,
алиасов, отсутствия ручных JavaScript-файлов, типов, состава файла компонента
и размера модулей. Если стандартных правил линтера недостаточно, добавь
проверку AST. Проверка `scripts/check-architecture.ts` работает по AST TypeScript:
100 содержательных строк на компонент, 230 строк на исходный TS-модуль.
Линтер отдельно требует `const` со стрелочными функциями и пустые строки.
`scripts/check-components.ts` входит в ту же команду: проверяет имена и состав
каталога, реэкспорт, собственный CSS Module и локальную область селекторов.
Правила проверяются тестами `scripts/component-layout.test.ts`.
