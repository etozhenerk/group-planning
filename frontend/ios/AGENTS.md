# Клиент iOS

Применяй [общие правила](../../AGENTS.md). Эта область отвечает за приложение
somewhere для iOS и его платформенные интеграции.
Также применяй [общие соглашения кода](../../docs/development.md).

## Текущее состояние

Выбраны Swift и SwiftUI. Экраны, навигация и состояние интерфейса реализуются
в коде iOS-приложения, данные и результаты операций приходят из API. См.
[ADR 0002](../../docs/architecture/0002-client-ui.md). Версии SDK, библиотеки
и минимум закреплены: Xcode 26.0.1 (17A400), Swift 6.2 в режиме Swift 6,
iOS 17.0, SDK iOS Simulator 26.0. Создана схема `Somewhere` без сторонних пакетов;
приложение показывает знак слева и название `somewhere`. Реализованы API-адаптер,
Codable-модели, Keychain-сессия и владельцы приватного состояния. Экраны и реальный
вход ещё не подключены. Устройство данных — в [ios-data.md](../../openspec/changes/gathering-activity-feed/ios-data.md).
Команды и ограничения — в [README.md](README.md).

## Оформление Swift

- Следуй [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/):
  имена должны быть понятны в месте использования. Типы и протоколы —
  `UpperCamelCase`, свойства и методы — `lowerCamelCase`; используй содержательные
  метки аргументов и минимально необходимую видимость.
- Для форматирования используем [swift-format](https://github.com/swiftlang/swift-format).
  Используй закреплённый swift-format 6.2.0 из Xcode и `.swift-format`:
  4 пробела, до 100 символов в строке. Не заменяй его другим SwiftFormat.
- Предпочитай `let` и типы-значения, если не нужна общая изменяемая идентичность.
  Обрабатывай optional, ошибки и отмену явно. Не используй принудительное
  раскрытие optional, `try!` или `as!` для сетевых и пользовательских данных.
- Разделяй небольшие представления, состояние и адаптеры. Файл называй по
  основной ответственности; не собирай экран, сетевой клиент и модели в одном файле.
- Изменения состояния UI выполняй на главном акторе, асинхронным задачам
  задавай владельца и правила отмены. Длительная работа не блокирует UI.

## Архитектура приложения

Основа — [рекомендации Apple по данным SwiftUI](https://developer.apple.com/documentation/swiftui/model-data):
у состояния есть один источник, представление зависит от данных, действия
меняют состояние через определённого владельца.

Для Somewhere приложение разделяется на представления, владельцев состояния
сценариев и адаптеры данных и системы. Конкретный механизм наблюдения выбирай
с учётом минимальной версии iOS; новый API нельзя считать доступным заранее.

- SwiftUI View отображает состояние и передаёт действия. Сетевые запросы,
  авторизация, сессия и системные интеграции находятся за отдельными адаптерами.
- Владелец состояния координирует загрузку, ошибки, повтор и навигацию. Данные
  сервера и локальное состояние формы имеют явно определённые источники.
- Зависимости передаются при сборке приложения; представление не создаёт
  глобальный сетевой клиент или хранилище сессии.
- SwiftUI-представления собирают экраны из клиентских компонентов. Ответы API
  преобразуются в модели приложения; черновики форм и состояние навигации
  принадлежат клиенту. Серверные бизнес-решения не дублируются в UI.
- Начинай с небольших модулей. Дополнительный domain-слой или отдельный пакет
  вводи при реальной сложности или повторном использовании.

## Правила изменений

- Следуй общему API-контракту и сохраняй совместимость с сервером между
  независимыми выпусками. Обрабатывай состояния сети и повторные действия.
- Изменения экранов и навигации требуют новой сборки приложения. Проверяй
  SwiftUI-реализацию затронутого сценария по согласованным макетам с учётом
  safe area, клавиатуры и системной навигации.
- Для ссылок-приглашений проектируй вход в нужный план, авторизацию по
  согласованному сценарию и возврат к исходному действию.
- Учитывай жизненный цикл приложения: сворачивание, восстановление и возврат
  из системных диалогов. Состояние общего плана подтверждается сервером.
- Уведомления, календарь, фотографии и другие системные возможности подключай
  по требованиям конкретной фичи с обработкой отказа в разрешении.
- Проверяй доступность затронутых экранов и увеличение системного размера текста.

## Проверки

Из `frontend/ios` запускай `sh scripts/format.sh --check` и
`sh scripts/build.sh`: строгий swift-format, чистая simulator-сборка и анализ.
`sh scripts/test.sh` выполняет Swift Testing на отдельном временном iPhone 17:
контрактные fixtures, URLSession/отмена, настоящий Keychain, 401/403 и гонки
сессии. Скрипт ждёт загрузки симулятора и удаляет только созданное им устройство.
Тестовый хост подписывается локально (`CODE_SIGN_IDENTITY=-`), без Apple-аккаунта.
Не отключай подпись в этом тесте: Keychain требует simulated entitlements.
`sh scripts/build.sh Release` проверяет оптимизированную сборку.
`sh scripts/check-toolchain.sh` проверяет точные инструменты; версия Xcode
лежит в `.xcode-version`, compiler/formatter/SDK — в `Config/toolchain.env`.
Сборка использует схему `Somewhere`, `generic/platform=iOS Simulator`,
отключённую подпись и игнорируемый `.build/DerivedData`.

CI выполняет те же команды на `macos-15` с выбранным Xcode 26.0.1.
Тесты моделей/сессии находятся в `SomewhereTests`; общие fixtures включены
из `contracts/fixtures/cases.json` ссылкой в проекте, без копирования исходника.
UI и жизненный цикл проверяй вместе с соответствующими экранами. Текущий
unit target не доказывает работу всего мобильного сценария или реального OAuth.
Для документации запускай `npm run agent:check` из корня. Не выдавай
проверку документов или сборку за проверку всего мобильного сценария.
