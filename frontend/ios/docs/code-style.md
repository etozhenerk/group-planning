# Код и файлы iOS

Обязательные правила для исходников, тестов и прототипов. Применяй вместе
с [AGENTS.md](../AGENTS.md), который задаёт архитектуру, проверки и ограничения среды.

## Основа правил

- [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/): имена и читаемый API.
- [swift-format](https://github.com/swiftlang/swift-format): автоматическое оформление Swift.
- [SwiftUI Model data](https://developer.apple.com/documentation/swiftui/model-data): владение состоянием и зависимости представлений.

Apple не задаёт единственное обязательное дерево папок или шаблон MVVM.
Ниже — соглашения somewhere на основе этих рекомендаций. Отступы, размещение
файлов и ориентир размера фиксируются проектом.

## Структура

Каталоги на диске и группы Xcode должны отражать одну структуру.
В синхронизированной группе `Somewhere` используй:

| Каталог | Ответственность |
| --- | --- |
| `App/` | Точка входа, сборка зависимостей и корневое представление |
| `Features/<Feature>/` | Экраны и компоненты одного сценария: `Create`, `Feed`, `Invitation` |
| `Features/<Feature>/Model/` | Владелец состояния и локальные модели сценария |
| `State/` | Общее состояние приложения и сессии |
| `Data/API/` | HTTP, DTO, декодирование и запросы |
| `Data/Session/`, `Data/Drafts/`, `Data/Links/` | Сессия, черновики и входящие ссылки |
| `UI/` | Компоненты, modifiers, цвета и типографика для нескольких сценариев |
| `Resources/` | Asset catalog, локализуемые ресурсы и системный launch screen |

Компонент одной фичи оставляй рядом с её экраном. Переноси в `UI` при реальном
использовании разными сценариями. Не создавай общий `Helpers` или `Utils`.
Дополнительный Swift package нужен при отдельной границе зависимости или
повторном использовании, а не для каждой папки.

## Файлы и имена

- Один основной View, владелец состояния или адаптер — один файл с именем типа:
  `CreateMeetingScreen.swift`, `CreationOwner.swift`, `ParticipantAvatar.swift`.
- Не помещай два самостоятельных экрана или компонента в один файл. Небольшие
  private-типы, функции и `#Preview` только для основного типа допустимы рядом.
  Связанные DTO одного ответа можно объединять в файл с предметным именем.
- Для extension отдельного назначения используй `Type+Purpose.swift`.
  Не выноси каждый метод в extension или отдельный файл. Conformance и тесно
  связанные helpers могут оставаться в файле основного типа.
- Типы и протоколы — `UpperCamelCase`, свойства и методы — `lowerCamelCase`.
  Имя и метки аргументов должны читаться в месте вызова. Не добавляй префикс
  проекта ко всем типам; аббревиатуры используй только общепринятые.
- Не создавай обязательную папку на каждый View, файл стилей или реэкспорт.
  Несколько View одной фичи находятся рядом в отдельных файлах. Локальный
  внешний вид задаётся во View, общий — в именованных modifiers и стилях `UI`.

## Оформление и размер

Используй `swift-format` из закреплённого Xcode и `.swift-format`: четыре пробела,
целевая ширина 100 символов и не больше одной пустой строки подряд.
Не подменяй инструмент библиотекой SwiftFormat с похожим именем.

В файле сначала imports, затем основной тип и его связанные расширения/preview.
Во View: входные данные и зависимости, локальное состояние, initializer при
необходимости, `body`, private-части представления. У владельца состояния:
зависимости и состояние, initializer, действия, private-реализация.
Отделяй объявления и логические этапы пустыми строками.

После примерно 200 строк проверь разделение ответственности. Это ориентир
ревью, не лимит Swift. Самостоятельный элемент интерфейса выноси в отдельный
View; вычисления, преобразования и работу с данными — в модель или адаптер.
Не превращай длинный `body` в набор несвязанных computed properties лишь для
обхода длины файла. Для короткой связной части `@ViewBuilder` допустим.

## Состояние и асинхронность

- View отображает данные и передаёт действия. `body` не выполняет запросы,
  не создаёт хранилище или глобальный клиент и не меняет модель при вычислении.
- Временное состояние UI принадлежит `@State`, ссылка на чужое изменяемое
  значение — `@Binding`. Наблюдаемый владелец сценария использует `@Observable`;
  создавший его View удерживает экземпляр через `@State`, bindings к observable
  модели оформляй через `@Bindable`. Не создавай владельца заново в `body`.
- Для владельцев UI-состояния используй `@MainActor`. Зависимости передавай
  явно. Серверные модели, сеть, Keychain и сохранение черновика отделены от View.
- Задаче назначай владельца и правила отмены. Для работы на время показа
  используй `.task`/`.task(id:)`; долгоживущие операции держи у владельца сценария.
  Не используй `Task.detached` или `@unchecked Sendable` для обхода диагностики.
- Предпочитай `let`, минимальную видимость, структуры для значений и явную
  обработку optional. `try!`, `as!`, force unwrap сетевых и пользовательских
  данных запрещены. Не скрывай ошибки запроса через `try?` и пустой результат.
- Проверяй отмену и актуальность ответа после выхода, смены профиля или экрана.
  Серверные бизнес-решения не дублируй в представлении.

## Ресурсы и тесты

Изображения и цвета размещай в asset catalog; имена отражают назначение,
а не внешний вид. Общую палитру и типографику бери из `UI`. Пользовательские
строки оформляй средствами локализации SwiftUI/Foundation; не собирай предложения
конкатенацией. Масштабирование текста и Reduce Motion — часть UI-контракта.

`SomewhereTests` содержит проверки моделей и адаптеров, `SomewhereUITests` —
сценарии пользователя. Файл теста называй по предмету с суффиксом `Tests`;
fixtures и doubles держи в тестовом target. `SomewhereUITestSupport` не должен
попадать в обычную сборку. Общие API-fixtures подключай ссылкой из `contracts`.

## Что проверяется

`sh scripts/format.sh --check` проверяет оформление без записи, `--write`
форматирует. `sh scripts/build.sh` выполняет чистую сборку и анализ;
Swift 6 проверяет concurrency. Unit и UI-команды описаны в AGENTS.md.

Выбор каталога, обязанности типа, размер View, смысловые отступы и соответствие
макетам проверяются при ревью: форматтер не доказывает архитектуру.
Правила применяются к новому и изменяемому коду; прежние несоответствия исправляй
в затронутой области. Массовую перестройку файлов проводи отдельной задачей.
