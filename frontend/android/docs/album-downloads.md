# Сохранение альбома в галерею

`AlbumDownloadRepository` получает полный `/memories/snapshot` и сохраняет
первоначальный набор ID, независимо от просмотренных страниц. Каждый запрос
оригинала идёт через текущую сессию на origin API. Метаданные проверяются до
записи: встреча, опубликованные memory-фото, уникальные ID, тип и размер.
Имена файлов строятся из ID, а не из присланного сервером пути.

Скачивание последовательное: в памяти находится один оригинал, весь пакет
готовится в закрытом cache-каталоге. Изображения не декодируются и не
перекодируются; исходные байты, качество и EXIF сохраняются.

## Системная запись

- Android 10 / API 29 и новее: новые записи принадлежат приложению и создаются
  с `IS_PENDING=1`. Только после подготовки всех файлов и повторной проверки
  доступа они публикуются. Запрос чтения всей галереи не требуется.
- Android 8–9 / API 26–28: `WRITE_EXTERNAL_STORAGE` объявлен только до API 28.
  Отсутствие разрешения возвращает `PermissionRequired` до скачивания и
  создания записей. Вызывающий экран запрашивает его только после явного
  действия сохранения. До финальной фазы файлы находятся только в private
  cache; при системной записи нет гарантии атомарной видимости всего пакета.

Публикация больших наборов ограничивает размер Binder batch. При ошибке
удаляются только URI, возвращённые `insert` текущей операции. Ранее сохранённые
или чужие фотографии не участвуют в rollback. После успешной системной
записи готовые личные копии сохраняются даже при последующем закрытии экрана.

Правила Android: [доступ к общим медиа и IS_PENDING](https://developer.android.com/training/data-storage/shared/media).

## Отмена и временные данные

Операция выполняется в coroutine вызывающего владельца. Общая блокировка
экспортера исключает одновременную подготовку из разных runtime. Lease сессии
регистрирует всю операцию, поэтому выход и отзыв доступа отменяют также
этапы между HTTP-запросами. До финальной передачи системе отмена удаляет
созданные URI и временную папку в `NonCancellable` cleanup.

Следующая операция удаляет оставшиеся после завершения процесса каталоги
`album-*` только внутри собственного cache namespace. Симлинки не обходятся,
посторонние каталоги не удаляются. Этот механизм очищает private cache;
восстановление pending URI выполняется отдельно по журналу владения.

## Восстановление после остановки процесса

На API 29+ до первого `insert` записывается намерение с новым UUID операции.
Журнал находится в `noBackupFilesDir/album-pending-v1`, ограничен 4 КиБ,
проверяет версию, канонический UUID и фазу. Запись синхронизируется с диском
и заменяется атомарно; неатомарного fallback нет. Файловая блокировка держится
до завершения операции и освобождается ОС при остановке процесса. Повреждённый
журнал блокирует новую операцию до очистки проблемы, без удаления медиа.

Имя каждой записи содержит UUID операции. Поэтому остановка после `insert`,
даже до получения URI клиентом, не теряет владение. Перед новой операцией
`MediaStoreAlbumGallery.begin()` восстанавливает журнал. Запрос и само удаление
ограничены пакетом приложения, каталогом `Pictures/somewhere/`, префиксом
валидированного UUID и `IS_PENDING=1`. Сканирования чужой галереи нет.
Повторный запуск восстановления безопасен. `recoverPending()` доступен для
явного вызова на IO dispatcher, но к старту приложения отдельно не подключён.

Публикация идёт пакетами до 100 записей. Общей транзакции на весь альбом нет:
после остановки между пакетами уже опубликованные фотографии остаются личными
копиями, а оставшиеся pending удаляются. Если все копии опубликованы, но
приватный журнал очистить не удалось, возвращается `SavedCleanupPending`
с `savedCount`; вызывающий UI не должен предлагать слепой повтор как будто
ничего не сохранилось. Успешный `publish()` делает последующий `discard()`
безопасным no-op. При живой ошибке до успешного завершения rollback касается
только URI текущей операции, включая её частично опубликованные записи.

Гарантия recovery не распространяется на API 26–28, удаление данных приложения,
переустановку, потерю питания и pending-записи старой версии без журнала.
Без доказанного владения такие записи приложение не удаляет.

Особенности API: [MediaStore](https://developer.android.com/reference/android/provider/MediaStore)
и [MediaColumns](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns).
На API 30+ используется `QUERY_ARG_MATCH_PENDING`; на API 29 — совместимый
`setIncludePending`. Это не расширяет доступ к чужим pending.

## Проверки

`AlbumDownloadTests` и `AlbumTemporaryFilesTests` входят в обычный
`:app:testDebugUnitTest`. `scripts/test-album-gallery.sh` запускает
`AlbumGalleryDeviceTests` только в отдельном QA-приложении на явно указанном
устройстве; проверяет реальные записи MediaStore на API 29+, байты и EXIF,
pending/publication и rollback собственных URI. `AlbumPendingJournalTests`
проверяет ограничение размера, строгую схему, блокировку, атомарную замену
и запрет симлинков. `scripts/test-album-recovery.sh` дополнительно реально
останавливает только QA-пакет на явно выбранном устройстве: до публикации,
между пакетами 100/101 и после публикации до очистки журнала. Новый процесс
вызывает обычный `begin()` и проверяет сохранность прежних и посторонних
записей. Логи seed после force-stop ожидаемо содержат прерванный тест;
доказательством служат завершённые проверки в новом процессе.

Это проверка адаптера, не приёмка пользовательского экрана и не проверка
API 26–28. Запуск: `ANDROID_SERIAL=emulator-5554 sh scripts/test-album-recovery.sh`.
Для уже проверенных QA APK можно передать `SOMEWHERE_ALBUM_SKIP_BUILD=true`.
