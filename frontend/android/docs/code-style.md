# Код и файлы Android

Обязательные правила для исходников, тестов и прототипов. Применяй вместе
с [AGENTS.md](../AGENTS.md), который задаёт архитектуру, проверки и ограничения среды.

## Основа правил

- [Android Kotlin Style Guide](https://developer.android.com/kotlin/style-guide): оформление и имена.
- [Kotlin Coding Conventions](https://kotlinlang.org/docs/coding-conventions.html): организация файлов и объявлений.
- [Compose API Guidelines](https://developer.android.com/develop/ui/compose/api-guidelines): API компонентов.
- [Android Architecture Recommendations](https://developer.android.com/topic/architecture/recommendations): слои и состояние.

Ниже конкретизированы соглашения somewhere. Дерево пакетов и ориентир размера
файлов — решения проекта, а не обязательный для всех Android-приложений стандарт.

## Структура

Используй существующий модуль `app`. От корневого package
`dev.groupplanning.android` каталоги повторяют package declaration; имена пакетов
строчными буквами. Размещай код по таблице:

| Каталог | Ответственность |
| --- | --- |
| `ui/<feature>/` | Экран и компоненты одного сценария: `create`, `meetings`, `onboarding` |
| `ui/components/` | Компоненты, используемые разными сценариями |
| `ui/theme/`, `ui/brand/`, `ui/motion/` | Тема, знак, общие правила движения |
| `state/` | ViewModel, маршруты и модели состояния экранов |
| `data/api/` | HTTP, DTO, сериализация и запросы |
| `data/repository/` | Доступ к данным и координация источников |
| `data/session/`, `data/drafts/`, `data/links/` | Сессия, черновики и контекст входящих ссылок |

Компонент конкретной фичи оставляй в её пакете. Переноси в общий пакет,
когда есть потребители из разных сценариев. Не добавляй общие `Utils`,
`Helpers` или `Common` для несвязанных функций. Новую feature-папку создавай
под сценарий, дополнительный Gradle-модуль — под обоснованную границу сборки.

## Файлы и имена

- Один основной экран, UI-компонент, ViewModel или repository — один файл,
  названный как основное объявление: `CreationScreen.kt`, `CreationViewModel.kt`.
- Не вкладывай второй самостоятельный экран или компонент в тот же файл.
  Небольшие private-функции, preview и типы, обслуживающие только основное
  объявление, могут оставаться рядом. Связанные модели одного ответа API
  допускаются в одном файле с предметным именем.
- Не создавай папку на каждый Composable. Несколько самостоятельных компонентов
  одной фичи лежат рядом, каждый в своём файле. Compose не требует отдельного
  файла стилей или реэкспорта. Общие цвета и типографика принадлежат теме;
  локальные modifiers — компоненту, повторяемое поведение — именованному modifier.
- Типы и файлы — `UpperCamelCase`, обычные функции и свойства — `lowerCamelCase`.
  Composable, создающий UI и возвращающий `Unit`, — `UpperCamelCase`;
  Composable, возвращающий значение, — обычное имя функции.
- Начинай файл с annotations при необходимости, package, импортов и объявлений.
  Между разделами — пустая строка. Импорты явные, без `*`, порядок задаёт ktlint.
- В классе сначала свойства и инициализация, затем методы, затем companion object.
  Связанные методы располагай рядом; не сортируй их механически по алфавиту.

## Размер и читаемость

Один файл решает одну задачу. После примерно 200 строк проверь, не появились ли
в нём независимые компоненты, преобразования или работа с данными. Это ориентир
для ревью, не лимит компилятора. Разделяй по ответственности, сохраняя связную
логику; не дроби выражения ради количества файлов.

Используй четыре пробела и строку до 100 символов по `.editorconfig`.
Отделяй проверку входных условий, подготовку данных и побочные эффекты пустыми
строками. Форматтер не определяет смысловые границы блоков — их проверяет автор.

## Компоненты и состояние

- Экран связывает ViewModel с UI. Вложенные компоненты принимают значения
  и callbacks; не передавай им целую ViewModel или сетевой клиент.
- У переиспользуемого UI-компонента принимай `modifier: Modifier = Modifier`
  первым необязательным параметром и применяй к корневому элементу один раз.
  Обязательные значения идут перед необязательными, trailing content slot — последним.
- ViewModel публикует неизменяемое состояние; `MutableStateFlow` остаётся private.
  UI собирает Flow через `collectAsStateWithLifecycle`. Локальное визуальное
  состояние хранится в Compose, данные сценария — у его владельца.
- Доступ к сети и хранилищу проходит через repository. Зависимости передаются
  явно. Не запускай операции в теле Composable; используй lifecycle-aware effects
  для UI-задач и `viewModelScope` для работы сценария.
- Отмену coroutine пробрасывай. Изменение профиля и поздние ответы не должны
  возвращать очищенные данные. Для внешних данных запрещены `!!` и скрытие ошибок.

## Ресурсы и тесты

Android-ресурсы — в `src/main/res`, имена файлов и ключей — `lower_snake_case`.
Пользовательские строки — в string resources, общие цвета и типографика — в теме.
Не дублируй ресурсы между экранами; системные XML-цвета сверяй с Compose-темой.

JVM-тесты — в `src/test`, package повторяет проверяемую область; имя описывает
предмет проверки с суффиксом `Tests`. Проверки устройства — в `src/androidTest`,
QA-интерфейса — в `src/androidTestQa`. Подставные credentials и доверие тестовому
CA находятся только в тестовых source sets. `src/production` и `src/qa` —
альтернативные точки сборки runtime, их нельзя смешивать.

## Что проверяется

`./gradlew --no-daemon formatCheck` проверяет Kotlin и Gradle Kotlin DSL;
`formatApply` исправляет оформление. Версия ktlint закреплена в version catalog.
`sh scripts/check.sh` добавляет сборки, Android Lint и JVM-тесты; предупреждения
компилятора и Lint блокируют проверку, кроме исключений версий из AGENTS.md.

Границы ответственности, выбор пакета, размер компонентов, смысловые отступы
и соответствие дизайну проверяются при ревью: ktlint не доказывает архитектуру.
Правила применяются к новому и изменяемому коду; прежние несоответствия исправляй
в затронутой области, не смешивая массовое перемещение с функциональной задачей.
