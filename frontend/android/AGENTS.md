# Клиент Android

Применяй [общие правила](../../AGENTS.md). Эта область отвечает за приложение
somewhere для Android и его платформенные интеграции.
Также применяй [общие соглашения кода](../../docs/development.md) и
[правила структуры файлов и компонентов](docs/code-style.md). Прочитай оба
документа до редактирования исходников этой платформы.

## Стек и границы

Kotlin и Jetpack Compose. Экраны, навигация и состояние интерфейса находятся
в клиенте; данные и результаты операций приходят из API. См.
[ADR 0002](../../docs/architecture/0002-client-ui.md).
Один модуль `app`; зависимости закреплены в `gradle/libs.versions.toml`,
wrapper содержит SHA-256. Версии инструментов и запуск — в [README](README.md).
Production и QA разделены source sets; тестовые настройки входа не входят
в обычное приложение. Изменения дизайна следуют общим макетам.

## Оформление Kotlin

Основа — [Android Kotlin Style Guide](https://developer.android.com/kotlin/style-guide).

- Используй отступ в четыре пробела, типы и файлы основных типов называй
  `UpperCamelCase`, свойства и обычные функции — `lowerCamelCase`. UI-компоненты
  Compose с результатом `Unit` называй `UpperCamelCase` согласно
  [Compose API Guidelines](https://developer.android.com/develop/ui/compose/api-guidelines).
- Не используй wildcard-импорты. Предпочитай `val`, минимальную видимость
  и явные типы на публичных границах модулей.
- Обрабатывай nullable-значения через систему типов. Не используй `!!` для
  сетевых или пользовательских данных; ожидаемые ошибки отражай в состоянии.
- Выноси отображение, владельца состояния и доступ к данным в небольшие файлы
  по их ответственности. Не создавай общий файл утилит для несвязанных операций.
- Асинхронную работу связывай с жизненным циклом владельца. Не используй
  `GlobalScope`, не подавляй отмену coroutine как обычную ошибку.

## Архитектура приложения

Основа — [Android Architecture Recommendations](https://developer.android.com/topic/architecture/recommendations):
UI и data разделены, состояние имеет один источник, данные идут к UI,
действия пользователя — к владельцу состояния.

- Compose-компоненты отображают состояние и передают события. ViewModel
  координирует состояние сценария и обращается к repository; UI и ViewModel
  не работают напрямую с сетевым клиентом или системным хранилищем.
- Repository предоставляет данные и скрывает их источники: сеть, сессию,
  локальное хранение. Зависимости передаются явно при сборке приложения.
- Между слоями используй coroutines и Flow; учитывай жизненный цикл подписок
  и восстановление состояния. Конкретные библиотеки DI и навигации пока не выбраны.
- Дополнительный domain-слой и use case вводи при повторном использовании
  или усложнении операций; он не обязателен для каждой простой операции.
- Права и бизнес-решения встречи проверяются сервером. Android отвечает
  за композицию экранов, навигацию, состояние клиента и системные интеграции.
  Ответы API преобразуются в модели приложения отдельно от UI.

## Мобильный онбординг

Следуй общему [решению для iOS и Android](../../docs/design/mobile-onboarding.md):
пять слайдов с примерами функций, свайп/кнопки/индикатор, вход на последнем экране.
Сохраняй смысл и порядок; используй нативные Compose/Material 3 контролы,
учитывай TalkBack, размер текста и системное отключение анимации.

## Правила изменений

- Следуй общему API-контракту и сохраняй совместимость с сервером между
  независимыми выпусками. Обрабатывай состояния сети и повторные действия.
- Изменения экранов и навигации требуют новой сборки приложения. Проверяй
  Compose-реализацию затронутого сценария по согласованным макетам с учётом
  системных отступов, клавиатуры и жизненного цикла экрана.
- Для ссылок-приглашений проектируй вход в нужный план, авторизацию по
  согласованному сценарию и возврат к исходному действию.
- Учитывай пересоздание экрана, уничтожение процесса и восстановление состояния.
  Подтверждение участия и голоса не должны зависеть от жизни экрана.
- Уведомления, календарь, фотографии и другие системные возможности подключай
  по требованиям фичи с обработкой отказа в разрешении.
- Для затронутых экранов проверяй системную навигацию назад, доступность
  и увеличение размера текста.

## Проверки

Задай JAVA_HOME на JDK 17 и ANDROID_HOME на SDK с platform 36 / Build Tools 36.0.0.
Из frontend/android запускай `sh scripts/check.sh`: toolchain, clean,
formatCheck, Debug/Release APK, lintDebug/lintRelease, testDebugUnitTest и
сборку instrumentation APK (Debug и отдельный QA).
Отдельные команды и пути APK — в [README.md](README.md).
`./gradlew --no-daemon formatApply` применяет ktlint 1.5.0; `formatCheck` проверяет
без записи. Android Studio style, 4 пробела, лимит 100, без wildcard imports;
Compose-функции допускают UpperCamelCase. Kotlin warnings и Lint warnings — ошибки.
JVM-тесты читают общие contracts/fixtures без копии и проверяют HTTPS transport,
сериализацию, состояние, 401/403, отмену и ViewModel lifecycle. Команда
`sh scripts/test-device.sh` проверяет реальный Android Keystore на уже открытом
устройстве. Она не запускает эмуляторы и отказывается работать, если их несколько.
`sh scripts/test-ui.sh` использует отдельный Go HTTPS fixture и QA target с другим
application ID; проверяет слайды, список, форму, черновик, приглашения, Share и три ответа.
Проверяются повтор потерянного ответа, история, настройки организатора, конфликт
ревизий, клавиатура и закрытие чата после снятия участия. В конце runner отдельно
останавливает QA-процесс и проверяет восстановление черновика и неподтверждённого
сообщения. `sh scripts/test-ui.sh persistence` выполняет только эти две стадии.
Настройки устройства, временно изменённые тестами, восстанавливаются.
Не переносить тестовые credentials/CA/intent-настройки в production source set.
CI собирает оба тестовых набора, но не выполняет их на устройстве.

Gradle ограничен двумя workers и heap 2 ГБ, без параллельных проектов и постоянного
daemon. Для локальных UI-проверок используй только один Android-эмулятор:
проверь adb devices, переиспользуй запущенный или один существующий AVD.
Не создавай клоны, не сбрасывай данные и не запускай дополнительные устройства.
Сборка/Lint выполняются без эмулятора; CI использует ту же команду check.sh.
Для инструкций/документов запускай npm run agent:check из корня.
Не выдавай сборку или NO-SOURCE за прохождение пользовательского сценария.

Уведомления Lint о новых версиях (`AndroidGradlePluginVersion`, `GradleDependency`,
`NewerVersionAvailable`, `OldTargetApi`) остаются информационными: закреплённый совместимый стек
обновляется отдельной проверяемой правкой. `targetSdk = 36` меняется вместе
с проверкой поведения на новой платформе, а не вслед за обновлением образа runner.
Проверка `ExpiredTargetSdkVersion` и остальные предупреждения Lint блокируют
сборку. Baseline и подавления ошибок кода не используются.
