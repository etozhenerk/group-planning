# Клиент Android

Применяй [общие правила](../../AGENTS.md). Эта область отвечает за приложение
Somewhere для Android и его платформенные интеграции.
Также применяй [общие соглашения кода](../../docs/development.md).

## Текущее состояние

Выбраны Kotlin и нативная оболочка на Jetpack Compose. Основные продуктовые
экраны управляются через BDUI; см. [ADR 0001](../../docs/architecture/0001-bdui.md).
Движок и способ его встраивания, версии SDK и команды сборки ещё не выбраны.
При создании приложения закрепи настройки инструментов и реальные команды проверок.
Приложение и интеграция рендерера пока отсутствуют.

## Оформление Kotlin

Основа — [Android Kotlin Style Guide](https://developer.android.com/kotlin/style-guide).

- Используй отступ в четыре пробела, типы и файлы основных типов называй
  `UpperCamelCase`, свойства и обычные функции — `lowerCamelCase`. UI-компоненты
  Compose с результатом `Unit` называй `UpperCamelCase` согласно
  [Compose API Guidelines](https://developer.android.com/develop/ui/compose/api-guidelines).
- Не используй wildcard-импорты. Предпочитай `val`, минимальную видимость
  и явные типы на публичных границах модулей.
- Обрабатывай nullable-значения через систему типов. Не используй `!!` для
  сетевых или пользовательских данных; ожидаемые ошибки отражай в состоянии.
- Выноси отображение, владельца состояния и доступ к данным в небольшие файлы
  по их ответственности. Не создавай общий файл утилит для несвязанных операций.
- Асинхронную работу связывай с жизненным циклом владельца. Не используй
  `GlobalScope`, не подавляй отмену coroutine как обычную ошибку.

## Архитектура приложения

Основа — [Android Architecture Recommendations](https://developer.android.com/topic/architecture/recommendations):
UI и data разделены, состояние имеет один источник, данные идут к UI,
действия пользователя — к владельцу состояния.

- Compose и адаптер BDUI отображают состояние и передают события. ViewModel
  координирует состояние сценария и обращается к repository; UI и ViewModel
  не работают напрямую с сетевым клиентом или системным хранилищем.
- Repository предоставляет данные и скрывает их источники: сеть, сессию,
  локальное хранение. Зависимости передаются явно при сборке приложения.
- Между слоями используй coroutines и Flow; учитывай жизненный цикл подписок
  и восстановление состояния. Конкретные библиотеки DI и навигации пока не выбраны.
- Дополнительный domain-слой и use case вводи при повторном использовании
  или усложнении операций; он не обязателен для каждой простой операции.
- Бизнес-правила встречи и формирования BDUI остаются на сервере. Android
  отвечает за оболочку, рендерер, состояние клиента и системные интеграции.

## Правила изменений

- Следуй общему API-контракту и сохраняй совместимость с сервером между
  независимыми выпусками. Обрабатывай состояния сети и повторные действия.
- Основные экраны получаются из общего BDUI-описания. Оболочка выполняет
  поддерживаемые действия и системные интеграции. Отличай серверную правку
  от изменений рендерера и SDK, требующих новой сборки; проверяй старую сборку.
- Для ссылок-приглашений проектируй вход в нужный план, авторизацию по
  согласованному сценарию и возврат к исходному действию.
- Учитывай пересоздание экрана, уничтожение процесса и восстановление состояния.
  Подтверждение участия и голоса не должны зависеть от жизни экрана.
- Уведомления, календарь, фотографии и другие системные возможности подключай
  по требованиям фичи с обработкой отказа в разрешении.
- Для затронутых экранов проверяй системную навигацию назад, доступность
  и увеличение размера текста.

## Проверки

Сборка и тесты Android ещё не настроены. Пока доступна проверка обвязки
`npm run agent:check` из корня. При появлении приложения укажи точные команды
сборки, модульных тестов и сценариев на устройстве или эмуляторе.
В инициализацию включи форматтер с правилами выбранного руководства,
Android Lint и проверки состояния первого сценария. Версии и команды
сохраняй в проекте; работа этих проверок пока не подтверждена.
