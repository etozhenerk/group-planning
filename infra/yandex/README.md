# Инфраструктура somewhere в Yandex Cloud

Этот Terraform-модуль создаёт основу выбранного окружения: обычную ВМ Intel
Ice Lake 2 vCPU 50% / 4 ГБ, SSD 10 ГБ (параметр до 40 ГБ), статический IPv4,
отдельную группу безопасности и сервисную учётную запись. Также создаются
приватный S3-бакет копий, четыре контейнера Lockbox без значений и адресные IAM-права. Используется существующая
подсеть. Чужие сети и security groups не изменяются.

Установку PostgreSQL, копий и агентов выполняют [скрипты ОС](../host/README.md).
Модуль не устанавливает приложение или его миграции. Получение секретов,
проверка прикладного восстановления и допуск реальных данных выполняются по [плану](../../openspec/changes/deployment-and-store-release/tasks.md).
ВМ сама по себе не означает готовности сервиса. Домен продукта — `smwhere.ru`.

## Подготовка

Нужны Terraform 1.14.x, Yandex CLI и доступ владельца к целевому облаку.
Версия provider закреплена; `.terraform.lock.hcl` хранится в Git.
Текущий lock проверен для macOS ARM64. Перед работой с Linux дополнить его
официальными checksum через `terraform providers lock -platform=darwin_arm64
-platform=linux_amd64` в сети с доступом к реестру; запуск Terraform на Linux
пока не проверен. Официальное зеркало Yandex Cloud может отставать по версии.
CLI устанавливается из [официального источника](https://yandex.cloud/ru/docs/cli/operations/install-cli).
Войти через `yc init`; токены в чат, tfvars и Git не копируются.

1. Проверить статус облака, биллинг и квоты: 2 vCPU, 4 ГБ RAM, выбранный объём SSD
   именно в выбранной зоне, 1 статический IPv4, 1 группа безопасности.
2. Снять инвентаризацию ресурсов. Найти существующую подсеть в этой зоне.
   Лимит сетей может быть исчерпан; новая сеть модулю не нужна.
3. Получить ID официального Ubuntu 24.04 LTS:
   `yc compute image get-latest-from-family ubuntu-2404-lts --folder-id standard-images`.
   Зафиксировать именно ID, чтобы повторный plan не выбирал новый образ автоматически.
4. Скопировать `terraform.tfvars.example` в `terraform.tfvars`. Указать ID,
   публичный SSH-ключ и текущий IPv4 администратора с `/32`.
   Закрытый ключ хранить отдельно с правами `0600`; в metadata идёт только открытый.

## Проверка и применение

Из этого каталога, в shell без `set -x`:

```sh
umask 077
export YC_TOKEN="$(yc iam create-token)"
terraform init
terraform fmt -check
terraform validate
terraform test
terraform plan -out=foundation.tfplan
terraform show foundation.tfplan
# После проверки состава новых ресурсов, конфигурации и цены:
terraform apply foundation.tfplan
unset YC_TOKEN
```

Базовый план создаёт 15 ресурсов: service account, IP, security group, диск, ВМ, S3,
его IAM-binding, роль записи метрик, четыре Lockbox и три IAM-member. Базовая
стоимость ВМ/SSD/IP — 2 363,41 ₽ за 720 ч с НДС по консоли 24.10.2026;
остальные сервисы входят в отдельные строки общей сметы. Проверить plan на
отсутствие удаления, замены чужих ресурсов, лишних сервисов и широкого SSH.
Запускать один Terraform-процесс за раз. Сохранить state и lock-файл; state,
план и tfvars игнорируются Git и резервируются в зашифрованном хранилище владельца.
Потеря state требует импорта существующих ресурсов до нового apply.

После apply проверить по SSH `cloud-init status --wait`, `ss -lntup`,
публичную недоступность 5432/8080 и доступ к SSH только с разрешённого адреса.
Во время подготовки 80/443 открыты в security group; Caddy отвечает HTTP 503
до готовности приложения и HTTPS. PostgreSQL использует только Unix socket.
Учётная запись `somewhere-admin` используется для установки, приложение —
непривилегированный пользователь `somewhere`.

`terraform test` использует mock-provider, облачные ресурсы не создаёт. Проверяет
параметры принятой сметы, закрытые порты БД/Go, ограничение SSH, неверный ключ
и несовпадение зон. Эти тесты не заменяют реальный plan, установку ОС и проверку
портов снаружи. Токен для validate/test не нужен.

## Telegram-бот из релиза

[telegram.tf](telegram.tf) добавляет восемь ресурсов при `telegram_bot_enabled=true`:
два отдельных service accounts, четыре адресных IAM-права, закрытую функцию
и scaling policy. Токен загружается отдельно
в секрет `telegram_token_secret_id` с ключом `telegram-token`; payload не должен
попадать в Terraform state, plan, CLI argv или Git.

В игнорируемом файле, например `../local/telegram.tfvars.json`, задать:

```json
{
  "telegram_bot_enabled": true,
  "telegram_async_enabled": false,
  "telegram_bot": {
    "chat_id": "CONFIRMED_NUMERIC_CHAT_ID",
    "release_zip": "../local/releases/MONITORING_TAG/monitoring-functions.zip",
    "release_sha256": "VERIFIED_SHA256",
    "dashboards": {"vm": "VM_DASHBOARD_ID", "postgres": "POSTGRES_DASHBOARD_ID"}
  }
}
```

Сначала скачать и проверить весь набор GitHub Release по [инструкции релизов](../../docs/releases.md).
Первый plan/apply выполняется с `telegram_async_enabled=false`: создаются функция
и права invoker на неё. Затем установить `true`, повторить plan/apply и проверить
реальную ACTIVE-версию, один async retry и лимиты по 1 на зону. В каждом plan
передавать **оба** файла `-var-file`: основу ВМ и Telegram. Потеря bot-настроек
не является способом отключения: `prevent_destroy` остановит такой план.
Отключать доставку следует через канал Monium, сохраняя ресурсы и секрет.

Provider 0.239.0 перезаписывает `log_options.folder_id` пустым `log_group_id`
при формировании запроса. Поэтому блок `log_options` не передаётся: остаётся стандартное журналирование
Cloud Functions. Отдельный `yandex_logging_group` не создаётся: с 22.10.2026
Cloud Logging закрыт для новых клиентов; логи переезжают в Monium.
[Официальное изменение](https://yandex.cloud/ru/docs/logging/migration-to-monium).
Provider также может вернуть лишь warning при неудаче сборки; проверка
`yc serverless function version list` обязательна. Наличие function ID
само по себе не подтверждает выкладку. При обновлении должна появиться новая
ACTIVE-версия, а не сохраниться прежняя после предупреждения.

Канал Monium выбирает функцию и аккаунт invoker; он не становится каналом
по умолчанию для всех алертов. Его добавляют к пяти правилам каталога бота,
сохраняя независимый штатный канал. Инструкция проверки и отката — в
[модуле бота](../telegram-bot/README.md). Probe подключается отдельно после DNS,
HTTPS и работающего `/readyz`.

## Изменения и удаление

Диск, адрес и ВМ защищены `prevent_destroy` в Terraform; boot disk не удаляется
автоматически вместе с ВМ. Ручные действия вне Terraform требуют осторожности:
эта защита не блокирует удаление через консоль/API.
Новый образ или зона требуют отдельного плана переноса данных; снятие защиты
ради прохождения plan недопустимо. Полный `terraform destroy` для рабочего
окружения не является процедурой отката приложения.
При смене адреса администратора сначала обновить `/32` в tfvars и проверить
plan изменения группы безопасности. Порт PostgreSQL наружу не открывать.

Конфигурация ОС ограничивает журналы 256 МБ и 14 днями, отключает вход по
паролю/root и включает автоматические обновления безопасности без автоматической
перезагрузки. Установка релиза и копий должна иметь отдельные проверяемые команды.

## Мониторинг и бюджет

Панели нового Monium хранятся в [каталоге мониторинга](../monitoring/README.md).
Provider 0.239.0 вернул несовместимый ответ Dashboard API; панелей от этой
попытки не появилось. Они созданы через UI и намеренно не находятся в Terraform
state. Не применять старый `dashboards.tfplan` и не импортировать панели вслепую.
Бюджет Billing также вне state: месячный cost budget 3 950 ₽, пороги 50/80%,
уведомление о полном лимите 100%; получатель — аккаунт владельца. Автоостановки нет.
Прогнозный бюджет и доставка уведомлений проверяются отдельно.

При расширении менять только `boot_disk_gib` и проверять plan. Полная процедура
и ограничения — в [инструкции ОС](../host/README.md). `prevent_destroy` не
защищает от уменьшения размера через чужой API и не заменяет копию.
