# Инфраструктура somewhere в Yandex Cloud

Этот Terraform-модуль создаёт основу выбранного окружения: обычную ВМ Intel
Ice Lake 2 vCPU 50% / 4 ГБ, SSD 40 ГБ, статический IPv4, отдельную группу
безопасности и сервисную учётную запись без ролей. Используется существующая
подсеть. Чужие сети и security groups не изменяются.

Модуль не устанавливает приложение или БД. Подключение PostgreSQL, миграций,
копий, Lockbox, мониторинга и проверка восстановления выполняются до допуска
реальных данных по [плану](../../openspec/changes/deployment-and-store-release/tasks.md).
ВМ сама по себе не означает готовности сервиса. Домен продукта — `smwhere.ru`.

## Подготовка

Нужны Terraform 1.14.x, Yandex CLI и доступ владельца к целевому облаку.
Версия provider закреплена; `.terraform.lock.hcl` хранится в Git.
Текущий lock проверен для macOS ARM64. Перед работой с Linux дополнить его
официальными checksum через `terraform providers lock -platform=darwin_arm64
-platform=linux_amd64` в сети с доступом к реестру; запуск Terraform на Linux
пока не проверен. Официальное зеркало Yandex Cloud может отставать по версии.
CLI устанавливается из [официального источника](https://yandex.cloud/ru/docs/cli/operations/install-cli).
Войти через `yc init`; токены в чат, tfvars и Git не копируются.

1. Проверить статус облака, биллинг и квоты: 2 vCPU, 4 ГБ RAM, 40 ГБ SSD
   именно в выбранной зоне, 1 статический IPv4, 1 группа безопасности.
2. Снять инвентаризацию ресурсов. Найти существующую подсеть в этой зоне.
   Лимит сетей может быть исчерпан; новая сеть модулю не нужна.
3. Получить ID официального Ubuntu 24.04 LTS:
   `yc compute image get-latest-from-family ubuntu-2404-lts --folder-id standard-images`.
   Зафиксировать именно ID, чтобы повторный plan не выбирал новый образ автоматически.
4. Скопировать `terraform.tfvars.example` в `terraform.tfvars`. Указать ID,
   публичный SSH-ключ и текущий IPv4 администратора с `/32`.
   Закрытый ключ хранить отдельно с правами `0600`; в metadata идёт только открытый.

## Проверка и применение

Из этого каталога, в shell без `set -x`:

```sh
umask 077
export YC_TOKEN="$(yc iam create-token)"
terraform init
terraform fmt -check
terraform validate
terraform test
terraform plan -out=foundation.tfplan
terraform show foundation.tfplan
# После проверки ровно пяти новых ресурсов, конфигурации и цены:
terraform apply foundation.tfplan
unset YC_TOKEN
```

План создаёт только service account, IP, security group, диск и ВМ. Ожидаемая
стоимость этих ресурсов — 2 793,25 ₽ за 720 ч с НДС по консоли 24.10.2026;
остальные сервисы входят в отдельные строки общей сметы. Проверить plan на
отсутствие удаления, замены чужих ресурсов, лишних сервисов и широкого SSH.
Запускать один Terraform-процесс за раз. Сохранить state и lock-файл; state,
план и tfvars игнорируются Git и резервируются в зашифрованном хранилище владельца.
Потеря state требует импорта существующих ресурсов до нового apply.

После apply проверить по SSH `cloud-init status --wait`, `ss -lntup`,
публичную недоступность 5432/8080 и доступ к SSH только с разрешённого адреса.
Во время подготовки 80/443 открыты в security group, но веб-сервер ещё не установлен.
Учётная запись `somewhere-admin` используется для установки, приложение —
непривилегированный пользователь `somewhere`.

`terraform test` использует mock-provider, облачные ресурсы не создаёт. Проверяет
параметры принятой сметы, закрытые порты БД/Go, ограничение SSH, неверный ключ
и несовпадение зон. Эти тесты не заменяют реальный plan, установку ОС и проверку
портов снаружи. Токен для validate/test не нужен.

## Изменения и удаление

Диск, адрес и ВМ защищены `prevent_destroy` в Terraform; boot disk не удаляется
автоматически вместе с ВМ. Ручные действия вне Terraform требуют осторожности:
эта защита не блокирует удаление через консоль/API.
Новый образ или зона требуют отдельного плана переноса данных; снятие защиты
ради прохождения plan недопустимо. Полный `terraform destroy` для рабочего
окружения не является процедурой отката приложения.
При смене адреса администратора сначала обновить `/32` в tfvars и проверить
plan изменения группы безопасности. Порт PostgreSQL наружу не открывать.

Конфигурация ОС ограничивает журналы 256 МБ и 14 днями, отключает вход по
паролю/root и включает автоматические обновления безопасности без автоматической
перезагрузки. Установка релиза и копий должна иметь отдельные проверяемые команды.
