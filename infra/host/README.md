# Эксплуатация одного узла somewhere

Скрипты предназначены для выделенной Ubuntu 24.04 amd64. PostgreSQL 16
устанавливается **на облачную ВМ**, локальная БД/Docker не нужны.
Прикладной адаптер, миграции и выпуск Go/web выполняются отдельно по группе 14.
До их проверки HTTP возвращает 503; реальные данные пользователей не принимаются.

## Подготовка ОС

После Terraform дождаться `cloud-init status --wait`. Войти как
`somewhere-admin` ключом владельца; SSH открыт только его `/32`.
Скопировать файлы этого каталога на сервер в `/tmp/somewhere-host/`.
Из этой директории последовательно выполнить от root:

```sh
bash prepare.sh
bash install-metrics.sh FOLDER_ID
bash configure-operations.sh PRIVATE_BUCKET AGE_PUBLIC_RECIPIENT
```

`prepare.sh` устанавливает PostgreSQL/Caddy, роли и ограничения. Он не удаляет
БД при повторе, но перезапускает её; применять только при подготовке пустого
узла. При наличии `somewhere.service` скрипт останавливается до изменений.
Дальнейшие обновления ОС/БД требуют отдельного окна и проверки совместимости.
Unified Agent закреплён на 26.10.50; SHA256 — проверенное при установке содержимое
официального пакета. Обновление версии и checksum выполняется отдельным изменением.

Ключ `age` создаётся владельцем; закрытая identity остаётся вне ВМ и Git,
в защищённом хранилище владельца. На сервер передаётся **только public recipient**.
Потеря identity делает копии невосстановимыми. Для текущего окружения identity
находится в игнорируемом `infra/local/backup.agekey` (0600), SSH-ключ —
`infra/local/somewhere-admin`, state — `infra/yandex/terraform.tfstate`.
До допуска данных сохранить identity/SSH/state в отдельном защищённом хранилище;
наличие этих файлов на одном компьютере не является такой резервной копией.

## PostgreSQL

- `listen_addresses=''`: только Unix socket, peer-аутентификация.
- `somewhere_migrator` владеет БД и выполняет будущие миграции.
- `somewhere` получает DML, без superuser/создания БД/ролей. Для будущих таблиц
  public настроены default privileges владельца; миграции в других схемах
  должны выдать права явно.
- `somewhere_metrics` имеет `pg_monitor`; экспортирует только агрегаты,
  не тексты/параметры запросов и не пользовательские данные.
- 30 соединений, shared_buffers 256 МБ, work_mem 4 МБ, WAL 80–256 МБ,
  временные файлы одного процесса ограничены 256 МБ. Это не общий лимит БД.

Проверка: `sudo -u somewhere psql -X -d somewhere -c 'SELECT current_user'`.
Будущий pgx DSN использует `/var/run/postgresql`, а переход на managed —
конфигурацию host/TLS/CA и отдельные роли из storage-design.md.
Пока приложение использует memory.Store и не подключено к этой БД.

## Копии

`somewhere-backup.timer` запускает копию ежедневно в **03:00 UTC / 06:00 МСК**
с задержкой до 10 минут, `Persistent=true`. Принудительный запуск и проверка:

```sh
sudo systemctl start somewhere-backup.service
sudo systemctl status somewhere-backup.service --no-pager
sudo cat /var/lib/somewhere-backup/latest.json
systemctl list-timers somewhere-backup.timer
```

`pg_dump -Fc` поступает прямо в `age`, без plaintext-файла. Зашифрованный объект
загружается в `database/TIMESTAMP.dump.age` приватного S3 с IAM из metadata;
статических ключей нет. Только после HTTP 200 заменяются локальная последняя
копия и manifest. Retention S3 — 7 дней, локально — одна последняя копия.
Manifest содержит timestamp и SHA256, без секретов. Роль `storage.uploader`
не позволяет runtime удалять копии или менять retention. Размер бакета — 20 ГиБ.

Проверенное скачивание на компьютер владельца (из корня репозитория):

```sh
python3 infra/host/pull-backup.py \
  --host somewhere-admin@SERVER_IP \
  --key infra/local/somewhere-admin \
  --known-hosts infra/local/known_hosts \
  --bucket PRIVATE_BUCKET \
  --output infra/local/latest.dump.age
```

Команда использует авторизованный `yc` из PATH; другой путь передать через `--yc`.
Токен остаётся в памяти процесса. Проверяется SHA256 скачанного объекта; предыдущая
копия заменяется после успешной проверки. SSH host key уже должен быть проверен
и записан в known_hosts, автоматического отключения проверки нет.

Одна копия скачана и проверена 24.10.2026. **Автоматический ежедневный экспорт
на независимый узел ещё не включён**: нужен регулярно работающий компьютер/узел
и расписание с контролем свежести. Пока не обещать региональный RPO 24 ч.

## Репетиция восстановления

Сначала сверить checksum, затем восстановить в **новую отдельную БД**, не поверх
рабочей. На компьютере с установленным [age](https://github.com/FiloSottile/age)
расшифровка передаётся через SSH по stdin непосредственно в `pg_restore`:

```sh
age --decrypt -i infra/local/backup.agekey infra/local/latest.dump.age |
  ssh -i infra/local/somewhere-admin -o IdentitiesOnly=yes \
  -o StrictHostKeyChecking=yes -o UserKnownHostsFile=infra/local/known_hosts \
  somewhere-admin@SERVER_IP \
  'sudo -u postgres pg_restore --exit-on-error --dbname=RESTORE_TEST_DB'
```

Тестовую БД предварительно создать с владельцем `somewhere_migrator` через
`createdb`; не использовать имя `somewhere`. В shell включить `set -o pipefail`.
Проверить данные, владельцев, runtime-права и ограничения; удалить только свою
одноразовую тестовую БД после проверки. `pg_dump` не копирует кластерные роли:
на новом сервере их заранее создаёт `prepare.sh`.

Пройдена цепочка: собственная тестовая строка → pg_dump/age → S3 → скачивание/
checksum → отдельная БД → чтение строки. Затем тестовые данные удалены,
сделана новая чистая копия. Это проверка механизма, **не** восстановление
пользовательских сессий, receipts и задач: прикладные таблицы ещё не созданы.

## Рост диска 10 → 20 → 40 ГБ

Начать расширение при занятости >70%, остатке <3 ГБ или прогнозе заполнения
<30 дней. Алерт на диске 10 ГБ: Warning <3 ГиБ, Alarm <2 ГиБ за 5 минут.
До масштабного импорта оценить пик: БД + WAL + одна локальная копия + новый
временный зашифрованный dump + логи + артефакты. Сборку приложения выполнять
вне production-ВМ. Нельзя планировать расход свободного места до нуля.

1. Сделать успешную копию и скачать её; проверить квоту нужного размера в зоне d.
2. Изменить **только** `boot_disk_gib` в локальном tfvars. Проверить цену:
   20 ГБ добавляют 143,28 ₽/720 ч; 40 ГБ относительно 10 ГБ — 429,84 ₽/720 ч.
3. Новый Terraform plan должен увеличивать существующий диск, без замены/удаления
   ВМ или диска. Сохранённый старый plan повторно не применять.
4. После apply проверить `lsblk -f`, `findmnt /`, `df -h /`.
   Для текущего корня `/dev/vda1` с ext4, если раздел/ФС сами не увеличились:
   `sudo growpart /dev/vda 1`, затем `sudo resize2fs /dev/vda1`.
   Перед командами вновь подтвердить устройство и тип ФС; для другого типа
   использовать его процедуру. Проверить БД, копию и график места.
5. Обновить пороги; на 40 ГБ аварийный абсолютный остаток — 5 ГБ.

Уменьшить существующий диск нельзя. Смена образа/зоны требует переноса;
`prevent_destroy` не снимать ради прохождения плана.

## Мониторинг, DNS и выпуск

Exporters слушают только 127.0.0.1:9108 и localhost:16241. Все системные метрики
отправляются раз в 60 с. Буфер Unified Agent ограничен 128 МБ, память — 256 МБ;
PG exporter — 64 МБ. Конфигурации панелей/алертов — [рядом](../monitoring/README.md).

После покупки `smwhere.ru` на аккаунт владельца добавить A-запись корня
на вывод Terraform `public_ipv4`; текущий адрес зафиксирован в отчёте
развёртывания. Не использовать IP неудачной первой попытки. Не добавлять AAAA
без рабочего IPv6. Для дополнительных поддоменов сначала согласовать origins.
Затем выпустить Caddy HTTPS, проверить обновление сертификата и только после
приёмки постоянного хранилища установить Go/web релиз. Порт 5432 не открывать.
