# Метрики и уведомления somewhere

Три уровня готовности: **подключено** (есть источник в облаке), **код готов**
(проверен локально, нужен деплой/доступ), **план** (инструментирование ещё не написано).
Пустой график не считается нулём или нормальным состоянием. Live-инвентарь и
панели — в [README](README.md); правила бота — в [каталоге](../telegram-bot/internal/notify/rules.json).

## Бизнес-панель — код подготовлен, источник ещё не развёрнут

Отдельная закрытая панель «somewhere — Бизнес» использует агрегаты из PostgreSQL.
Восемь значений `somewhere_business_`: `users`, `meetings`, `chats`,
`chats_with_messages`, `messages`, `logins_total`, `logins_today`,
`tracking_started_timestamp_seconds`; девятый ряд `collection_success` проверяет
сбор. Первые пять показывают текущие числа. Чат — лента встречи, включая пустую;
активные чаты здесь означают наличие хотя бы одного пользовательского сообщения.
Системные события ленты не считаются сообщениями.

Вход — сохранение новой сессии после авторизации; счётчик постоянный, сутки UTC.
Повторное использование/обновление сессии, logout и cleanup не меняют число входов.
До включения учёта достоверной истории нет; текущие сессии в неё не подмешиваются.
Тестовый аккаунт владельца входит в общие значения. Нет меток с ID, IP или PII.
При ошибке SQL экспортируется только `collection_success=0`; прочие значения
отсутствуют. Нулевая точка допустима только после успешного чтения реального нуля.

Включение — отдельный флаг `somewhere-migrate -business-metrics` из проверенного
backend-релиза, под ролью migrator; затем обновление `postgres-metrics.py` и restart
его службы. Unified Agent уже опрашивает закрытый `127.0.0.1:9108/metrics` раз в
минуту. Схема и проверки — [business-metrics.md](../../openspec/changes/deployment-and-store-release/business-metrics.md).

## Ресурсы и БД — подключено

| Метрика | Источник / смысл | Контроль |
| --- | --- | --- |
| CPU | Unified Agent: нормализованная загрузка с учётом гарантированной доли CPU | >70/90% за 10 мин |
| RAM | 100 × (MemTotal − MemAvailable) / MemTotal | >80/90% за 5 мин; отдельно OOM/swap |
| Диск | Свободные байты `/`, ГиБ; bytes/sec и операции чтения/записи | <3/<2 ГиБ за 5 мин; рост/IOPS смотреть на панели |
| Сеть | RX/TX интерфейса, входящие/исходящие bytes/sec | Суточный/месячный объём, бюджет; пороги скорости после baseline |
| PostgreSQL | up, подключения/лимит, блокировки, deadlocks, transactions | up <0,9/<0,5 за 2 мин; остальные диагностические |
| Копия | Возраст последнего успешного backup | >25/>26 ч за 5 мин; отдельно доказательство restore |

Warning/Alarm используют одно указанное окно bootstrap. Полные запросы находятся
в dashboard JSON и rules.json; изменения фильтров/порогов синхронизировать между ними.
Статус сообщения берётся из Monium, а не пересчитывается ботом по последней точке.
NO_DATA/ERROR тоже требуют уведомления. Доставка email пока не подтверждена,
поэтому наличие пяти алертов само по себе не обеспечивает оповещение владельца.

## Внешний HTTP-пинг — код готов

[probe.Probe](../telegram-bot/probe.go) раз в минуту делает GET фиксированного
HTTPS `/readyz` с новым соединением, без redirect, с timeout 10 с и лимитом тела
16 КиБ. Успех — проверенный TLS, HTTP 200, тело прочитано в пределах лимита.
Это проверка доступности endpoint, не бизнес-сценария и не ICMP ping.
`/readyz` должен отражать готовность API/его обязательных зависимостей.

| Имя `somewhere_probe_…` | Единица / значение |
| --- | --- |
| `success` | 1 / 0; сбой сети или TLS тоже даёт 0 |
| `status_code` | HTTP status, 0 при отсутствии ответа |
| `duration_seconds` | Полное время запроса с чтением ограниченного тела |
| `dns_seconds` | DNS lookup, если этап наблюдался и прошёл |
| `tcp_seconds` | Установка TCP; при нескольких попытках — последнее успешное измерение |
| `tls_seconds` | TLS handshake, если прошёл |
| `ttfb_seconds` | От начала запроса до первого байта ответа |
| `certificate_days` | Дней до истечения leaf-сертификата при успешном TLS |
| `last_run_timestamp_seconds` | Unix time начала проверки |

Максимум 9 рядов, фиксированные labels `environment=production`, `probe=api`;
origin/IP/status не создают новые label values. Непройденные этапы отсутствуют,
не заменяются нулём. При отказе записи в Monium функция возвращает ошибку;
возраст последнего результата и errors функции контролируются отдельно.

После подключения: три неуспеха подряд — Alarm; свежесть >3 мин — отдельный Alarm;
сертификат <14 дней Warning, <7 Alarm. Не пересылать прошлый успешный probe как
текущий. DNS-кеш resolver и выбор адресов влияют на этапные тайминги; они полезны
для диагностики, но не являются полной трассировкой сети. Региональный отказ
Yandex Cloud требует независимой внешней проверки за пределами региона.

## API, тайминги, OK/Bad RPS — план

Источник Go middleware на закрытом `/metrics`; Caddy измеряет внешний трафик
и ошибки upstream. Не складывать Go и proxy счётчики одного запроса.

| Показатель | Определение |
| --- | --- |
| API RPS | Завершённые API-запросы/с, окна 1 и 5 мин; health/static исключены |
| OK RPS | 2xx; 3xx/OAuth redirect отдельной линией |
| Bad RPS | 5xx и server/upstream timeout, без двойного счёта 504 + timeout |
| Отклонённые | Прочие 4xx, 429, отмены клиентом — отдельные исходы |
| Error rate | Bad / (2xx + 3xx + Bad), рядом абсолютные ошибки за 5 мин |
| Latency | Histogram p50/p95/p99: read/write/auth, успешные/ошибочные отдельно |
| In-flight | Текущие запросы в работе, завершения и отмены |
| PG pool | Ожидание подключения, занятые/свободные connections, latency, блокировки |
| Worker | Длина/возраст очереди, длительность, retries/final failures, lag по due_at |

Алерт API: Bad >1% за 5 мин при ≥100 eligible requests; для малого MVP ≥5 Bad/5 мин
или неуспешный probe. p95 >500 мс на операциях API — ориентир из deployment design,
сигнал после 10 мин и ≥100 наблюдений; внешние OAuth/файлы измерять отдельно.
Само число RPS не авария. Предел производительности ещё не измерен; проверка
5 → 10 → 20 → 50 RPS с реальными сценариями нужна после постоянного хранилища.

## Трафик ботов и остальных клиентов — план

Ограниченные классы: `verified_bot`, `suspected_bot`, `preview`, `monitor`, `unknown`.
Подтверждённый бот — только после проверки документированного IP/DNS источника;
User-Agent сам по себе даёт лишь предполагаемого бота. Preview — отдельный класс
для загрузки карточек ссылок, собственный probe — monitor с проверкой источника.
Все остальные — **неизвестные**, а не доказанно люди. Авторизация пользователя
также не гарантирует отсутствие автоматизации. Не доверять произвольному
X-Forwarded-For от клиента: источники proxy должны быть явно доверенными.

Считать requests, request bytes и response bytes по этим пяти классам и scope
`api/public/assets`; не умножать их на user ID, route, version и статус.
Показывать долю предполагаемой автоматизации рядом с latency/429/расходом.
Порог алерта выбирать после недели baseline и только при влиянии на обслуживание.
Классификация диагностическая и не является защитой от ботов или основанием бана.

## Размеры и проверка

Поставка 60 с, бюджет до 500 активных рядов и 20 условий. Histogram buckets:
0,01 / 0,025 / 0,05 / 0,1 / 0,25 / 0,5 / 0,75 / 1 / 2,5 / 5 / +Inf секунд.
Суммарная оценка с HTTP и worker — около 354 рядов, её нужно измерить заново
после instrumenting. Не включать IP, email, URL/query/invite, токены, сырой UA,
SQL/аргументы и пользовательские идентификаторы в labels/уведомления.

Сценарии приёмки: 2xx/3xx/401/404/429/500, proxy timeout, отмена, counter reset,
нет данных, устаревшая точка, малое число запросов, поддельный UA, отказ TLS/DNS,
пропавший probe, Alarm → OK → NO_DATA, отказ графика и Telegram, ротация токена.
Бот имеет локальные fake HTTP/race-тесты; live IAM/чат/доставка проверяются отдельно.
Детальное проектирование: [observability-plan](../../openspec/changes/deployment-and-store-release/observability-plan.md).
